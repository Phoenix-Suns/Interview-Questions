# I. JUNIOR — SwiftUI Fundamentals

## Chủ đề 1: View và State

### Câu 1. Khi giao diện cần thay đổi sau một thao tác của người dùng, bạn xử lý dữ liệu đó như thế nào?

**Ý chính:**
Dùng `@State` cho **local mutable state**. Khi giá trị thay đổi, `SwiftUI` sẽ **re-render body**.

**Ý diễn giải:**
`@State` phù hợp với dữ liệu thuộc sở hữu của một View, ví dụ trạng thái bật/tắt hoặc text input. SwiftUI theo dõi giá trị này và tính lại giao diện khi nó thay đổi.

**Ví dụ:**

```kotlin
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("Count: \(count)")

            Button("Increase") {
                count += 1
            }
        }
    }
}
```

---

### Câu 2. Nếu một màn hình con cần nhận dữ liệu từ màn hình cha nhưng không được phép thay đổi dữ liệu đó, bạn làm thế nào?

**Ý chính:**
Truyền dữ liệu bằng `let` hoặc property thường. Đây là **one-way data flow**.

**Ý diễn giải:**
View cha sở hữu dữ liệu và truyền xuống View con. View con chỉ hiển thị dữ liệu, không trực tiếp thay đổi state của cha.

**Ví dụ:**

```kotlin
struct ParentView: View {
    let name = "Nghia"

    var body: some View {
        ChildView(name: name)
    }
}

struct ChildView: View {
    let name: String

    var body: some View {
        Text(name)
    }
}
```

---

### Câu 3. Nếu một màn hình con cần thay đổi dữ liệu đang được sở hữu bởi màn hình cha thì sao?

**Ý chính:**
Dùng `@Binding` để tạo **two-way binding** giữa parent và child.

**Ý diễn giải:**
`@Binding` không sở hữu dữ liệu. Nó tạo một tham chiếu tới state bên ngoài, cho phép View con đọc và cập nhật dữ liệu của View cha.

**Ví dụ:**

```kotlin
struct ParentView: View {
    @State private var isOn = false

    var body: some View {
        ChildView(isOn: $isOn)
    }
}

struct ChildView: View {
    @Binding var isOn: Bool

    var body: some View {
        Toggle("Enable", isOn: $isOn)
    }
}
```

---

### Câu 4. Vì sao một giá trị thay đổi nhưng giao diện đôi khi không cập nhật?

**Ý chính:**
SwiftUI chỉ update khi dữ liệu được theo dõi bởi **property wrapper** hoặc **Observable state**.

**Ý diễn giải:**
Nếu thay đổi một property bình thường, SwiftUI không biết dữ liệu đã thay đổi. Dữ liệu cần nằm trong `@State`, `@Binding`, `@Observable`, `ObservableObject` hoặc nguồn state mà SwiftUI quan sát.

**Ví dụ:**

```kotlin
struct WrongView: View {
    var count = 0

    var body: some View {
        Button("Increase") {
            count += 1
        }
    }
}
```

Đúng:

```kotlin
struct CorrectView: View {
    @State private var count = 0

    var body: some View {
        Button("Increase") {
            count += 1
        }
    }
}
```

---

### Câu 5. `body` của SwiftUI View có ý nghĩa gì?

**Ý chính:**
`body` mô tả **UI declaration**, SwiftUI tự tính **View hierarchy** từ state hiện tại.

**Ý diễn giải:**
`body` không nên được hiểu giống hàm tạo UI truyền thống. Nó mô tả giao diện dựa trên state hiện tại. Khi state thay đổi, SwiftUI có thể tính lại body và cập nhật phần cần thiết.

**Ví dụ:**

```kotlin
struct GreetingView: View {
    @State private var name = "Nghia"

    var body: some View {
        Text("Hello \(name)")
    }
}
```

## Chủ đề 2: Layout

### Câu 6. Khi muốn sắp xếp các phần tử theo chiều dọc hoặc chiều ngang, bạn thường sử dụng gì?

**Ý chính:**
Dùng `VStack`, `HStack`, `ZStack`.

**Ý diễn giải:**
`VStack` xếp theo chiều dọc, `HStack` theo chiều ngang và `ZStack` chồng các View lên nhau.

**Ví dụ:**

```kotlin
VStack {
    Text("Title")

    HStack {
        Text("Left")
        Text("Right")
    }
}
```

---

### Câu 7. Khi nào nên sử dụng `Spacer`?

**Ý chính:**
`Spacer` dùng để chiếm **available space** và đẩy các View ra xa nhau.

**Ý diễn giải:**
SwiftUI layout theo không gian được cấp. `Spacer` nhận phần không gian còn lại và giúp căn chỉnh các phần tử.

**Ví dụ:**

```kotlin
HStack {
    Text("Left")

    Spacer()

    Text("Right")
}
```

---

### Câu 8. `frame` dùng để làm gì?

**Ý chính:**
`frame` đặt **size constraint** và **alignment** cho View.

**Ý diễn giải:**
`frame` không phải lúc nào cũng thay đổi kích thước nội dung gốc. Nó tạo một vùng layout cho View và có thể căn chỉnh View bên trong vùng đó.

**Ví dụ:**

```kotlin
Text("Hello")
    .frame(
        maxWidth: .infinity,
        alignment: .leading
    )
```

---

### Câu 9. Vì sao modifier trong SwiftUI có thứ tự quan trọng?

**Ý chính:**
Modifier tạo **new View wrapper**, nên thứ tự ảnh hưởng layout và rendering.

**Ý diễn giải:**
Mỗi modifier có thể bọc View trước đó bằng một View mới. Vì vậy `padding().background()` và `background().padding()` có kết quả khác nhau.

**Ví dụ:**

```kotlin
Text("Hello")
    .padding()
    .background(Color.yellow)
```

Khác với:

```kotlin
Text("Hello")
    .background(Color.yellow)
    .padding()
```

---

### Câu 10. Khi danh sách có nhiều phần tử, nên dùng `VStack` hay `LazyVStack`?

**Ý chính:**
Danh sách lớn nên dùng `LazyVStack` để **lazy create views**.

**Ý diễn giải:**
`VStack` có thể tạo toàn bộ View trong hierarchy, còn `LazyVStack` tạo View khi cần hiển thị gần vùng nhìn thấy, phù hợp danh sách dài.

**Ví dụ:**

```kotlin
ScrollView {
    LazyVStack {
        ForEach(0..<1000) { index in
            Text("Item \(index)")
        }
    }
}
```

# II. JUNIOR → MID — Data Flow

## Chủ đề 3: Property Wrapper

### Câu 11. Bạn phân biệt dữ liệu thuộc sở hữu của màn hình và dữ liệu được truyền từ bên ngoài như thế nào?

**Ý chính:**
`@State` = **owns state**.
`@Binding` = **references external state**.

**Ý diễn giải:**
Nếu View tạo và quản lý dữ liệu thì dùng `@State`. Nếu dữ liệu thuộc View khác và chỉ cần truyền vào để đọc/ghi thì dùng `@Binding`.

**Ví dụ:**

```kotlin
struct Parent: View {
    @State private var name = ""

    var body: some View {
        Child(name: $name)
    }
}

struct Child: View {
    @Binding var name: String

    var body: some View {
        TextField("Name", text: $name)
    }
}
```

---

### Câu 12. Khi một đối tượng được nhiều View sử dụng, bạn tổ chức dữ liệu đó như thế nào?

**Ý chính:**
Dùng **shared observable state**, ví dụ `@Observable`, `@Environment`, hoặc `ObservableObject`.

**Ý diễn giải:**
State dùng chung không nên truyền qua quá nhiều tầng View. Có thể đưa dependency vào Environment hoặc dùng một observable model phù hợp với kiến trúc ứng dụng.

**Ví dụ:**

```kotlin
@Observable
class UserStore {
    var name = "Nghia"
}

struct ProfileView: View {
    var store: UserStore

    var body: some View {
        Text(store.name)
    }
}
```

---

### Câu 13. Khi nào nên dùng `@StateObject` thay vì `@ObservedObject`?

**Ý chính:**
`@StateObject` **owns lifecycle**.
`@ObservedObject` chỉ **observes external object**.

**Ý diễn giải:**
Nếu View tự tạo ViewModel và chịu trách nhiệm giữ nó sống qua các lần render thì dùng `@StateObject`. Nếu ViewModel được tạo từ bên ngoài và truyền vào thì dùng `@ObservedObject`.

**Ví dụ:**

```kotlin
struct ParentView: View {
    @StateObject private var viewModel = UserViewModel()

    var body: some View {
        ChildView(viewModel: viewModel)
    }
}

struct ChildView: View {
    @ObservedObject var viewModel: UserViewModel

    var body: some View {
        Text(viewModel.name)
    }
}
```

---

### Câu 14. Vì sao không nên tạo ViewModel trực tiếp trong `body`?

**Ý chính:**
`body` có thể chạy nhiều lần. Tạo object trong đó có thể gây **new instance**, mất state và side effect.

**Ý diễn giải:**
SwiftUI có thể tính lại `body` nhiều lần. Nếu khởi tạo ViewModel trực tiếp trong body, object có thể bị tạo lại ngoài ý muốn.

**Ví dụ:**

Sai:

```kotlin
var body: some View {
    let viewModel = UserViewModel()

    Text(viewModel.name)
}
```

Tốt hơn:

```kotlin
@StateObject private var viewModel = UserViewModel()
```

---

### Câu 15. `@Environment` giải quyết vấn đề gì?

**Ý chính:**
`@Environment` giúp inject **shared dependency/context** mà không cần truyền qua nhiều View.

**Ý diễn giải:**
Nó phù hợp với các dependency hoặc context dùng xuyên nhiều cấp như theme, locale, dismiss action hoặc custom service.

**Ví dụ:**

```kotlin
struct DetailView: View {
    @Environment(\.dismiss) private var dismiss

    var body: some View {
        Button("Close") {
            dismiss()
        }
    }
}
```

# III. MID LEVEL — View Lifecycle & Rendering

## Chủ đề 4: Lifecycle

### Câu 16. Khi một màn hình xuất hiện lần đầu, bạn thường thực hiện công việc tải dữ liệu ở đâu?

**Ý chính:**
Ưu tiên `.task` cho **async lifecycle work**.

**Ý diễn giải:**
`.task` phù hợp với Swift Concurrency và có thể tự động cancel khi View không còn tồn tại. Nó thường phù hợp hơn cho async loading.

**Ví dụ:**

```kotlin
struct UserView: View {
    var body: some View {
        Text("User")
            .task {
                await loadUser()
            }
    }

    func loadUser() async {
    }
}
```

---

### Câu 17. `onAppear` và `task` khác nhau như thế nào?

**Ý chính:**
`onAppear` = lifecycle callback.
`.task` = lifecycle + **async/await + cancellation**.

**Ý diễn giải:**
`onAppear` phù hợp với logic đồng bộ hoặc trigger đơn giản. `.task` phù hợp với asynchronous work vì tích hợp Swift Concurrency.

**Ví dụ:**

```kotlin
Text("Screen")
    .onAppear {
        print("Appear")
    }
    .task {
        await loadData()
    }
```

---

### Câu 18. Vì sao không nên giả định `onAppear` chỉ chạy một lần?

**Ý chính:**
View có thể **appear/disappear multiple times**.

**Ý diễn giải:**
Navigation, scrolling hoặc thay đổi hierarchy có thể khiến View xuất hiện lại. Vì vậy side effect cần được thiết kế để tránh gọi API không cần thiết.

**Ví dụ:**

```kotlin
.onAppear {
    if items.isEmpty {
        loadData()
    }
}
```

---

### Câu 19. SwiftUI có tạo lại toàn bộ UI mỗi khi state thay đổi không?

**Ý chính:**
`body` có thể được recompute, nhưng SwiftUI dùng **diffing** để update phần cần thiết.

**Ý diễn giải:**
SwiftUI là declarative. Khi state thay đổi, framework so sánh hierarchy mới và cũ để xác định phần giao diện cần cập nhật.

**Ví dụ:**

```kotlin
@State private var count = 0

var body: some View {
    VStack {
        Text("\(count)")
        Image(systemName: "star")
    }
}
```

Khi `count` đổi, SwiftUI không nhất thiết render lại mọi pixel.

---

### Câu 20. Làm thế nào để xử lý side effect trong SwiftUI?

**Ý chính:**
Tách **state** và **side effect**, xử lý bằng `.task`, action hoặc ViewModel.

**Ý diễn giải:**
Không nên gọi API hoặc thực hiện logic side effect trực tiếp trong phần UI declaration. UI nên mô tả state, còn business logic nên nằm trong ViewModel hoặc service.

**Ví dụ:**

```kotlin
struct UserView: View {
    @StateObject var viewModel = UserViewModel()

    var body: some View {
        List(viewModel.users) { user in
            Text(user.name)
        }
        .task {
            await viewModel.loadUsers()
        }
    }
}
```

# IV. MID LEVEL — Navigation

## Chủ đề 5: NavigationStack

### Câu 21. Khi ứng dụng có nhiều màn hình và cần quản lý đường đi của người dùng, bạn tổ chức navigation như thế nào?

**Ý chính:**
Dùng `NavigationStack` và quản lý **navigation state/path**.

**Ý diễn giải:**
`NavigationStack` là API navigation hiện đại. Với flow đơn giản có thể dùng `NavigationLink`, còn flow phức tạp có thể quản lý bằng `NavigationPath`.

**Ví dụ:**

```kotlin
NavigationStack {
    List {
        NavigationLink("Detail") {
            DetailView()
        }
    }
}
```

---

### Câu 22. Khi navigation cần được điều khiển bằng code thay vì người dùng bấm trực tiếp, bạn làm thế nào?

**Ý chính:**
Quản lý `NavigationPath` hoặc route bằng **programmatic navigation**.

**Ý diễn giải:**
Navigation state có thể được thay đổi từ ViewModel hoặc action. Điều này phù hợp với deep link, authentication flow hoặc coordinator pattern.

**Ví dụ:**

```kotlin
struct RootView: View {
    @State private var path = NavigationPath()

    var body: some View {
        NavigationStack(path: $path) {
            Button("Go Detail") {
                path.append("detail")
            }
            .navigationDestination(for: String.self) { route in
                Text(route)
            }
        }
    }
}
```

---

### Câu 23. Bạn xử lý Deep Link trong ứng dụng SwiftUI như thế nào?

**Ý chính:**
Parse URL → map thành **Route** → update navigation state.

**Ý diễn giải:**
Không nên để URL trực tiếp quyết định UI. Nên chuyển URL thành route hoặc domain action, sau đó cập nhật navigation state.

**Ví dụ:**

```kotlin
.onOpenURL { url in
    if url.host == "profile" {
        path.append("profile")
    }
}
```

# V. MID LEVEL — List & Identity

## Chủ đề 6: List và ForEach

### Câu 24. Vì sao mỗi phần tử trong danh sách cần có định danh ổn định?

**Ý chính:**
SwiftUI cần `id` để **identify views**, diff data và giữ state đúng.

**Ý diễn giải:**
Identity giúp SwiftUI biết item nào được thêm, xóa hoặc thay đổi. ID không ổn định có thể gây animation lỗi hoặc state bị chuyển sang item khác.

**Ví dụ:**

```kotlin
struct User: Identifiable {
    let id: UUID
    let name: String
}

List(users) { user in
    Text(user.name)
}
```

---

### Câu 25. Vì sao dùng index làm ID đôi khi gây lỗi?

**Ý chính:**
Index không phải **stable identity** khi insert, delete hoặc reorder.

**Ý diễn giải:**
Nếu danh sách thay đổi thứ tự, index của item thay đổi. SwiftUI có thể hiểu nhầm item cũ thành item mới.

**Ví dụ:**

Không tốt:

```kotlin
ForEach(0..<users.count, id: \.self) { index in
    Text(users[index].name)
}
```

Tốt hơn:

```kotlin
ForEach(users) { user in
    Text(user.name)
}
```

---

### Câu 26. `List` và `ScrollView + LazyVStack` nên được chọn như thế nào?

**Ý chính:**
`List` cho **platform list behavior**.
`LazyVStack` cho **custom layout**.

**Ý diễn giải:**
`List` có nhiều hành vi hệ thống sẵn như selection, swipe action và accessibility. `ScrollView + LazyVStack` linh hoạt hơn khi cần UI tùy chỉnh mạnh.

**Ví dụ:**

```kotlin
List(users) { user in
    Text(user.name)
}
```

Hoặc:

```kotlin
ScrollView {
    LazyVStack {
        ForEach(users) { user in
            Text(user.name)
        }
    }
}
```

# VI. MID LEVEL — Swift Concurrency

## Chủ đề 7: async/await

### Câu 27. Khi cần tải dữ liệu từ API, bạn tổ chức asynchronous code như thế nào?

**Ý chính:**
Dùng `async/await`, `Task`, và xử lý `Error`.

**Ý diễn giải:**
Swift Concurrency giúp code asynchronous dễ đọc hơn callback. Network layer thường trả về dữ liệu bằng `async throws`.

**Ví dụ:**

```kotlin
func loadUser() async throws -> User {
    let url = URL(string: "https://example.com/user")!

    let (data, _) = try await URLSession.shared.data(from: url)

    return try JSONDecoder().decode(User.self, from: data)
}
```

---

### Câu 28. Vì sao không nên dùng `Task.detached` một cách tùy tiện?

**Ý chính:**
`Task.detached` không kế thừa **actor context, priority, cancellation**.

**Ý diễn giải:**
Detached task tách khỏi structured concurrency. Nó phù hợp với trường hợp đặc biệt nhưng dễ gây khó quản lý lifecycle và thread safety.

**Ví dụ:**

```kotlin
Task {
    await loadData()
}
```

Thường ưu tiên hơn:

```kotlin
Task.detached {
    await heavyBackgroundWork()
}
```

---

### Câu 29. `MainActor` dùng để giải quyết vấn đề gì?

**Ý chính:**
`@MainActor` đảm bảo code chạy trên **main thread actor**, phù hợp UI state.

**Ý diễn giải:**
UI state nên được cập nhật trong MainActor để tránh race condition và đảm bảo an toàn với UIKit/SwiftUI UI updates.

**Ví dụ:**

```kotlin
@MainActor
class UserViewModel: ObservableObject {
    @Published var name = ""

    func updateName() {
        name = "Nghia"
    }
}
```

---

### Câu 30. Làm thế nào để tránh request cũ ghi đè kết quả request mới?

**Ý chính:**
Dùng **task cancellation**, request identity hoặc kiểm tra latest state.

**Ý diễn giải:**
Ví dụ search text thay đổi liên tục. Request cũ có thể trả về sau request mới. Cần cancel task cũ hoặc xác định request nào còn hợp lệ.

**Ví dụ:**

```kotlin
.task(id: keyword) {
    try? await Task.sleep(for: .milliseconds(300))

    guard !Task.isCancelled else {
        return
    }

    await search(keyword)
}
```

---

### Câu 31. Structured Concurrency có lợi ích gì?

**Ý chính:**
Task có **parent-child relationship**, hỗ trợ cancellation và lifecycle management.

**Ý diễn giải:**
Task con thuộc task cha. Khi task cha bị cancel hoặc hoàn thành, hệ thống có thể quản lý các task liên quan tốt hơn.

**Ví dụ:**

```kotlin
func loadScreen() async {
    async let user = loadUser()
    async let posts = loadPosts()

    let result = await (user, posts)
}
```

# VII. SENIOR — Architecture

## Chủ đề 8: MVVM

### Câu 32. Bạn chia trách nhiệm giữa View và ViewModel như thế nào?

**Ý chính:**
View = **render + user interaction**.
ViewModel = **state + business/UI logic**.

**Ý diễn giải:**
View nên càng đơn giản càng tốt, chỉ render state và gửi action. ViewModel xử lý dữ liệu, loading, error và gọi use case hoặc repository.

**Ví dụ:**

```kotlin
@MainActor
class UserViewModel: ObservableObject {
    @Published var users: [User] = []

    func load() async {
        users = await repository.getUsers()
    }
}

struct UserView: View {
    @StateObject var viewModel = UserViewModel()

    var body: some View {
        List(viewModel.users) {
            Text($0.name)
        }
    }
}
```

---

### Câu 33. Bạn tránh ViewModel trở thành một class quá lớn như thế nào?

**Ý chính:**
Tách **UseCase, Repository, Service**, giữ ViewModel tập trung vào screen state.

**Ý diễn giải:**
ViewModel không nên chứa toàn bộ business logic, network, database và navigation. Nên chia dependency theo responsibility.

**Ví dụ:**

```kotlin
class UserViewModel {
    private let getUsersUseCase: GetUsersUseCase

    func loadUsers() async {
        users = await getUsersUseCase.execute()
    }
}
```

---

### Câu 34. State của một màn hình phức tạp nên được tổ chức như thế nào?

**Ý chính:**
Dùng một **single UI state model** hoặc state rõ ràng: loading, success, error.

**Ý diễn giải:**
Thay vì có quá nhiều Boolean như `isLoading`, `hasError`, `isEmpty`, nên mô hình hóa state rõ ràng để tránh trạng thái mâu thuẫn.

**Ví dụ:**

```kotlin
enum UserState {
    case idle
    case loading
    case success([User])
    case error(String)
}
```

---

### Câu 35. Bạn xử lý user action trong một màn hình phức tạp như thế nào?

**Ý chính:**
Dùng **Action/Event pattern** để tập trung xử lý interaction.

**Ý diễn giải:**
Các thao tác như refresh, retry, delete hoặc select có thể được biểu diễn thành event. Điều này giúp View đơn giản hơn và dễ test.

**Ví dụ:**

```kotlin
enum UserAction {
    case load
    case refresh
    case delete(UUID)
}

func handle(_ action: UserAction) {
    switch action {
    case .load:
        load()

    case .refresh:
        refresh()

    case .delete(let id):
        delete(id)
    }
}
```

# VIII. SENIOR — State Management

## Chủ đề 9: Observation

### Câu 36. Observation hiện đại khác ObservableObject truyền thống như thế nào?

**Ý chính:**
`@Observable` cung cấp **fine-grained observation**, giảm phụ thuộc vào `@Published`.

**Ý diễn giải:**
Observation framework hiện đại cho phép SwiftUI theo dõi property được sử dụng trực tiếp. Nó có thể giúp quản lý state tự nhiên hơn so với mô hình `ObservableObject`.

**Ví dụ:**

```kotlin
@Observable
class CounterStore {
    var count = 0
}

struct CounterView: View {
    var store = CounterStore()

    var body: some View {
        Button("\(store.count)") {
            store.count += 1
        }
    }
}
```

---

### Câu 37. Làm thế nào để tránh việc một thay đổi nhỏ làm ảnh hưởng quá nhiều phần UI?

**Ý chính:**
Chia state theo **responsibility** và tạo View nhỏ có dependency rõ ràng.

**Ý diễn giải:**
Không nên đưa toàn bộ application state vào một object khổng lồ. State nên được chia theo feature hoặc screen để giảm unnecessary updates và coupling.

**Ví dụ:**

```kotlin
struct ProfileView: View {
    let user: User

    var body: some View {
        UserHeader(user: user)
        UserInfo(user: user)
    }
}
```

---

### Câu 38. Bạn thiết kế state cho loading, empty và error như thế nào để tránh conflict?

**Ý chính:**
Dùng **sealed state / enum state machine** thay vì nhiều Boolean.

**Ý diễn giải:**
Nếu dùng nhiều Boolean, có thể xảy ra `isLoading = true` và `isError = true` cùng lúc. Enum đảm bảo chỉ một trạng thái hợp lệ.

**Ví dụ:**

```kotlin
enum ScreenState<T> {
    case loading
    case success(T)
    case empty
    case error(Error)
}
```

# IX. SENIOR — Performance

## Chủ đề 10: Performance Optimization

### Câu 39. Khi một màn hình SwiftUI bị lag, bạn bắt đầu kiểm tra từ đâu?

**Ý chính:**
Kiểm tra **state updates, body recomputation, identity, heavy work, list rendering**.

**Ý diễn giải:**
Không nên tối ưu ngẫu nhiên. Cần xác định state nào thay đổi quá nhiều, View nào quá lớn, list có identity đúng không và có heavy computation trong body không.

**Ví dụ:**

Không tốt:

```kotlin
var body: some View {
    let sortedItems = items.sorted()

    List(sortedItems) {
        Text($0.name)
    }
}
```

Tốt hơn:

```kotlin
let sortedItems: [Item]

var body: some View {
    List(sortedItems) {
        Text($0.name)
    }
}
```

---

### Câu 40. Vì sao không nên thực hiện công việc nặng trong `body`?

**Ý chính:**
`body` có thể chạy nhiều lần, nên phải giữ **cheap and pure**.

**Ý diễn giải:**
Sorting lớn, decoding hoặc network call trong body có thể làm UI chậm. Body nên chỉ mô tả giao diện.

**Ví dụ:**

Sai:

```kotlin
var body: some View {
    let image = loadLargeImage()

    Image(uiImage: image)
}
```

Tốt hơn:

```kotlin
.task {
    image = await loadLargeImage()
}
```

---

### Câu 41. Bạn tối ưu danh sách có hàng nghìn phần tử như thế nào?

**Ý chính:**
Dùng `List` hoặc `LazyVStack`, **stable ID**, pagination và tránh View quá nặng.

**Ý diễn giải:**
Không nên load toàn bộ dữ liệu hoặc tạo quá nhiều view phức tạp cùng lúc. Cần lazy loading và pagination nếu dữ liệu lớn.

**Ví dụ:**

```kotlin
ScrollView {
    LazyVStack {
        ForEach(items) { item in
            ItemRow(item: item)
        }
    }
}
```

---

### Câu 42. `EquatableView` hoặc Equatable có thể giúp gì trong performance?

**Ý chính:**
Giúp SwiftUI biết View **không cần update** nếu input không thay đổi.

**Ý diễn giải:**
Với View phức tạp và input có thể so sánh, Equatable giúp tối ưu một số trường hợp rendering. Tuy nhiên không nên dùng như giải pháp đầu tiên.

**Ví dụ:**

```kotlin
struct UserRow: View, Equatable {
    let user: User

    var body: some View {
        Text(user.name)
    }
}
```

# X. SENIOR — Memory Management

## Chủ đề 11: ARC và Retain Cycle

### Câu 43. SwiftUI có thể gặp memory leak không?

**Ý chính:**
Có. SwiftUI vẫn dùng **ARC**, có thể gặp **retain cycle**.

**Ý diễn giải:**
Các closure, Combine subscription, Timer hoặc reference giữa object với nhau vẫn có thể gây retain cycle.

**Ví dụ:**

```kotlin
class ViewModel {
    var callback: (() -> Void)?

    func setup() {
        callback = {
            self.doSomething()
        }
    }

    func doSomething() {
    }
}
```

Cần cân nhắc:

```kotlin
callback = { [weak self] in
    self?.doSomething()
}
```

---

### Câu 44. Khi nào cần sử dụng `[weak self]`?

**Ý chính:**
Dùng khi closure có thể được giữ lâu và tạo **strong reference cycle**.

**Ý diễn giải:**
Không phải closure nào cũng cần `[weak self]`. Cần xem ownership graph. Nếu object giữ closure và closure giữ lại object thì có nguy cơ retain cycle.

**Ví dụ:**

```kotlin
class TimerManager {
    var callback: (() -> Void)?

    func start() {
        callback = { [weak self] in
            self?.update()
        }
    }

    func update() {
    }
}
```

**Ý diễn giải:**

**Ví dụ:**

```kotlin
struct HomeView: View {
```

# SWIFTUI SENIOR — ADVANCED INTERVIEW

# I. Rendering System & View Identity

## Câu 1 — Vì sao bạn không nên coi một SwiftUI View là một đối tượng giao diện tồn tại lâu dài?

**Ý chính:**
`View` là **value type description**, không phải UI object lâu dài. SwiftUI quản lý **rendered identity** riêng.

**Ý diễn giải:**
Trong SwiftUI, `View` thường là một `struct` mô tả giao diện tại một thời điểm. `body` có thể được tạo lại rất nhiều lần. State thực tế không nằm trực tiếp trong View struct mà được SwiftUI lưu theo identity của View trong hierarchy.

**Ví dụ:**

```kotlin
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        Text("\(count)")
    }
}
```

`CounterView` struct có thể được tạo lại nhiều lần, nhưng `count` vẫn được giữ nếu View identity không thay đổi.

---

## Câu 2 — Điều gì giúp SwiftUI biết state nào thuộc về View nào?

**Ý chính:**
SwiftUI dùng **View Identity + position in hierarchy + explicit ID** để gắn state.

**Ý diễn giải:**
`@State` không thực sự nằm trong struct View. SwiftUI lưu state bên ngoài và liên kết nó với identity của View. Nếu identity thay đổi, SwiftUI có thể coi đó là một View mới và reset state.

**Ví dụ:**

```kotlin
if isLoggedIn {
    ProfileView()
} else {
    LoginView()
}
```

Hai View khác nhau có identity khác nhau.

---

## Câu 3 — Vì sao thay đổi cấu trúc `if` có thể làm mất state?

**Ý chính:**
Thay đổi **structural identity** có thể khiến SwiftUI tạo View identity mới.

**Ý diễn giải:**
Nếu một View xuất hiện ở vị trí khác trong hierarchy hoặc bị thay thế bởi một loại View khác, SwiftUI có thể không còn liên kết được state cũ với View mới.

**Ví dụ:**

```kotlin
if isPremium {
    PremiumProfileView()
} else {
    NormalProfileView()
}
```

Khi đổi điều kiện, SwiftUI có thể destroy state của View cũ và tạo state mới.

---

## Câu 4 — `id()` trong SwiftUI thực sự có tác động gì?

**Ý chính:**
`.id()` thay đổi **explicit identity**, có thể force SwiftUI coi View là View mới.

**Ý diễn giải:**
Khi giá trị `.id()` thay đổi, SwiftUI thường discard state liên quan tới identity cũ và tạo lại View subtree.

**Ví dụ:**

```kotlin
ProfileView()
    .id(userId)
```

Khi `userId` thay đổi, `ProfileView` có thể được reset state.

---

## Câu 5 — Khi nào bạn chủ động dùng `.id()` để reset UI?

**Ý chính:**
Dùng khi cần **recreate View state**, nhưng không nên lạm dụng.

**Ý diễn giải:**
Ví dụ một form cần reset hoàn toàn khi đổi account. Thay vì reset từng `@State`, có thể thay đổi identity của View.

**Ví dụ:**

```kotlin
FormView()
    .id(currentUser.id)
```

Khi user đổi, toàn bộ local state của `FormView` được tạo lại.

# II. Body Recalculation & Rendering

## Câu 6 — `body` chạy lại có nghĩa là toàn bộ UI được vẽ lại không?

**Ý chính:**
Không. `body recomputation` khác với **rendering**.

**Ý diễn giải:**
SwiftUI có thể gọi lại `body` để tạo hierarchy mô tả mới. Sau đó framework diff hierarchy cũ và mới để xác định phần UI thực sự cần update.

**Ví dụ:**

```kotlin
@State private var count = 0

var body: some View {
    VStack {
        Text("\(count)")
        HeavyView()
    }
}
```

`body` có thể được tính lại nhưng `HeavyView` không nhất thiết bị render lại hoàn toàn.

---

## Câu 7 — Vì sao không nên coi số lần `body` chạy là một performance bug?

**Ý chính:**
`body` được thiết kế để **cheap and frequent**.

**Ý diễn giải:**
SwiftUI có thể recompute body thường xuyên. Vấn đề không phải body chạy nhiều mà là bạn đặt expensive work bên trong body.

**Ví dụ:**

Không tốt:

```kotlin
var body: some View {
    let result = largeData.sorted {
        complexCalculation($0, $1)
    }

    List(result) {
        Text($0.name)
    }
}
```

Tốt hơn:

```kotlin
@State private var sortedData: [Item] = []

.task {
    sortedData = await processData()
}
```

---

## Câu 8 — Một thay đổi state có luôn làm toàn bộ View tree tính lại không?

**Ý chính:**
Không nhất thiết. SwiftUI dùng **dependency tracking**.

**Ý diễn giải:**
SwiftUI theo dõi View nào phụ thuộc vào state nào. Với Observation hiện đại, dependency có thể granular hơn so với việc một object thay đổi khiến nhiều View cùng invalidated.

**Ví dụ:**

```kotlin
@Observable
class Store {
    var name = ""
    var age = 0
}
```

Một View chỉ đọc `name` có thể không cần quan tâm tới thay đổi `age`.

---

## Câu 9 — Làm thế nào để tìm View đang update quá nhiều?

**Ý chính:**
Dùng **Instruments, SwiftUI debugging tools, logging, signposts**.

**Ý diễn giải:**
Không nên đoán. Có thể dùng Instruments để xem rendering, body evaluation, CPU hoặc memory. Với debug đơn giản có thể đặt log trong `body`.

**Ví dụ:**

```kotlin
var body: some View {
    let _ = print("ProfileView body")

    return Text(name)
}
```

Nếu log xuất hiện quá nhiều, cần kiểm tra nguồn state.

---

## Câu 10 — Vì sao chia nhỏ View có thể cải thiện performance?

**Ý chính:**
Giúp **isolate dependencies** và giảm vùng cần update.

**Ý diễn giải:**
Một View lớn đọc nhiều state sẽ dễ bị invalidation. Tách thành các View nhỏ giúp mỗi View chỉ phụ thuộc vào state cần thiết.

**Ví dụ:**

```kotlin
struct ProfileView: View {
    let user: User

    var body: some View {
        Header(user: user)
        Statistics(user: user)
        Posts(userId: user.id)
    }
}
```

# III. State Ownership

## Câu 11 — Bạn xác định View nào nên sở hữu state bằng cách nào?

**Ý chính:**
State nên thuộc **lowest common owner** cần quản lý nó.

**Ý diễn giải:**
Nếu chỉ một View sử dụng state thì state nên nằm trong View đó. Nếu nhiều View cùng cần state thì đưa state lên ancestor chung thấp nhất.

**Ví dụ:**

```kotlin
struct ParentView: View {
    @State private var selectedTab = 0

    var body: some View {
        ChildA(selectedTab: $selectedTab)
        ChildB(selectedTab: $selectedTab)
    }
}
```

---

## Câu 12 — Khi nào `@State` chứa object là lựa chọn không tốt?

**Ý chính:**
Khi ownership và lifecycle object phức tạp, cần **observable model lifecycle management**.

**Ý diễn giải:**
`@State` có thể giữ reference type trong Observation hiện đại, nhưng nếu object có dependency, lifecycle hoặc side effect phức tạp, cần thiết kế ownership rõ ràng thay vì tạo object tùy tiện trong View.

**Ví dụ:**

```kotlin
@State private var viewModel = UserViewModel()
```

Có thể hợp lý với Observation, nhưng cần đảm bảo View thực sự là owner.

---

## Câu 13 — State hoisting là gì?

**Ý chính:**
Đưa state lên parent để tạo **single source of truth**.

**Ý diễn giải:**
Khi nhiều View cần cùng một dữ liệu, tránh mỗi View giữ bản copy riêng. Parent giữ state và truyền xuống qua binding hoặc parameter.

**Ví dụ:**

```kotlin
struct ParentView: View {
    @State private var text = ""

    var body: some View {
        InputView(text: $text)
        PreviewView(text: text)
    }
}
```

---

## Câu 14 — Một `@Binding` có sở hữu dữ liệu không?

**Ý chính:**
Không. `@Binding` chỉ là **reference to external state**.

**Ý diễn giải:**
View sử dụng Binding có thể đọc và ghi dữ liệu, nhưng lifecycle và ownership thuộc View hoặc source khác.

**Ví dụ:**

```kotlin
struct ToggleView: View {
    @Binding var enabled: Bool
}
```

`ToggleView` không sở hữu `enabled`.

---

## Câu 15 — Vì sao duplicated state là nguy hiểm?

**Ý chính:**
Dễ gây **state inconsistency**.

**Ý diễn giải:**
Nếu cùng một dữ liệu được lưu ở nhiều nơi, các bản copy có thể không đồng bộ. Nên có một single source of truth và derive dữ liệu còn lại khi cần.

**Ví dụ:**

Không tốt:

```kotlin
@State var firstName = "John"
@State var fullName = "John Doe"
```

Tốt hơn:

```kotlin
var fullName: String {
    "\(firstName) \(lastName)"
}
```

# IV. Observation Framework

## Câu 16 — Observation framework giải quyết hạn chế gì của ObservableObject?

**Ý chính:**
Cung cấp **fine-grained observation** và giảm boilerplate `@Published`.

**Ý diễn giải:**
Với `ObservableObject`, việc object phát `objectWillChange` có thể làm các View phụ thuộc object bị invalidated rộng hơn. `@Observable` theo dõi property access chi tiết hơn.

**Ví dụ:**

```kotlin
@Observable
class UserStore {
    var name = ""
    var age = 0
}
```

---

## Câu 17 — Tại sao một View không đọc property thì không nên bị ảnh hưởng bởi property đó?

**Ý chính:**
Đây là lợi ích của **dependency tracking**.

**Ý diễn giải:**
SwiftUI chỉ nên update phần UI phụ thuộc dữ liệu thay đổi. Điều này giảm unnecessary invalidation.

**Ví dụ:**

```kotlin
struct NameView: View {
    let store: Store

    var body: some View {
        Text(store.name)
    }
}
```

`NameView` không phụ thuộc trực tiếp vào `store.age`.

---

## Câu 18 — Khi dùng `@Observable`, dependency được theo dõi vào thời điểm nào?

**Ý chính:**
Khi View **reads observable property** trong quá trình evaluation.

**Ý diễn giải:**
SwiftUI ghi nhận property nào được đọc trong quá trình tạo body. Khi property đó thay đổi, View phụ thuộc có thể bị invalidated.

**Ví dụ:**

```kotlin
var body: some View {
    Text(store.name)
}
```

`store.name` trở thành dependency.

# V. Concurrency & Actor Isolation

## Câu 19 — Vì sao ViewModel thường được đánh dấu `@MainActor`?

**Ý chính:**
UI state cần **MainActor isolation**.

**Ý diễn giải:**
ViewModel thường thay đổi state được UI quan sát. `@MainActor` giúp đảm bảo các thay đổi đó xảy ra trong actor phù hợp với UI.

**Ví dụ:**

```kotlin
@MainActor
class UserViewModel: ObservableObject {
    @Published var users: [User] = []
}
```

---

## Câu 20 — Nếu ViewModel là `@MainActor`, toàn bộ network request có chạy trên main thread không?

**Ý chính:**
Không. `await` cho phép task **suspend**, async function có thể chạy ở executor khác.

**Ý diễn giải:**
`@MainActor` bảo vệ actor-isolated code. Khi gọi async operation và `await`, task có thể suspend. Network không có nghĩa là blocking main thread.

**Ví dụ:**

```kotlin
@MainActor
func load() async {
    let users = await repository.getUsers()
    self.users = users
}
```

MainActor không bị block trong lúc `await`.

---

## Câu 21 — `Task` và `Task.detached` khác nhau như thế nào?

**Ý chính:**
`Task` kế thừa **context**.
`Task.detached` tách khỏi **parent context**.

**Ý diễn giải:**
Task thông thường thường kế thừa priority, actor context và cancellation relationship phù hợp với structured work. Detached task độc lập hơn và phải quản lý cẩn thận.

**Ví dụ:**

```kotlin
Task {
    await loadData()
}
```

Khác với:

```kotlin
Task.detached {
    await heavyWork()
}
```

---

## Câu 22 — Khi nào một Task tự động bị cancel trong SwiftUI?

**Ý chính:**
`.task` có lifecycle liên kết với **View identity/lifecycle**.

**Ý diễn giải:**
Task gắn với View có thể bị cancel khi View biến mất hoặc identity thay đổi. Vì vậy async code nên hỗ trợ cooperative cancellation.

**Ví dụ:**

```kotlin
Text("Loading")
    .task {
        await loadData()
    }
```

---

## Câu 23 — Cancellation trong Swift Concurrency có nghĩa là task bị dừng ngay lập tức không?

**Ý chính:**
Không. Cancellation là **cooperative cancellation**.

**Ý diễn giải:**
Task nhận trạng thái cancelled nhưng code cần kiểm tra cancellation hoặc gọi API suspension hỗ trợ cancellation.

**Ví dụ:**

```kotlin
for item in items {
    guard !Task.isCancelled else {
        return
    }

    await process(item)
}
```

---

## Câu 24 — Làm thế nào để xử lý race condition khi search?

**Ý chính:**
Dùng **cancellation + request identity + debounce**.

**Ý diễn giải:**
Khi người dùng gõ nhanh, request cũ có thể trả về sau request mới. Cần cancel task cũ hoặc đảm bảo chỉ kết quả mới nhất được cập nhật.

**Ví dụ:**

```kotlin
.task(id: searchText) {
    try? await Task.sleep(for: .milliseconds(300))

    guard !Task.isCancelled else {
        return
    }

    results = await search(searchText)
}
```

---

## Câu 25 — `Sendable` giải quyết vấn đề gì?

**Ý chính:**
`Sendable` giúp đảm bảo dữ liệu an toàn khi **crossing concurrency domains**.

**Ý diễn giải:**
Khi dữ liệu được truyền giữa actor hoặc concurrent task, Swift cần biết kiểu dữ liệu đó an toàn để chuyển qua các isolation boundary.

**Ví dụ:**

```kotlin
struct User: Sendable {
    let id: Int
    let name: String
}
```

# VI. Navigation Architecture

## Câu 26 — Vì sao navigation không nên được xử lý hoàn toàn bằng Boolean?

**Ý chính:**
Boolean navigation dễ tạo **invalid navigation states**.

**Ý diễn giải:**
Nhiều Boolean như `showProfile`, `showSettings`, `showDetail` có thể cùng `true`. Với app lớn, nên biểu diễn route rõ ràng.

**Ví dụ:**

Không tốt:

```kotlin
@State var showProfile = false
@State var showSettings = false
@State var showDetail = false
```

Tốt hơn:

```kotlin
enum Route: Hashable {
    case profile
    case settings
    case detail(Int)
}
```

---

## Câu 27 — Bạn thiết kế navigation cho ứng dụng lớn như thế nào?

**Ý chính:**
Dùng **Route model + NavigationStack path + Router/Coordinator**.

**Ý diễn giải:**
Navigation state nên được tách khỏi UI cụ thể. Route biểu diễn destination, Router quản lý path và View chỉ render navigation.

**Ví dụ:**

```kotlin
enum Route: Hashable {
    case profile(Int)

@Observable
class Router {
    var path = NavigationPath()
}
```

## Câu 28 — Deep Link nên đi thẳng vào View hay đi qua Route?

**Ý chính:**
Deep Link → **parse → domain route → navigation state**.

**Ý diễn giải:**
Không nên để URL trực tiếp tạo View. Nên parse URL thành route để dễ validate, test và hỗ trợ nhiều navigation flow.

**Ví dụ:**

```kotlin
func handle(url: URL) {
    if url.path.contains("profile") {
        router.path.append(Route.profile(1))
    }
}
```

# VII. Architecture

## Câu 29 — Khi nào MVVM bắt đầu không đủ?

**Ý chính:**
Khi state, navigation và side effect quá phức tạp, cần **unidirectional data flow**.

**Ý diễn giải:**
MVVM đơn giản dễ bắt đầu nhưng ViewModel có thể trở thành Massive ViewModel. Với feature phức tạp, có thể dùng reducer, action, state pattern hoặc kiến trúc MVI/TCA.

**Ví dụ:**

```kotlin
struct FeatureState {
    var users: [User] = []
    var isLoading = false
}

enum FeatureAction {
    case load
    case loaded([User])
    case failed(Error)
}
```

---

## Câu 30 — Vì sao một UI state nên là immutable từ góc nhìn rendering?

**Ý chính:**
Immutable state giúp **predictable state transition**.

**Ý diễn giải:**
Khi state được thay đổi theo action rõ ràng, dễ debug, test và replay. Điều này đặc biệt hữu ích với reducer architecture.

**Ví dụ:**

```kotlin
struct State {
    var count = 0
}

func reduce(
    state: inout State,
    action: Action
) {
    switch action {
    case .increment:
        state.count += 1
    }
}
```

---

## Câu 31 — Side effect nên nằm ở đâu trong architecture?

**Ý chính:**
Tách side effect khỏi **pure state transition**.

**Ý diễn giải:**
Network, database, analytics hoặc timer không nên trộn với UI rendering. Reducer hoặc ViewModel có thể trigger effect, sau đó effect trả kết quả về state.

**Ví dụ:**

```kotlin
enum Action {
    case load
    case loaded([User])
}
```

`load` trigger API.

API trả về → dispatch `loaded`.

---

## Câu 32 — Làm thế nào để tránh Massive ViewModel?

**Ý chính:**
Tách **feature logic, use case, service, repository, child state**.

**Ý diễn giải:**
ViewModel không nên trở thành nơi chứa toàn bộ business logic. Nó nên tập trung vào screen state orchestration.

**Ví dụ:**

```kotlin
class ProfileViewModel {
    private let getProfile: GetProfileUseCase
    private let updateProfile: UpdateProfileUseCase
}
```

# VIII. PreferenceKey & Communication

**Ý diễn giải:**

```kotlin
struct SizePreferenceKey: PreferenceKey {

    }
}
```

Child:

```kotlin
GeometryReader { proxy in

        .preference(

            value: proxy.size
        )
}
```

**Ý chính:**
Không. Nó phù hợp cho **layout/UI metadata**, không phải business state.

**Ý diễn giải:**
PreferenceKey nên dùng cho những trường hợp communication liên quan layout như size, offset hoặc anchor. Business state nên dùng state management bình thường.

**Ví dụ:**

Phù hợp:

```kotlin
Scroll offset
View size
Anchor position
```

Không phù hợp:

```kotlin
Current user
Cart items
Authentication state
```

```kotlin
@Environment(\.dismiss)
var dismiss
```

**Ý diễn giải:**
Nếu một View có nhiều dependency quan trọng nhưng tất cả đều lấy từ Environment, việc đọc code và test có thể khó hơn. Dependency quan trọng nên được inject rõ ràng.

Không rõ dependency:

```kotlin
@Environment(AppStore.self)
```

# X. Animation & Transaction

## Câu 37 — SwiftUI animation thực sự gắn với điều gì?

**Ý chính:**
Animation gắn với **state transition + transaction**.

**Ý diễn giải:**
SwiftUI không phải animate từng frame bằng imperative code. Khi state thay đổi, framework biết giá trị trước và sau rồi nội suy các animatable property.

**Ví dụ:**

```kotlin
@State private var expanded = false

var body: some View {
    Rectangle()
        .frame(
            height: expanded ? 200 : 100
        )
        .animation(
            .easeInOut,
            value: expanded
        )
}
```

---

## Câu 38 — Vì sao `.animation()` không nên được đặt tùy tiện ở View cha?

**Ý chính:**
Có thể animate **unintended state changes**.

**Ý diễn giải:**
Nếu animation áp dụng quá rộng, những thay đổi state không liên quan cũng có thể bị animate. Nên giới hạn animation vào giá trị cụ thể.

**Ví dụ:**

Tốt:

```kotlin
.animation(
    .easeInOut,
    value: isExpanded
)
```

Thay vì:

```kotlin
.animation(.easeInOut)
```

---

## Câu 39 — `withAnimation` và `.animation(value:)` khác nhau như thế nào?

**Ý chính:**

`withAnimation` = animate một **state mutation**.
`.animation(value:)` = animate khi **specific value changes**.

**Ý diễn giải:**
`withAnimation` phù hợp khi muốn chủ động animate action. `.animation(value:)` phù hợp khi View phản ứng với thay đổi của một giá trị.

**Ví dụ:**

```kotlin
Button("Expand") {
    withAnimation {
        expanded.toggle()
    }
}
```

# XI. Layout System

## Câu 40 — SwiftUI layout được quyết định như thế nào?

**Ý chính:**
Parent **proposes size**, child **chooses size**, parent **places child**.

**Ý diễn giải:**
SwiftUI layout thường có ba bước: proposal, child response và placement. Hiểu cơ chế này giúp debug các vấn đề về `frame`, `GeometryReader` và layout priority.

```kotlin
HStack {
```

Parent đề xuất không gian, mỗi child quyết định kích thước phù hợp.

**Ý chính:**
Nó nhận **available space** và có behavior layout đặc biệt.

**Ý diễn giải:**
GeometryReader thường mở rộng để chiếm không gian được parent đề xuất. Nếu dùng không đúng, nó có thể làm layout lớn bất ngờ.

**Ý diễn giải:**

```kotlin
HStack {

}
```

# XIV. Senior Design Questions

## Câu 47 — Bạn thiết kế một màn hình có API, cache, pagination, refresh và retry như thế nào?

**Ý chính:**
Tách **UI State + Action + UseCase + Repository + async task**.

**Ý diễn giải:**
View chỉ render state. ViewModel hoặc Store xử lý action. Repository quản lý remote/cache. Pagination cần tránh duplicate request và race condition.

**Ví dụ:**

```kotlin
enum State {
    case loading
    case content([Item])
    case error(Error)
}

enum Action {
    case load
    case refresh
    case loadNextPage
    case retry
}
```

---

## Câu 48 — Làm thế nào để tránh duplicate API request khi View xuất hiện nhiều lần?

**Ý chính:**
Dùng **state guard, task cancellation, request deduplication**.

**Ý diễn giải:**
Không nên giả định `.task` hoặc `onAppear` chỉ chạy một lần. Cần kiểm tra trạng thái loading hoặc quản lý request trong ViewModel.

**Ví dụ:**

```kotlin
func load() async {
    guard !isLoading else {
        return
    }

    isLoading = true

    defer {
        isLoading = false
    }

    users = await repository.getUsers()
}
```

## Câu 49 — Nếu một SwiftUI screen có hơn 30 `@State`, bạn đánh giá như thế nào?

**Ý chính:**
Có thể đang bị **state fragmentation** hoặc thiếu state model.

**Ý diễn giải:**
Không phải số lượng state luôn là lỗi, nhưng nhiều state thường khiến khó kiểm soát transition. Có thể nhóm thành UI state hoặc chia feature thành child View.

**Ví dụ:**

Không tốt:

```kotlin
@State var isLoading = false
@State var hasError = false
@State var isEmpty = false
@State var showDialog = false
@State var showSheet = false
```

Tốt hơn:

```kotlin
struct ScreenState {
    var contentState: ContentState
    var dialog: Dialog?
}
```

## Câu 50 — Theo bạn, câu hỏi quan trọng nhất khi review một SwiftUI architecture là gì?

**Ý chính:**
**Who owns the state? Who can change it? What depends on it?**

**Ý diễn giải:**
Đây là ba câu hỏi cốt lõi của SwiftUI architecture. Nếu không biết ai sở hữu state, ai có quyền thay đổi và View nào phụ thuộc vào nó, ứng dụng rất dễ trở thành spaghetti state.

**Ví dụ:**

```kotlin
Parent
  └── owns state

Child A
  └── reads state

Child B
  └── modifies through Binding

Repository
  └── provides data

ViewModel
  └── coordinates state changes
```
