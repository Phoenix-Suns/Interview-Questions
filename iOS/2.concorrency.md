# CẤP ĐỘ 1: JUNIOR — CƠ BẢN

## Chủ đề: Async/Await

### 1. Khi một hàm phải chờ dữ liệu từ mạng nhưng bạn không muốn chặn luồng đang chạy, bạn sẽ thiết kế nó như thế nào?

**Ý chính:** `async/await` - bất đồng bộ, không blocking thread.

**Diễn giải:**
Hàm được khai báo `async` để có thể tạm dừng khi chờ kết quả. `await` chỉ làm coroutine/task hiện tại tạm dừng, không giữ thread đứng chờ. Khi dữ liệu có kết quả, execution tiếp tục.

**Ví dụ:**

```swift
func loadUser() async throws -> User {
    let data = try await URLSession.shared.data(from: url).0
    return try JSONDecoder().decode(User.self, from: data)
}
```

---

### 2. Nếu một thao tác mất vài giây mới hoàn thành, điều gì xảy ra với phần code phía sau trong cùng một hàm?

**Ý chính:** `await` - suspend, không block.

**Diễn giải:**
Code phía sau `await` chưa chạy ngay. Task sẽ tạm dừng tại điểm đó. Thread có thể được sử dụng cho công việc khác. Khi operation hoàn thành, task tiếp tục từ vị trí đã dừng.

**Ví dụ:**

```swift
func load() async {
    print("Start")

    let result = await fetchData()

    print("End")
}
```

---

### 3. Bạn muốn chạy một công việc bất đồng bộ từ một hàm thông thường thì làm thế nào?

**Ý chính:** `Task {}` - tạo asynchronous context.

**Diễn giải:**
Nếu hàm hiện tại không phải `async`, có thể tạo một `Task` để bước vào Swift Concurrency. Tuy nhiên không nên dùng `Task` tùy tiện vì nó tạo một lifecycle riêng và có thể gây khó kiểm soát cancellation.

**Ví dụ:**

```swift
func buttonTapped() {
    Task {
        let data = await loadData()
        print(data)
    }
}
```

---

### 4. Nếu một hàm bất đồng bộ có thể thất bại, bạn sẽ xử lý lỗi như thế nào?

**Ý chính:** `async throws` + `try await` + `do-catch`.

**Diễn giải:**
Swift kết hợp asynchronous execution và error handling bằng `async throws`. Caller sử dụng `try await` và có thể bắt lỗi bằng `do-catch`.

**Ví dụ:**

```swift
func load() async throws -> User {
    try await api.fetchUser()
}

Task {
    do {
        let user = try await load()
        print(user)
    } catch {
        print(error)
    }
}
```

---

### 5. Khi bạn gọi nhiều thao tác bất đồng bộ liên tiếp, chúng có nhất thiết chạy đồng thời không?

**Ý chính:** `await` tuần tự nếu viết tuần tự.

**Diễn giải:**
Hai lời gọi viết nối tiếp nhau sẽ chờ nhau hoàn thành. `async` không đồng nghĩa với parallel. Muốn chạy đồng thời phải tạo concurrency rõ ràng.

**Ví dụ:**

```swift
let user = try await loadUser()
let posts = try await loadPosts()
```

`loadPosts()` chỉ bắt đầu sau khi `loadUser()` hoàn thành.

## Chủ đề: Task & Cancellation

### 6. Một công việc bất đồng bộ đang chạy nhưng người dùng rời khỏi màn hình. Bạn sẽ làm gì để tránh tiếp tục công việc không còn cần thiết?

**Ý chính:** `Task` + cancellation.

**Diễn giải:**
Lưu reference đến `Task`, sau đó gọi `cancel()` khi View/ViewModel không còn cần kết quả. Cancellation trong Swift là cooperative, nghĩa là operation cần kiểm tra trạng thái hủy.

**Ví dụ:**

```swift
var task: Task<Void, Never>?

func load() {
    task = Task {
        await fetchData()
    }
}

func stop() {
    task?.cancel()
}
```

---

### 7. Gọi hủy một công việc bất đồng bộ có đảm bảo công việc dừng ngay lập tức không?

**Ý chính:** Cancellation là **cooperative**, không force kill.

**Diễn giải:**
`cancel()` chỉ đánh dấu task đã bị cancel. Code đang chạy phải kiểm tra cancellation hoặc gọi API có hỗ trợ cancellation. Vì vậy cancellation không giống việc kill thread.

**Ví dụ:**

```swift
Task {
    try Task.checkCancellation()

    let data = try await fetch()
}
```

---

### 8. Bạn kiểm tra một task đã bị hủy bằng cách nào mà không tự động throw error?

**Ý chính:** `Task.isCancelled`.

**Diễn giải:**
`Task.isCancelled` trả về trạng thái cancellation hiện tại. Nó phù hợp khi muốn tự quyết định có tiếp tục hay không mà không muốn phát sinh `CancellationError`.

**Ví dụ:**

```swift
Task {
    if Task.isCancelled {
        return
    }

    await process()
}
```

---

### 9. Một task cha bị hủy thì các công việc con của nó có bị hủy theo không?

**Ý chính:** Structured concurrency → cancellation propagation.

**Diễn giải:**
Trong structured concurrency, child task nằm trong lifecycle của parent. Khi parent bị cancel, cancellation được propagate xuống child. Đây là một lý do nên ưu tiên structured concurrency thay vì tạo các task rời rạc.

**Ví dụ:**

```swift
await withTaskGroup(of: Void.self) { group in
    group.addTask {
        await task1()
    }

    group.addTask {
        await task2()
    }
}
```

---

### 10. Tại sao không nên tạo `Task` ở mọi nơi trong ứng dụng?

**Ý chính:** Unstructured task, lifecycle, cancellation, memory.

**Diễn giải:**
Task được tạo tự do có lifecycle khó quản lý. Nó có thể tiếp tục chạy sau khi UI đã biến mất, giữ reference tới object hoặc tạo race condition. Senior cần xác định rõ owner và lifecycle của task.

**Ví dụ:**

```swift
class ViewModel {
    var task: Task<Void, Never>?

    func load() {
        task = Task {
            await fetch()
        }
    }

    deinit {
        task?.cancel()
    }
}
```

# CẤP ĐỘ 2: MIDDLE — CORE CONCURRENCY

## Chủ đề: Structured Concurrency

### 11. Khi có ba request độc lập và bạn muốn giảm tổng thời gian chờ, bạn sẽ tổ chức chúng thế nào?

**Ý chính:** Structured concurrency + parallel child tasks.

**Diễn giải:**
Nếu request không phụ thuộc nhau, không nên await tuần tự. Có thể sử dụng `async let` cho số lượng operation cố định hoặc `TaskGroup` khi số lượng dynamic.

**Ví dụ:**

```swift
async let user = loadUser()
async let posts = loadPosts()
async let settings = loadSettings()

let result = try await (user, posts, settings)
```

---

### 12. Khi nào bạn chọn cách chạy một vài công việc cố định cùng lúc thay vì tạo một nhóm công việc động?

**Ý chính:** `async let` cho fixed concurrency.

**Diễn giải:**
Nếu biết trước số lượng operation và chúng có kiểu kết quả rõ ràng, `async let` đơn giản và dễ đọc. Nếu số lượng task thay đổi theo runtime thì `TaskGroup` phù hợp hơn.

**Ví dụ:**

```swift
async let profile = fetchProfile()
async let avatar = fetchAvatar()

let result = try await (profile, avatar)
```

---

### 13. Nếu số lượng công việc phụ thuộc vào dữ liệu runtime, bạn sẽ tổ chức việc chạy chúng như thế nào?

**Ý chính:** `TaskGroup` - dynamic concurrency.

**Diễn giải:**
`TaskGroup` cho phép tạo nhiều child task trong runtime và thu thập kết quả. Parent sẽ đợi các child task hoàn thành trước khi scope kết thúc.

**Ví dụ:**

```swift
let results = await withTaskGroup(of: Image.self) { group in
    for url in urls {
        group.addTask {
            await loadImage(url)
        }
    }

    var images: [Image] = []

    for await image in group {
        images.append(image)
    }

    return images
}
```

---

### 14. Nếu một công việc trong một nhóm bị lỗi, bạn muốn toàn bộ nhóm dừng theo thì nên thiết kế thế nào?

**Ý chính:** `withThrowingTaskGroup` + error propagation.

**Diễn giải:**
`withThrowingTaskGroup` cho phép child task throw. Khi một child fail, error được propagate ra ngoài và các child task còn lại có thể được cancel theo structured concurrency.

**Ví dụ:**

```swift
try await withThrowingTaskGroup(of: Data.self) { group in
    for url in urls {
        group.addTask {
            try await download(url)
        }
    }

    for try await data in group {
        print(data)
    }
}
```

---

### 15. Nếu một request thất bại nhưng các request còn lại vẫn có ích, bạn sẽ xử lý thế nào?

**Ý chính:** Không để một child failure phá toàn bộ workflow; collect từng result.

**Diễn giải:**
Không phải lúc nào cũng muốn fail-fast. Có thể catch lỗi bên trong child task và trả về một enum/result riêng, hoặc dùng non-throwing `TaskGroup`.

**Ví dụ:**

```swift
await withTaskGroup(of: Result<Data, Error>.self) { group in
    for url in urls {
        group.addTask {
            do {
                return .success(try await download(url))
            } catch {
                return .failure(error)
            }
        }
    }

    for await result in group {
        print(result)
    }
}
```

## Chủ đề: Actor & Data Race

### 16. Hai công việc chạy đồng thời cùng thay đổi một dữ liệu dùng chung thì vấn đề gì có thể xảy ra?

**Ý chính:** Data race.

**Diễn giải:**
Nếu nhiều execution context cùng đọc/ghi shared mutable state mà không có synchronization, kết quả có thể phụ thuộc timing. Đây là data race và có thể dẫn tới crash hoặc state không nhất quán.

**Ví dụ:**

```swift
final class Counter {
    var value = 0

    func increment() {
        value += 1
    }
}
```

Nhiều task cùng gọi `increment()` có thể gây race.

---

### 17. Bạn sẽ thiết kế một object chứa state dùng chung như thế nào để nhiều task có thể truy cập an toàn?

**Ý chính:** `actor` - isolated mutable state.

**Diễn giải:**
`actor` bảo vệ mutable state của nó bằng actor isolation. Code bên ngoài muốn truy cập state isolated thường phải đi qua `await`.

**Ví dụ:**

```swift
actor Counter {
    private var value = 0

    func increment() {
        value += 1
    }

    func getValue() -> Int {
        value
    }
}
```

---

### 18. Vì sao việc chuyển một class thành actor không đơn giản chỉ là thay từ khóa?

**Ý chính:** Isolation boundary + `await` + Sendability.

**Diễn giải:**
Actor tạo ra isolation boundary. Các method/property isolated có thể yêu cầu `await` khi truy cập từ context khác. Các dữ liệu đi qua boundary cũng phải phù hợp với concurrency safety.

**Ví dụ:**

```swift
let counter = Counter()

await counter.increment()
let value = await counter.getValue()
```

---

### 19. Actor có đảm bảo toàn bộ chương trình bên trong actor chỉ chạy một thread duy nhất không?

**Ý chính:** Không. Actor bảo vệ state, không phải thread.

**Diễn giải:**
Actor isolation đảm bảo các access tới isolated state được serialize phù hợp. Swift Concurrency quản lý executor/thread. Không nên đồng nhất actor với một thread riêng.

**Ví dụ:**

```swift
actor Cache {
    var values: [String: Data] = [:]
}
```

Điểm quan trọng là `values` được bảo vệ, không phải actor sở hữu một thread cố định.

---

### 20. Nếu một actor gọi một hàm async rất lâu, các operation khác của actor có bị block hoàn toàn không?

**Ý chính:** Actor reentrancy.

**Diễn giải:**
Khi actor gặp `await`, nó có thể tạm nhường quyền để xử lý operation khác. Vì vậy actor không phải lock truyền thống. State có thể thay đổi giữa hai lần execution trước và sau `await`.

**Ví dụ:**

```swift
actor BankAccount {
    var balance = 100

    func process() async {
        let current = balance

        await externalWork()

        // balance có thể đã thay đổi
        balance = current - 10
    }
}
```

# CẤP ĐỘ 3: SENIOR — SWIFT CONCURRENCY

## Chủ đề: Actor Reentrancy & State Consistency

### 21. Một hàm trong object bảo vệ state bằng actor, nhưng sau khi chờ một operation bên ngoài thì state không còn giống lúc đầu. Vì sao?

**Ý chính:** Actor reentrancy + suspension point.

**Diễn giải:**
`await` là suspension point. Trong thời gian hàm tạm dừng, actor có thể xử lý message khác và thay đổi state. Khi hàm tiếp tục, assumptions được tạo trước `await` có thể không còn đúng.

**Ví dụ:**

```swift
actor Bank {
    var balance = 100

    func withdraw() async {
        let oldBalance = balance

        await networkCheck()

        // Không nên giả định balance vẫn là oldBalance
        balance = oldBalance - 50
    }
}
```

---

### 22. Bạn sẽ viết lại logic ở câu trước thế nào để tránh ghi đè state mới?

**Ý chính:** Re-check state sau `await`, tránh giữ stale state.

**Diễn giải:**
Không nên đọc state, await, rồi sử dụng giá trị cũ để ghi lại. Sau suspension point cần đọc lại state hoặc thiết kế operation atomic trong actor.

**Ví dụ:**

```swift
actor Bank {
    var balance = 100

    func withdraw() async {
        await networkCheck()

        guard balance >= 50 else {
            return
        }

        balance -= 50
    }
}
```

---

### 23. Trong một hệ thống cache dùng chung, bạn sẽ đảm bảo hai request cùng lúc không cùng tải một resource như thế nào?

**Ý chính:** Actor + request coalescing / in-flight task.

**Diễn giải:**
Không chỉ bảo vệ dictionary. Cần lưu cả request đang chạy. Nếu request thứ hai tới trong lúc request đầu tiên đang tải, nó dùng lại task hiện tại thay vì tạo request mới.

**Ví dụ:**

```swift
actor ImageCache {
    private var cache: [URL: Data] = [:]
    private var running: [URL: Task<Data, Error>] = [:]

    func image(for url: URL) async throws -> Data {
        if let cached = cache[url] {
            return cached
        }

        if let task = running[url] {
            return try await task.value
        }

        let task = Task {
            try await download(url)
        }

        running[url] = task

        defer {
            running[url] = nil
        }

        let data = try await task.value
        cache[url] = data

        return data
    }
}
```

# Chủ đề: MainActor & UI

### 24. Một ViewModel cập nhật dữ liệu UI từ một task chạy bất đồng bộ. Làm sao đảm bảo việc cập nhật UI đúng execution context?

**Ý chính:** `@MainActor`.

**Diễn giải:**
State được UI sử dụng nên được isolation trên `MainActor`. Có thể đánh dấu toàn bộ ViewModel bằng `@MainActor` để các mutation của nó diễn ra đúng context.

**Ví dụ:**

```swift
@MainActor
final class UserViewModel: ObservableObject {
    @Published var user: User?

    func load() async {
        user = try? await api.fetchUser()
    }
}
```

---

### 25. Có phải cứ dùng `@MainActor` thì toàn bộ công việc bên trong đều chạy trên main thread và có thể gây lag UI không?

**Ý chính:** `MainActor` bảo vệ UI state; tránh CPU-heavy work trên main actor.

**Diễn giải:**
`@MainActor` isolation không có nghĩa mọi logic đều nên nằm ở đó. Công việc CPU nặng nên được thiết kế ngoài MainActor. MainActor nên chủ yếu quản lý UI state và orchestration.

**Ví dụ:**

```swift
@MainActor
func load() async {
    let data = try? await repository.fetch()
    items = process(data)
}
```

Nếu `process()` CPU-heavy, nên tách khỏi MainActor.

---

### 26. Một ViewModel được đánh dấu `@MainActor`, nhưng repository thực hiện network request. Request đó có giữ main thread trong lúc chờ không?

**Ý chính:** `await` không block thread.

**Diễn giải:**
MainActor có thể suspend tại `await`. Network operation chạy theo cơ chế asynchronous của API. Khi có kết quả, continuation quay lại context phù hợp.

**Ví dụ:**

```swift
@MainActor
func load() async {
    let users = try? await repository.fetchUsers()
    self.users = users ?? []
}
```

---

### 27. Bạn sẽ đặt `@MainActor` ở ViewModel hay chỉ ở từng property/method? Khi nào chọn mỗi cách?

**Ý chính:** Isolation boundary rõ ràng.

**Diễn giải:**
Nếu gần như toàn bộ ViewModel phục vụ UI state, đánh dấu class `@MainActor` thường đơn giản và an toàn hơn. Nếu object có cả logic non-UI cần chạy độc lập, có thể isolation hẹp hơn.

**Ví dụ:**

```swift
@MainActor
final class ViewModel {
    var state: State
}
```

# Chủ đề: Sendable & Swift 6

### 28. Khi dữ liệu được truyền từ một concurrency domain sang domain khác, bạn cần quan tâm điều gì?

**Ý chính:** `Sendable`.

**Diễn giải:**
Swift cần đảm bảo dữ liệu truyền qua concurrency boundary an toàn. Value types thường dễ đáp ứng hơn. Reference types chứa mutable state cần thiết kế cẩn thận hoặc được isolation bằng actor.

**Ví dụ:**

```swift
struct User: Sendable {
    let id: Int
    let name: String
}
```

---

### 29. Vì sao một class mutable thông thường thường khó đáp ứng yêu cầu concurrency safety?

**Ý chính:** Shared mutable reference state.

**Diễn giải:**
Class có reference semantics. Nhiều task có thể giữ cùng một object và cùng thay đổi state. Nếu object không có synchronization hoặc isolation thì dễ xảy ra data race.

**Ví dụ:**

```swift
final class User {
    var name: String = ""
}
```

---

### 30. Bạn gặp cảnh báo concurrency liên quan đến một closure đang gửi object sang context khác. Bạn sẽ phân tích vấn đề từ đâu?

**Ý chính:** Boundary → captured values → `Sendable` → isolation.

**Diễn giải:**
Trước tiên xác định closure chạy ở đâu và object được truyền qua boundary nào. Sau đó kiểm tra các giá trị captured có mutable shared state hay không, có `Sendable` không và có actor isolation phù hợp không.

**Ví dụ:**

```swift
Task.detached {
    // Capturing non-Sendable mutable object
    // có thể gây lỗi/warning trong Swift concurrency
}
```

# Chủ đề: Task, Task.detached

### 31. Một task được tạo trong context hiện tại và một task hoàn toàn tách khỏi context hiện tại khác nhau ở điểm nào?

**Ý chính:** `Task` kế thừa context; `Task.detached` không kế thừa context.

**Diễn giải:**
`Task {}` có thể kế thừa actor isolation, priority và task-local values từ context tạo nó. `Task.detached` độc lập hơn và không nên dùng chỉ vì muốn “chạy background”.

**Ví dụ:**

```swift
Task {
    await work()
}

Task.detached {
    await work()
}
```

---

### 32. Vì sao bạn không nên dùng `Task.detached` để giải quyết mọi vấn đề về performance?

**Ý chính:** Detached task mất structured context + isolation.

**Diễn giải:**
`Task.detached` không tự động kế thừa actor isolation và các context liên quan. Nó làm lifecycle và Sendable requirement phức tạp hơn. Senior chỉ dùng nó khi thực sự cần một task độc lập.

**Ví dụ:**

```swift
Task.detached(priority: .background) {
    await heavyWork()
}
```

Không nên mặc định thay mọi `Task` bằng cách này.

### 33. Khi người dùng liên tục nhập text để search server, làm sao tránh gửi một request cho mỗi ký tự?

**Ý chính:** Debounce + cancellation.

**Diễn giải:**
Mỗi lần text thay đổi, cancel task trước đó. Task mới delay một khoảng ngắn rồi mới search. Nếu user tiếp tục nhập, task cũ bị cancel.

**Ví dụ:**

```swift
var searchTask: Task<Void, Never>?

func search(_ text: String) {
    searchTask?.cancel()

    searchTask = Task {
        try? await Task.sleep(for: .milliseconds(300))

        guard !Task.isCancelled else { return }

        await performSearch(text)
    }
}
```

## Chủ đề: Continuation & Legacy API

### 34. Một SDK cũ chỉ cung cấp callback nhưng codebase mới sử dụng async/await. Bạn sẽ kết nối hai mô hình này như thế nào?

**Ý chính:** `withCheckedContinuation` / `withCheckedThrowingContinuation`.

**Diễn giải:**
Continuation biến callback-based API thành async function. API cũ gọi completion thì continuation resume. `CheckedContinuation` giúp phát hiện một số lỗi như resume nhiều lần.

**Ví dụ:**

```swift
func fetchUser() async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        legacyAPI.fetchUser { result in
            continuation.resume(with: result)
        }
    }
}
```

---

### 35. Lỗi nguy hiểm nhất khi tự chuyển callback API thành async function bằng continuation là gì?

**Ý chính:** Resume exactly once.

**Diễn giải:**
Continuation phải được resume đúng một lần. Nếu không resume, task chờ vĩnh viễn. Nếu resume hai lần, chương trình có thể crash. Vì vậy cần kiểm soát mọi success/error/cancellation path.

**Ví dụ:**

```swift
withCheckedContinuation { continuation in
    legacyAPI { value in
        continuation.resume(returning: value)

        // Không được resume lần nữa
    }
}
```

### 36. Nếu API cũ có thể gọi callback nhiều lần nhưng bạn muốn expose nó dưới dạng async function trả về một kết quả duy nhất, bạn xử lý thế nào?

**Ý chính:** Continuation chỉ phù hợp one-shot; nhiều event dùng `AsyncStream`.

**Diễn giải:**
Continuation phù hợp operation chỉ có một completion. Nếu callback phát event nhiều lần như location, socket hoặc notification, nên dùng `AsyncStream` hoặc `AsyncThrowingStream`.

**Ví dụ:**

```swift
func events() -> AsyncStream<String> {
    AsyncStream { continuation in
        legacyAPI.onEvent { value in
            continuation.yield(value)
        }

        legacyAPI.onStop {
            continuation.finish()
        }
    }
}
```

# Chủ đề: AsyncSequence

### 37. Khi một nguồn dữ liệu liên tục phát ra nhiều giá trị theo thời gian, bạn sẽ thiết kế API bất đồng bộ thế nào?

**Ý chính:** `AsyncSequence` / `AsyncStream`.

**Diễn giải:**
Không nên tạo một async function cho từng event. `AsyncSequence` biểu diễn một stream dữ liệu mà consumer có thể đọc bằng `for await`.

**Ví dụ:**

```swift
for await event in events() {
    print(event)
}
```

### 38. Nếu UI không còn quan tâm tới một stream dữ liệu nữa, bạn làm sao dừng việc nhận dữ liệu?

**Ý chính:** Task cancellation + stream termination.

**Diễn giải:**
Task đang `for await` có thể bị cancel. Producer cũng nên phản ứng với cancellation và giải phóng resource thông qua `onTermination`.

**Ví dụ:**

```swift
let task = Task {
    for await value in stream {
        handle(value)
    }
}

task.cancel()
```

### 39. Khi nào bạn chọn stream dữ liệu thay vì callback truyền thống?

**Ý chính:** `AsyncSequence` - multiple values, lifecycle, cancellation.

**Diễn giải:**
Stream phù hợp với event liên tục: WebSocket, location, notifications, database changes. Consumer có thể dùng cùng mô hình `async/await`, dễ kết hợp cancellation và structured concurrency.

**Ví dụ:**

```swift
for await notification in notifications {
    handle(notification)
}
```

# Chủ đề: Cancellation & Resource Management

### 40. Một task bị cancel trong lúc đang thực hiện nhiều bước. Bạn thiết kế code thế nào để không tiếp tục các bước không cần thiết?

**Ý chính:** Cancellation checkpoints.

**Diễn giải:**
Cancellation không tự động dừng mọi synchronous code. Cần đặt checkpoint ở các bước phù hợp bằng `Task.isCancelled` hoặc `Task.checkCancellation()` và dùng API hỗ trợ cancellation.

**Ví dụ:**

```swift
func process() async throws {
    try Task.checkCancellation()

    let data = try await download()

    try Task.checkCancellation()

    process(data)
}
```

### 41. Nếu task bị cancel nhưng API network bên dưới vẫn tiếp tục chạy thì vấn đề nằm ở đâu?

**Ý chính:** Cancellation propagation không tự động với mọi API.

**Diễn giải:**
Swift Task cancellation cần được API phía dưới hỗ trợ. Nếu wrapper không forward cancellation xuống `URLSession` hoặc SDK thì request có thể vẫn chạy dù caller đã cancel task.

**Ví dụ:**

```swift
let task = Task {
    try await api.fetch()

task.cancel()
```

Việc cancel task không đảm bảo mọi API bên dưới tự dừng nếu API không hỗ trợ.

### 43. Bạn thiết kế một màn hình cần tải profile, danh sách bài viết và danh sách notification. Ba nguồn dữ liệu độc lập. Bạn sẽ thiết kế flow như thế nào?

```swift
@MainActor
final class DashboardViewModel {
    var profile: Profile?
    var posts: [Post] = []
    var notifications: [Notification] = []

    func load() async {
        async let profile = repository.loadProfile()
        async let posts = repository.loadPosts()
        async let notifications = repository.loadNotifications()

        self.profile = try? await profile
        self.posts = (try? await posts) ?? []
        self.notifications = (try? await notifications) ?? []
    }
}
```

### 45. Bạn xây dựng một image downloader dùng chung cho toàn app. Làm sao đảm bảo nhiều màn hình yêu cầu cùng một ảnh không tạo nhiều request?

**Ý chính:** Actor + cache + in-flight request deduplication.

**Diễn giải:**
Dùng actor để bảo vệ cache. Ngoài cached data, lưu các request đang chạy. Nếu URL đã có task trong `inFlight`, caller mới await task đó thay vì tạo request mới.

**Ví dụ:**

```swift
actor ImageLoader {
    private var cache: [URL: Data] = [:]
    private var inFlight: [URL: Task<Data, Error>] = [:]

    func load(_ url: URL) async throws -> Data {
        if let data = cache[url] {
            return data
        }

        if let task = inFlight[url] {
            return try await task.value
        }

        let task = Task {
            try await download(url)
        }

        inFlight[url] = task

        defer {
            inFlight[url] = nil
        }

        let data = try await task.value
        cache[url] = data

        return data
    }
}
```

### 46. Một actor chứa cache nhưng sau một `await`, dữ liệu trong cache có thể đã thay đổi. Bạn sẽ thiết kế API thế nào để tránh bug logic?

**Ý chính:** Actor reentrancy + minimize suspension + revalidate state.

**Diễn giải:**
Không nên giữ assumption về state qua `await`. Nếu operation yêu cầu tính nhất quán, phần kiểm tra và mutation nên được thực hiện trong cùng actor-isolated operation khi có thể. Sau `await` phải re-check các điều kiện quan trọng.

**Ví dụ:**

```swift
actor Cache {
    private var values: [String: Data] = [:]

    func get(_ key: String) async -> Data? {
        if let value = values[key] {
            return value
        }

        let value = await download(key)

        // Có thể state đã thay đổi trong lúc await.
        values[key] = value

        return value
    }
}
```

### 47. Bạn có một repository vừa được gọi từ UI vừa được gọi từ background task. Bạn sẽ tổ chức isolation ở tầng nào?

**Ý chính:** UI isolation ≠ repository isolation; isolate state tại nơi sở hữu state.

**Diễn giải:**
Không nên đánh dấu toàn bộ repository `@MainActor` chỉ vì UI gọi nó. UI/ViewModel có thể thuộc MainActor, còn repository nên độc lập nếu nó không sở hữu UI state. Shared mutable state thì dùng actor hoặc cơ chế isolation phù hợp.

**Ví dụ:**

```swift

    private var users: [Int: User] = [:]

struct UserRepository {
    let cache: UserCache

    func loadUser(id: Int) async throws -> User {
        if let user = await cache.user(id) {
            return user
        }

        let user = try await api.fetchUser(id)
        await cache.save(user)

        return user
    }
}
```

## Chủ đề: Race Condition & Correctness

### 48. Hai request cùng đọc một trạng thái là “chưa có dữ liệu”, sau đó cả hai cùng tạo dữ liệu mới. Dù bạn đã dùng async/await, tại sao lỗi vẫn xảy ra?

**Ý chính:** `async/await` không tự giải quyết race condition.

**Diễn giải:**
Async/await chỉ thay đổi cách viết asynchronous code. Nó không tự động bảo vệ shared mutable state. Nếu hai task có thể cùng kiểm tra và thay đổi state mà không có isolation, race condition vẫn xảy ra.

**Ví dụ:**

```swift
// Cả hai task có thể nhìn thấy cache[key] == nil
if cache[key] == nil {
    cache[key] = await createValue()
}
```

Cần đưa state vào actor hoặc thiết kế operation có isolation phù hợp.

---

### 49. Một team nói rằng “chỉ cần thêm actor là mọi race condition đều biến mất”. Bạn đánh giá nhận định này thế nào?

**Ý chính:** Actor giải quyết data race trên isolated state, không tự giải quyết mọi logical race.

**Diễn giải:**
Actor rất mạnh trong việc bảo vệ mutable state, nhưng vẫn có logical race do suspension point, stale state, thứ tự operation hoặc external side effects. Đặc biệt phải hiểu actor reentrancy.

Ví dụ:

```swift
actor Store {
    var balance = 100

    func check() async -> Bool {
        balance > 0
    }

    func withdraw() {
        balance -= 1
    }
}
```

Một flow kiểu:

```swift
if await store.check() {
    await externalOperation()
    await store.withdraw()
}
```

vẫn có thể sai vì state có thể thay đổi trong `await`.

### 50. Bạn được giao migrate một codebase iOS lớn từ callback, GCD và OperationQueue sang Swift Concurrency. Bạn sẽ thực hiện migration như thế nào?

**Ý chính:** Incremental migration → async boundary → structured concurrency → actor isolation → MainActor → Sendable → cancellation → testing.

**Diễn giải:**
Không nên rewrite toàn bộ cùng lúc. Trước tiên xác định các async boundary quan trọng và chuyển API callback thành `async/await`. Sau đó chuyển các flow orchestration sang structured concurrency. UI state được xác định rõ `@MainActor`. Shared mutable state được chuyển sang actor hoặc thiết kế lại. Tiếp theo bật dần strict concurrency và xử lý `Sendable`.

Quan trọng nhất là không chỉ “đổi syntax”. Migration phải cải thiện **ownership, lifecycle, cancellation và data-race safety**.

**Ví dụ:**

```swift
// Trước

func fetchUser(completion: @escaping (Result<User, Error>) -> Void) {
    api.fetch { result in
        completion(result)
    }
}


// Sau

func fetchUser() async throws -> User {
    try await withCheckedThrowingContinuation { continuation in
        api.fetch { result in
            continuation.resume(with: result)
        }
    }
}
```

Sau đó flow phía trên có thể trở thành:

```swift
@MainActor
final class ViewModel {
    var state: State = .idle

    func load() async {
        state = .loading

        do {
            let user = try await repository.fetchUser()
            state = .loaded(user)
        } catch is CancellationError {
            // Không cần hiển thị lỗi cancellation
        } catch {
            state = .error(error)
        }
    }
}
```

# CẤP ĐỘ 6: SENIOR+ — DEEP DIVE

## Chủ đề: Actor Reentrancy

### 51. Vì sao một actor vẫn có thể xảy ra lỗi logic dù state bên trong nó không bị truy cập đồng thời?

**Ý chính:** `actor` chống **data race**, nhưng không đảm bảo **logic atomicity** qua `await`.

**Diễn giải:**
Actor serialize access vào state, nhưng khi gặp `await`, actor có thể nhường quyền cho operation khác. Khi quay lại, state có thể đã thay đổi. Vì vậy actor không đảm bảo toàn bộ một method async là atomic.

**Ví dụ:**

```swift
actor BankAccount {
    private var balance = 100

    func withdraw() async {
        guard balance >= 50 else {
            return
        }

        await checkWithServer()

        balance -= 50
    }
}
```

Trong thời gian `checkWithServer()` chạy, một task khác có thể thay đổi `balance`.

---

### 52. Bạn sẽ sửa logic ở trên như thế nào nếu điều kiện kiểm tra số dư phải luôn chính xác?

**Ý chính:** Không giữ **stale state** qua `await`; kiểm tra lại state sau suspension point.

**Diễn giải:**
Giá trị đọc trước `await` có thể trở nên lỗi thời. Nếu business rule phụ thuộc state hiện tại, cần thiết kế lại flow để validation và mutation được thực hiện ở thời điểm phù hợp.

**Ví dụ:**

```swift
actor BankAccount {
    private var balance = 100

    func withdraw() async {
        await checkWithServer()

        guard balance >= 50 else {
            return
        }

        balance -= 50
    }
}
```

Điểm quan trọng là không sử dụng assumption được tạo trước `await`.

---

### 53. Actor có giống một mutex không?

**Ý chính:** Không. `actor` là **isolation model**, không phải mutex.

**Diễn giải:**
Mutex khóa một vùng code. Actor bảo vệ state bằng isolation và executor. Actor cho phép code bên trong chạy, suspension và tiếp tục sau `await`, trong khi operation khác có thể được xử lý.

**Ví dụ:**

```swift
actor Counter {
    private var value = 0

    func increment() {
        value += 1
    }
}
```

Không cần tự tạo lock để bảo vệ `value`.

---

### 54. Tại sao việc thêm `await` vào một actor method có thể làm thay đổi behavior của hệ thống?

**Ý chính:** `await` tạo **suspension point** → actor có thể **re-enter**.

**Diễn giải:**
Trước `await`, operation đang thực hiện trên actor. Khi gặp `await`, actor có thể xử lý operation khác. Khi operation ban đầu tiếp tục, state có thể khác trước đó.

**Ví dụ:**

```swift
actor Store {
    var value = 0

    func update() async {
        value = 10

        await something()

        // value không nhất thiết vẫn là 10
        print(value)
    }
}
```

# Chủ đề: Task Lifecycle

### 55. Một Task giữ reference mạnh đến ViewModel, và ViewModel giữ reference đến Task. Điều gì có thể xảy ra?

**Ý chính:** **Retain cycle / extended lifetime**.

**Diễn giải:**
Task có thể capture `self` mạnh. ViewModel giữ Task, trong khi Task giữ ViewModel. Nếu task không kết thúc hoặc không được cancel, object có thể sống lâu hơn dự kiến.

**Ví dụ:**

```swift
@MainActor
final class ViewModel {
    var task: Task<Void, Never>?

    func start() {
        task = Task {
            await self.load()
        }
    }

    func load() async {
        // long-running work
    }
}
```

Nếu task sống rất lâu, `ViewModel` cũng có thể bị giữ lại.

---

### 56. Bạn có nên luôn dùng `[weak self]` bên trong Task để tránh memory leak không?

**Ý chính:** Không. **Weak capture không phải giải pháp mặc định**.

**Diễn giải:**
Cần hiểu lifecycle trước. Nếu Task thuộc về ViewModel và ViewModel cần sống cho đến khi task hoàn thành thì strong capture có thể hợp lý. Nếu task phải không giữ object sống lâu hơn lifecycle của nó thì mới cân nhắc weak capture hoặc cancellation.

**Ví dụ:**

```swift
task = Task { [weak self] in
    guard let self else { return }

    await self.load()
}
```

Quan trọng hơn `[weak self]` là thiết kế **ownership + cancellation** đúng.

---

### 57. Một Task chạy vô hạn để nhận dữ liệu từ WebSocket. Bạn sẽ thiết kế lifecycle của nó thế nào?

**Ý chính:** Owner rõ ràng + `cancel()` + cancellation-aware loop.

**Diễn giải:**
Task phải có một owner chịu trách nhiệm tạo và cancel. Khi ViewModel/service không còn sử dụng WebSocket, cancel task. Vòng lặp phải phản ứng với cancellation.

**Ví dụ:**

```swift
final class SocketService {
    private var task: Task<Void, Never>?

    func start() {
        task = Task {
            for await event in socket.events {
                if Task.isCancelled {
                    break
                }

                handle(event)
            }
        }
    }

    func stop() {
        task?.cancel()
        task = nil
    }
}
```

# Chủ đề: Cancellation

### 58. Tại sao `Task.cancel()` không giống việc kill một thread?

**Ý chính:** Cancellation là **cooperative**.

**Diễn giải:**
`cancel()` chỉ đánh dấu task đã bị cancel. Task phải kiểm tra trạng thái hoặc gọi API hỗ trợ cancellation. Swift không cưỡng chế dừng arbitrary synchronous code.

**Ví dụ:**

```swift
let task = Task {
    while !Task.isCancelled {
        doWork()
    }
}

task.cancel()
```

Nếu `doWork()` là một vòng lặp synchronous không kiểm tra cancellation, task vẫn tiếp tục.

---

### 59. Một hàm synchronous CPU-heavy chạy 10 giây. Bạn gọi `Task.cancel()` nhưng CPU vẫn chạy. Tại sao?

**Ý chính:** Cancellation chỉ là **signal**, không interrupt synchronous computation.

**Diễn giải:**
Nếu code đang chạy CPU-bound và không có suspension point/checkpoint, cancellation không thể tự dừng nó. Cần chia computation thành các bước và kiểm tra cancellation.

**Ví dụ:**

```swift
func calculate() async throws -> Int {
    var result = 0

    for i in 0..<10_000_000 {
        try Task.checkCancellation()

        result += i
    }

    return result
}
```

### 60. Bạn có một pipeline gồm 5 bước async. Nếu bước cuối bị cancel, làm sao đảm bảo resource của các bước trước được giải phóng?

**Ý chính:** `defer` + cancellation-aware cleanup.

**Diễn giải:**
Cancellation có thể xảy ra ở nhiều điểm. Resource cleanup không nên phụ thuộc vào việc operation kết thúc thành công. `defer` giúp cleanup khi scope kết thúc.

**Ví dụ:**

```swift
func process() async throws {
    let resource = acquireResource()

    defer {
        release(resource)
    }

    try Task.checkCancellation()

    let data = try await load()

    try Task.checkCancellation()

    await process(data)
}
```

# Chủ đề: Structured Concurrency

### 61. Vì sao structured concurrency được xem là an toàn hơn việc tạo hàng loạt Task độc lập?

**Ý chính:** **Lifecycle + cancellation + error propagation + ownership**.

**Diễn giải:**
Child task nằm trong scope của parent. Parent biết child nào đang chạy và phải chờ child hoàn thành. Cancellation và error có thể được propagate. Điều này làm lifecycle dễ reasoning hơn.

**Ví dụ:**

```swift
func loadAll() async {
    await withTaskGroup(of: Void.self) { group in
        group.addTask {
            await loadA()
        }

        group.addTask {
            await loadB()
        }
    }

    // Tất cả child task đã hoàn thành
}
```

---

### 62. Nếu bạn tạo `Task` bên trong một function rồi return ngay, task đó có còn chạy không?

**Ý chính:** `Task` độc lập có **lifecycle riêng**.

**Diễn giải:**
Task được tạo bằng `Task {}` không tự động bị hủy chỉ vì function tạo nó đã return. Đây là điểm khác với child task trong structured concurrency.

**Ví dụ:**

```swift
func start() {
    Task {
        await longRunningWork()
    }

    print("Function returned")
}
```

`longRunningWork()` vẫn có thể tiếp tục sau khi `start()` return.

---

### 63. Khi nào việc tạo unstructured Task là hợp lý?

**Ý chính:** Khi cần **fire-and-manage-later lifecycle** hoặc bridge từ synchronous context.

**Diễn giải:**
Ví dụ UI action cần bắt đầu async operation, hoặc một service cần giữ Task để cancel sau. Nhưng phải có owner rõ ràng và không tạo task vô tội vạ.

**Ví dụ:**

```swift
final class ViewModel {
    private var loadTask: Task<Void, Never>?

    func refresh() {
        loadTask?.cancel()

        loadTask = Task {
            await load()
        }
    }
}
```

# Chủ đề: TaskGroup

### 64. Với 10.000 item cần xử lý, bạn có nên tạo 10.000 child task cùng lúc không?

**Ý chính:** Không mặc định. Cần **limit concurrency**.

**Diễn giải:**
Task nhẹ không có nghĩa số lượng vô hạn là miễn phí. Quá nhiều task có thể gây áp lực CPU, memory, network và server. Senior cần cân nhắc concurrency limit và backpressure.

**Ví dụ:**

```swift
// Không nên mặc định làm:

await withTaskGroup(of: Result.self) { group in
    for item in 10_000_items {
        group.addTask {
            await process(item)
        }
    }
}
```

Một thiết kế tốt hơn là chia thành batch hoặc dùng worker pool với giới hạn concurrency.

---

### 65. Nếu TaskGroup trả kết quả theo thứ tự hoàn thành thay vì thứ tự input, bạn xử lý thế nào?

**Ý chính:** `TaskGroup` result order không đảm bảo; gắn **index/ID** với result.

**Diễn giải:**
Child nào hoàn thành trước sẽ được lấy trước. Nếu UI hoặc business logic yêu cầu thứ tự ban đầu, phải lưu index hoặc key rồi sort/reconstruct kết quả.

**Ví dụ:**

```swift
let results = await withTaskGroup(
    of: (Int, String).self
) { group in

    for (index, item) in items.enumerated() {
        group.addTask {
            let result = await process(item)
            return (index, result)
        }
    }

    var values: [(Int, String)] = []

    for await result in group {
        values.append(result)
    }

    return values.sorted { $0.0 < $1.0 }
}
```

# Chủ đề: Sendable

### 66. Vì sao một struct có thể an toàn hơn một class khi truyền giữa các task?

**Ý chính:** **Value semantics** + immutable state.

**Diễn giải:**
Struct được copy theo value semantics. Nếu các property của nó cũng concurrency-safe, việc truyền qua concurrency boundary dễ đảm bảo hơn. Class dùng reference semantics nên nhiều task có thể cùng truy cập một instance.

**Ví dụ:**

```swift
struct User: Sendable {
    let id: Int
    let name: String
}
```

Trong khi:

```swift
final class User {
    var name: String
}
```

có shared mutable state nếu nhiều nơi cùng giữ reference.

---

### 67. `@unchecked Sendable` có ý nghĩa gì và tại sao Senior phải cực kỳ cẩn thận với nó?

**Ý chính:** `@unchecked Sendable` = **tự cam kết thread-safety**, compiler không kiểm tra đầy đủ.

**Diễn giải:**
Khi đánh dấu `@unchecked Sendable`, developer nói với compiler rằng type an toàn khi truyền qua concurrency boundary. Nếu assertion sai, data race có thể xảy ra mà compiler không bảo vệ được.

**Ví dụ:**

```swift
final class ThreadSafeCache: @unchecked Sendable {
    private let lock = NSLock()
    private var value: String?

    func get() -> String? {
        lock.lock()
        defer { lock.unlock() }

        return value
    }
}
```

Chỉ dùng khi bạn thực sự chứng minh được synchronization là đúng.

# Chủ đề: Continuation

### 68. Bạn wrap một callback API bằng continuation nhưng đôi khi app treo vĩnh viễn. Bạn sẽ kiểm tra gì đầu tiên?

**Ý chính:** Continuation phải được **resume exactly once**.

**Diễn giải:**
Nếu callback không được gọi ở một execution path, continuation sẽ chờ mãi. Nếu callback được gọi nhiều lần, continuation có thể crash. Cần kiểm tra tất cả success, failure, cancellation và early-return paths.

**Ví dụ:**

```swift
func load() async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in

        legacyAPI.load { result in
            switch result {
            case .success(let data):
                continuation.resume(returning: data)

            case .failure(let error):
                continuation.resume(throwing: error)
            }
        }
    }
}
```

Không được có path nào quên `resume()`.

# Chủ đề: AsyncSequence

### 69. Bạn chuyển callback stream sang AsyncStream nhưng memory/resource không được giải phóng sau khi consumer dừng. Bạn sẽ kiểm tra gì?

**Ý chính:** `onTermination` + cancellation + producer lifecycle.

**Diễn giải:**
`AsyncStream` không tự biết cách dừng resource của hệ thống bên dưới. Khi consumer cancel hoặc stream kết thúc, cần cleanup subscription, timer, socket hoặc observer.

**Ví dụ:**

```swift
func events() -> AsyncStream<Event> {
    AsyncStream { continuation in

        let observer = registerObserver { event in
            continuation.yield(event)
        }

        continuation.onTermination = { @Sendable _ in
            observer.cancel()
        }
    }
}
```

Đây là điểm rất hay được hỏi khi chuyển từ NotificationCenter/RxSwift sang Swift Concurrency.

# Chủ đề: MainActor & Architecture

### 70. Một ViewModel toàn bộ đều nằm trên MainActor nhưng bên trong có một thuật toán xử lý dữ liệu rất nặng. Bạn sẽ thiết kế lại thế nào?

**Ý chính:** **Không đưa CPU-heavy work vào MainActor**; tách computation khỏi UI isolation.

**Diễn giải:**
`@MainActor` phù hợp với UI state, nhưng CPU-heavy work không nên chiếm execution context của UI. Nên tách pure computation thành một component độc lập, sau đó đưa kết quả về MainActor để cập nhật UI.

**Ví dụ:**

```swift
struct DataProcessor {
    func process(_ data: [Int]) -> [Int] {
        // CPU-heavy work
        data.sorted()
    }
}

@MainActor
final class ViewModel {
    private let processor = DataProcessor()

    var result: [Int] = []

    func load() async {
        let data = await fetchData()

        let processed = processor.process(data)

        result = processed
    }
}
```

Nếu `process()` thực sự nặng, cần thiết kế execution boundary phù hợp thay vì mặc định nhét toàn bộ ViewModel vào MainActor.

Điểm Senior cần nói thêm:

> `@MainActor` không phải nơi để “đẩy tất cả background work”. Nó là nơi bảo vệ UI state. CPU-heavy computation nên có ownership/isolation riêng.

### Một số “bẫy” rất dễ bị interviewer hỏi tiếp

Nếu interviewer đào sâu sau 20 câu trên, hãy đặc biệt nhớ các cặp này:

| Interviewer hỏi | Câu trả lời Senior nên hướng tới |
|---|---|
| `async` có nghĩa là chạy background không? | **Không**. `async` nói về suspension, không phải background thread. |
| `await` có block thread không? | **Không**. Task suspend, thread có thể làm việc khác. |
| `Task.cancel()` có kill task không? | **Không**. Cancellation là cooperative. |
| Actor có nghĩa là một thread riêng không? | **Không**. Actor là isolation, không phải thread. |
| Actor có loại bỏ mọi race condition không? | **Không**. Data race được bảo vệ, nhưng logical race vẫn có thể xảy ra. |
| `@MainActor` có nghĩa mọi code chạy liên tục trên main thread không? | Không. Có suspension; quan trọng là isolation của UI state. |
| `Task.detached` dùng để chạy background? | Không nên hiểu đơn giản như vậy. Nó là task **không kế thừa context**. |
| `async let` có phải thread mới không? | Không. Nó tạo concurrent child task, runtime quyết định execution. |
| `TaskGroup` có đảm bảo thứ tự result không? | Không. Result thường đến theo completion order. |
| Cancellation có tự truyền xuống URLSession/SDK không? | Không nhất thiết. Underlying API phải hỗ trợ/được bridge đúng. |
| `Sendable` có nghĩa immutable không? | Không hoàn toàn. Nó là contract về việc type an toàn khi truyền qua concurrency boundary. |

| Continuation có thể resume nhiều lần không? | Không. Phải **exactly once**. |
| AsyncStream dùng cho callback một lần? | Không tối ưu. One-shot → continuation; nhiều event → AsyncStream. |

# CÁCH TRẢ LỜI CÂU CONCURRENCY Ở LEVEL SENIOR

Một câu trả lời Senior tốt thường không dừng ở:

> “Dùng `actor` để thread-safe.”

Mà nên đi theo chuỗi:

```text
Shared state?
    ↓
Ai sở hữu state?
    ↓
Có concurrency boundary?
    ↓
Có await/suspension point?
    ↓
Có thể xảy ra reentrancy?
    ↓
Task lifecycle thuộc về ai?
    ↓
Cancellation truyền tới đâu?
    ↓
Dữ liệu có Sendable không?
    ↓
Có giới hạn concurrency không?
    ↓
Có logical race dù không có data race không?
````

Đặc biệt, nếu interviewer đưa một đoạn code có `actor`, **đừng mặc định kết luận “an toàn”**.

Hãy tìm:

```swift
actor Something {
    var state: State

    func operation() async {
        let oldState = state

        await externalWork()

        state = oldState
    }
}
```

Câu hỏi quan trọng nhất là:

> **“Trong khoảng thời gian `await`, state có thể bị thay đổi không?”**

Nếu có, đó chính là chỗ để đào sâu **actor reentrancy + stale state + logical race** — một trong những chủ đề phân biệt Senior với người chỉ biết syntax Swift Concurrency.
