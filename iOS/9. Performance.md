# I. INSTRUMENTS

## 1. Khi người dùng nói “app chậm”, bạn sẽ bắt đầu điều tra từ đâu?

**Ý chính:** `Measure first` - xác định symptom và bottleneck bằng Instruments.

**Ý diễn giải:**
Không nên đoán nguyên nhân. Trước tiên xác định vấn đề là launch chậm, scroll lag, memory tăng, CPU cao, network chậm hay battery drain. Sau đó chọn instrument phù hợp.

**Ví dụ:**

```text
Launch chậm
    ↓
Time Profiler / launch metrics

CPU cao
    ↓
Time Profiler

Memory tăng
    ↓
Allocations / Memory Graph

Leak
    ↓
Leaks / Memory Graph

Scroll lag
    ↓
Time Profiler + Core Animation
```

---

## 2. Time Profiler cho bạn biết điều gì mà việc nhìn code bằng mắt thường không cho biết?

**Ý chính:** `CPU hot path`.

**Ý diễn giải:**
Time Profiler cho biết thời gian CPU đang tiêu ở đâu. Nó giúp xác định function nào thực sự là bottleneck thay vì tối ưu code mà thực tế không đáng kể.

**Ví dụ:**

```text
Time Profiler

processImage()
   42%

JSONDecoder
   21%

layoutSubviews
   18%

other
   19%
```

Từ đó ưu tiên `processImage()` thay vì tối ưu những phần chỉ chiếm 1–2%.

---

## 3. Một function xuất hiện nhiều lần trong Time Profiler. Có chắc function đó là bottleneck không?

**Ý chính:** Cần nhìn `self time`, `total time`, call count và context.

**Ý diễn giải:**
Một function có thể xuất hiện nhiều vì được gọi rất thường xuyên nhưng mỗi lần rất nhanh. Ngược lại một function ít gọi nhưng mỗi lần cực kỳ nặng cũng có thể là bottleneck.

**Ví dụ:**

```text
Function A
Calls: 100,000
Total: 500 ms

Function B
Calls: 10
Total: 5 sec
```

B mới có thể là ưu tiên cao hơn.

---

## 4. Khi CPU thấp nhưng UI vẫn giật, bạn sẽ nghi ngờ những vấn đề nào?

**Ý chính:** `GPU / rendering / layout / memory bandwidth`.

**Ý diễn giải:**
Frame drop không nhất thiết do CPU. Có thể GPU rendering nặng, transparency, shadow, offscreen rendering, layout quá phức tạp hoặc memory pressure.

**Ví dụ:**

```text
CPU: 20%
GPU: 95%

→ Không nên chỉ tối ưu Swift code.
→ Kiểm tra rendering pipeline.
```

# II. MAIN THREAD

## 5. Vì sao một thao tác chỉ mất 30 ms cũng có thể làm animation giật?

**Ý chính:** `Frame budget`.

**Ý diễn giải:**
Ở 60 FPS, mỗi frame chỉ có khoảng 16.67 ms. Nếu main thread bị chặn quá lâu trong một frame, frame có thể bị missed. 120 Hz còn có budget khoảng 8.33 ms.

**Ví dụ:**

```text
60 FPS
≈ 16.67 ms / frame

120 FPS
≈ 8.33 ms / frame
```

Một operation:

```swift
let result = expensiveCalculation()
```

nằm trên main actor trong lúc scrolling có thể gây frame drop dù tổng thời gian chỉ vài chục ms.

---

## 6. Bạn phát hiện JSON decoding đang chạy trên main thread. Vì sao đây có thể trở thành vấn đề?

**Ý chính:** `CPU-heavy synchronous work` chặn UI.

**Ý diễn giải:**
JSON decoding lớn có thể tiêu CPU ngay trên main thread. Khi đó input, layout và rendering phải chờ. Cần đo kích thước payload và chuyển phần computation khỏi UI-critical path khi cần.

**Ví dụ:**

```swift
// Không lý tưởng nếu payload rất lớn
@MainActor
func load() {
    let model = try! JSONDecoder().decode(
        HugeModel.self,
        from: data
    )
}
```

Nên tách computation khỏi UI update.

---

## 7. Có phải mọi work asynchronous đều tự động không block main thread không?

**Ý chính:** `async != background`.

**Ý diễn giải:**
Một hàm async vẫn có thể thực hiện synchronous CPU-heavy work trên MainActor. `await` chỉ giúp suspension; không tự biến mọi computation thành background work.

**Ví dụ:**

```swift
@MainActor
func process() async {
    await fetch()

    // Vẫn có thể chạy trên MainActor
    // nếu đây là synchronous CPU work.
    expensiveCalculation()
}
```

---

## 8. Bạn sẽ xác định main thread đang bị block bởi code nào như thế nào?

**Ý chính:** `Time Profiler + Main Thread call stack + signposts`.

**Ý diễn giải:**
Xem call stack trong thời điểm hitch, tìm synchronous work trên main thread và dùng signpost để đánh dấu các operation quan trọng.

**Ví dụ:**

```swift
let log = OSLog(
    subsystem: "com.example.app",
    category: .pointsOfInterest
)

os_signpost(
    .begin,
    log: log,
    name: "DecodeImage"
)

decodeImage()

os_signpost(
    .end,
    log: log,
    name: "DecodeImage"
)
```

# III. COLLECTIONVIEW / SCROLLING

## 9. CollectionView scroll bị giật khi hiển thị 1.000 ảnh. Bạn sẽ debug theo thứ tự nào?

**Ý chính:** `Measure → CPU → Main Thread → Image pipeline → Layout → Reuse → Network → Rendering`.

**Ý diễn giải:**
Không kết luận ngay là cache thiếu. Cần phân tích toàn bộ pipeline. Một nguyên nhân rất phổ biến là decode hoặc resize ảnh lớn ngay trên main thread.

**Ví dụ:**

```text
1. CPU?
2. Main Thread?
3. Image decode?
4. Resize/downsample?
5. Network?
6. Cache?
7. Cell configuration?
8. Auto Layout?
9. Reuse?
10. Rendering/GPU?
```

---

## 10. Vì sao tải ảnh xong nhưng collection vẫn lag?

**Ý chính:** `Image decoding` có thể đắt hơn network.

**Ý diễn giải:**
Network chỉ trả bytes. Để hiển thị, app còn phải decode compressed image thành pixel buffer và có thể resize. Một ảnh 4000×3000 có thể tốn rất nhiều memory và CPU dù file JPEG không lớn.

**Ví dụ:**

```text
JPEG
  ↓
Compressed bytes
  ↓
Decode
  ↓
Raw pixels
  ↓
Resize
  ↓
Render
```

Không nên chỉ nhìn thời gian download.

---

## 11. Tại sao downsampling ảnh quan trọng hơn chỉ cache ảnh?

**Ý chính:** `Match decoded size to display size`.

**Ý diễn giải:**
Cache chỉ giảm request/decode lặp lại. Nếu bạn vẫn decode ảnh 4000 px để hiển thị thumbnail 100 px thì CPU và memory vẫn bị lãng phí.

**Ví dụ:**

```text
Ảnh gốc:
4000 × 3000

UI cần:
100 × 75

❌ Decode 4000 × 3000

✅ Downsample gần 100 × 75
```

---

## 12. Một cell được reuse nhưng ảnh cũ đôi khi vẫn xuất hiện. Tại sao vấn đề này vừa là correctness vừa là performance?

**Ý chính:** `Cell reuse + stale async result + unnecessary work`.

**Ý diễn giải:**
Request cũ có thể tiếp tục chạy và khi hoàn thành ghi vào cell mới. Ngoài bug hiển thị, request/decode cũ còn tiêu tốn tài nguyên không cần thiết.

**Ví dụ:**

```swift
final class ImageCell: UICollectionViewCell {

    private var task: Task<Void, Never>?

    override func prepareForReuse() {
        super.prepareForReuse()

        task?.cancel()
        task = nil
        imageView?.image = nil
    }
}
```

# IV. MEMORY

## 13. Memory usage tăng đều khi người dùng scroll nhưng sau khi rời màn hình vẫn giảm rất ít. Bạn sẽ phân biệt leak và cache growth thế nào?

**Ý chính:** `Memory Graph + Allocations + ownership vs intended cache`.

**Ý diễn giải:**
Không phải mọi memory growth đều là leak. Cache có chủ ý có thể giữ object sống lâu. Leak xảy ra khi object vẫn reachable qua reference graph dù business lifecycle đã kết thúc.

**Ví dụ:**

```text
Memory tăng
    ↓
Object vẫn reachable?
    ↓
Có cache ownership hợp lệ?
    ├── Có → cache policy
    └── Không → tìm retain path
```

---

## 14. Một singleton giữ 10.000 image trong memory. Bạn gọi đây là memory leak ngay không?

**Ý chính:** Không. Có thể là `unbounded cache`.

**Ý diễn giải:**
Singleton có thể chủ động sở hữu cache. Nếu cache không có eviction policy, đây là memory management problem nhưng không nhất thiết là ARC leak.

**Ví dụ:**

```swift
final class ImageCache {

    static let shared = ImageCache()

    var images: [URL: UIImage] = [:]
}
```

Đây có thể gây memory growth nếu dictionary không có eviction.

---

## 15. NSCache phù hợp với loại data nào và vì sao?

**Ý chính:** `Recreatable memory cache` + eviction.

**Ý diễn giải:**
NSCache phù hợp image/data có thể tải hoặc tạo lại. System có thể evict object khi memory pressure xảy ra, nên không thể dùng nó làm source of truth.

**Ví dụ:**

```swift
let cache =
    NSCache<NSURL, UIImage>()

cache.setObject(
    image,
    forKey: url as NSURL
)
```

---

## 16. Autoreleasepool có thể giúp gì khi xử lý hàng nghìn object?

**Ý chính:** `Reduce temporary object lifetime`.

**Ý diễn giải:**
Một số API/framework tạo autoreleased Objective-C objects. Khi xử lý batch lớn, autoreleasepool giúp temporary objects được giải phóng sớm hơn thay vì tích tụ tới cuối outer scope.

**Ví dụ:**

```swift
for item in items {

    autoreleasepool {
        process(item)
    }
}
```

# V. RENDERING / CORE ANIMATION

## 17. Một UI đơn giản nhưng có rất nhiều transparency, shadow và mask bị lag khi scroll. Bạn nghi ngờ gì?

**Ý chính:** `GPU rendering + offscreen rendering + compositing`.

**Ý diễn giải:**
Transparency và hiệu ứng layer có thể làm GPU phải thực hiện nhiều pass hoặc blending. Shadow/mask phức tạp cũng có thể tăng render cost.

**Ví dụ:**

```swift
view.layer.shadowOpacity = 0.3
view.layer.shadowRadius = 20
view.layer.masksToBounds = true
```

Các combination phức tạp cần được đo trong rendering tools thay vì đoán.

---

## 18. `shadowPath` có thể cải thiện performance của shadow như thế nào?

**Ý chính:** `Explicit geometry`.

**Ý diễn giải:**
Khi biết trước hình dạng shadow, cung cấp `shadowPath` để Core Animation không phải suy ra geometry từ layer mỗi lần render.

**Ví dụ:**

```swift
let path = UIBezierPath(
    roundedRect: view.bounds,
    cornerRadius: 12
)

view.layer.shadowPath =
    path.cgPath
```

# VI. STARTUP TIME

## 19. App launch chậm. Bạn sẽ chia vấn đề thành những phần nào?

**Ý chính:** `Pre-main + post-main + first frame`.

**Ý diễn giải:**
Không nên chỉ đo `application(_:didFinishLaunching...)`. Cần phân biệt thời gian trước main, initialization sau main, dependency construction, database migration, synchronous disk I/O và thời điểm first frame.

**Ví dụ:**

```text
App Launch
   ↓
Pre-main
   ↓
main()
   ↓
App initialization
   ↓
Dependency creation
   ↓
Database setup
   ↓
First screen
   ↓
First frame
```

Một app có thể chậm do work xảy ra trước khi UI xuất hiện dù business code trong ViewController rất nhỏ.

---

## 20. Bạn được giao giảm startup time 40%. Bạn sẽ làm như thế nào?

**Ý chính:** `Profile → rank cost → defer/lazy → remove unnecessary work → remeasure`.

**Ý diễn giải:**
Trước tiên đo launch thực tế. Xác định phần nào chiếm thời gian lớn nhất. Sau đó trì hoãn những service không cần để hiển thị first screen, giảm synchronous disk/network work, tránh khởi tạo mọi dependency ngay launch và đo lại.

**Ví dụ:**

```text
❌ Startup

App launch
   ↓
Create Analytics
   ↓
Create Database
   ↓
Create WebSocket
   ↓
Load User
   ↓
Load Recommendations
   ↓
Create Image Cache
   ↓
Show UI
```

Có thể chuyển thành:

```text
✅ Startup

App launch
   ↓
Create minimal dependencies
   ↓
Show UI
   ↓
Lazy initialize
   ├── Analytics
   ├── Recommendations
   └── WebSocket
```

# VII. APP SIZE

## 21. App size tăng mạnh sau khi thêm vài package. Bạn sẽ xác định nguyên nhân thế nào?

**Ý chính:** `Dependency audit + binary/resources analysis`.

**Ý diễn giải:**
Không chỉ nhìn số lượng package. Một package có thể kéo rất nhiều binary, resources, architecture slices hoặc generated code. Cần phân tích binary size và resource contribution.

**Ví dụ:**

```text
App Size
 ├── App Binary
 ├── Frameworks
 ├── Assets
 ├── Localization
 ├── Fonts
 └── Other Resources
```

---

## 22. Một dependency chỉ dùng một tính năng nhỏ nhưng làm app tăng nhiều MB. Bạn sẽ cân nhắc gì?

**Ý chính:** `Dependency cost vs feature value`.

**Ý diễn giải:**
Xem có thể dùng system API thay thế, import module nhỏ hơn, bỏ dependency hoặc tách implementation nội bộ hay không. Không nên giữ một dependency lớn chỉ vì một utility nhỏ nếu size impact đáng kể.

**Ví dụ:**

```text
Package A
100 KB functionality
+
8 MB transitive dependency
```

Có thể không đáng.

# VIII. BATTERY / BACKGROUND

## 23. Một app không render UI nhiều nhưng pin tụt nhanh. Bạn sẽ điều tra những gì?

**Ý chính:** `CPU + networking + location + timers + background work`.

**Ý diễn giải:**
Battery drain không chỉ đến từ UI. Polling liên tục, location, WebSocket, background activity và wakeups có thể làm app tiêu pin đáng kể.

**Ví dụ:**

```text
Battery drain
    ↓
CPU wakeups?
    ↓
Network polling?
    ↓
Location?
    ↓
Timer?
    ↓
Background task?
    ↓
WebSocket?
```

---

## 24. Polling server mỗi 2 giây có vấn đề gì ngoài việc tốn network?

**Ý chính:** `Wakeups + radio power + CPU + battery`.

**Ý diễn giải:**
Mỗi request có thể làm device wake up, network radio hoạt động và CPU xử lý response. Tần suất cao có thể tốn pin rất nhiều dù payload nhỏ.

**Ví dụ:**

```text
Every 2 seconds
      ↓
Request
      ↓
Wake CPU
      ↓
Wake network
      ↓
Parse
      ↓
Sleep
      ↓
Repeat
```

Có thể thay bằng push/WebSocket/background scheduling tùy use case.

# SENIOR SCENARIO: COLLECTIONVIEW 1.000 ẢNH

## 25. Interviewer đưa tình huống:

> “CollectionView có 1.000 ảnh, scroll bị giật. Bạn debug từ đâu?”

**Ý chính:** Không tối ưu ngay. `Profile the entire rendering/data pipeline`.

**Ý diễn giải:**
Câu trả lời Senior nên đi theo pipeline:

```text
                    CollectionView
                          ↓
                    Cell Creation
                          ↓
                    Cell Reuse
                          ↓
                  Image Request
                          ↓
                       Cache
                          ↓
                      Decode
                          ↓
                     Downsample
                          ↓
                       Layout
                          ↓
                      Rendering
                          ↓
                         GPU
```

Phân tích từng tầng:

```text
CPU?
 ↓
Time Profiler

Main Thread?
 ↓
Frame budget / call stack

Memory?
 ↓
Allocations / Memory Graph

Image decode?
 ↓
Inspect image pipeline

Cache?
 ↓
Hit/miss ratio

Network?
 ↓
Request latency / concurrency

Reuse?
 ↓
prepareForReuse / stale task

Layout?
 ↓
Auto Layout / self-sizing

Rendering?
 ↓
Core Animation / GPU
```

**Ví dụ:**

```swift
final class ImageCell: UICollectionViewCell {

    private var imageTask:
        Task<Void, Never>?

    override func prepareForReuse() {
        super.prepareForReuse()

        imageTask?.cancel()
        imageTask = nil

        imageView?.image = placeholder
    }

    func configure(
        with url: URL
    ) {
        imageTask?.cancel()

        imageTask = Task {

            let image =
                try await imageLoader.load(url)

            guard !Task.isCancelled else {
                return
            }

            imageView?.image = image
        }
    }
}
```

Nhưng đây mới chỉ là một phần. Nếu image loader decode ảnh 4000×3000 trên main thread thì vẫn lag. Cần tiếp tục kiểm tra:

```text
Request
 ↓
Cache
 ↓
Decode
 ↓
Downsample
 ↓
Main Thread
 ↓
Render
```
