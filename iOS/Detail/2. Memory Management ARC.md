# CHỦ ĐỀ 2: MEMORY MANAGEMENT — ARC (25 CÂU)

## CẤP ĐỘ 1: JUNIOR (CƠ BẢN) - 7 Câu

### 1. Cơ chế tự động quản lý bộ nhớ của Swift hoạt động dựa trên nguyên tắc đếm nào?

**Ý chính:** ARC (Automatic Reference Counting) - Đếm số lượng tham chiếu tự động.
**Diễn giải:** ARC tự động theo dõi số lượng tham chiếu (Reference Count - RC) đến một đối tượng (class/closure) trên Heap. Mỗi khi có một biến trỏ tới, RC tăng 1. Khi biến đó hủy hoặc trỏ đi nơi khác, RC giảm 1. Khi RC = 0, bộ nhớ của đối tượng được giải phóng.
**Ví dụ:**

```swift
var obj1: MyClass? = MyClass() // RC = 1
var obj2 = obj1 // RC = 2
obj1 = nil // RC = 1
obj2 = nil // RC = 0 -> Giải phóng (Deallocated)

```

### 2. Loại tham chiếu mặc định được hệ thống sử dụng khi bạn gán một đối tượng vào một biến là gì?

**Ý chính:** Tham chiếu mạnh (Strong Reference).
**Diễn giải:** Bất cứ khi nào bạn khởi tạo một class hoặc gán nó cho một thuộc tính/biến, hệ thống mặc định tạo một tham chiếu mạnh. Tham chiếu này giữ cho đối tượng không bị hủy chừng nào biến đó còn tồn tại.
**Ví dụ:**

```swift
class User { }
var user = User() // Đây ngầm định là Strong Reference

```

### 3. Từ khóa nào giúp giữ kết nối đến đối tượng mà không làm tăng biến đếm bộ nhớ, và tự động biến thành rỗng khi đối tượng bị hủy?

**Ý chính:** Tham chiếu yếu (`weak`).
**Diễn giải:** `weak` không làm tăng Reference Count. Nó cho phép ARC giải phóng đối tượng nếu không còn Strong Reference nào khác trỏ tới. Khi đối tượng bị hủy, biến `weak` tự động được ARC gán bằng `nil`.
**Ví dụ:**

```swift
class Node {
    weak var next: Node? // Sẽ thành nil khi đối tượng Node kia bị hủy
}

```

### 4. Tại sao một biến được khai báo là tham chiếu yếu bắt buộc phải là biến có thể thay đổi và có kiểu dữ liệu tùy chọn?

**Ý chính:** Bắt buộc là `var` và kiểu `Optional` (`?`).
**Diễn giải:** Vì ARC sẽ tự động gán giá trị `nil` cho biến đó khi đối tượng bị giải phóng. Hằng số (`let`) không thể thay đổi giá trị sau khởi tạo, và kiểu Non-optional không thể chứa giá trị `nil`.
**Ví dụ:**

```swift
// let weakObj: MyClass? = MyClass() // Lỗi Compile
weak var validWeakObj: MyClass? = MyClass() // Hợp lệ

```

### 5. Sự khác biệt về nơi cấp phát ô nhớ mặc định giữa hai cấu trúc Struct và Class là gì?

**Ý chính:** `Struct` (Value Type) cấp phát trên Stack; `Class` (Reference Type) cấp phát trên Heap.
**Diễn giải:** Stack quản lý bộ nhớ tĩnh, tự động vào/ra theo scope của hàm (LIFO), tốc độ rất nhanh. Heap quản lý bộ nhớ động, do ARC kiểm soát, linh hoạt hơn nhưng tốn chi phí quản lý vùng nhớ và con trỏ.
**Ví dụ:**

```swift
struct Point { var x: Int } // Lưu trên Stack
class User { var name: String = "" } // Lưu trên Heap

```

### 6. Hiện tượng gì xảy ra khi hai đối tượng class tham chiếu trực tiếp lẫn nhau bằng tham chiếu mặc định?

**Ý chính:** Retain Cycle (Vòng lặp tham chiếu) dẫn đến Memory Leak (Rò rỉ bộ nhớ).
**Diễn giải:** Khi A giữ mạnh B, và B giữ mạnh A, Reference Count của cả hai không bao giờ có thể giảm xuống 0. Dù ứng dụng không còn dùng đến A và B, vùng nhớ của chúng vẫn bị giam giữ vĩnh viễn.
**Ví dụ:**

```swift
class A { var b: B? }
class B { var a: A? }
let objA = A()
let objB = B()
objA.b = objB
objB.a = objA // Gây ra Retain Cycle

```

### 7. Hàm đặc biệt nào được hệ thống tự động gọi ngay trước khi một đối tượng bị quét sạch hoàn toàn khỏi bộ nhớ?

**Ý chính:** `deinit` (Deinitializer).
**Diễn giải:** Đây là nơi lý tưởng để thực hiện các thao tác dọn dẹp như gỡ bỏ NotificationCenter observer, đóng file, hay ngắt kết nối mạng trước khi object biến mất vĩnh viễn.
**Ví dụ:**

```swift
class Session {
    deinit {
        print("Session đã bị giải phóng bộ nhớ")
    }
}

```

## CẤP ĐỘ 2: MIDDLE (TRUNG CẤP) - 8 Câu

### 8. Điểm khác biệt lớn nhất về mặt tính năng và rủi ro giữa hai từ khóa bẻ gãy vòng lặp tham chiếu (`weak` và `unowned`) là gì?

**Ý chính:** `weak` an toàn, có thể thành `nil` (Optional). `unowned` không phải Optional, gây crash nếu đối tượng đã bị hủy.
**Diễn giải:** Dùng `weak` khi đối tượng trỏ tới có thể biến mất trước. Dùng `unowned` khi chắc chắn vòng đời của đối tượng trỏ tới dài hơn hoặc bằng vòng đời của đối tượng hiện tại. Truy cập `unowned` đã deallocate sẽ gây lỗi "Fatal error: Attempted to read an unowned reference".
**Ví dụ:**

```swift
class Customer { var card: CreditCard? }
class CreditCard {
    unowned let customer: Customer // Thẻ luôn phải có chủ, nếu gọi card.customer khi customer đã chết -> Crash
    init(customer: Customer) { self.customer = customer }
}

```

### 9. Tại sao việc sử dụng khối lệnh đóng gói (closure) trong một lớp lại là nguyên nhân phổ biến nhất gây rò rỉ bộ nhớ?

**Ý chính:** Closure ngầm định bắt giữ mạnh (strong capture) các biến ngoại cảnh, bao gồm cả `self`.
**Diễn giải:** Closure là một Reference Type. Khi bạn lưu một closure vào một thuộc tính của class, và bên trong closure đó bạn lại gọi đến `self.property`, class đang giữ closure và closure lại giữ class. Kết quả là tạo ra Retain Cycle.
**Ví dụ:**

```swift
class Handler {
    var onAction: (() -> Void)?
    func setup() {
        onAction = { 
            print(self) // Closure capture strong 'self' -> Retain Cycle
        }
    }
}

```

### 10. Cú pháp nào được đặt ở đầu khối lệnh để thay đổi quyền sở hữu mặc định của các biến môi trường mà khối lệnh đó truy cập?

**Ý chính:** Capture List (`[weak self]` hoặc `[unowned self]`).
**Diễn giải:** Khai báo một mảng các biến cần thay đổi tính chất tham chiếu (từ strong sang weak/unowned) ngay trước khai báo tham số của closure. Giúp bẻ gãy vòng lặp tham chiếu.
**Ví dụ:**

```swift
var onUpdate: (() -> Void)?
onUpdate = { [weak self] in
    self?.doSomething() // self giờ là Optional
}

```

### 11. Trong mô hình thiết kế Ủy quyền (Delegate), tại sao thuộc tính delegate bắt buộc phải được thiết lập là tham chiếu yếu?

**Ý chính:** Để tránh Retain Cycle giữa Class cha và Class con (Delegator và Delegate).
**Diễn giải:** Thông thường, Class A (như ViewController) sẽ tạo ra Class B (như TableView) và gán `B.delegate = A`. A đang giữ mạnh B. Nếu `delegate` trong B cũng là tham chiếu mạnh, B sẽ giữ ngược lại A, không bên nào có thể deinit.
**Ví dụ:**

```swift
protocol TaskDelegate: AnyObject {}
class Task {
    weak var delegate: TaskDelegate? // Phải là weak
}

```

### 12. Cơ chế tối ưu vùng nhớ nào giúp Swift không bị hao tổn tài nguyên khi sao chép các cấu trúc dữ liệu khổng lồ (như Array, Dictionary)?

**Ý chính:** Copy-on-Write (CoW).
**Diễn giải:** Khi bạn gán mảng A cho mảng B, Swift không copy toàn bộ dữ liệu trên bộ nhớ ngay lập tức. Cả A và B cùng trỏ chung về một vùng nhớ bộ đệm. Việc copy thực sự chỉ xảy ra khi B (hoặc A) bắt đầu thực hiện thao tác **ghi** (thêm/sửa/xóa).
**Ví dụ:**

```swift
var array1 = [1, 2, 3, 4] // Dữ liệu 10MB
var array2 = array1 // Vẫn chung ô nhớ, tốn 0MB copy
array2.append(5) // Lúc này vùng nhớ mới thực sự bị nhân bản độc lập

```

### 13. Khái niệm Vòng đời đối tượng (Object Lifetime) trên Heap kết thúc chính xác khi điều kiện nào xảy ra?

**Ý chính:** Khi Strong Reference Count giảm xuống đúng bằng 0.
**Diễn giải:** ARC chỉ quan tâm đến Strong RC. Khi không còn bất cứ strong reference nào trỏ tới object, vùng nhớ chứa object sẽ lập tức bắt đầu quy trình hủy: gọi `deinit`, giải phóng các tham chiếu nó đang giữ, và trả lại vùng nhớ.
**Ví dụ:**

```swift
var a: ClassA? = ClassA() // Strong RC = 1
var b = a                 // Strong RC = 2
a = nil                   // Strong RC = 1 (Chưa deinit)
b = nil                   // Strong RC = 0 -> deinit được gọi

```

### 14. Từ khóa nào cảnh báo cho hệ thống bộ nhớ rằng một khối lệnh có khả năng sống sót lâu hơn cả hàm gọi nó?

**Ý chính:** `@escaping`.
**Diễn giải:** Mặc định, closure truyền vào hàm là non-escaping (chạy xong hàm là hủy, ARC không cần lưu trên Heap). Nếu closure được lưu vào một biến bên ngoài hàm hoặc chạy bất đồng bộ, nó phải là `@escaping` để báo compiler đẩy nó lên Heap và theo dõi ARC khắt khe.
**Ví dụ:**

```swift
func fetchData(completion: @escaping () -> Void) {
    DispatchQueue.main.asyncAfter(deadline: .now() + 1) {
        completion() // Closure thực thi sau khi fetchData đã return
    }
}

```

### 15. Điều gì xảy ra khi bạn khai báo Capture List gán giá trị mới ngay lúc định nghĩa closure (ví dụ `[view = self.button]`)?

**Ý chính:** Biến đó được đánh giá (evaluated) và chốt giá trị ngay tại thời điểm closure được tạo ra, không phải lúc closure thực thi.
**Diễn giải:** Nó tạo ra một hằng số nội bộ bên trong closure lưu giữ mạnh (strong) đối tượng được gán tại đúng khoảnh khắc đó, kể cả khi tham chiếu gốc bên ngoài sau này bị thay đổi.
**Ví dụ:**

```swift
var x = 10
let closure = { [val = x] in print(val) }
x = 20
closure() // Vẫn in ra 10, vì val đã chốt lúc khởi tạo closure

```

### 16. (Tình huống) Một closure giữ ViewModel, ViewModel lại lưu closure đó làm thuộc tính. Vì sao object không được giải phóng và bạn xử lý triệt để như thế nào?

**Ý chính:** Tạo ra Retain Cycle do ViewModel giữ tham chiếu mạnh tới closure (lưu ở property), và closure giữ tham chiếu mạnh tới `self` (ViewModel). Xử lý bằng `[weak self]`.
**Diễn giải:** Closure là Reference Type. Khi gán `self.onFetch = { self.update() }`, closure tạo một strong reference ngược lại `self`. Để phá vỡ, ta phải yêu cầu closure không tăng Reference Count của `self` bằng Capture List. Đồng thời phải kiểm tra `self` còn sống hay không trước khi gọi lệnh.
**Ví dụ:**

```swift
class ViewModel {
    var onComplete: (() -> Void)?
    func load() {
        // LỖI: onComplete = { self.didLoad() }
        // FIX:
        onComplete = { [weak self] in
            guard let self = self else { return }
            self.didLoad()
        }
    }
    func didLoad() {}
}

```

### 18. Cơ chế nội tại nào dưới nền tảng Swift cho phép biến `weak` tự động chuyển thành `nil` một cách an toàn mà không gây xung đột đa luồng?

**Ý chính:** Side Tables (Bảng phụ).
**Diễn giải:** Swift quản lý Reference Count nội bộ (inline) trên object. Nhưng khi có biến `weak` trỏ tới, hệ thống tách phần quản lý bộ đếm này ra một cấu trúc bộ nhớ phụ gọi là Side Table. Khi object `deinit`, vùng nhớ data bị xóa, nhưng Side Table vẫn tồn tại để điều phối chuyển các pointer weak đang trỏ tới nó thành `nil`, đảm bảo thread-safe.
**Ví dụ:**
*(Không code, hỏi về System Internals).* Strong RC = 0 -> Object deinit -> Weak references clear via Side Table -> Side Table deallocated.

### 19. Việc sử dụng tham chiếu không sở hữu (`unowned`) ảnh hưởng thế nào đến bộ nhớ của một đối tượng sau khi nó đã chạy hàm `deinit`?

**Ý chính:** Vùng nhớ của đối tượng chưa được trả lại hoàn toàn cho OS (Unowned Zombie Object) cho đến khi Unowned Reference Count giảm về 0.
**Diễn giải:** Object có 3 loại đếm: Strong RC, Weak RC, Unowned RC. Khi Strong RC = 0, object gọi `deinit` và dọn dẹp các property. Tuy nhiên, nếu Unowned RC > 0, vùng nhớ core của object vẫn bị giữ lại dưới dạng trạng thái "Unallocated/Zombie". Nếu code cố truy cập vào, nó kiểm tra Unowned RC và throw "Fatal Error" một cách an toàn thay vì ghi đè memory bậy bạ.

### 20. Khái niệm "Value Semantics" (Ngữ nghĩa giá trị) giúp tránh rò rỉ bộ nhớ như thế nào, và có ngoại lệ nào khiến Struct vẫn bị dính Retain Cycle không?

**Ý chính:** Struct/Enum copy dữ liệu độc lập nên không có Reference Count -> không có Retain Cycle tự thân. Ngoại lệ: Khi Struct chứa thuộc tính là Class/Closure bị retain cycle.
**Diễn giải:** Bản thân Value Type không gây leak bộ nhớ. Tuy nhiên, nếu một Struct lưu một closure, và closure đó lại giữ một tham chiếu mạnh tới class cha đang giữ struct, chuỗi Retain Cycle vẫn hình thành thông qua struct đó.
**Ví dụ:**

```swift
struct Task { var execute: () -> Void }
class Manager {
    var task: Task?
    func setup() {
        task = Task(execute: { print(self) }) // Vẫn tạo Retain Cycle (Manager -> Task(Struct) -> Closure -> Manager)
    }
}

```

### 21. Ngoài việc xem cấu trúc tham chiếu, công cụ cấu hình nào trong Xcode dùng để theo dõi sự tăng giảm dung lượng RAM theo thời gian thực và bắt các rò rỉ âm thầm?

**Ý chính:** Instruments (Allocations và Leaks template).
**Diễn giải:**

* **Allocations:** Giúp theo dõi tổng lượng Heap bị chiếm dụng, xem đường cong bộ nhớ (Memory Growth) qua các thế hệ (Generations) để bắt tình trạng object sinh ra nhưng không chết đi sau mỗi lần lặp.
* **Leaks:** Tự động quét vùng nhớ Heap định kỳ, phát hiện các chunk bộ nhớ không còn bất kỳ đường dẫn nào từ Root trỏ tới (Unreachable memory) nhưng chưa được giải phóng.

### 22. Khi một closure thay đổi giá trị của một biến Value Type (như Int) từ phạm vi bên ngoài, cơ chế bộ nhớ của biến Int đó bị biến đổi như thế nào?

**Ý chính:** Trình biên dịch bọc (Box) biến Stack đó đưa lên lưu trữ trên Heap.
**Diễn giải:** Theo nguyên tắc, `Int` lưu trên Stack và biến mất khi ra khỏi block. Nhưng do closure (sống trên Heap) cần thay đổi biến này bất cứ lúc nào trong tương lai, Swift âm thầm nâng cấp (promoted) biến `Int` đó vào một ô nhớ Heap ẩn. Cả closure và hàm bên ngoài giờ cùng trỏ vào ô nhớ Heap đó qua tham chiếu.
**Ví dụ:**

```swift
func makeCounter() -> () -> Int {
    var count = 0 // Bị đẩy lên Heap
    return {
        count += 1
        return count
    }
}

```

### 23. Từ khóa bọc biểu thức thành closure (`@autoclosure`) có nguy cơ gây rò rỉ bộ nhớ không và vì sao?

**Ý chính:** Mặc định KHÔNG gây rò rỉ vì nó ngầm định là `non-escaping`.
**Diễn giải:** `@autoclosure` bắt buộc phải chạy và kết thúc ngay bên trong hàm gọi nó. Trình biên dịch cấm việc lưu trữ nó ra biến bên ngoài. Do đó nó không bao giờ sống lâu hơn hàm, không gây Retain Cycle. Để nó có nguy cơ, phải chủ động khai báo `@autoclosure @escaping`.
**Ví dụ:**

```swift
// An toàn tuyệt đối:
func log(_ msg: @autoclosure () -> String) { print(msg()) }

```

### 24. Trong Swift, điều gì xảy ra nếu ta dùng `[unowned self]` nhưng đối tượng `self` lại được khởi tạo và quản lý bộ nhớ hoàn toàn trong Objective-C (như một số đối tượng UIKit/Foundation cũ)?

**Ý chính:** Hành vi trở thành `unowned(unsafe)` (Unmanaged pointer), truy cập vào có thể gây rác bộ nhớ (Memory Corruption) thay vì crash an toàn (Fatal Error).
**Diễn giải:** Swift xử lý `unowned` an toàn bằng cách kiểm tra Unowned RC trước. Nhưng các class thuần Objective-C (chưa áp dụng chuẩn ARC mới) không hỗ trợ cơ chế này. Con trỏ trở thành con trỏ "lơ lửng" (Dangling pointer), truy cập vào sẽ trỏ trúng vùng nhớ đã bị đối tượng khác chiếm dụng, gây ra các lỗi undefine behaviors cực khó fix.

### 25. Kỹ thuật tiêu chuẩn để tự động hóa việc phát hiện Memory Leak của một ViewController hoặc ViewModel ngay trong môi trường Unit Test là gì?

**Ý chính:** Gán đối tượng vào một biến `weak` và dùng `addTeardownBlock` để `XCTAssertNil` nó sau khi scope của Test Method kết thúc.
**Diễn giải:** Bằng cách này, mỗi khi một bài test chạy xong, ta đảm bảo rằng đối tượng đã được giải phóng. Nếu `weak var` không bị gán `nil`, đồng nghĩa đối tượng đang bị dính Retain Cycle ở đâu đó trong logic code.
**Ví dụ:**

```swift
extension XCTestCase {
    func trackForMemoryLeaks(_ instance: AnyObject, file: StaticString = #file, line: UInt = #line) {
        weak var weakInstance = instance
        addTeardownBlock { // Chạy ngay khi test hoàn tất
            XCTAssertNil(weakInstance, "Memory leak detected", file: file, line: line)
        }
    }
}

```
