# CHỦ ĐỀ 7: DEPENDENCY INJECTION ⭐⭐⭐⭐

Dependency Injection không chỉ là:

> “Truyền dependency qua constructor.”

Ở level Senior cần hiểu:

```text
Ai tạo dependency?
        ↓
Ai sở hữu dependency?
        ↓
Dependency sống bao lâu?
        ↓
Dependency được truyền qua boundary nào?
        ↓
Production và Test thay dependency thế nào?
```

Một flow phổ biến:

```text
Composition Root
      ↓
Dependency Container
      ↓
Factory
      ↓
ViewModel / Service
      ↓
Protocol
      ↓
Concrete Implementation
```

---

# I. CORE CONCEPTS

## 1. Một class cần API để hoạt động. Vì sao truyền API từ bên ngoài thường tốt hơn tự tạo API bên trong?

**Ý chính:** `Dependency Injection` + explicit dependency + loose coupling.

**Ý diễn giải:**
Class không nên vừa sử dụng vừa quyết định implementation của dependency nếu dependency đó cần thay đổi hoặc test. Inject từ bên ngoài giúp dependency rõ ràng và dễ thay thế.

**Ví dụ:**

```swift
protocol API {
    func fetchUser() async throws -> User
}

final class UserViewModel {

    private let api: API

    init(api: API) {
        self.api = api
    }

    func load() async throws {
        let user = try await api.fetchUser()
        print(user)
    }
}
```

Thay vì:

```swift
final class UserViewModel {

    private let api = RealAPI()
}
```

---

## 2. Tại sao Constructor Injection thường được ưu tiên cho dependency bắt buộc?

**Ý chính:** `Explicit + required + valid object`.

**Ý diễn giải:**
Object được tạo ra là đã có đủ dependency cần thiết. Không tồn tại trạng thái “object được tạo nhưng chưa setup dependency”.

**Ví dụ:**

```swift
final class UserViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

Không cần:

```swift
final class UserViewModel {

    var repository: UserRepository!

}
```

vì object có thể bị dùng trước khi repository được inject.

---

## 3. Property Injection phù hợp với dependency nào hơn Constructor Injection?

**Ý chính:** Dependency `optional`, framework-managed hoặc được cấu hình sau initialization.

**Ý diễn giải:**
Property Injection phù hợp khi dependency không bắt buộc ngay lúc tạo object hoặc lifecycle bị framework kiểm soát. Nhược điểm là object có thể tồn tại ở trạng thái chưa hoàn chỉnh.

**Ví dụ:**

```swift
final class AnalyticsViewController: UIViewController {

    var analytics: Analytics?

    func trackScreen() {
        analytics?.track("profile")
    }
}
```

---

## 4. Nếu một dependency bắt buộc nhưng bạn dùng Property Injection, rủi ro gì?

**Ý chính:** `Invalid state + runtime failure`.

**Ý diễn giải:**
Compiler không buộc caller phải inject property. Object có thể được tạo mà thiếu dependency.

**Ví dụ:**

```swift
final class ViewModel {

    var repository: UserRepository!

    func load() async {
        await repository.load()
    }
}

let vm = ViewModel()

// Có thể crash vì repository chưa được inject.
```

Constructor Injection giải quyết:

```swift
let vm = ViewModel(
    repository: repository
)
```

# II. PROTOCOL-BASED DI

## 5. Vì sao Protocol thường được dùng làm dependency boundary?

**Ý chính:** `Abstraction + replaceable implementation`.

**Ý diễn giải:**
Consumer chỉ phụ thuộc vào behavior cần thiết, không phụ thuộc concrete implementation. Production dùng implementation thật, test dùng fake/mock.

**Ví dụ:**

```swift
protocol UserRepository {
    func loadUser() async throws -> User
}

final class UserViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

Production:

```swift
struct RealUserRepository: UserRepository {

    func loadUser() async throws -> User {
        // API
    }
}
```

Test:

```swift
struct MockUserRepository: UserRepository {

    func loadUser() async throws -> User {
        User(id: 1, name: "Test")
    }
}
```

---

## 6. Có nên tạo Protocol cho tất cả class để “dễ test” không?

**Ý chính:** Không. `Abstraction should have value`.

**Ý diễn giải:**
Protocol chỉ đáng tạo khi cần thay implementation, tạo boundary, giảm coupling hoặc hỗ trợ testing. Tạo protocol cho mọi class làm code nhiều abstraction nhưng không có lợi ích thật.

**Ví dụ:**

```swift
protocol UserNameFormatter {
    func format(_ name: String) -> String
}

final class UserNameFormatterImpl: UserNameFormatter {
    func format(_ name: String) -> String {
        name.uppercased()
    }
}
```

Nếu class cực kỳ đơn giản, chỉ có một implementation và không có boundary cần thiết, protocol có thể là unnecessary.

# III. FACTORY

## 7. Một ViewController cần 7 dependency và việc tạo nó xuất hiện ở 10 nơi. Bạn sẽ giải quyết thế nào?

**Ý chính:** `Factory` + centralized composition.

**Ý diễn giải:**
Không nên lặp logic construction ở 10 nơi. Factory gom cách tạo feature và giúp thay đổi dependency chain tại một điểm.

**Ví dụ:**

```swift
final class ProfileFactory {

    let container: AppContainer

    init(container: AppContainer) {
        self.container = container
    }

    func makeViewController()
        -> UIViewController {

        let viewModel = ProfileViewModel(
            repository: container.userRepository,
            analytics: container.analytics
        )

        return ProfileViewController(
            viewModel: viewModel
        )
    }
}
```

Flow:

```text
Factory
   ↓
ViewModel
   ↓
Repository
   ↓
API
```

---

## 8. Factory khác Dependency Container ở trách nhiệm nào?

**Ý chính:** `Factory = tạo object`; `Container = quản lý dependency graph`.

**Ý diễn giải:**
Factory thường biết cách tạo một feature cụ thể. Container giữ các shared dependency và lifecycle như API client, database, analytics.

**Ví dụ:**

```swift
final class AppContainer {

    lazy var api: API = RealAPI()

    lazy var database: Database =
        RealDatabase()

    lazy var userRepository:
        UserRepository = RealUserRepository(
            api: api,
            database: database
        )
}
```

Factory:

```swift
final class ProfileFactory {

    let container: AppContainer

    func makeViewModel()
        -> ProfileViewModel {

        ProfileViewModel(
            repository: container.userRepository
        )
    }
}
```

# IV. DEPENDENCY CONTAINER

## 9. Dependency Container nên được đặt ở đâu trong application architecture?

**Ý chính:** `Composition Root`.

**Ý diễn giải:**
Container nên ở nơi app biết concrete implementation nào được dùng. Business code không nên biết container tồn tại.

**Ví dụ:**

```swift
@main
struct MyApp {

    let container = AppContainer()

    var body: some Scene {
        WindowGroup {
            RootView(
                viewModel:
                    container.makeRootViewModel()
            )
        }
    }
}
```

---

## 10. Một Dependency Container có nên được truyền xuống toàn bộ ViewModel và Service không?

**Ý chính:** Không. `Inject dependencies, not container`.

**Ý diễn giải:**
Nếu ViewModel nhận cả container, nó có thể lấy bất kỳ service nào. Dependency lại trở thành hidden. Tốt hơn là container resolve ở composition root rồi inject dependency cụ thể.

**Ví dụ:**

Sai:

```swift
final class ViewModel {

    let container: AppContainer

    init(container: AppContainer) {
        self.container = container
    }

    func load() async {
        await container.api.fetch()
        await container.analytics.track()
        await container.database.save()
    }
}
```

Tốt hơn:

```swift
final class ViewModel {

    private let api: API
    private let analytics: Analytics

    init(
        api: API,
        analytics: Analytics
    ) {
        self.api = api
        self.analytics = analytics
    }
}
```

# V. SERVICE LOCATOR

## 11. Vì sao Service Locator dễ tạo hidden dependency?

**Ý chính:** Dependency không xuất hiện trong `initializer/API`, mà được lấy ngầm từ global/container.

**Ý diễn giải:**
Nhìn vào class bạn không biết nó phụ thuộc gì. Muốn hiểu lifecycle hoặc test class phải tìm các lần gọi `shared`, `resolve` hoặc global container.

**Ví dụ:**

```swift
final class ProfileViewModel {

    func load() async {

        let api =
            AppContainer.shared.api

        let analytics =
            AppContainer.shared.analytics

        let user =
            await api.fetchUser()

        await analytics.track("loaded")

        print(user)
    }
}
```

Nhìn initializer:

```swift
let vm = ProfileViewModel()
```

không hề biết ViewModel cần:

```text
API
Analytics
```

Đây chính là **hidden dependency**.

---

## 12. Service Locator có ưu điểm gì khiến nó vẫn xuất hiện trong production code?

**Ý chính:** `Convenience + centralized resolution + legacy integration`.

**Ý diễn giải:**
Service Locator dễ dùng khi có nhiều dependency hoặc codebase cũ. Nó cũng có thể giảm boilerplate ở một số infrastructure layer. Vấn đề là không nên để business logic truy cập locator trực tiếp khắp nơi.

**Ví dụ:**

```swift
let service =
    ServiceLocator.shared.resolve(
        UserService.self
    )
```

Một cách dùng ít gây coupling hơn là resolve ở composition root:

```swift
let service =
    ServiceLocator.shared.resolve(
        UserService.self
    )

let vm = ViewModel(
    service: service
)
```

# VI. ENVIRONMENT / SWIFTUI DI

## 13. Trong SwiftUI, khi nhiều màn hình cùng cần một dependency như session hoặc app configuration, bạn có thể truyền dependency theo hierarchy như thế nào?

**Ý chính:** `Environment`.

**Ý diễn giải:**
Environment cho phép đưa dependency xuống view hierarchy mà không phải truyền qua từng intermediate view. Nó phù hợp dependency có phạm vi rõ trong UI tree.

**Ví dụ:**

```swift
struct AppSessionKey:
    EnvironmentKey {

    static let defaultValue =
        AppSession()
}

extension EnvironmentValues {

    var appSession: AppSession {
        get {
            self[
                AppSessionKey.self
            ]
        }

        set {
            self[
                AppSessionKey.self
            ] = newValue
        }
    }
}
```

Inject:

```swift
RootView()
    .environment(
        \.appSession,
        session
    )
```

Read:

```swift
struct ProfileView: View {

    @Environment(
        \.appSession
    )
    private var session

    var body: some View {
        Text(session.userName)
    }
}
```

---

## 14. Environment có phải luôn tốt hơn Constructor Injection trong SwiftUI không?

**Ý chính:** Không. `Explicit dependency` vs `contextual dependency`.

**Ý diễn giải:**
Constructor rõ dependency nhất và dễ test/reasoning. Environment tiện cho dependency xuyên nhiều tầng UI và có lifecycle theo hierarchy. Không nên dùng Environment để che giấu mọi dependency.

**Ví dụ:**

Constructor:

```swift
struct ProfileView: View {

    let viewModel: ProfileViewModel

    var body: some View {
        Text(viewModel.title)
    }
}
```

Environment:

```swift
struct ProfileView: View {

    @Environment(
        \.appSession
    )
    private var session

    var body: some View {
        Text(session.userName)
    }
}
```

Nếu View chỉ cần một dependency rõ ràng, constructor thường dễ reasoning hơn.

# VII. TESTING DEPENDENCY

## 15. Một ViewModel gọi API thật trong unit test làm test chậm và không deterministic. Bạn sẽ thay dependency thế nào?

**Ý chính:** `Dependency Injection + Test Double`.

**Ý diễn giải:**
Inject protocol rồi dùng fake/mock trong test. Test không cần server thật, network thật hoặc timing thật.

**Ví dụ:**

```swift
protocol API {
    func fetchUser()
        async throws -> User
}
```

Production:

```swift
struct RealAPI: API {

    func fetchUser()
        async throws -> User {
        // Real network
    }
}
```

Test:

```swift
struct FakeAPI: API {

    let user: User

    func fetchUser()
        async throws -> User {
        user
    }
}
```

Test ViewModel:

```swift
func testLoadUser() async throws {

    let api = FakeAPI(
        user: User(
            id: 1,
            name: "Alice"
        )
    )

    let vm = UserViewModel(
        api: api
    )

    try await vm.load()

    XCTAssertEqual(
        vm.user?.name,
        "Alice"
    )
}
```

# VIII. SENIOR SCENARIOS

## 16. Một class có 15 dependency truyền qua constructor. Bạn có coi đó là dấu hiệu tốt vì “dependency đều explicit” không?

**Ý chính:** Explicit dependency tốt, nhưng quá nhiều dependency có thể báo hiệu `God Object`.

**Ý diễn giải:**
Constructor injection làm dependency rõ ràng, nhưng nếu một class cần 15 service thì vấn đề có thể nằm ở responsibility. Nên xem có thể tách feature/service hoặc gom cohesive capability hay không.

**Ví dụ:**

```swift
final class CheckoutViewModel {

    init(
        api: API,
        database: Database,
        analytics: Analytics,
        logger: Logger,
        payment: Payment,
        cart: Cart,
        user: UserService,
        notification: NotificationService,
        image: ImageService,
        cache: Cache,
        router: Router,
        flags: FeatureFlags,
        clock: Clock,
        reachability: Reachability,
        tracker: Tracker
    ) {
        // 🚨 Quá nhiều responsibility
    }
}
```

Không phải cứ “constructor injection” là architecture tốt.

---

## 17. Một ViewModel vừa cần `UserRepository`, vừa cần `UserCache`, vừa cần `UserAPI`. Có thể architecture đang có vấn đề gì?

**Ý chính:** `Abstraction leakage`.

**Ý diễn giải:**
Nếu ViewModel phải biết repository, cache và API cùng lúc, data layer có thể chưa encapsulate đúng responsibility. Thường ViewModel chỉ cần abstraction ở mức business/data operation phù hợp.

**Ví dụ:**

Không lý tưởng:

```swift
final class UserViewModel {

    let repository: UserRepository
    let cache: UserCache
    let api: API
}
```

Có thể tốt hơn:

```swift
final class UserViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

Repository quyết định cache/API.

## 18. Bạn có một singleton `AppDependencies.shared` và toàn app lấy dependency từ đó. Bạn sẽ cải thiện dần mà không rewrite toàn bộ app thế nào?

**Ý chính:** `Incremental migration`.

**Ý diễn giải:**
Không cần thay toàn bộ một lần. Bắt đầu từ feature mới dùng constructor injection. Với code cũ, resolve dependency ở composition boundary rồi truyền xuống. Dần dần giảm direct access tới singleton.

**Ví dụ:**

```swift
// Legacy

final class OldViewModel {

    func load() async {
        await AppDependencies.shared.api.fetch()
    }
}
```

Chuyển dần:

```swift
final class NewViewModel {

    private let api: API

    init(api: API) {
        self.api = api
    }
}
```

Composition:

```swift
let vm = NewViewModel(
    api: AppDependencies.shared.api
)
```

Global vẫn tồn tại ở composition root, nhưng không còn leak vào business code.

## 19. Làm thế nào thiết kế Dependency Injection để production và test dùng cùng một architecture nhưng implementation khác nhau?

**Ý chính:** `Protocol + Composition Root`.

**Ý diễn giải:**
Business code chỉ biết protocol. Composition root của production tạo real implementation. Test composition root tạo fake implementation.

**Ví dụ:**

```swift
protocol ImageLoader {
    func load(
        _ url: URL
    ) async throws -> Data
}
```

Production:

```swift
let loader: ImageLoader =
    URLSessionImageLoader()
```

Test:

```swift
let loader: ImageLoader =
    FakeImageLoader()
```

Cùng ViewModel:

```swift
let vm = ImageViewModel(
    loader: loader
)
```

Không cần thay business code.

## 20. Nếu interviewer hỏi:

> **“Bạn thiết kế DI cho một app lớn thế nào?”**

**Ý chính:** `Composition Root + Constructor Injection + Protocol boundaries + Factory + scoped lifecycle + minimal container exposure`.

**Ý diễn giải:**

Một cấu trúc tốt có thể là:

```text
                         App
                          │
                  Composition Root
                          │
                  Dependency Container
                          │
             ┌────────────┼────────────┐
             ↓            ↓            ↓
           Factory      Factory      Factory
             ↓            ↓            ↓
          Profile      Search       Checkout
             ↓            ↓            ↓
         ViewModel    ViewModel    ViewModel
             ↓            ↓            ↓
          Protocol     Protocol     Protocol
             ↓            ↓            ↓
         Concrete     Concrete     Concrete
```

Nguyên tắc:

```text
Container
   ↓
Tạo dependency

Factory
   ↓
Tạo feature

Constructor
   ↓
Inject dependency

Protocol
   ↓
Boundary

Business code
   ↓
Không biết container

Test
   ↓
Fake / Mock implementation
```

Ví dụ:

```swift
final class AppContainer {

    lazy var api: API =
        URLSessionAPI()

    lazy var database: Database =
        CoreDataDatabase()

    lazy var userRepository:
        UserRepository =
            UserRepositoryImpl(
                api: api,
                database: database
            )

    func makeProfileViewModel()
        -> ProfileViewModel {

        ProfileViewModel(
            repository:
                userRepository
        )
    }
}
```

Feature chỉ biết:

```swift
let vm =
    container.makeProfileViewModel()
```

Và bản thân ViewModel chỉ biết:

```swift
final class ProfileViewModel {

    private let repository:
        UserRepository

    init(
        repository: UserRepository
    ) {
        self.repository = repository
    }
}
```

# CÁC CÂU BẪY SENIOR

## 21. “Constructor Injection luôn tốt hơn mọi loại DI.” Có đúng không?

**Ý chính:** Không tuyệt đối.

**Ý diễn giải:**
Constructor Injection tốt cho required dependency. Property Injection có thể phù hợp framework lifecycle. Environment phù hợp contextual UI dependency. Quan trọng là semantics của dependency.

---

## 22. “Dùng Protocol thì code đã loose coupling.” Có đúng không?

**Ý chính:** Không. `Protocol ≠ automatic decoupling`.

**Ý diễn giải:**
Nếu protocol quá lớn, implementation leak hoặc dependency graph vẫn coupling mạnh thì thêm protocol chỉ tạo abstraction giả.

**Ví dụ:**

```swift
protocol EverythingService {

    func api()
    func database()
    func analytics()
    func navigate()
    func track()
    func cache()
}
```

Đây vẫn là coupling lớn dù đã có protocol.

---

## 23. “Mock mọi dependency sẽ giúp test tốt hơn.” Có đúng không?

**Ý chính:** Không. `Mock only meaningful boundaries`.

**Ý diễn giải:**
Mock quá nhiều làm test gắn với implementation. Chỉ thay dependency khi cần kiểm soát side effect, I/O, time hoặc external system.

**Ví dụ:**

```text
Không nhất thiết mock:

PureFormatter
PureMapper
SimpleValueType
```

Nên mock/fake:

```text
Network
Database
Clock
File system
Authentication
External SDK
```

---

## 24. “Dependency Container giải quyết dependency graph.” Có đúng hoàn toàn không?

**Ý chính:** Container giúp compose graph; không tự làm graph tốt.

**Ý diễn giải:**
Bạn vẫn có thể tạo circular dependency, giant container hoặc lifetime sai ngay cả khi dùng DI container.

**Ví dụ:**

```text
A
↓
B
↓
C
↓
A

❌ Circular dependency
```

DI container chỉ expose vấn đề này; nó không tự thiết kế architecture đúng.

---

## 25. “Environment trong SwiftUI tốt hơn truyền dependency bằng initializer vì code ngắn hơn.” Có đúng không?

**Ý chính:** Không. `Explicitness vs convenience`.

**Ý diễn giải:**
Initializer làm dependency visible ngay tại API. Environment giảm boilerplate nhưng có thể tạo hidden dependency nếu lạm dụng.

**Ví dụ:**

```swift
// Explicit

ProfileView(
    repository: repository
)
```

so với:

```swift
ProfileView()
    .environment(
        \.repository,
        repository
    )
```

Code thứ hai ngắn hơn nhưng người đọc View không nhìn thấy dependency ngay tại initializer.

# DEPENDENCY INJECTION — SENIOR CHEAT SHEET

```text
Constructor Injection
→ Required dependency
→ Explicit
→ Dễ test
→ Preferred default

Property Injection
→ Optional/framework lifecycle dependency
→ Có risk invalid state

Protocol
→ Abstraction boundary
→ Replace implementation
→ Testability

Factory
→ Create feature/object
→ Hide construction complexity

Dependency Container
→ Compose dependency graph
→ Manage lifecycle/scope

Service Locator
→ Resolve dependency on demand
→ Convenient
→ Dễ hidden dependency

Environment
→ Contextual dependency trong SwiftUI
→ Truyền xuyên hierarchy
→ Có thể hidden dependency nếu lạm dụng

Composition Root
→ Nơi biết concrete implementation

Test
→ Fake/Mock dependency
→ Deterministic
```

Một câu trả lời tốt nhất về DI không phải:

> “Tôi dùng Constructor Injection vì nó dễ test.”

Mà là:

> **“Tôi muốn dependency explicit, ownership rõ và composition tập trung. Required dependencies được inject qua constructor; feature creation nằm ở factory/composition root; business code không truy cập container trực tiếp. Protocol chỉ được thêm tại những boundary có giá trị, còn SwiftUI Environment chỉ dùng cho contextual dependencies phù hợp.”**
