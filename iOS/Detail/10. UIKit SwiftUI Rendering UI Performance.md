# I. SWIFTUI — STATE / IDENTITY / DIFFING

## 1. Hai SwiftUI View có cùng giao diện nhưng framework vẫn có thể coi chúng là hai View khác nhau. Điều gì quyết định việc đó?

**Ý chính:** `View identity`.

**Ý diễn giải:**
SwiftUI không chỉ nhìn UI đang trông giống nhau. Identity cho framework biết view nào là “cùng một view” qua các lần cập nhật. Identity ảnh hưởng state retention, lifecycle và cách diffing được thực hiện.

**Ví dụ:**

```swift
struct Row: View {
    let title: String

    var body: some View {
        Text(title)
    }
}
```

Trong `ForEach`, identity nên ổn định:

```swift
ForEach(items, id: \.id) { item in
    Row(title: item.title)
}
```

---

## 2. Một row trong danh sách mất toàn bộ local state sau khi danh sách được cập nhật. Bạn nghi ngờ điều gì trước tiên?

**Ý chính:** `Identity changed`.

**Ý diễn giải:**
SwiftUI gắn local state với identity của View. Nếu item bị coi là một View mới, state cũ có thể bị reset.

**Ví dụ:**

```swift
struct Item: Identifiable {
    let id: UUID
    let name: String
}

ForEach(items) { item in
    Row(item: item)
}
```

Tránh kiểu:

```swift
ForEach(items) { item in
    Row(item: item)
        .id(UUID())
}
```

Vì mỗi lần tạo UUID mới có thể phá identity continuity.

---

## 3. Vì sao dùng `.id(...)` có thể làm SwiftUI reset state?

**Ý chính:** `.id` thay đổi `View identity`.

**Ý diễn giải:**
Khi ID thay đổi, SwiftUI có thể coi View đó là một instance logic mới. Local state gắn với identity cũ không còn được giữ.

**Ví dụ:**

```swift
@State private var counter = 0
```

Nếu:

```swift
Text("Hello")
    .id(currentID)
```

và `currentID` thay đổi:

```swift
currentID = UUID()
```

View có thể được coi là identity mới và state liên quan bị reset.

---

## 4. SwiftUI có thực sự “vẽ lại toàn bộ màn hình” mỗi khi state thay đổi không?

**Ý chính:** `Body recomputation ≠ full rendering`.

**Ý diễn giải:**
SwiftUI có thể recompute `body`, nhưng điều đó không có nghĩa toàn bộ pixel trên màn hình đều được render lại. Framework sử dụng identity, diffing và rendering system để xác định phần nào thực sự cần cập nhật.

**Ví dụ:**

```swift
struct CounterView: View {

    @State private var count = 0

    var body: some View {
        VStack {
            Text("Hello")

            Text("\(count)")

            Button("Add") {
                count += 1
            }
        }
    }
}
```

Việc `count` thay đổi không có nghĩa mọi thứ trong pipeline đều bị xây dựng và render từ đầu theo cách naïve.

---

## 5. Một `body` được tính lại rất nhiều lần có nhất thiết là performance bug không?

**Ý chính:** Không. `Recomputation` bình thường; vấn đề là expensive work trong `body`.

**Ý diễn giải:**
SwiftUI được thiết kế để recompute view descriptions. Điều đáng lo là bạn thực hiện network, parsing, sorting lớn hoặc tạo object tốn kém ngay trong `body`.

**Ví dụ:**

```swift
var body: some View {
    let sorted = hugeArray.sorted()

    return List(sorted) { item in
        Text(item.name)
    }
}
```

`sorted()` ở đây có thể là vấn đề nếu chạy lặp lại với dataset lớn.

Tốt hơn:

```swift
var sortedItems: [Item] {
    hugeArray.sorted()
}
```

và quản lý dữ liệu ở model/view model phù hợp.

# II. SWIFTUI — PROPERTY WRAPPERS / STATE OWNERSHIP

## 6. Khi nào một View nên tự sở hữu một state và khi nào chỉ nên nhận state từ bên ngoài?

**Ý chính:** `@State` = local owner; `@Binding` = external source of truth.

**Ý diễn giải:**
Nếu View là owner của UI-local state, dùng `@State`. Nếu state thuộc parent hoặc model khác, child nên nhận `Binding` hoặc read-only value thay vì tạo bản sao state.

**Ví dụ:**

```swift
struct ParentView: View {

    @State private var isOn = false

    var body: some View {
        ChildView(isOn: $isOn)
    }
}

struct ChildView: View {

    @Binding var isOn: Bool

    var body: some View {
        Toggle("Enabled", isOn: $isOn)
    }
}
```

---

## 7. Tại sao tạo một `@State` mới trong child có thể là sai architecture dù UI vẫn hoạt động?

**Ý chính:** `Duplicate source of truth`.

**Ý diễn giải:**
Nếu parent và child cùng lưu một dữ liệu logic thành hai state độc lập, chúng có thể lệch nhau. State nên có một owner rõ ràng.

**Ví dụ:**

```swift
struct Parent: View {

    @State private var isOn = false

    var body: some View {
        Child(initialValue: isOn)
    }
}
```

Nếu child lại làm:

```swift
struct Child: View {

    @State var isOn: Bool

    var body: some View {
        Toggle("Enabled", isOn: $isOn)
    }
}
```

thì parent và child đã có hai source of truth khác nhau.

---

## 8. Một Observable object được truyền từ parent xuống child. Khi nào dùng ownership và khi nào chỉ observe nó?

**Ý chính:** `@StateObject` = owner; `@ObservedObject` = observer.

**Ý diễn giải:**
View tạo và sở hữu lifecycle của observable object nên dùng `@StateObject`. Nếu object được tạo ở bên ngoài rồi truyền vào, child thường dùng `@ObservedObject`.

**Ví dụ:**

```swift
struct ParentView: View {

    @StateObject private var vm =
        ProfileViewModel()

    var body: some View {
        ChildView(vm: vm)
    }
}

struct ChildView: View {

    @ObservedObject var vm:
        ProfileViewModel

    var body: some View {
        Text(vm.name)
    }
}
```

---

## 9. Nếu child dùng `@StateObject` để tạo lại một ViewModel mà parent đã sở hữu, vấn đề gì có thể xảy ra?

**Ý chính:** `Ownership mismatch`.

**Ý diễn giải:**
Nếu parent đã là owner nhưng child lại coi nó là owner, lifecycle/state ownership trở nên không rõ. Có thể dẫn tới object được giữ ở nơi không mong muốn hoặc state bị reset/reinitialized theo identity.

**Ví dụ:**

```swift
struct Parent: View {

    @StateObject private var vm =
        ViewModel()

    var body: some View {
        Child(vm: vm)
    }
}
```

Child nên:

```swift
struct Child: View {

    @ObservedObject var vm: ViewModel
}
```

thay vì tạo ownership mới.

# III. ENVIRONMENT / OBSERVATION

## 10. Environment giúp giải quyết vấn đề gì trong SwiftUI?

**Ý chính:** `Contextual dependency/state` xuyên view hierarchy.

**Ý diễn giải:**
Environment giúp tránh truyền cùng một dependency qua nhiều tầng trung gian. Nó phù hợp với dependency có scope theo view hierarchy.

**Ví dụ:**

```swift
struct AppSession {
    let userName: String
}

private struct SessionKey:
    EnvironmentKey {

    static let defaultValue =
        AppSession(userName: "")
}

extension EnvironmentValues {

    var appSession: AppSession {
        get {
            self[SessionKey.self]
        }

        set {
            self[SessionKey.self] = newValue
        }
    }
}
```

Inject:

```swift
RootView()
    .environment(
        \.appSession,
        AppSession(userName: "Alice")
    )
```

---

## 11. Environment có thể làm architecture xấu đi trong trường hợp nào?

**Ý chính:** `Hidden dependency`.

**Ý diễn giải:**
Nếu View phụ thuộc vào quá nhiều Environment values, nhìn vào initializer sẽ không biết View cần gì. Điều này giống hidden dependency trong Service Locator.

**Ví dụ:**

```swift
struct ProfileView: View {

    @Environment(\.session)
    private var session

    @Environment(\.analytics)
    private var analytics

    @Environment(\.router)
    private var router

    @Environment(\.featureFlags)
    private var flags

    // ...
}
```

Khi dependency ít và quan trọng, explicit initializer có thể dễ reasoning hơn.

---

## 12. Observation framework giải quyết vấn đề gì so với cách quan sát object trước đây?

**Ý chính:** `Fine-grained observation` + giảm boilerplate.

**Ý diễn giải:**
Observation framework cho phép framework theo dõi property access và thay đổi một cách tích hợp hơn với SwiftUI. Nó giảm một số boilerplate so với mô hình `ObservableObject/@Published`.

**Ví dụ:**

```swift
import Observation

@Observable
final class UserModel {
    var name = ""
    var age = 0
}
```

View:

```swift
struct ProfileView: View {

    var model: UserModel

    var body: some View {
        Text(model.name)
    }
}
```

Điểm Senior cần quan tâm là **property nào thực sự được View đọc** và dependency đó ảnh hưởng invalidation thế nào.

# IV. SWIFTUI — LAZY / EQUATABLE / PERFORMANCE

## 13. Vì sao một container lazy có thể cải thiện performance của danh sách lớn?

**Ý chính:** `Deferred creation/work`.

**Ý diễn giải:**
Lazy container không cần tạo toàn bộ child hierarchy ngay lập tức. Nó trì hoãn tạo item cho đến khi cần hiển thị.

**Ví dụ:**

```swift
ScrollView {
    LazyVStack {
        ForEach(items) { item in
            Row(item: item)
        }
    }
}
```

So với:

```swift
ScrollView {
    VStack {
        ForEach(items) { item in
            Row(item: item)
        }
    }
}
```

Với dataset rất lớn, lazy container thường phù hợp hơn.

---

## 14. `LazyVStack` có nghĩa chỉ tồn tại đúng số row đang nhìn thấy không?

**Ý chính:** Không tuyệt đối; `Lazy` trì hoãn creation nhưng framework vẫn có thể giữ/prepare thêm item.

**Ý diễn giải:**
Không nên hiểu lazy như một virtualization contract đơn giản là “chỉ có đúng N cell”. Framework có thể tạo thêm item tùy layout, scrolling và lifecycle.

**Ví dụ:**

```swift
ScrollView {
    LazyVStack {
        ForEach(0..<10000) { index in
            Text("\(index)")
        }
    }
}
```

Điểm cần nhớ là **deferred work**, không phải một con số item tồn tại cố định.

---

## 15. Khi nào `.equatable()` có thể giúp giảm work trong SwiftUI?

**Ý chính:** `Skip update when input considered equal`.

**Ý diễn giải:**
Nếu một View nhận dữ liệu lớn nhưng nội dung thực tế không thay đổi, `Equatable` có thể giúp SwiftUI bỏ qua một số update. Nhưng nó không phải thuốc chữa cho state architecture sai.

**Ví dụ:**

```swift
struct UserRow: View, Equatable {

    let id: Int
    let name: String

    static func == (
        lhs: UserRow,
        rhs: UserRow
    ) -> Bool {
        lhs.id == rhs.id &&
        lhs.name == rhs.name
    }

    var body: some View {
        Text(name)
    }
}
```

Sử dụng:

```swift
UserRow(
    id: user.id,
    name: user.name
)
.equatable()
```

---

## 16. Vì sao không nên dùng Equatable để che một ViewModel hoặc state model quá lớn?

**Ý chính:** `Optimization ≠ architecture fix`.

**Ý diễn giải:**
Nếu View phụ thuộc quá nhiều state nhưng chỉ cần một phần nhỏ, vấn đề gốc là dependency granularity. `.equatable()` chỉ có thể giảm update trong một số trường hợp chứ không sửa source-of-truth design.

**Ví dụ:**

```swift
struct HugeState {
    var users: [User]
    var posts: [Post]
    var messages: [Message]
    var settings: Settings
    var analytics: AnalyticsState
}
```

Nếu một Row chỉ cần:

```swift
struct RowState: Equatable {
    let title: String
    let selected: Bool
}
```

thì dependency nhỏ hơn sẽ hợp lý hơn.

# V. UIKIT — LAYOUT PASS

## 17. Khi constraint thay đổi, UIKit không cập nhật frame theo kiểu ngay lập tức ở cùng dòng code. Tại sao?

**Ý chính:** `Layout pass`.

**Ý diễn giải:**
UIKit sử dụng deferred layout system. Khi hierarchy hoặc constraint thay đổi, view được đánh dấu cần layout và UIKit thực hiện layout ở pass thích hợp.

**Ví dụ:**

```swift
heightConstraint.constant = 200

view.setNeedsLayout()
```

Khi cần geometry mới ngay:

```swift
view.layoutIfNeeded()
```

---

## 18. Nếu một view liên tục gọi `setNeedsLayout()` trong `layoutSubviews()`, điều gì có thể xảy ra?

**Ý chính:** `Layout loop / unnecessary layout passes`.

**Ý diễn giải:**
Bạn có thể tạo vòng lặp layout hoặc khiến UIKit phải thực hiện nhiều layout pass không cần thiết. `layoutSubviews()` nên chỉ cập nhật layout dựa trên state hiện tại, không liên tục invalidating chính nó.

**Ví dụ:**

```swift
override func layoutSubviews() {
    super.layoutSubviews()

    setNeedsLayout()
}
```

Đây là pattern đáng nghi ngờ.

---

## 19. Auto Layout constraint conflict có thể ảnh hưởng performance ngoài việc tạo log warning không?

**Ý chính:** `Constraint solving cost + fallback behavior`.

**Ý diễn giải:**
Constraint system phải giải quyết mâu thuẫn và phá một hoặc nhiều constraint. Nếu hierarchy phức tạp và conflict xảy ra thường xuyên, nó vừa gây correctness issue vừa có thể tăng layout work.

**Ví dụ:**

```swift
NSLayoutConstraint.activate([
    view.widthAnchor.constraint(equalToConstant: 100),
    view.widthAnchor.constraint(equalToConstant: 200)
])
```

Hai constraint required mâu thuẫn nhau.

# VI. UIKIT — DISPLAY / RENDERING

## 20. Layout đã đúng nhưng giao diện vẫn giật. Bạn sẽ phân biệt layout cost và rendering cost như thế nào?

**Ý chính:** `Layout ≠ Rendering`.

**Ý diễn giải:**
Layout xác định geometry. Rendering biến hierarchy/layer thành nội dung hiển thị. Một UI có layout đơn giản nhưng rendering nặng do alpha, shadow, mask, blur hoặc compositing.

**Ví dụ:**

```text
Layout
 ↓
Frame / bounds / constraints

Display
 ↓
Draw content

Rendering
 ↓
CALayer / Core Animation / GPU
```

Có thể dùng:

```text
Time Profiler
Core Animation
Instruments
```

để xác định bottleneck.

# VII. CORE ANIMATION / CALAYER

## 21. UIView và CALayer có quan hệ với nhau như thế nào?

**Ý chính:** `UIView` quản lý UI abstraction; `CALayer` chịu trách nhiệm phần lớn rendering backing.

**Ý diễn giải:**
Mỗi UIView thường có một backing layer. UIView cung cấp event, hierarchy, layout và interaction; CALayer cung cấp geometry, visual properties và Core Animation integration.

**Ví dụ:**

```swift
view.layer.cornerRadius = 16
view.layer.opacity = 0.8
view.layer.masksToBounds = true
```

---

## 22. Vì sao một thay đổi về layer property có thể animation được mà không cần tự quản lý frame?

**Ý chính:** `Core Animation`.

**Ý diễn giải:**
Core Animation quản lý interpolation giữa các model/presentation values cho các animatable properties của CALayer.

**Ví dụ:**

```swift
UIView.animate(withDuration: 0.3) {
    self.view.layer.opacity = 0
}
```

Core Animation sẽ xử lý phần interpolation/rendering.

---

## 23. Model layer và presentation layer khác nhau như thế nào trong lúc animation?

**Ý chính:** `Model = intended state`; `Presentation = currently displayed state`.

**Ý diễn giải:**
Model layer chứa giá trị mà app đã đặt. Presentation layer phản ánh trạng thái đang hiển thị tại thời điểm đó.

**Ví dụ:**

```swift
view.layer.position = targetPosition

let currentPosition =
    view.layer.presentation()?
        .position
```

Trong quá trình animation, hai giá trị có thể khác nhau.

---

# VIII. OFFSCREEN RENDERING

## 24. Một view có shadow, mask và blur phức tạp nhưng layout rất nhẹ. Vì sao vẫn có thể lag?

**Ý chính:** `Offscreen rendering + compositing`.

**Ý diễn giải:**
Một số hiệu ứng cần render layer vào intermediate buffer rồi mới composite lên màn hình. Điều này có thể tăng GPU work và memory bandwidth.

**Ví dụ:**

```swift
view.layer.shadowOpacity = 0.3
view.layer.shadowRadius = 20

view.layer.cornerRadius = 20
view.layer.masksToBounds = true
```

Không phải combination nào cũng xấu, nhưng nếu xuất hiện hàng trăm lần trong scrolling hierarchy thì cần profile.

---

## 25. `shouldRasterize` có phải luôn là cách tốt để giảm rendering cost không?

**Ý chính:** Không. `Rasterization` có trade-off.

**Ý diễn giải:**
Rasterization cache kết quả render thành bitmap để tái sử dụng trong một số trường hợp. Nếu layer thay đổi liên tục hoặc kích thước lớn, rasterization có thể làm performance tệ hơn và tăng memory.

**Ví dụ:**

```swift
view.layer.shouldRasterize = true

view.layer.rasterizationScale =
    UIScreen.main.scale
```

Không nên bật toàn app theo kiểu blanket optimization.

# IX. SWIFTUI ↔ UIKIT RENDERING

## 26. Khi nhúng UIKit View vào SwiftUI, bạn cần đặc biệt chú ý điều gì về `updateUIView`?

**Ý chính:** `Idempotent update + minimal mutation`.

**Ý diễn giải:**
SwiftUI có thể gọi `updateUIView` nhiều lần. Không nên mỗi lần update lại remove/add subview, tạo network task hoặc reset toàn bộ UIKit state.

**Ví dụ:**

```swift
struct LegacyView:
    UIViewRepresentable {

    var title: String

    func makeUIView(
        context: Context
    ) -> UILabel {
        UILabel()
    }

    func updateUIView(
        _ uiView: UILabel,
        context: Context
    ) {
        if uiView.text != title {
            uiView.text = title
        }
    }
}
```

---

## 27. Nếu `UIViewRepresentable` tạo một UIKit object có state nội bộ nhưng SwiftUI liên tục recreate wrapper, làm sao giữ identity đúng?

**Ý chính:** `UIView lifecycle + SwiftUI identity`.

**Ý diễn giải:**
Wrapper là value type nên có thể được tạo lại nhiều lần. UIKit view object thật được framework quản lý theo lifecycle. Đừng dùng việc recreate wrapper như bằng chứng rằng UIKit object luôn bị destroy/create.

**Ví dụ:**

```swift
struct MapView:
    UIViewRepresentable {

    func makeUIView(
        context: Context
    ) -> MKMapView {
        MKMapView()
    }

    func updateUIView(
        _ uiView: MKMapView,
        context: Context
    ) {
        // update existing UIKit object
    }
}
```

---

## 28. Một SwiftUI View chứa UIViewRepresentable có performance thấp hơn hoàn toàn so với native SwiftUI không?

**Ý chính:** Không tuyệt đối; bottleneck phụ thuộc component và rendering path.

**Ý diễn giải:**
Interop không tự động chậm. Một UIKit component được tối ưu tốt có thể tốt hơn một custom SwiftUI implementation phức tạp. Cần đo thực tế.

**Ví dụ:**

```text
SwiftUI
   ↓
UIViewRepresentable
   ↓
UIKit
   ↓
CALayer
   ↓
Core Animation
```

So sánh performance phải dựa trên workload thực tế.

# X. SENIOR SCENARIOS

## 29. Một SwiftUI list rất lớn bị lag khi state của parent thay đổi dù row data gần như không đổi. Bạn sẽ kiểm tra gì?

**Ý chính:** `Dependency granularity + identity + unnecessary invalidation`.

**Ý diễn giải:**
Kiểm tra parent state mà row đang phụ thuộc, identity của ForEach, các environment values và work trong body. Nếu một state không liên quan khiến toàn bộ subtree invalidated thường xuyên, nên giảm dependency hoặc chia nhỏ state.

**Ví dụ:**

```swift
struct Parent: View {

    @State private var timer = 0
    let items: [Item]

    var body: some View {

        VStack {
            Text("\(timer)")

            List(items) { item in
                Row(item: item)
            }
        }
    }
}
```

Nếu Row vô tình phụ thuộc thêm vào state không cần thiết, mỗi tick có thể làm tăng work.

## 30. Một UIKit CollectionView hiển thị 500 cell đều có shadow, rounded corners, transparency và image. Scroll bị giật. Bạn sẽ phân tích từ đâu?

**Ý chính:** `Main thread + layout + image decode + compositing + GPU`.

**Ý diễn giải:**
Không nên sửa từng hiệu ứng ngay. Trước tiên profile frame. Sau đó kiểm tra image decode/downsampling, cell configure, Auto Layout, shadow/mask, blending và memory bandwidth.

# XI. 10 CÂU BẪY SENIOR

## 31. “SwiftUI View là struct nên mỗi lần body chạy là object mới.” Bạn đánh giá câu này thế nào?

**Ý chính:** `Value description ≠ UIKit object lifecycle`.

**Ý diễn giải:**
SwiftUI View là value type dùng để mô tả UI. Không nên suy luận trực tiếp rằng mỗi lần body recompute là toàn bộ underlying platform UI bị destroy/create.

---

## 32. “Body recompute nhiều lần nghĩa app đang chậm.” Đúng không?

**Ý chính:** Không.

**Ý diễn giải:**
Recompute là một phần bình thường của declarative UI. Chỉ đáng lo khi recomputation kéo theo expensive work, excessive invalidation hoặc rendering cost cao.

---

## 33. “LazyVStack luôn nhanh hơn VStack.” Đúng không?

**Ý chính:** Không.

**Ý diễn giải:**
Lazy có lợi khi nhiều child và creation cost đáng kể. Với danh sách nhỏ, lazy có thể không đem lại lợi ích đáng kể và còn thêm semantics complexity.

---

## 34. “Equatable sẽ giải quyết SwiftUI performance.” Đúng không?

**Ý chính:** Không.

**Ý diễn giải:**
Equatable chỉ là một optimization tool. Nếu state ownership hoặc identity sai, `.equatable()` không sửa được architecture.

---

## 35. “CALayer luôn nhanh hơn UIView.” Đúng không?

**Ý chính:** Không nên so sánh như vậy.

**Ý diễn giải:**
UIView và CALayer có trách nhiệm khác nhau. Bạn chọn abstraction phù hợp với requirement. Tự bỏ UIView để dùng layer không đảm bảo performance tốt hơn.

---

## 36. “shouldRasterize = true là tối ưu GPU.” Đúng không?

**Ý chính:** Không. Có trade-off giữa render reuse và memory/rasterization cost.

**Ý diễn giải:**
Chỉ nên dùng khi profile cho thấy workload phù hợp, đặc biệt với content tương đối tĩnh và render lặp lại.

---

## 37. “Shadow gây lag.” Có phải luôn đúng?

**Ý chính:** Không. `Rendering cost depends on context`.

**Ý diễn giải:**
Một shadow đơn giản trên vài view có thể không đáng kể. Vấn đề xuất hiện khi có rất nhiều layer, shadow phức tạp hoặc scrolling workload lớn.

---

## 38. “MainActor và main thread là cùng một khái niệm.” Đúng không?

**Ý chính:** Không hoàn toàn.

**Ý diễn giải:**
`MainActor` là concurrency isolation domain. Trong UIKit/iOS, nó gắn với main-thread-affine UI execution, nhưng không nên đồng nhất actor model với cách quản lý thread thủ công.

---

## 39. “UIKit layout xong là rendering xong.” Đúng không?

**Ý chính:** Không. `Layout` và `Rendering` là các bước khác nhau.

**Ý diễn giải:**

```text
Constraint/Layout
      ↓
Geometry
      ↓
Display
      ↓
Core Animation
      ↓
Compositing
      ↓
GPU
      ↓
Screen
```

Một màn hình có layout rất nhanh vẫn có thể render chậm.

---

## 40. “Nếu UI lag thì chắc chắn do CPU.” Đúng không?

**Ý chính:** Không. Có thể là `CPU + GPU + memory + layout + synchronization`.

**Ý diễn giải:**
Senior phải xác định frame budget bị phá ở đâu. Có thể do main-thread CPU, image decode, Auto Layout, rendering, blending, GPU hoặc memory pressure.
