# I. URLSESSION & HTTP

## 1. Một ứng dụng cần gọi API HTTPS và lấy cả dữ liệu lẫn thông tin response. Bạn sẽ thực hiện request như thế nào?

**Ý chính:** `URLSession` + `URLRequest` + HTTP response.

**Ý diễn giải:**
`URLSession` là API networking chính của Apple. Với request cần control method, headers, body hoặc timeout, tạo `URLRequest`. Sau khi request hoàn thành, kiểm tra cả `Data` và `HTTPURLResponse`.

**Ví dụ:**

```swift
let url = URL(string: "https://api.example.com/users")!

var request = URLRequest(url: url)
request.httpMethod = "GET"

let (data, response) = try await URLSession.shared.data(
    for: request
)

guard let httpResponse = response as? HTTPURLResponse else {
    throw APIError.invalidResponse
}

print(httpResponse.statusCode)
print(data)
```

---

## 2. Vì sao nhận được `Data` từ URLSession chưa có nghĩa request thành công?

**Ý chính:** `Transport success` khác `HTTP success`.

**Ý diễn giải:**
URLSession có thể hoàn thành request thành công ở tầng transport nhưng server trả HTTP 400, 401, 404 hoặc 500. Vì vậy phải kiểm tra status code trước khi decode business data.

**Ví dụ:**

```swift
let (data, response) = try await URLSession.shared.data(
    for: request
)

guard let http = response as? HTTPURLResponse else {
    throw APIError.invalidResponse
}

guard (200..<300).contains(http.statusCode) else {
    throw APIError.httpStatus(http.statusCode)
}
```

---

## 3. Bạn sẽ phân biệt lỗi mất mạng, timeout và server trả lỗi 500 như thế nào?

**Ý chính:** `Transport error` vs `HTTP error`.

**Ý diễn giải:**
Mất mạng hoặc timeout thường không có HTTP response hợp lệ. Trong khi HTTP 500 nghĩa là server đã nhận request và trả response. Ba loại lỗi này có retry policy khác nhau.

**Ví dụ:**

```swift
enum APIError: Error {
    case offline
    case timeout
    case server(Int)
}
```

Mapping có thể dựa trên:

```swift
do {
    let (data, response) = try await session.data(for: request)
} catch let error as URLError {
    switch error.code {
    case .notConnectedToInternet:
        throw APIError.offline

    case .timedOut:
        throw APIError.timeout

    default:
        throw error
    }
}
```

---

## 4. Một request POST bị timeout. Bạn có nên gửi lại ngay request đó không?

**Ý chính:** `Retry safety` + `idempotency`.

**Ý diễn giải:**
Timeout không chứng minh server chưa xử lý request. Server có thể đã nhận và thực hiện thành công nhưng response bị mất. Retry POST có thể tạo duplicate side effect. Cần biết operation có idempotent không hoặc dùng idempotency key.

**Ví dụ:**

```swift
var request = URLRequest(url: paymentURL)
request.httpMethod = "POST"

request.setValue(
    UUID().uuidString,
    forHTTPHeaderField: "Idempotency-Key"
)
```

Server có thể dùng key này để nhận diện cùng một operation.

# II. CODABLE & API MODEL

## 5. Một API trả JSON có cấu trúc khác với model mà app muốn sử dụng. Bạn sẽ xử lý ở đâu?

**Ý chính:** `DTO` + mapping.

**Ý diễn giải:**
Không nhất thiết để domain model phụ thuộc trực tiếp vào JSON structure. DTO đại diện API response, sau đó mapper chuyển DTO thành domain model.

**Ví dụ:**

```swift
struct UserDTO: Decodable {
    let user_id: Int
    let display_name: String
}

struct User {
    let id: Int
    let name: String
}

extension UserDTO {
    func toDomain() -> User {
        User(
            id: user_id,
            name: display_name
        )
    }
}
```

---

## 6. Nếu backend đổi tên field nhưng UI không nên thay đổi, bạn sẽ bảo vệ app khỏi thay đổi đó như thế nào?

**Ý chính:** `API boundary` + `CodingKeys` / DTO mapping.

**Ý diễn giải:**
Backend-specific naming nên bị hấp thụ ở data layer. Presentation và domain không cần biết API field tên gì.

**Ví dụ:**

```swift
struct UserDTO: Decodable {
    let name: String

    enum CodingKeys: String, CodingKey {
        case name = "display_name"
    }
}
```

---

## 7. Một field đôi lúc không xuất hiện trong JSON. Bạn có nên cho mọi field thành Optional không?

**Ý chính:** Không. `Optional` phải phản ánh business semantics.

**Ý diễn giải:**
Field có thể thiếu thật sự thì Optional hợp lý. Nhưng nếu field bắt buộc mà backend thiếu, đó có thể là invalid response và nên fail thay vì âm thầm dùng default.

**Ví dụ:**

```swift
struct UserDTO: Decodable {
    let id: Int
    let nickname: String?
}
```

Không nên:

```swift
struct UserDTO: Decodable {
    let id: Int?
    let name: String?
    let age: Int?
    let email: String?
}
```

chỉ để tránh decode error.

# III. AUTHENTICATION

## 8. Access token và refresh token phục vụ hai mục đích khác nhau như thế nào?

**Ý chính:** `Access token` dùng gọi API; `Refresh token` dùng lấy access token mới.

**Ý diễn giải:**
Access token thường có lifetime ngắn hơn để giảm tác động khi bị lộ. Refresh token có lifetime dài hơn và cần được bảo vệ nghiêm ngặt hơn.

**Ví dụ:**

```swift
struct TokenSet {
    let accessToken: String
    let refreshToken: String
}
```

Request:

```swift
request.setValue(
    "Bearer \(tokens.accessToken)",
    forHTTPHeaderField: "Authorization"
)
```

---

## 9. Access token nên được lưu ở đâu?

**Ý chính:** `Keychain`.

**Ý diễn giải:**
Token là credential và không nên lưu trong UserDefaults hoặc plain text file. Keychain cung cấp cơ chế secure storage phù hợp hơn.

**Ví dụ:**

```swift
let query: [String: Any] = [
    kSecClass as String: kSecClassGenericPassword,
    kSecAttrAccount as String: "access_token",
    kSecValueData as String:
        Data(token.utf8)
]

SecItemAdd(
    query as CFDictionary,
    nil
)
```

---

## 10. Nếu người dùng logout nhưng access token vẫn còn trong memory cache, vấn đề có thể xảy ra gì?

**Ý chính:** `Credential lifecycle` + cache invalidation.

**Ý diễn giải:**
Logout không chỉ là xóa token khỏi Keychain. Cần clear in-memory token, user-scoped cache, pending requests và state liên quan user.

**Ví dụ:**

```swift
func logout() {
    tokenStore.clear()
    imageCache.removeAllObjects()
    userCache.removeAll()
}
```

# IV. REFRESH TOKEN — SENIOR DEEP DIVE

## 11. Có 5 request cùng lúc nhận HTTP 401 vì access token hết hạn. Bạn sẽ refresh token bao nhiêu lần?

**Ý chính:** `Single-flight refresh` → chỉ nên có **một refresh operation đang chạy**.

**Ý diễn giải:**
Nếu mỗi request tự refresh token, app có thể tạo 5 refresh requests đồng thời. Điều này vừa lãng phí vừa có thể làm refresh token bị invalid hoặc tạo race condition.

Nên có một nơi duy nhất quản lý refresh. Các request khác await cùng operation.

**Ví dụ:**

```swift
actor AuthManager {

    private var refreshTask: Task<String, Error>?

    func validAccessToken() async throws -> String {

        if let refreshTask {
            return try await refreshTask.value
        }

        let task = Task {
            try await refreshAccessToken()
        }

        refreshTask = task

        defer {
            refreshTask = nil
        }

        return try await task.value
    }
}
```

Luồng:

```text
Request A ──┐
Request B ──┤
Request C ──┼──→ AuthManager
Request D ──┤        ↓
Request E ──┘   refresh 1 lần
                    ↓
              access token mới
                    ↓
          A B C D E tiếp tục
```

Đây là một câu **rất mạnh để phân biệt Senior**.

---

## 12. Vì sao chỉ dùng một Boolean `isRefreshing` chưa chắc giải quyết được vấn đề refresh token đồng thời?

**Ý chính:** `isRefreshing` chỉ là state; cần `synchronization + waiter management`.

**Ý diễn giải:**
Một Boolean không tự bảo vệ khỏi concurrent access. Quan trọng hơn, request B cần biết phải chờ kết quả refresh của request A, chứ không chỉ biết `isRefreshing == true`.

**Ví dụ:**

```swift
actor AuthManager {

    private var isRefreshing = false

    // Chỉ có Boolean thì request khác
    // vẫn chưa biết phải await kết quả nào.
}
```

Tốt hơn là lưu task:

```swift
private var refreshTask: Task<Token, Error>?
```

---

## 13. Nếu refresh token cũng hết hạn, flow authentication nên kết thúc như thế nào?

**Ý chính:** `Refresh failure` → clear credential → unauthenticated state → login.

**Ý diễn giải:**
Không được retry refresh vô hạn. Nếu refresh token không còn hợp lệ, authentication session phải chuyển sang unauthenticated. App có thể clear credential và đưa user về login.

**Ví dụ:**

```swift
do {
    let token = try await auth.refresh()
    return token
} catch AuthError.refreshExpired {
    await auth.logout()
    throw AuthError.sessionExpired
}
```

---

## 14. Làm thế nào tránh vòng lặp vô hạn: request → 401 → refresh → request → 401 → refresh?

**Ý chính:** `Retry limit / request state`.

**Ý diễn giải:**
Một request chỉ nên retry authentication một số lần rất giới hạn, thường là một lần sau refresh. Nếu request retry vẫn 401 thì coi authentication thất bại.

**Ví dụ:**

```swift
func send(
    _ request: URLRequest,
    retriedAfterRefresh: Bool = false
) async throws -> Data {

    let response = try await perform(request)

    if response.statusCode == 401,
       !retriedAfterRefresh {

        try await auth.refresh()

        let retryRequest = try await authorized(request)

        return try await send(
            retryRequest,
            retriedAfterRefresh: true
        )
    }

    return response.data
}
```

---

## 15. Sau khi refresh token thành công, request cũ nên gửi lại request object cũ hay tạo lại?

**Ý chính:** `Rebuild authorized request`.

**Ý diễn giải:**
Request cũ có thể chứa Authorization header cũ. Thường nên tạo lại authorized request từ request gốc nhưng inject access token mới.

**Ví dụ:**

```swift
func authorized(
    _ original: URLRequest,
    token: String
) -> URLRequest {

    var request = original

    request.setValue(
        "Bearer \(token)",
        forHTTPHeaderField: "Authorization"
    )

    return request
}
```

# V. RETRY / BACKOFF

## 16. Những lỗi nào thường phù hợp để retry?

**Ý chính:** `Transient errors`.

**Ý diễn giải:**
Retry thường phù hợp với lỗi tạm thời như network interruption, timeout hoặc một số server errors như 503. Không nên retry validation error 400, authentication failure không thể refresh, hay business error.

**Ví dụ:**

```swift
func shouldRetry(statusCode: Int) -> Bool {
    statusCode == 408 ||
    statusCode == 429 ||
    (500...599).contains(statusCode)
}
```

---

## 17. Vì sao retry liên tục ngay lập tức có thể làm hệ thống tệ hơn?

**Ý chính:** `Retry storm`.

**Ý diễn giải:**
Khi server đang quá tải, hàng nghìn client cùng retry ngay có thể tiếp tục làm server quá tải. Vì vậy retry nên dùng exponential backoff và thường có jitter.

**Ví dụ:**

```swift
func delay(
    attempt: Int
) -> Duration {

    let seconds = pow(
        2,
        Double(attempt)
    )

    return .seconds(seconds)
}
```

---

## 18. Exponential backoff và jitter giải quyết hai vấn đề khác nhau như thế nào?

**Ý chính:** Backoff giảm tần suất; jitter tránh đồng bộ retry.

**Ý diễn giải:**
Backoff làm khoảng cách giữa các lần retry tăng dần. Jitter thêm randomization để nhiều client không retry đúng cùng thời điểm.

**Ví dụ:**

```swift
let base = pow(2.0, Double(attempt))

let jitter = Double.random(
    in: 0...0.5
)

let delay = base + jitter
```

---

## 19. Bạn có nên retry HTTP 429 không?

**Ý chính:** Có thể retry, nhưng tôn trọng `Retry-After`.

**Ý diễn giải:**
429 biểu thị rate limit. Nếu server gửi `Retry-After`, client nên ưu tiên thông tin đó thay vì tự retry liên tục.

**Ví dụ:**

```swift
if response.statusCode == 429 {

    if let value = response.value(
        forHTTPHeaderField: "Retry-After"
    ) {
        print("Wait \(value) seconds")
    }
}
```

# VI. TIMEOUT & CANCELLATION

## 20. Timeout khác cancellation ở góc độ business như thế nào?

**Ý chính:** Timeout = operation vượt thời gian cho phép; cancellation = caller không còn cần operation.

**Ý diễn giải:**
Timeout thường là policy của network operation. Cancellation thường đến từ lifecycle hoặc user action. Cả hai có thể dừng task nhưng semantics khác nhau và UI có thể xử lý khác.

**Ví dụ:**

```swift
do {
    let data = try await fetch()
} catch is CancellationError {
    // User/navigation không còn cần
} catch {
    // Network/timeout/error
}
```

---

## 21. User search liên tục khi nhập text. Bạn thiết kế network layer thế nào để request cũ không tiếp tục tiêu tốn tài nguyên?

**Ý chính:** `Cancellation + debounce`.

**Ý diễn giải:**
Mỗi query mới cancel task cũ. Chờ một khoảng debounce rồi mới gửi request. Nếu request cũ đã chạy, cancellation phải được propagate xuống URLSession.

**Ví dụ:**

```swift
var searchTask: Task<Void, Never>?

func search(_ text: String) {

    searchTask?.cancel()

    searchTask = Task {

        try? await Task.sleep(
            for: .milliseconds(300)
        )

        guard !Task.isCancelled else {
            return
        }

        let results = try await api.search(text)

        await MainActor.run {
            updateUI(results)
        }
    }
}
```

# VII. HTTP CACHE

## 22. Nếu một endpoint trả cùng dữ liệu nhiều lần, bạn sẽ giảm network request như thế nào?

**Ý chính:** `Caching`.

**Ý diễn giải:**
Có thể dùng HTTP cache semantics, memory cache hoặc disk cache tùy yêu cầu freshness. Cache strategy phải xác định TTL/invalidation/source of truth.

**Ví dụ:**

```swift
var request = URLRequest(url: url)

request.cachePolicy =
    .returnCacheDataElseLoad
```

Trong production không nên áp dụng một cache policy cho mọi endpoint.

---

## 23. ETag giải quyết vấn đề gì?

**Ý chính:** `Conditional request` + `304 Not Modified`.

**Ý diễn giải:**
Client lưu ETag từ response trước. Khi request lại, gửi `If-None-Match`. Nếu resource chưa thay đổi, server có thể trả 304 thay vì gửi toàn bộ body.

**Ví dụ:**

```swift
request.setValue(
    etag,
    forHTTPHeaderField: "If-None-Match"
)
```

---

## 24. Memory cache có thể thay thế database không?

**Ý chính:** Không. `Cache != source of truth`.

**Ý diễn giải:**
Memory cache có thể bị evict hoặc mất khi app terminate. Nó chỉ nên tăng tốc truy cập. Dữ liệu quan trọng cần source of truth persistent hoặc server.

**Ví dụ:**

```swift
let cache = NSCache<NSURL, NSData>()
```

Không nên:

```swift
cache.setObject(
    importantUserData,
    forKey: userURL
)

// coi cache là database
```

# VIII. UPLOAD / DOWNLOAD / BACKGROUND

## 25. Một app cần tải file vài trăm MB trong khi user rời app. Bạn sẽ thiết kế thế nào?

**Ý chính:** `Background URLSession`.

**Ý diễn giải:**
Không nên phụ thuộc vào một Task thông thường để đảm bảo file transfer tiếp tục sau khi app bị background/suspend. Background URLSession cho phép hệ thống quản lý transfer và đánh thức app khi phù hợp.

**Ví dụ:**

```swift
let configuration =
    URLSessionConfiguration.background(
        withIdentifier: "com.example.downloads"
    )

let session = URLSession(
    configuration: configuration,
    delegate: self,
    delegateQueue: nil
)

let task = session.downloadTask(
    with: downloadURL
)

task.resume()
```

Điểm Senior cần hiểu:

```text
App
 ↓
Background URLSession
 ↓
System-managed transfer
 ↓
App được đánh thức khi phù hợp
```

# IX. WEBSOCKET

## 26. Một chat app cần nhận message liên tục từ server. Vì sao request-response thông thường không phải lựa chọn tối ưu?

**Ý chính:** `Persistent bidirectional connection`.

**Ý diễn giải:**
HTTP request-response phù hợp khi client chủ động request. Chat cần server push event liên tục, nên WebSocket phù hợp hơn vì giữ connection và hỗ trợ hai chiều.

**Ví dụ:**

```swift
let task = URLSession.shared.webSocketTask(
    with: URL(string: "wss://example.com/chat")!
)

task.resume()
```

---

## 27. WebSocket disconnect thì chỉ cần connect lại ngay lập tức không?

**Ý chính:** `Reconnect policy + exponential backoff + lifecycle`.

**Ý diễn giải:**
Reconnect ngay liên tục có thể tạo reconnect storm. Cần backoff, jitter và xem app đang foreground/background hay không.

**Ví dụ:**

```swift
func reconnect(attempt: Int) async {

    let delay = min(
        pow(2.0, Double(attempt)),
        30
    )

    try? await Task.sleep(
        for: .seconds(delay)
    )

    connect()
}
```

---

## 28. Người dùng rời màn hình chat nhưng WebSocket vẫn tiếp tục nhận message. Bạn sẽ kiểm tra gì?

**Ý chính:** Connection lifecycle + task cancellation.

**Ý diễn giải:**
WebSocket phải có owner rõ ràng. Khi feature không còn active, subscription/read loop cần cancel hoặc connection chuyển sang lifecycle phù hợp. Không nên để mỗi screen tự tạo một connection mà không quản lý.

**Ví dụ:**

```swift
private var receiveTask: Task<Void, Never>?

func start() {
    receiveTask = Task {
        while !Task.isCancelled {
            try await receiveMessage()
        }
    }
}

func stop() {
    receiveTask?.cancel()
}
```

# X. URLPROTOCOL / TESTABILITY

## 29. Bạn muốn Unit Test networking mà không gọi server thật. Làm thế nào để intercept request ngay tại URL loading layer?

**Ý chính:** `URLProtocol`.

**Ý diễn giải:**
`URLProtocol` cho phép intercept URL loading request trong test. Có thể trả response/data giả mà không cần server thật. Đây là một kỹ thuật mạnh để test URLSession-based networking.

**Ví dụ:**

```swift
final class MockURLProtocol: URLProtocol {

    static var responseData: Data!

    override class func canInit(
        with request: URLRequest
    ) -> Bool {
        true
    }

    override class func canonicalRequest(
        for request: URLRequest
    ) -> URLRequest {
        request
    }

    override func startLoading() {

        let response = HTTPURLResponse(
            url: request.url!,
            statusCode: 200,
            httpVersion: nil,
            headerFields: nil
        )!

        client?.urlProtocol(
            self,
            didReceive: response,
            cacheStoragePolicy: .notAllowed
        )

        client?.urlProtocol(
            self,
            didLoad: Self.responseData
        )

        client?.urlProtocolDidFinishLoading(self)
    }

    override func stopLoading() {}
}
```

Sau đó:

```swift
let configuration =
    URLSessionConfiguration.ephemeral

configuration.protocolClasses = [
    MockURLProtocol.self
]

let session = URLSession(
    configuration: configuration
)
```

# XI. SENIOR SCENARIOS

## 30. Bạn được giao thiết kế một API client dùng chung cho toàn app. Kiến trúc của bạn sẽ gồm những thành phần nào?

**Ý chính:** `Request builder + URLSession + authentication + retry + decoding + error mapping + cancellation`.

**Ý diễn giải:**
Không nên để từng ViewModel tự dựng URLRequest. API client nên centralize các concern chung nhưng không trở thành một God Object. Authentication, request execution, response validation và decoding nên có boundary rõ.

**Ví dụ:**

```swift
protocol APIClient {

    func request<T: Decodable>(
        _ endpoint: Endpoint
    ) async throws -> T
}
```

## 33. Bạn có nên kiểm tra network connectivity trước mỗi request bằng Reachability rồi mới gọi API?

**Ý chính:** Reachability là `hint`, không phải guarantee.

**Ý diễn giải:**
Network có thể thay đổi ngay sau khi kiểm tra. Việc “đang connected” không đảm bảo request tiếp theo thành công. Request thực tế mới là source of truth.

**Ví dụ:**

```swift
if reachability.isConnected {
    do {
        let data = try await api.fetch()
    } catch {
        // Network vẫn có thể fail
    }
}
```

Không nên:

```swift
guard reachability.isConnected else {
    return
}

// giả định request chắc chắn thành công
```

## 34. Một request mất 15 giây mới trả về nhưng UI chỉ cần kết quả trong 2 giây. Bạn giải quyết thế nào?

**Ý chính:** `Timeout policy` + `Cancellation`.

**Ý diễn giải:**
Nếu product requirement chỉ cần response trong 2 giây, request nên có timeout hoặc caller cancellation phù hợp. Không nhất thiết phải để network operation giữ resource 15 giây nếu kết quả đã không còn hữu ích.

**Ví dụ:**

```swift
var request = URLRequest(url: url)

request.timeoutInterval = 2
```

Hoặc:

```swift
let task = Task {
    try await api.fetch()
}

Task {
    try await Task.sleep(
        for: .seconds(2)
    )

    task.cancel()
}
```

## 35. API trả về cùng một resource nhưng nhiều request đồng thời cùng tải resource đó. Bạn sẽ giải quyết thế nào?

**Ý chính:** `Request deduplication / in-flight task`.

**Ý diễn giải:**
Caching giải quyết trường hợp request hoàn thành rồi. Khi request đầu tiên vẫn đang chạy, các caller mới nên join vào request hiện tại thay vì tạo request mới.

**Ví dụ:**

```swift
actor ResourceLoader {

    private var inFlight:
        [URL: Task<Data, Error>] = [:]

    func load(
        _ url: URL
    ) async throws -> Data {

        if let task = inFlight[url] {
            return try await task.value
        }

        let task = Task {
            try await download(url)
        }

        inFlight[url] = task

        defer {
            inFlight[url] = nil
        }

        return try await task.value
    }
}
```

# XII. SENIOR — THIẾT KẾ END-TO-END

## 36. Bạn sẽ thiết kế authentication flow hoàn chỉnh của một app production như thế nào?

**Ý chính:** `Access token + refresh token + secure storage + single-flight refresh + retry once + logout on refresh failure`.

**Ý diễn giải:**

Flow nên gần như:

```text
Request
   ↓
Access Token
   ↓
API
   ↓
200 ───────────→ Return result
   │
   └── 401
        ↓
   AuthManager
        ↓
   Refresh đang chạy?
      /       \
    Có         Không
    ↓            ↓
 await task    refresh()
    \            /
     \          /
      Token mới
          ↓
   Retry original request
          ↓
      ┌───┴───┐
     200     401
      ↓        ↓
   success   logout
```

**Ví dụ:**

```swift
actor AuthManager {

    private var token: Token?
    private var refreshTask: Task<Token, Error>?

    func accessToken() async throws -> Token {

        if let refreshTask {
            return try await refreshTask.value
        }

        guard token?.isExpired == true else {
            return token!
        }

        let task = Task {
            try await refresh()
        }

        refreshTask = task

        defer {
            refreshTask = nil
        }

        let newToken = try await task.value

        token = newToken

        return newToken
    }
}
```

Điểm Senior phải nói được:

```text
1. Token storage
2. Concurrent refresh
3. Retry limit
4. Cancellation
5. Logout
6. Secure storage
7. Error mapping
8. Request replay
9. Refresh failure
10. App lifecycle
```

# XIII. 10 CÂU “BẪY” NETWORKING SENIOR

## 37. Nếu request timeout, server có chắc chắn chưa xử lý request không?

**Ý chính:** Không.

**Ý diễn giải:**
Client timeout chỉ nói client không nhận được kết quả đúng hạn. Server có thể đã xử lý thành công. Đây là lý do retry mutation phải đặc biệt cẩn thận.

---

## 38. Nếu URLSession trả error, có chắc server không nhận request không?

**Ý chính:** Không chắc.

**Ý diễn giải:**
Transport failure có thể xảy ra sau khi request đã rời client. Không nên suy luận đơn giản “error = server chưa nhận”.

---

## 39. Nếu access token hết hạn thì request nào cũng phải tự refresh?

**Ý chính:** Không. `Single-flight centralized refresh`.

**Ý diễn giải:**
Authentication nên tập trung ở AuthManager/interceptor/network layer. Một refresh operation nên phục vụ nhiều request đang chờ.

---

## 40. Nếu refresh token request trả 500 thì có nên logout ngay không?

**Ý chính:** Không nhất thiết.

**Ý diễn giải:**
500 có thể là transient server failure. Có thể retry refresh theo policy. Chỉ nên coi session invalid khi nhận dấu hiệu authentication thực sự không còn hợp lệ.

---

## 41. Có nên retry mọi request bị timeout?

**Ý chính:** Không.

**Ý diễn giải:**
Retry phải phụ thuộc idempotency, request semantics, số lần retry và trạng thái server. Mutation timeout đặc biệt nguy hiểm.

---

## 42. Có nên gọi Reachability trước rồi mới gọi API?

**Ý chính:** Không cần dùng nó như gate tuyệt đối.

**Ý diễn giải:**
Reachability chỉ là tín hiệu. Mạng có thể thay đổi ngay sau check.

---

## 43. Cache có phải source of truth không?

**Ý chính:** Không.

**Ý diễn giải:**
Cache chỉ tối ưu tốc độ. Nó có thể bị evict hoặc stale.

---

## 44. Background URLSession có nghĩa app được chạy code liên tục dưới background không?

**Ý chính:** Không.

**Ý diễn giải:**
System quản lý transfer và lifecycle. App không được tự do chạy CPU vô hạn dưới background.

---

## 45. WebSocket có nghĩa connection luôn sống không?

**Ý chính:** Không.

**Ý diễn giải:**
Connection có thể disconnect vì network, server, app lifecycle hoặc timeout. Cần reconnect policy.

---

## 46. HTTP 401 và 403 có cùng nghĩa không?

**Ý chính:** Không.

**Ý diễn giải:**
401 liên quan authentication/credential. 403 nghĩa request đã được hiểu nhưng không được phép thực hiện action đó.
