## 1. Một màn hình được tạo ra nhưng bạn chưa hề truy cập đến view của nó. Khi nào phần giao diện thực sự được tạo?

**Ý chính:** `loadView` → `viewDidLoad` - view được tạo khi `view` được truy cập lần đầu.

**Ý diễn giải:**
`UIViewController` có thể tồn tại mà view của nó chưa được load. Khi hệ thống hoặc code truy cập `view`, UIKit mới load view. `loadView()` chịu trách nhiệm tạo root view, sau đó `viewDidLoad()` được gọi một lần sau khi view đã được load.

**Ví dụ:**

```swift
final class ProfileViewController: UIViewController {

    override func loadView() {
        let view = UIView()
        view.backgroundColor = .systemBackground
        self.view = view
    }

    override func viewDidLoad() {
        super.viewDidLoad()

        print("View đã được load")
    }
}
```

## 2. Bạn đặt logic khởi tạo UI vào một callback nhưng callback đó không chạy lại khi người dùng quay lại màn hình. Vì sao?

**Ý chính:** `viewDidLoad` chỉ chạy một lần cho vòng đời của loaded view.

**Ý diễn giải:**
`viewDidLoad` phù hợp cho setup một lần như tạo UI, bind delegate, tạo constraint. Khi controller rời màn hình rồi quay lại mà view vẫn còn, `viewDidLoad` không chạy lại. Logic cần cập nhật mỗi lần xuất hiện nên đặt ở appearance lifecycle phù hợp.

**Ví dụ:**

```swift
override func viewDidLoad() {
    super.viewDidLoad()

    setupUI()
}

override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)

    refreshIfNeeded()
}
```

---

## 3. Bạn cần cập nhật UI ngay trước khi màn hình xuất hiện và mỗi lần người dùng quay lại màn hình. Bạn sẽ chọn thời điểm nào?

**Ý chính:** `viewWillAppear`.

**Ý diễn giải:**
`viewWillAppear` được gọi trước khi view xuất hiện. Nó phù hợp cho dữ liệu cần refresh mỗi lần screen trở lại. Nếu công việc chỉ cần thực hiện một lần, nên dùng `viewDidLoad`.

**Ví dụ:**

```swift
override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)

    loadLatestData()
}
```

---

## 4. Có một API được gọi trong `viewWillAppear`, nhưng user push/pop nhanh làm request bị lặp. Bạn sẽ xử lý thế nào?

**Ý chính:** Lifecycle awareness + deduplication + cancellation.

**Ý diễn giải:**
Không nên mặc định gọi API mỗi lần callback chạy. Cần xác định khi nào dữ liệu thực sự stale, đồng thời có thể cancel request cũ hoặc deduplicate request đang chạy.

**Ví dụ:**

```swift
private var loading = false

override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)

    guard !loading else { return }

    loading = true

    Task {
        defer { loading = false }

        await loadData()
    }
}
```

# Chủ đề: Auto Layout & Constraint

## 5. Bạn chỉ cung cấp một vài constraint nhưng hệ thống vẫn có thể tính ra kích thước của UILabel. Điều gì giúp nó làm được điều đó?

**Ý chính:** `Intrinsic Content Size`.

**Ý diễn giải:**
Một số UIKit view biết kích thước tự nhiên dựa trên content. UILabel là ví dụ điển hình. Khi kết hợp intrinsic size với các constraint về vị trí hoặc width/height còn thiếu, Auto Layout có thể suy ra frame.

**Ví dụ:**

```swift
let label = UILabel()
label.text = "Hello UIKit"

view.addSubview(label)

NSLayoutConstraint.activate([
    label.leadingAnchor.constraint(equalTo: view.leadingAnchor, constant: 20),
    label.topAnchor.constraint(equalTo: view.topAnchor, constant: 20)
])
```

Không cần tự đặt width/height cho label trong trường hợp này.

---

## 6. Hai view cùng muốn chiếm nhiều không gian hơn mức có thể. UIKit quyết định view nào co trước bằng cách nào?

**Ý chính:** Compression Resistance + Content Hugging Priority.

**Ý diễn giải:**
Compression resistance quyết định mức độ view chống bị thu nhỏ. Content hugging quyết định mức độ view chống bị kéo lớn hơn intrinsic size.

**Ví dụ:**

```swift
leftLabel.setContentCompressionResistancePriority(
    .required,
    for: .horizontal
)

rightLabel.setContentHuggingPriority(
    .required,
    for: .horizontal
)
```

---

## 7. Khi chạy app, console báo hệ thống không thể thỏa một số constraint. Bạn sẽ tìm nguyên nhân từ đâu?

**Ý chính:** Unsatisfiable Constraints + symbolic breakpoint + constraint identification.

**Ý diễn giải:**
Đầu tiên đọc log để xác định constraint nào bị phá. Sau đó kiểm tra hierarchy, priorities và các constraint mâu thuẫn. Có thể đặt symbolic breakpoint vào `UIViewAlertForUnsatisfiableConstraints`.

**Ví dụ:**

```swift
view.addConstraint(
    widthConstraint
)

widthConstraint.identifier = "ProfileAvatarWidth"
```

Khi log lỗi xuất hiện, identifier giúp tìm constraint nhanh hơn.

## 8. Bạn cần thay đổi layout bằng animation. Nếu chỉ thay constraint mà không làm gì thêm, vì sao UI thường nhảy ngay lập tức thay vì animate?

**Ý chính:** Constraint update + `layoutIfNeeded()` trong animation block.

**Ý diễn giải:**
Việc thay constraint chỉ cập nhật trạng thái layout. Để Core Animation nội suy frame từ trạng thái cũ sang mới, cần buộc layout trong animation block.

**Ví dụ:**

```swift
isExpanded = true

expandedConstraint.isActive = true
collapsedConstraint.isActive = false

UIView.animate(withDuration: 0.3) {
    self.view.layoutIfNeeded()
}
```

---

## 9. `setNeedsLayout()` và `layoutIfNeeded()` khác nhau ở thời điểm thực thi như thế nào?

**Ý chính:** `setNeedsLayout` = đánh dấu để layout sau; `layoutIfNeeded` = yêu cầu layout ngay nếu cần.

**Ý diễn giải:**
`setNeedsLayout()` không ép layout ngay. UIKit sẽ xử lý ở layout pass tiếp theo. `layoutIfNeeded()` được dùng khi cần geometry mới ngay tại thời điểm hiện tại, đặc biệt trong animation.

**Ví dụ:**

```swift
view.setNeedsLayout()

// Khi cần frame mới ngay
view.layoutIfNeeded()
```

## 10. Một custom view có kích thước phụ thuộc vào nội dung bên trong. Bạn sẽ để Auto Layout biết kích thước tự nhiên của nó bằng cách nào?

**Ý chính:** Override `intrinsicContentSize`.

**Ý diễn giải:**
Custom view có thể cung cấp kích thước tự nhiên để Auto Layout sử dụng. Khi content thay đổi, có thể gọi `invalidateIntrinsicContentSize()`.

**Ví dụ:**

```swift
final class BadgeView: UIView {

    var text: String = "" {
        didSet {
            invalidateIntrinsicContentSize()
        }
    }

    override var intrinsicContentSize: CGSize {
        CGSize(
            width: text.count * 10 + 20,
            height: 32
        )
    }
}
```

# Chủ đề: UITableView / UICollectionView

## 11. Một danh sách có hàng nghìn dòng nhưng bạn không muốn tạo hàng nghìn cell ngay từ đầu. Cơ chế nào giúp UIKit giải quyết việc này?

**Ý chính:** Cell reuse.

**Ý diễn giải:**
UIKit chỉ giữ số lượng cell cần thiết cho vùng hiển thị và một vùng gần đó. Khi cell rời màn hình, nó được đưa vào reuse pool và dùng lại cho item khác.

**Ví dụ:**

```swift
let cell = tableView.dequeueReusableCell(
    withIdentifier: "Cell",
    for: indexPath
)
```

---

## 12. Một cell hiển thị ảnh của item A, sau khi scroll nhanh lại xuất hiện ảnh của item B. Nguyên nhân thường là gì?

**Ý chính:** Reuse + asynchronous result không còn thuộc cell/item hiện tại.

**Ý diễn giải:**
Request của item cũ có thể hoàn thành sau khi cell đã được reuse cho item mới. Kết quả cũ lúc đó ghi nhầm vào cell mới. Cần cancel request hoặc kiểm tra identity trước khi apply kết quả.

**Ví dụ:**

```swift
final class ImageCell: UITableViewCell {

    var imageTask: Task<Void, Never>?

    override func prepareForReuse() {
        super.prepareForReuse()

        imageTask?.cancel()
        imageTask = nil
        imageView?.image = nil
    }
}
```

---

## 13. Vì sao cần reset trạng thái cell trong `prepareForReuse()`?

**Ý chính:** Reusable state phải được làm sạch.

**Ý diễn giải:**
Cell được dùng lại cho item khác. Nếu không reset image, selection, hidden state hoặc async task, dữ liệu của item cũ có thể xuất hiện ở item mới.

**Ví dụ:**

```swift
override func prepareForReuse() {
    super.prepareForReuse()

    titleLabel.text = nil
    subtitleLabel.text = nil
    iconView.image = nil
    imageTask?.cancel()
}
```

---

## 14. Bạn muốn cập nhật một danh sách phức tạp mà không tự quản lý insert/delete/move index thủ công. Bạn sẽ làm thế nào?

**Ý chính:** `UICollectionViewDiffableDataSource`.

**Ý diễn giải:**
Diffable data source sử dụng snapshot để mô tả trạng thái danh sách. UIKit tự tính phần thay đổi dựa trên identity của item và section.

**Ví dụ:**

```swift
var snapshot = NSDiffableDataSourceSnapshot<Section, Item>()

snapshot.appendSections([.main])
snapshot.appendItems(items)

dataSource.apply(snapshot, animatingDifferences: true)
```

---

## 15. Vì sao identity của item phải ổn định khi dùng diffable data source?

**Ý chính:** Identity quyết định item nào là cùng một item.

**Ý diễn giải:**
Diffable cần biết item cũ và item mới có phải cùng entity hay không. Nếu identity thay đổi ngẫu nhiên, UIKit sẽ coi chúng là item mới và mất continuity của UI.

**Ví dụ:**

```swift
struct Item: Hashable {
    let id: UUID
    let title: String
}
```

Không nên tạo ID mới mỗi lần snapshot.

## 16. Bạn có một danh sách lớn và muốn tải dữ liệu trước khi người dùng cuộn tới. Cơ chế nào phù hợp?

**Ý chính:** Prefetching.

**Ý diễn giải:**
Prefetching cho phép chuẩn bị dữ liệu trước khi cell cần hiển thị. Nó có thể giảm cảm giác chờ khi scrolling, nhưng phải kết hợp cancellation và giới hạn concurrency.

**Ví dụ:**

```swift
func tableView(
    _ tableView: UITableView,
    prefetchRowsAt indexPaths: [IndexPath]
) {
    for indexPath in indexPaths {
        preload(indexPath)
    }
}
```

---

## 17. Khi nào prefetching có thể làm performance tệ hơn thay vì tốt hơn?

**Ý chính:** Over-prefetching → network, memory, CPU lãng phí.

**Ý diễn giải:**
Nếu preload quá nhiều dữ liệu hoặc người dùng scroll theo hướng khác, công việc đã preload trở thành waste. Senior cần cân bằng latency và resource usage.

**Ví dụ:**

```swift
func tableView(
    _ tableView: UITableView,
    cancelPrefetchingForRowsAt indexPaths: [IndexPath]
) {
    for indexPath in indexPaths {
        cancelPreload(indexPath)
    }
}
```

# Chủ đề: Responder Chain & Event Handling

## 18. Một button không tự xử lý được một action và hệ thống vẫn tìm được object khác để xử lý. UIKit thực hiện việc đó như thế nào?

**Ý chính:** Responder Chain.

**Ý diễn giải:**
UIKit truyền event/action qua chuỗi responder. Nếu responder hiện tại không xử lý, hệ thống tìm responder tiếp theo như view superview, view controller, window hoặc application tùy event.

**Ví dụ:**

```swift
override var next: UIResponder? {
    return superview
}
```

---

## 19. Vì sao hiểu responder chain có thể giúp bạn giảm việc truyền callback qua nhiều tầng UI?

**Ý chính:** Event routing qua responder chain.

**Ý diễn giải:**
Một số action có thể được xử lý bởi responder ở cấp cao hơn thay vì mỗi child phải giữ callback reference tới parent. Điều này có thể giảm coupling nếu dùng đúng phạm vi.

**Ví dụ:**

```swift
@objc func saveDocument(_ sender: Any) {
    print("Save")
}
```

Action có thể được route qua responder chain nếu target phù hợp.

---

## 20. Bạn cần phát hiện một thao tác kéo, vuốt hoặc pinch thay vì chỉ nhận touch thô. Bạn sẽ dùng cách nào?

**Ý chính:** Gesture Recognizer.

**Ý diễn giải:**
Gesture recognizer đóng gói pattern của touch như tap, pan, pinch, rotation và swipe. Nó dễ kết hợp với view hierarchy hơn so với tự xử lý toàn bộ touch sequence.

**Ví dụ:**

```swift
let pan = UIPanGestureRecognizer(
    target: self,
    action: #selector(handlePan)
)

view.addGestureRecognizer(pan)

@objc
private func handlePan(_ gesture: UIPanGestureRecognizer) {
    let translation = gesture.translation(in: view)
    print(translation)
}
```

---

## 21. Hai gesture trên cùng một view xung đột với nhau. Bạn sẽ kiểm soát việc này thế nào?

**Ý chính:** Gesture delegate + simultaneous recognition/failure relationships.

**Ý diễn giải:**
Có thể quyết định gesture nào được nhận đồng thời, gesture nào phải chờ gesture khác fail, hoặc gesture nào được ưu tiên.

**Ví dụ:**

```swift
func gestureRecognizer(
    _ gestureRecognizer: UIGestureRecognizer,
    shouldRecognizeSimultaneouslyWith otherGestureRecognizer: UIGestureRecognizer
) -> Bool {
    true
}
```

---

## 22. Tại sao việc tự override touch event trong mọi view thường không phải lựa chọn đầu tiên?

**Ý chính:** Gesture recognizer giúp tách interaction logic khỏi raw touch handling.

**Ý diễn giải:**
`touchesBegan`, `touchesMoved`... rất low-level. Nếu chỉ cần tap/pan/swipe/pinch, gesture recognizer dễ đọc, tái sử dụng và compose hơn.

**Ví dụ:**

```swift
override func touchesBegan(
    _ touches: Set<UITouch>,
    with event: UIEvent?
) {
    super.touchesBegan(touches, with: event)
}
```

# Chủ đề: Navigation & Presentation

## 23. Bạn cần mở màn hình chi tiết và muốn người dùng có thể quay lại màn hình trước bằng back button. Bạn sẽ chọn cơ chế nào?

**Ý chính:** Navigation stack + `push`.

**Ý diễn giải:**
Push đưa controller vào navigation stack. Navigation controller quản lý back navigation và stack history.

**Ví dụ:**

```swift
let detailVC = DetailViewController()

navigationController?.pushViewController(
    detailVC,
    animated: true
)
```

---

## 24. Một màn hình chỉ là luồng tạm thời như login, share hoặc chọn item. Tại sao presentation thường phù hợp hơn push?

**Ý chính:** Modal presentation.

**Ý diễn giải:**
Presentation thể hiện một flow tạm thời hoặc task độc lập với navigation stack chính. Sau khi hoàn thành, flow có thể dismiss toàn bộ.

**Ví dụ:**

```swift
let vc = LoginViewController()

present(
    vc,
    animated: true
)
```

---

## 25. Khi dismiss một màn hình modal, bạn cần trả kết quả về màn hình gọi. Bạn sẽ thiết kế communication như thế nào?

**Ý chính:** Delegate / closure / shared state tùy ownership.

**Ý diễn giải:**
Không nên để child trực tiếp biết quá nhiều về parent. Với flow đơn giản có thể dùng closure; flow phức tạp có thể dùng delegate hoặc coordinator.

**Ví dụ:**

```swift
final class PickerViewController: UIViewController {

    var onSelected: ((String) -> Void)?

    func didSelect(_ value: String) {
        onSelected?(value)
        dismiss(animated: true)
    }
}
```

---

## 26. Một controller vừa tạo dependency, vừa push controller tiếp theo, vừa xử lý business flow. Vấn đề architecture nào đang xuất hiện?

**Ý chính:** High coupling + responsibility overload.

**Ý diễn giải:**
View controller đang trở thành nơi chứa composition, navigation và business logic. Có thể tách navigation thành coordinator/router và business logic thành ViewModel/use case/service.

**Ví dụ:**

```swift
final class ProfileCoordinator {

    func showDetail(id: Int) {
        let vc = DetailViewController(id: id)
        navigationController.pushViewController(
            vc,
            animated: true
        )
    }
}
```

# Chủ đề: Animation & CALayer

## 27. Một view có thể thay đổi opacity, position hoặc transform rất mượt mà mà không cần tự quản lý từng frame. Thành phần nào chịu trách nhiệm rendering?

**Ý chính:** Core Animation + `CALayer`.

**Ý diễn giải:**
UIView sử dụng CALayer cho rendering. Các property phù hợp có thể được Core Animation animate trên layer, giúp animation chạy hiệu quả.

**Ví dụ:**

```swift
UIView.animate(withDuration: 0.3) {
    self.view.alpha = 0
}
```

---

## 28. Tại sao animation có thể trông như đã chạy xong trong khi giá trị thật của property chưa đổi?

**Ý chính:** Model layer vs presentation layer.

**Ý diễn giải:**
Core Animation duy trì model state và presentation state. Presentation layer phản ánh trạng thái đang hiển thị trong quá trình animation, còn model layer chứa giá trị cuối mà app đã đặt.

**Ví dụ:**

```swift
view.layer.opacity = 0

let visibleOpacity = view.layer.presentation()?
    .opacity
```

Trong animation, `presentation()` có thể khác model value.

---

## 29. Một view có shadow phức tạp và scrolling rất nặng. Bạn sẽ tối ưu phần nào trước?

**Ý chính:** `shadowPath` + rendering cost.

**Ý diễn giải:**
Nếu shadow cần thiết và hình dạng biết trước, `shadowPath` giúp Core Animation tránh phải suy ra shape từ toàn bộ layer. Đây là một tối ưu rendering phổ biến.

**Ví dụ:**

```swift
let path = UIBezierPath(
    roundedRect: view.bounds,
    cornerRadius: 12
)

view.layer.shadowPath = path.cgPath
view.layer.shadowOpacity = 0.2
```

# Chủ đề: UIViewController Containment

## 30. Bạn cần xây dựng một màn hình lớn từ nhiều phần độc lập, mỗi phần có controller riêng và lifecycle riêng. Bạn sẽ làm thế nào mà không biến một UIViewController thành “God Object”?

**Ý chính:** `UIViewController containment`.

**Ý diễn giải:**
Một container controller có thể quản lý nhiều child view controller. Mỗi child chịu trách nhiệm phần UI của mình. Container quyết định hierarchy, layout và lifecycle coordination.

**Ví dụ:**

```swift
final class DashboardViewController: UIViewController {

    let header = HeaderViewController()
    let content = ContentViewController()

    override func viewDidLoad() {
        super.viewDidLoad()

        addChild(header)
        view.addSubview(header.view)
        header.didMove(toParent: self)

        addChild(content)
        view.addSubview(content.view)
        content.didMove(toParent: self)

        header.view.frame = CGRect(
            x: 0,
            y: 0,
            width: view.bounds.width,
            height: 100
        )

        content.view.frame = CGRect(
            x: 0,
            y: 100,
            width: view.bounds.width,
            height: view.bounds.height - 100
        )
    }
}
```

Containment đặc biệt phù hợp với dashboard, tab-like custom container, split UI và feature composition.

# Chủ đề: UIKit ↔ SwiftUI

## 31. Bạn có một custom UIKit component cũ nhưng muốn sử dụng nó bên trong SwiftUI. Bạn sẽ làm thế nào?

**Ý chính:** `UIViewRepresentable`.

**Ý diễn giải:**
`UIViewRepresentable` tạo bridge từ SwiftUI sang UIKit. `makeUIView` tạo UIKit view, `updateUIView` đồng bộ state từ SwiftUI xuống UIKit.

**Ví dụ:**

```swift
struct LegacyProgressView: UIViewRepresentable {

    var progress: Float

    func makeUIView(context: Context) -> UIProgressView {
        UIProgressView(progressViewStyle: .default)
    }

    func updateUIView(
        _ uiView: UIProgressView,
        context: Context
    ) {
        uiView.progress = progress
    }
}
```

Luồng:

```text
SwiftUI
   ↓
UIViewRepresentable
   ↓
UIKit UIView
```

## 32. Nếu UIKit delegate của một custom view cần trả callback về SwiftUI, bạn sẽ thiết kế bridge như thế nào?

**Ý chính:** Coordinator.

**Ý diễn giải:**
`Coordinator` đóng vai trò cầu nối giữa callback/delegate của UIKit và state/action phía SwiftUI. Nó tránh việc nhét logic delegate trực tiếp vào View value type.

**Ví dụ:**

```swift
struct SearchView: UIViewRepresentable {

    @Binding var text: String

    func makeCoordinator() -> Coordinator {
        Coordinator(self)
    }

    func makeUIView(context: Context) -> UISearchBar {
        let searchBar = UISearchBar()
        searchBar.delegate = context.coordinator
        return searchBar
    }

    func updateUIView(
        _ uiView: UISearchBar,
        context: Context
    ) {
        uiView.text = text
    }

    final class Coordinator: NSObject, UISearchBarDelegate {

        var parent: SearchView

        init(_ parent: SearchView) {
            self.parent = parent
        }

        func searchBar(
            _ searchBar: UISearchBar,
            textDidChange searchText: String
        ) {
            parent.text = searchText
        }
    }
}
```

## 33. Bạn có một SwiftUI screen mới nhưng toàn bộ navigation hiện tại vẫn dùng UIKit. Làm sao đưa SwiftUI vào mà không rewrite navigation?

**Ý chính:** `UIHostingController`.

**Ý diễn giải:**
`UIHostingController` bọc SwiftUI view thành một UIViewController. Vì vậy navigation controller hiện tại có thể push/present nó như controller bình thường.

**Ví dụ:**

```swift
let view = ProfileView()

let hostingController = UIHostingController(
    rootView: view
)

navigationController?.pushViewController(
    hostingController,
    animated: true
)
```

Luồng:

```text
UIKit
   ↓
UIHostingController
   ↓
SwiftUI
```

## 34. Khi bridge UIKit và SwiftUI, vì sao không nên để hai bên cùng sở hữu một source of truth?

**Ý chính:** Single source of truth.

**Ý diễn giải:**
Nếu UIKit có state riêng và SwiftUI có state riêng, hai bên dễ lệch nhau. Nên xác định một bên sở hữu state và bên còn lại nhận dữ liệu/callback để đồng bộ.

**Ví dụ:**

```swift
struct CounterView: UIViewRepresentable {

    @Binding var value: Int

    func makeUIView(context: Context) -> UILabel {
        UILabel()
    }

    func updateUIView(
        _ uiView: UILabel,
        context: Context
    ) {
        uiView.text = "\(value)"
    }
}
```

SwiftUI giữ source of truth, UIKit chỉ render.

## 35. UIKit component có internal state riêng. SwiftUI liên tục gọi `updateUIView`. Bạn cần tránh lỗi gì?

**Ý chính:** `updateUIView` phải idempotent và chỉ đồng bộ state cần thiết.

**Ý diễn giải:**
Không nên mỗi lần `updateUIView` lại reset toàn bộ UIKit state hoặc tạo side effect không cần thiết. `updateUIView` nên phản ánh state mới từ SwiftUI mà không phá lifecycle nội bộ của component.

**Ví dụ:**

```swift
func updateUIView(
    _ uiView: CustomUIKitView,
    context: Context
) {
    if uiView.value != value {
        uiView.value = value
    }
}
```

## 36. Một UIKit view cần callback về SwiftUI nhiều lần trong thời gian dài. Vì sao callback một lần và stream event cần cách bridge khác nhau?

**Ý chính:** One-shot callback vs continuous event stream.

**Ý diễn giải:**
Một completion chỉ trả về một kết quả có thể bridge bằng continuation. Event liên tục như typing, socket hoặc sensor cần callback/delegate, Combine hoặc `AsyncSequence` tùy architecture.

**Ví dụ:**

```swift
struct EventView: UIViewRepresentable {

    let onEvent: (String) -> Void

    func makeUIView(context: Context) -> UIKitEventView {
        let view = UIKitEventView()
        view.onEvent = onEvent
        return view
    }

    func updateUIView(
        _ uiView: UIKitEventView,
        context: Context
    ) {}
}
```

# CÁC CÂU SENIOR DỄ BỊ HỎI VẶN

## 37. Nếu `viewDidLoad` chỉ chạy một lần, tại sao bạn không đặt toàn bộ logic refresh vào đó?

**Ý chính:** Initialization ≠ refresh.

**Ý diễn giải:**
`viewDidLoad` phù hợp setup lifecycle một lần. Dữ liệu có thể stale sau khi quay lại màn hình, nên refresh phải dựa trên business requirement và lifecycle thích hợp.

**Ví dụ:**

```swift
override func viewDidLoad() {
    super.viewDidLoad()

    setupUI()
}

override func viewWillAppear(_ animated: Bool) {
    super.viewWillAppear(animated)

    refreshIfStale()
}
```

## 38. Một UITableView scroll mượt khi có 20 cell nhưng giật mạnh khi có 2.000 cell. Số lượng data có nhất thiết là nguyên nhân trực tiếp không?

**Ý chính:** Rendering/per-cell cost quan trọng hơn tổng số item.

**Ý diễn giải:**
UITableView đã có reuse, nên 2.000 item không có nghĩa 2.000 cell cùng nằm trong memory. Vấn đề thường nằm ở configure cell, image decode, layout, expensive calculation hoặc data loading.

**Ví dụ:**

```swift
func tableView(
    _ tableView: UITableView,
    cellForRowAt indexPath: IndexPath
) -> UITableViewCell {

    let cell = tableView.dequeueReusableCell(
        withIdentifier: "Cell",
        for: indexPath
    )

    // Tránh CPU-heavy work ở đây
    configure(cell, item: items[indexPath.row])

    return cell
}
```

## 39. Nếu một UIViewController giữ một child controller bằng property nhưng child lại giữ parent, bạn cần kiểm tra điều gì?

**Ý chính:** Ownership graph + retain cycle.

**Ý diễn giải:**
Containment có ownership semantics rõ, nhưng các custom back-reference không đúng kiểu có thể tạo cycle. Cần xác định child có thực sự cần sở hữu parent hay chỉ cần non-owning relationship.

**Ví dụ:**

```swift
final class ChildViewController: UIViewController {
    weak var parentController: ParentViewController?
}
```

## 40. Một màn hình UIKit đang được migrate dần sang SwiftUI. Bạn sẽ tránh “big bang rewrite” bằng chiến lược nào?

**Ý chính:** Incremental migration + interoperability boundary.

**Ý diễn giải:**
Không cần rewrite toàn màn hình cùng lúc. Có thể đưa từng component UIKit vào SwiftUI bằng `UIViewRepresentable`, hoặc đưa từng SwiftUI screen vào UIKit bằng `UIHostingController`. Xác định ownership state ở mỗi boundary để tránh hai hệ thống cùng điều khiển một state.

**Ví dụ:**

```swift
// UIKit → SwiftUI

let vc = UIHostingController(
    rootView: NewSwiftUIScreen()
)

navigationController?.pushViewController(
    vc,
    animated: true
)
```

Hoặc:

```swift
// SwiftUI → UIKit

struct LegacyComponent: UIViewRepresentable {

    func makeUIView(
        context: Context
    ) -> LegacyUIKitView {
        LegacyUIKitView()
    }

    func updateUIView(
        _ uiView: LegacyUIKitView,
        context: Context
    ) {}
}
```

```text
1. UIViewController lifecycle
   ↓
2. Auto Layout / Constraint
   ↓
3. Intrinsic Content Size
   ↓
4. UITableView / UICollectionView
   ↓
5. Reuse + async cell lifecycle
   ↓
6. Responder chain + Gesture
   ↓
7. Navigation / Presentation
   ↓
8. Animation / CALayer / Rendering
   ↓
9. UIViewController containment
   ↓
10. UIKit ↔ SwiftUI interoperability
```

```text
"UITableView có reuse cell."
```

Mà nên nâng lên:

```text

    ↓
Async request lifecycle
    ↓
prepareForReuse
    ↓
Cancel request
    ↓
Verify item identity
    ↓
Cache
    ↓
Decode/resize image
    ↓
Main-thread performance
```

```text

    ↓

    ↓
CHCR Priority
    ↓
Unsatisfiable Constraint
    ↓
Layout Pass
    ↓
layoutIfNeeded
    ↓
Animation
    ↓

```
