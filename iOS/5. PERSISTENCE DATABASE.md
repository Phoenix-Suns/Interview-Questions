# CHỦ ĐỀ 5: PERSISTENCE / DATABASE ⭐⭐⭐⭐

Senior iOS không chỉ cần biết “lưu dữ liệu ở đâu”, mà phải trả lời được:

> **Dữ liệu này tồn tại bao lâu? Ai là source of truth? Khi nào đọc memory, disk, database hay network? Khi schema thay đổi thì sao? Khi nhiều task cùng truy cập database thì sao?**

Một caching strategy điển hình:

```text
Memory Cache
      ↓
Disk Cache
      ↓
Database
      ↓
Network
```

Nhưng Senior phải hiểu rằng **không phải dữ liệu nào cũng cần đi qua cả 4 tầng**.

# I. USERDEFAULTS / KEYCHAIN

## 1. Bạn cần lưu một cờ cho biết user đã xem onboarding hay chưa. Bạn sẽ lưu ở đâu?

**Ý chính:** `UserDefaults` - small preferences/configuration.

**Ý diễn giải:**
UserDefaults phù hợp với các giá trị nhỏ như boolean, setting, selected option, app preference. Nó không phù hợp cho database lớn hoặc sensitive credentials.

**Ví dụ:**

```swift
UserDefaults.standard.set(
    true,
    forKey: "hasSeenOnboarding"
)

let hasSeen = UserDefaults.standard.bool(
    forKey: "hasSeenOnboarding"
)
```

---

## 2. Bạn cần lưu access token để người dùng đăng nhập lâu dài. Vì sao cách lưu thông thường không phù hợp?

**Ý chính:** `Keychain` - secure credential storage.

**Ý diễn giải:**
Access token là credential nên cần secure storage. UserDefaults chỉ là preference storage, không phải nơi phù hợp để bảo vệ secret.

**Ví dụ:**

```swift
let data = Data(accessToken.utf8)

let query: [String: Any] = [
    kSecClass as String:
        kSecClassGenericPassword,

    kSecAttrAccount as String:
        "access_token",

    kSecValueData as String:
        data
]

SecItemAdd(
    query as CFDictionary,
    nil
)
```

---

## 3. Nếu app bị uninstall nhưng một số dữ liệu secure vẫn có thể tồn tại, bạn cần hiểu điều gì?

**Ý chính:** `Keychain lifecycle` khác app sandbox lifecycle.

**Ý diễn giải:**
Dữ liệu trong app sandbox thường mất khi app bị uninstall, nhưng Keychain có lifecycle riêng và có thể tồn tại qua uninstall tùy cách lưu/configuration. Vì vậy không nên giả định uninstall luôn đồng nghĩa “xóa toàn bộ credential”.

**Ví dụ:**

```swift
let query: [String: Any] = [
    kSecClass as String:
        kSecClassGenericPassword,

    kSecAttrAccount as String:
        "refresh_token"
]
```

Nếu security requirement cần xóa credential trong một flow cụ thể, app phải chủ động xóa.

# II. FILEMANAGER / CODABLE PERSISTENCE

## 4. Bạn chỉ cần lưu một configuration object nhỏ xuống disk để đọc lại sau khi app khởi động. Bạn sẽ chọn giải pháp nào?

**Ý chính:** `Codable + FileManager`.

**Ý diễn giải:**
Với dữ liệu nhỏ, cấu trúc đơn giản và không cần query phức tạp, encode object thành JSON/Data rồi lưu file là cách đơn giản và dễ maintain.

**Ví dụ:**

```swift
struct AppSettings: Codable {
    let theme: String
    let fontSize: Int
}

let settings = AppSettings(
    theme: "dark",
    fontSize: 18
)

let data = try JSONEncoder().encode(settings)

let url = FileManager.default
    .urls(
        for: .applicationSupportDirectory,
        in: .userDomainMask
    )[0]
    .appendingPathComponent("settings.json")

try data.write(
    to: url,
    options: .atomic
)
```

Đọc lại:

```swift
let data = try Data(contentsOf: url)

let settings = try JSONDecoder()
    .decode(AppSettings.self, from: data)
```

---

## 5. Tại sao bạn không nên dùng một JSON file khổng lồ làm database cho hàng chục nghìn record?

**Ý chính:** `No indexing + full serialization + poor query/migration`.

**Ý diễn giải:**
Mỗi lần đọc/ghi có thể phải load và encode một lượng lớn dữ liệu. Không có query engine/index/transaction tốt như database. Khi data tăng, performance và consistency sẽ trở thành vấn đề.

**Ví dụ:**

```swift
// Không phù hợp cho 100.000 records
let data = try JSONEncoder().encode(
    hugeArray
)

try data.write(
    to: hugeFileURL
)
```

Với dataset lớn, database thường phù hợp hơn.

---

## 6. Nếu đang ghi một file mà app bị crash hoặc mất điện, làm sao giảm nguy cơ file trở thành dữ liệu dở dang?

**Ý chính:** `Atomic write`.

**Ý diễn giải:**
Ghi atomically giúp tránh việc file đích bị thay thế bởi nội dung chưa hoàn chỉnh. Tùy use case có thể cần temp file + atomic replace và transaction-like strategy.

**Ví dụ:**

```swift
try data.write(
    to: fileURL,
    options: .atomic
)
```

# III. CORE DATA / SWIFTDATA

## 7. Core Data khác SQLite ở mục tiêu sử dụng như thế nào?

**Ý chính:** Core Data là `object graph + persistence framework`; SQLite là `relational database engine`.

**Ý diễn giải:**
Core Data cung cấp model, change tracking, relationships, faulting, managed objects và persistence abstraction. SQLite chủ yếu là database engine với tables, rows, SQL.

**Ví dụ:**

```text
Core Data
    ↓
Managed Object Model
    ↓
NSManagedObjectContext
    ↓
Persistent Store
    ↓
SQLite
```

SQLite có thể là backing store của Core Data nhưng hai khái niệm không đồng nghĩa.

---

## 8. Vì sao không nên coi Core Data chỉ là “SQLite wrapper”?

**Ý chính:** Core Data quản lý `object graph`, lifecycle và context.

**Ý diễn giải:**
Core Data không chỉ cung cấp CRUD trên rows. Nó quản lý object identity, relationship, faulting, change tracking và context concurrency.

**Ví dụ:**

```swift
let request =
    NSFetchRequest<User>(
        entityName: "User"
    )

let users = try context.fetch(request)
```

Bạn đang làm việc với managed objects chứ không trực tiếp viết SQL cho từng thao tác.

---

## 9. Một managed object được fetch ở background context rồi truyền trực tiếp sang main context. Vì sao đây là vấn đề?

**Ý chính:** `Managed object context confinement`.

**Ý diễn giải:**
Managed object gắn với context của nó. Không nên tự do truyền managed object qua các concurrency boundary. Thường nên truyền `NSManagedObjectID` hoặc value model rồi fetch lại ở context đích.

**Ví dụ:**

```swift
backgroundContext.perform {
    let user = try? backgroundContext
        .fetch(request)
        .first

    let id = user?.objectID

    DispatchQueue.main.async {
        guard let id else { return }

        mainContext.perform {
            let user = mainContext
                .object(with: id)

            print(user)
        }
    }
}
```

# IV. CONCURRENCY / DATABASE SAFETY

## 10. Một database layer được gọi đồng thời từ nhiều task. Bạn sẽ kiểm soát concurrency ở đâu?

**Ý chính:** `Isolation boundary` + context/actor phù hợp.

**Ý diễn giải:**
Không nên để mọi caller tự lock database. Có thể cô lập data access bằng actor/service hoặc tuân thủ concurrency model của persistence framework. Với Core Data, phải dùng context đúng queue.

**Ví dụ:**

```swift
actor DatabaseStore {

    func save(_ user: User) async throws {
        // Serialize access
        try await persist(user)
    }
}
```

Hoặc với Core Data:

```swift
context.perform {
    // Context-owned work
}
```

---

## 11. Actor có phải thay thế hoàn toàn database transaction không?

**Ý chính:** Không. `Actor isolation` và `transaction` giải quyết hai vấn đề khác nhau.

**Ý diễn giải:**
Actor bảo vệ access từ concurrency perspective. Transaction đảm bảo một nhóm database operations có tính atomicity/consistency. Có thể cần cả hai.

**Ví dụ:**

```swift
actor Store {

    func transfer(
        from source: Account,
        to target: Account
    ) async throws {

        // Actor bảo vệ access

        try await database.transaction {
            // Transaction bảo đảm
            // cả hai mutation thành công
            // hoặc cùng rollback
        }
    }
}
```

---

## 12. Nếu hai task cùng ghi một record gần như đồng thời, bạn cần quan tâm điều gì?

**Ý chính:** `Race condition + lost update + transaction/conflict policy`.

**Ý diễn giải:**
Không chỉ quan tâm crash. Một task có thể ghi đè dữ liệu của task kia. Cần xác định serialization, versioning, optimistic locking hoặc transaction tùy database.

**Ví dụ:**

```text
Task A đọc balance = 100
Task B đọc balance = 100

A ghi 80
B ghi 70

Kết quả:
70

Thay vì kết quả business mong muốn sau cả hai operation.
```

# V. CACHE STRATEGY

## 13. Tại sao memory cache thường được kiểm tra trước database?

**Ý chính:** `Latency` và giảm I/O.

**Ý diễn giải:**
Memory access nhanh hơn disk/database và tránh parsing hoặc database query lặp lại. Nhưng memory cache có thể bị evict nên không phải source of truth.

**Ví dụ:**

```swift
final class ImageRepository {

    private let memoryCache =
        NSCache<NSURL, UIImage>()

    func image(
        for url: URL
    ) async throws -> UIImage {

        if let image =
            memoryCache.object(
                forKey: url as NSURL
            ) {
            return image
        }

        // tiếp tục disk/database/network
        return try await loadFromLowerLayer(url)
    }
}
```

---

## 14. Khi một item không có trong memory cache, bạn có nhất thiết phải gọi network ngay không?

**Ý chính:** `Multi-level cache`.

**Ý diễn giải:**
Không. Có thể kiểm tra disk cache hoặc database trước. Strategy phù hợp tùy freshness, latency và cost.

**Ví dụ:**

```text
Memory
   ↓ miss
Disk
   ↓ miss
Database
   ↓ miss
Network
```

Một implementation đơn giản:

```swift
func load(
    _ key: String
) async throws -> Data {

    if let value = memory.get(key) {
        return value
    }

    if let value = try await disk.get(key) {
        memory.set(key, value)
        return value
    }

    let value = try await network.fetch(key)

    memory.set(key, value)
    try await disk.set(key, value)

    return value
}
```

---

## 15. Cache invalidation khó vì sao?

**Ý chính:** `Freshness + ownership + invalidation policy`.

**Ý diễn giải:**
Cache càng nhiều layer càng dễ có dữ liệu cũ. Cần quyết định TTL, version, event-driven invalidation, server validation hoặc write-through/write-back strategy.

**Ví dụ:**

```swift
struct CachedValue<Value> {
    let value: Value
    let expiresAt: Date

    var isExpired: Bool {
        Date() >= expiresAt
    }
}
```

Ví dụ TTL:

```swift
let expiresAt =
    Date().addingTimeInterval(300)
```

# VI. MIGRATION

## 16. App đã có hàng triệu bản ghi trong production. Thêm một field bắt buộc vào database có thể nguy hiểm ở đâu?

**Ý chính:** `Schema migration + existing data compatibility`.

**Ý diễn giải:**
Database cũ không có field mới. Nếu field mới bắt buộc nhưng không có default/migration rule, app có thể fail khi mở store hoặc mất dữ liệu. Migration phải backward-compatible và được test với real historical schemas.

**Ví dụ:**

```text
Version 1

User
 ├── id
 └── name


Version 2

User
 ├── id
 ├── name
 └── age
```

Cần xác định:

```text
User cũ
   ↓
Migration
   ↓
age = default/mapped value
```

---

## 17. Migration thành công ở môi trường test nhưng production vẫn có thể fail. Vì sao?

**Ý chính:** `Historical data + migration paths`.

**Ý diễn giải:**
Test database thường sạch và chỉ có một schema. Production có thể có dữ liệu từ rất nhiều version cũ, interrupted migration, corrupted data hoặc edge cases chưa từng xuất hiện trong fixture.

**Ví dụ:**

```text
Production:

V1 → V2 → V3 → V4

Không nên chỉ test:

V3 → V4
```

Cần kiểm tra các path/schema thực tế còn tồn tại.

---

## 18. Khi nào nên dùng lightweight migration và khi nào cần custom migration?

**Ý chính:** `Schema change đơn giản` vs `data transformation phức tạp`.

**Ý diễn giải:**
Lightweight migration phù hợp những thay đổi Core Data có thể tự suy luận như thêm attribute đơn giản. Khi cần transform dữ liệu hoặc thay đổi structure phức tạp, custom migration có thể cần thiết.

**Ví dụ:**

```text
Simple:

Add optional field
Rename with mapping

Complex:

Split 1 entity
    ↓
2 entities

Hoặc

old field:
"John Smith"

↓ migration

firstName:
"John"

lastName:
"Smith"
```

# VII. SOURCE OF TRUTH / OFFLINE-FIRST

## 19. Nếu app vừa có database local vừa có network, dữ liệu hiển thị trên UI nên lấy từ đâu?

**Ý chính:** `Single source of truth`.

**Ý diễn giải:**
Trong offline-first architecture, database local thường là source of truth cho UI. Network cập nhật local database, sau đó UI observe database. Điều này tránh việc UI phải ghép state từ hai nguồn khác nhau.

**Ví dụ:**

```text
Network
   ↓
Repository
   ↓
Database
   ↓
Observable state
   ↓
UI
```

Thay vì:

```text
Network ──┐
          ├──→ UI
Database ─┘
```

vì rất dễ xảy ra inconsistent state.

---

## 20. User cập nhật dữ liệu khi offline, sau đó online trở lại. Bạn sẽ thiết kế persistence flow như thế nào?

**Ý chính:** `Offline-first + local write + sync queue`.

**Ý diễn giải:**
Thay vì chờ server mới cập nhật UI, ghi thay đổi local trước, đánh dấu pending sync, sau đó đồng bộ khi network có lại. Cần conflict policy nếu server và client cùng thay đổi.

**Ví dụ:**

```text
User Edit
   ↓
Local Database
   ↓
UI cập nhật ngay
   ↓
Pending Sync
   ↓
Network available
   ↓
Sync Server
   ↓
Success / Conflict
```

Một model đơn giản:

```swift
struct PendingChange {
    let id: UUID
    let entityID: UUID
    let createdAt: Date
    let operation: Operation
}
```

# VIII. SENIOR SCENARIOS

## 21. User mở màn hình danh sách. Bạn muốn dữ liệu xuất hiện nhanh nhưng vẫn phải đảm bảo dữ liệu cuối cùng mới nhất. Bạn sẽ thiết kế thế nào?

**Ý chính:** `Stale-while-revalidate`.

**Ý diễn giải:**
Đầu tiên trả dữ liệu local/cache để UI hiển thị ngay. Sau đó chạy network ở background, cập nhật database/cache và để UI nhận dữ liệu mới.

**Ví dụ:**

```text
Open Screen
    ↓
Memory Cache?
    ↓ miss
Database
    ↓
Show UI immediately
    ↓
Network refresh
    ↓
Save Database
    ↓
UI updates
```

Code ý tưởng:

```swift
func load() async throws {

    if let local = try await database.products() {
        await MainActor.run {
            state = .loaded(local)
        }
    }

    let remote = try await api.products()

    try await database.save(remote)

    let latest = try await database.products()

    await MainActor.run {
        state = .loaded(latest)
    }
}
```

## 22. Bạn có nên lưu mọi API response vào database để “sau này offline dùng được”?

**Ý chính:** Không. `Persistence policy` phải dựa trên product requirement.

**Ý diễn giải:**
Lưu tất cả response làm database phình to, migration khó và cache invalidation phức tạp. Chỉ persist dữ liệu có giá trị offline hoặc cần lifecycle dài.

**Ví dụ:**

```text
Persist:
✓ User profile
✓ Orders
✓ Messages
✓ Offline documents

Không nhất thiết persist:
✗ One-time recommendation
✗ Temporary search result
✗ Short-lived telemetry
```

## 23. Một cache chứa dữ liệu user A nhưng sau login user B lại thấy dữ liệu cũ của A. Bạn sẽ tìm lỗi ở đâu?

**Ý chính:** `User-scoped cache + logout invalidation`.

**Ý diễn giải:**
Cache key có thể không gắn user identity hoặc cache không được clear khi session đổi. User-specific data nên có scope rõ.

**Ví dụ:**

```swift
struct CacheKey: Hashable {
    let userID: String
    let resourceID: String
}
```

Thay vì:

```swift
let key = resourceID
```

nên có:

```swift
let key = CacheKey(
    userID: currentUser.id,
    resourceID: resourceID
)
```

## 24. Database query nhanh trong simulator nhưng chậm trên thiết bị production với dữ liệu lớn. Bạn nghi ngờ gì?

**Ý chính:** `Dataset size + indexes + fetch size + query plan`.

**Ý diễn giải:**
Dataset thực tế lớn hơn nhiều. Có thể query chưa có index, fetch quá nhiều object, relationship faulting hoặc sort/filter tốn CPU.

**Ví dụ:**

```swift
request.fetchLimit = 50

request.sortDescriptors = [
    NSSortDescriptor(
        key: "createdAt",
        ascending: false
    )
]
```

Không nên mặc định:

```swift
let all = try context.fetch(
    hugeRequest
)
```

rồi mới filter trong memory.

## 25. Bạn cần chọn giữa Memory Cache, Disk Cache, Database và Network. Bạn sẽ đưa ra quyết định thế nào?

**Ý chính:** `Latency + persistence + size + freshness + source of truth`.

**Ý diễn giải:**

```text
Memory Cache
→ nhanh nhất
→ volatile
→ dữ liệu recreate được

Disk Cache
→ persistent hơn
→ phù hợp file/blob
→ không phải source of truth

Database
→ query/relationship/persistent state
→ phù hợp business data

Network
→ authoritative/fresh data
→ latency + connectivity phụ thuộc hệ thống
```

Một strategy phổ biến:

```text
Request
   ↓
Memory
   ↓ miss
Disk/Database
   ↓
Network
   ↓
Update persistent layer
   ↓
Update memory cache
   ↓
UI
```

Không phải mọi feature đều cần tất cả tầng.

# CÁC CÂU BẪY SENIOR

## 27. “NSCache là database nhẹ.” Đúng hay sai?

**Ý chính:** Sai. `NSCache` là memory cache.

**Ý diễn giải:**
NSCache có thể evict object khi memory pressure. App không được coi cache là persistent source of truth.

**Ví dụ:**

```swift
let cache = NSCache<NSURL, NSData>()

cache.setObject(
    data as NSData,
    forKey: url as NSURL
)
```

---

## 28. “Core Data dùng SQLite nên biết SQL là đủ.” Đúng hay sai?

**Ý chính:** Sai.

**Ý diễn giải:**
Core Data có object graph, context, managed object lifecycle, faulting và relationship semantics riêng. Biết SQL giúp nhưng không thay thế hiểu Core Data.

---

## 29. “Actor là đủ để database thread-safe.” Đúng hay sai?

**Ý chính:** Chưa đủ. `Framework concurrency rules` vẫn phải được tuân thủ.

**Ý diễn giải:**
Actor có thể serialize access tới service, nhưng nếu bên trong sử dụng Core Data thì context vẫn phải được truy cập đúng queue/concurrency model. Actor không biến mọi framework object thành Sendable.

---

## 30. “Cache hit nghĩa dữ liệu đúng.” Đúng hay sai?

**Ý chính:** Sai. `Hit ≠ fresh`.

**Ý diễn giải:**
Cache hit chỉ nghĩa có dữ liệu. Dữ liệu có thể stale, expired hoặc thuộc user/session khác nếu key/invalidation sai.

**Ví dụ:**

```swift
guard cached.expiresAt > Date() else {
    return try await refresh()
}
```

# CACHING STRATEGY SENIOR

Một strategy tương đối hoàn chỉnh:

```text
                         Request
                            │
                            ↓
                    ┌───────────────┐
                    │ Memory Cache? │
                    └───────┬───────┘
                            │
                     HIT ───┴─── MISS
                     │             │
                     ↓             ↓
                    UI       ┌────────────┐
                             │ Disk Cache?│
                             └──────┬─────┘
                                    │
                              HIT ──┴── MISS
                              │             │
                              ↓             ↓
                             UI      ┌────────────┐
                                     │  Database? │
                                     └──────┬─────┘
                                            │
                                      HIT ──┴── MISS
                                      │             │
                                      ↓             ↓
                                     UI         Network
                                                   │
                                                   ↓
                                             Validate / Decode
                                                   │
                                                   ↓
                                               Database
                                                   │
                                                   ↓
                                             Memory Cache
                                                   │
                                                   ↓
                                                   UI
```

Nhưng nếu dữ liệu yêu cầu **freshness cao**, strategy có thể đổi thành:

```text
Database
   ↓
Show stale data
   ↓
Network refresh
   ↓
Database update
   ↓
UI update
```

Đây chính là tư duy **stale-while-revalidate / offline-first**.

# 10 ĐIỂM PERSISTENCE SENIOR PHẢI NẮM

```text
1. UserDefaults
   → preferences

2. Keychain
   → credentials

3. FileManager
   → files/blobs

4. Codable
   → simple persistence

5. Core Data / SwiftData
   → structured persistent data

6. SQLite
   → relational database engine

7. Memory/Disk Cache
   → performance, not source of truth

8. Migration
   → schema evolution

9. Concurrency
   → context isolation / actor / transactions

10. Source of Truth
   → tránh UI ghép state từ nhiều nguồn
```

# CÔNG THỨC TRẢ LỜI SENIOR

Khi interviewer hỏi:

> **“Bạn lưu dữ liệu này ở đâu?”**

Đừng chỉ trả lời:

```text
"Core Data."
```

Hãy phân tích:

```text
Dữ liệu là gì?
    ↓
Sensitive?
    ↓
Kích thước bao nhiêu?
    ↓
Cần query không?
    ↓
Cần persistent bao lâu?
    ↓
Có offline không?
    ↓
Freshness yêu cầu thế nào?
    ↓
Có nhiều concurrent writer không?
    ↓
Có migration không?
    ↓
Ai là source of truth?
```

Sau đó mới chọn:

```text
Preference
    → UserDefaults

Credential
    → Keychain

Blob/File
    → FileManager

Simple Snapshot
    → Codable + File

Structured Data
    → Core Data / SwiftData / SQLite

Temporary Fast Data
    → Memory/Disk Cache

Authoritative Fresh Data
    → Network
```

Điểm quan trọng nhất ở Senior là hiểu:

> **Persistence không chỉ là “lưu dữ liệu”. Nó là bài toán về lifecycle, consistency, source of truth, performance, concurrency và data evolution.**
