# CHỦ ĐỀ 6: ARCHITECTURE ⭐⭐⭐⭐⭐

Đây là một trong những phần quan trọng nhất để phân biệt **Senior iOS** với người chỉ biết sử dụng framework.

Mục tiêu không phải nhớ tên `MVC`, `MVVM`, `MVI`, `VIPER`, `Clean Architecture`, mà phải trả lời được:

> **Tại sao cần layer này? Nó giải quyết vấn đề gì? Khi nào không cần? Trade-off là gì?**

---

# I. MVC / MVVM / MVI / VIPER

## 1. Một ViewController bắt đầu có rất nhiều code liên quan đến API, parsing, validation, navigation và UI. Vấn đề lớn nhất của thiết kế này là gì?

**Ý chính:** `Massive View Controller` - quá nhiều responsibility, coupling cao, khó test.

**Ý diễn giải:**
ViewController đang đồng thời xử lý presentation, business logic, networking và navigation. Khi mọi thứ nằm chung một nơi, code khó đọc, khó test và mỗi thay đổi có thể ảnh hưởng nhiều behavior khác nhau.

**Ví dụ:**

```swift
final class ProfileViewController: UIViewController {

    func loadProfile() {
        URLSession.shared.dataTask(with: url) { data, _, _ in
            // Network
            // Decode
            // Business logic
            // Update UI
            // Navigation
        }.resume()
    }
}
```

Một Senior sẽ bắt đầu tách responsibility thay vì chỉ làm ViewController nhỏ hơn bằng cách chia file.

---

## 2. Nếu ViewController chỉ nên chịu trách nhiệm hiển thị và nhận user interaction, logic nào nên được đưa ra ngoài?

**Ý chính:** `ViewModel` / `Use Case` / `Repository` tùy responsibility.

**Ý diễn giải:**
UI rendering thuộc presentation. Business rule thuộc domain/use case. Data access thuộc repository/data layer. Việc tách phải dựa trên responsibility chứ không phải cứ thấy code dài là tạo thêm layer.

**Ví dụ:**

```swift
final class ProfileViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }

    func load() async throws -> User {
        try await repository.loadUser()
    }
}
```

---

## 3. MVVM giải quyết vấn đề gì mà MVC truyền thống thường gặp?

**Ý chính:** Tách `View` khỏi `presentation logic`, giảm `ViewController responsibility`.

**Ý diễn giải:**
ViewModel giữ state và presentation logic để ViewController/View chỉ tập trung hiển thị và chuyển user action. Tuy nhiên MVVM không tự động làm code tốt nếu ViewModel trở thành một “God Object”.

**Ví dụ:**

```swift
final class ProfileViewModel {

    var title: String {
        "Profile"
    }

    func didTapLogout() {
        // Presentation logic
    }
}
```

---

## 4. Tại sao một ViewModel rất lớn vẫn có thể là một vấn đề dù project đã dùng MVVM?

**Ý chính:** `Massive ViewModel` - sai responsibility vẫn tồn tại.

**Ý diễn giải:**
Chuyển toàn bộ code từ ViewController sang ViewModel chỉ đổi vị trí của vấn đề. Nếu ViewModel vừa gọi API, xử lý database, business rule, navigation, analytics và formatting thì architecture vẫn coupling cao.

**Ví dụ:**

```swift
final class ViewModel {

    func load() {
        // API
        // Database
        // Business logic
        // Analytics
        // Navigation
        // Formatting
        // ...
    }
}
```

---

## 5. Nếu state của ứng dụng cần đi theo một hướng rõ ràng từ user action đến UI, kiến trúc nào thường phù hợp hơn?

**Ý chính:** `MVI` - unidirectional data flow.

**Ý diễn giải:**
MVI thường tổ chức theo:

```text
Intent
  ↓
Reducer
  ↓
State
  ↓
View
```

Điểm mạnh là state transition rõ ràng, dễ trace và debug. Trade-off là có thể verbose hơn MVVM.

**Ví dụ:**

```swift
enum Intent {
    case load
    case retry
}

enum State {
    case idle
    case loading
    case loaded
    case error
}

func reduce(
    state: State,
    intent: Intent
) -> State {

    switch intent {
    case .load:
        return .loading

    case .retry:
        return .loading
    }
}
```

---

## 6. VIPER khác MVVM chủ yếu ở mức độ tách responsibility như thế nào?

**Ý chính:** VIPER tách thành `View`, `Interactor`, `Presenter`, `Entity`, `Router`.

**Ý diễn giải:**
VIPER tách rất rõ presentation, business logic và navigation. Nó có thể phù hợp hệ thống lớn nhiều team nhưng đổi lại nhiều boilerplate và ceremony.

**Ví dụ:**

```swift
protocol ProfilePresenter {
    func didLoad()
}

protocol ProfileInteractor {
    func loadProfile()
}

protocol ProfileRouter {
    func showDetail()
}
```

---

## 7. Vì sao Senior không nên chọn VIPER chỉ vì project lớn?

**Ý chính:** Architecture phải dựa trên `complexity`, `change rate`, `team`, `testability`, không dựa trên size.

**Ý diễn giải:**
Project lớn nhưng feature đơn giản vẫn có thể bị over-engineering. Ngược lại, một module nhỏ nhưng business rule cực kỳ phức tạp có thể cần abstraction mạnh.

**Ví dụ:**

```swift
// Một feature CRUD rất đơn giản

struct SettingsView {
    var body: some View {
        Text("Settings")
    }
}
```

Không cần tạo 5 layer chỉ để đọc một setting.

# II. CLEAN ARCHITECTURE

## 8. Vì sao Clean Architecture thường chia code thành nhiều layer thay vì để feature gọi thẳng database và network?

**Ý chính:** `Separation of concerns` + `Dependency Inversion`.

**Ý diễn giải:**
Mỗi layer có responsibility riêng. Domain không cần biết dữ liệu đến từ API, database hay mock. Điều này giúp thay implementation mà ít ảnh hưởng business logic.

**Ví dụ:**

```text
View
  ↓
ViewModel
  ↓
UseCase
  ↓
Repository
  ↓
DataSource
  ├── Network
  └── Database
```

---

## 9. Domain layer nên biết URLSession hay Core Data không?

**Ý chính:** Không nên. `Domain` phải độc lập framework/infrastructure.

**Ý diễn giải:**
Domain chứa business rules và abstraction. Nếu domain trực tiếp import URLSession hoặc Core Data, dependency direction bị đảo và test/migration khó hơn.

**Ví dụ:**

```swift
protocol UserRepository {
    func loadUser() async throws -> User
}

struct GetUser {
    let repository: UserRepository

    func execute() async throws -> User {
        try await repository.loadUser()
    }
}
```

---

## 10. Repository thực sự giải quyết vấn đề gì?

**Ý chính:** `Abstraction over data sources`.

**Ý diễn giải:**
Repository che giấu việc dữ liệu đến từ network, database, cache hay nhiều nguồn kết hợp. Business layer chỉ quan tâm “lấy user”, không cần biết cách lấy.

**Ví dụ:**

```swift
protocol UserRepository {
    func user(id: Int) async throws -> User
}

struct UserRepositoryImpl: UserRepository {

    let api: API
    let database: Database

    func user(id: Int) async throws -> User {
        if let local = try await database.user(id: id) {
            return local
        }

        let remote = try await api.user(id: id)

        try await database.save(remote)

        return remote
    }
}
```

---

## 11. Repository có phải lúc nào cũng cần tồn tại không?

**Ý chính:** Không. Chỉ cần khi có `data abstraction`, nhiều data source hoặc policy cần encapsulate.

**Ý diễn giải:**
Nếu feature chỉ đọc một nguồn đơn giản và không có business/data complexity, tạo Repository chỉ để gọi một method có thể là unnecessary abstraction.

**Ví dụ:**

```swift
struct SettingsService {
    func isEnabled() -> Bool {
        UserDefaults.standard.bool(forKey: "enabled")
    }
}
```

Không nhất thiết phải tạo:

```text
View
↓
VM
↓
UseCase
↓
Repository
↓
DataSource
↓
UserDefaults
```

cho một operation đơn giản như vậy.

---

## 12. Use Case giải quyết vấn đề gì mà Repository không giải quyết?

**Ý chính:** `Business operation / business rule`.

**Ý diễn giải:**
Repository trả lời câu hỏi “dữ liệu lấy ở đâu”. Use Case trả lời “business operation cần làm gì”. Một use case có thể phối hợp nhiều repository/service.

**Ví dụ:**

```swift
struct CheckoutUseCase {

    let cartRepository: CartRepository
    let paymentService: PaymentService

    func execute() async throws {

        let cart = try await cartRepository.currentCart()

        try await paymentService.pay(
            amount: cart.total
        )
    }
}
```

---

## 13. Một Use Case chỉ gọi đúng một repository rồi return kết quả. Có chắc cần Use Case không?

**Ý chính:** Không. Tránh `pass-through abstraction`.

**Ý diễn giải:**
Nếu Use Case không thêm business rule, transformation hoặc orchestration, nó có thể chỉ tăng boilerplate. Senior cần đánh giá abstraction có tạo giá trị hay không.

**Ví dụ:**

```swift
struct GetUserUseCase {

    let repository: UserRepository

    func execute() async throws -> User {
        try await repository.user()
    }
}
```

Nếu hoàn toàn không có logic, layer này có thể là unnecessary.

# III. DEPENDENCY INVERSION / DEPENDENCY INJECTION

## 14. Một ViewModel trực tiếp khởi tạo URLSession, database và analytics bên trong initializer. Vấn đề gì xảy ra?

**Ý chính:** `Tight coupling` + `hidden concrete dependencies` + khó test.

**Ý diễn giải:**
ViewModel vừa sử dụng dependency vừa chịu trách nhiệm tạo dependency. Nó không thể dễ dàng thay implementation trong test và composition bị phân tán.

**Ví dụ:**

```swift
final class ViewModel {

    let api = RealAPI()
    let database = RealDatabase()
    let analytics = RealAnalytics()
}
```

---

## 15. Constructor Injection giúp gì cho một class?

**Ý chính:** Dependency rõ ràng, bắt buộc và dễ test.

**Ý diễn giải:**
Dependency được truyền từ bên ngoài, nên nhìn constructor là biết object cần gì. Object không thể được tạo ở trạng thái thiếu dependency bắt buộc.

**Ví dụ:**

```swift
final class ViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

---

## 16. Property Injection phù hợp với dependency nào?

**Ý chính:** Dependency `optional` hoặc được gắn sau initialization.

**Ý diễn giải:**
Property injection hữu ích khi dependency không bắt buộc lúc khởi tạo hoặc lifecycle framework khiến constructor injection khó dùng. Nhưng nó có nhược điểm object có thể tồn tại ở state chưa được configure.

**Ví dụ:**

```swift
final class ViewController: UIViewController {

    var analytics: Analytics?

    override func viewDidLoad() {
        super.viewDidLoad()

        analytics?.track("screen")
    }
}
```

---

## 17. Vì sao Constructor Injection thường được ưu tiên hơn Property Injection?

**Ý chính:** `Required dependency` phải rõ ngay khi object được tạo.

**Ý diễn giải:**
Constructor làm dependency explicit. Property injection dễ tạo object “chưa hoàn chỉnh”, khó phát hiện lỗi runtime.

**Ví dụ:**

```swift
final class ViewModel {

    private let repository: UserRepository

    init(repository: UserRepository) {
        self.repository = repository
    }
}
```

---

## 18. Dependency Inversion khác Dependency Injection ở điểm nào?

**Ý chính:** `Dependency Inversion` = nguyên tắc thiết kế; `Dependency Injection` = kỹ thuật thực hiện.

**Ý diễn giải:**
Dependency Inversion nói rằng high-level policy không nên phụ thuộc trực tiếp low-level implementation. Dependency Injection là một cách truyền implementation vào abstraction.

**Ví dụ:**

```swift
protocol PaymentService {
    func pay() async throws
}

final class CheckoutViewModel {

    private let payment: PaymentService

    init(payment: PaymentService) {
        self.payment = payment
    }
}
```

---

## 19. Tại sao protocol-based DI thường giúp test tốt hơn?

**Ý chính:** `Abstraction + replaceable implementation`.

**Ý diễn giải:**
Production có thể dùng implementation thật, test có thể dùng fake/mock. ViewModel không biết implementation cụ thể.

**Ví dụ:**

```swift
protocol API {
    func fetch() async throws -> User
}

struct MockAPI: API {
    func fetch() async throws -> User {
        User(id: 1)
    }
}
```

# IV. SERVICE LOCATOR / DEPENDENCY CONTAINER

## 20. Một class gọi `AppContainer.shared.api` bên trong method. Tại sao cách này dễ tạo vấn đề?

**Ý chính:** `Service Locator` → `hidden dependency`.

**Ý diễn giải:**
Nhìn vào initializer không biết class cần API. Dependency bị giấu trong implementation. Test phải thay global container hoặc setup environment phức tạp.

**Ví dụ:**

```swift
final class ViewModel {

    func load() async {
        let user = await AppContainer.shared.api.fetchUser()
    }
}
```

Người đọc class phải search toàn bộ source mới biết ViewModel phụ thuộc API.

---

## 21. Service Locator có phải luôn là thiết kế xấu không?

**Ý chính:** Không. Nhưng phải kiểm soát `scope`, `lifecycle`, `testability` và hidden dependency.

**Ý diễn giải:**
Service Locator có thể hữu ích cho composition root hoặc legacy system. Vấn đề xuất hiện khi business code truy cập global container trực tiếp và dependency không còn explicit.

**Ví dụ:**

```swift
let container = AppContainer()

let vm = ProfileViewModel(
    repository: container.userRepository
)
```

Cách này tốt hơn việc ViewModel tự gọi global singleton.

---

## 22. Dependency Container nên chịu trách nhiệm gì và không nên chịu trách nhiệm gì?

**Ý chính:** `Composition root` - tạo/wire dependency.

**Ý diễn giải:**
Container nên biết implementation cụ thể và cách kết nối chúng. Business object không nên biết container tồn tại.

**Ví dụ:**

```swift
final class AppContainer {

    lazy var api: API = RealAPI()

    lazy var repository: UserRepository =
        UserRepositoryImpl(api: api)

    func makeProfileViewModel() -> ProfileViewModel {
        ProfileViewModel(repository: repository)
    }
}
```

Flow:

```text
AppContainer
     ↓
create concrete dependencies
     ↓
inject
     ↓
Feature
```

# V. FACTORY / COORDINATOR / ROUTER

## 23. Khi việc tạo một feature cần rất nhiều dependency, object nào nên chịu trách nhiệm tạo chúng?

**Ý chính:** `Factory` / `Composition Root`.

**Ý diễn giải:**
Factory giúp gom logic construction và giảm việc ViewController tự biết cách tạo toàn bộ dependency chain.

**Ví dụ:**

```swift
final class ProfileFactory {

    let container: AppContainer

    func makeViewController() -> UIViewController {

        let vm = ProfileViewModel(
            repository: container.userRepository
        )

        return ProfileViewController(
            viewModel: vm
        )
    }
}
```

---

## 24. Coordinator giải quyết vấn đề gì?

**Ý chính:** `Navigation flow` + `screen composition`.

**Ý diễn giải:**
Coordinator tách navigation logic khỏi ViewController. Controller phát event, coordinator quyết định push/present flow tiếp theo.

**Ví dụ:**

```swift
final class ProfileCoordinator {

    let navigationController: UINavigationController

    func showDetail(id: Int) {

        let vc = DetailViewController(id: id)

        navigationController.pushViewController(
            vc,
            animated: true
        )
    }
}
```

---

## 25. Router khác Coordinator thế nào?

**Ý chính:** Router thường tập trung vào `routing`; Coordinator thường quản lý `flow lifecycle`.

**Ý diễn giải:**
Hai khái niệm không có một định nghĩa tuyệt đối. Router thường giải quyết “đi đâu”, còn Coordinator có thể quản lý cả việc tạo screen, dependency và toàn bộ flow.

**Ví dụ:**

```swift
protocol Router {
    func showDetail(id: Int)
}
```

Trong khi coordinator có thể:

```swift
final class CheckoutCoordinator {

    func start() {
        showCart()
    }

    func showCart() {
        // create + inject + push
    }

    func showPayment() {
        // create + inject + push
    }

    func finish() {
        // dismiss entire flow
    }
}
```

---

## 26. Vì sao để ViewController tự `push` mọi màn hình có thể làm architecture khó scale?

**Ý chính:** Navigation coupling.

**Ý diễn giải:**
ViewController biết quá nhiều về flow và cách tạo màn hình tiếp theo. Khi flow phức tạp, navigation logic bị phân tán ở nhiều controller và rất khó thay đổi.

**Ví dụ:**

```swift
final class CartViewController: UIViewController {

    func checkout() {

        let payment = PaymentViewController()

        payment.api = RealAPI()
        payment.database = RealDatabase()

        navigationController?.pushViewController(
            payment,
            animated: true
        )
    }
}
```

Coordinator/Factory có thể gom responsibility này.

# VI. MODULAR ARCHITECTURE

## 27. Khi một ứng dụng có hàng chục feature và team phát triển song song, tại sao chia module có thể tốt hơn chỉ chia folder?

**Ý chính:** `Module boundary` + ownership + dependency enforcement.

**Ý diễn giải:**
Folder chỉ tổ chức source code. Module tạo boundary compiler-level: public/internal dependency rõ ràng, build isolation tốt hơn và giảm việc feature truy cập implementation của feature khác.

**Ví dụ:**

```text
App
 ├── ProfileFeature
 ├── CheckoutFeature
 ├── SearchFeature
 │
 └── Core
      ├── Networking
      ├── DesignSystem
      └── Common
```

---

## 28. Feature-based architecture khác việc chia toàn bộ app thành UI/Domain/Data module như thế nào?

**Ý chính:** `Feature-first` groups related code by business capability.

**Ý diễn giải:**
Layer-first dễ dẫn đến một folder khổng lồ như:

```text
Views/
ViewModels/
Repositories/
Services/
```

Feature-first gom mọi thứ liên quan vào feature:

```text
Profile/
Checkout/
Search/
```

Giúp team ownership và thay đổi feature dễ hơn.

**Ví dụ:**

```text
Features/
├── Profile/
│   ├── Presentation/
│   ├── Domain/
│   └── Data/
│
└── Checkout/
    ├── Presentation/
    ├── Domain/
    └── Data/
```

# VII. DEPENDENCY GRAPH

## 29. Một project có rất nhiều module nhưng build dependency ngày càng phức tạp. Bạn sẽ đánh giá dependency graph như thế nào?

**Ý chính:** `Direction`, `cycle`, `fan-in`, `fan-out`, `stability`.

**Ý diễn giải:**
Không chỉ nhìn số lượng module. Cần xem module nào phụ thuộc module nào, có cycle không, module nào bị mọi feature phụ thuộc và implementation có bị leak qua boundary không.

**Ví dụ:**

```text
App
 ↓
Feature
 ↓
Domain
 ↓
Data
 ↓
Infrastructure
```

Flow một chiều dễ kiểm soát hơn:

```text
Feature A → Core

Feature B → Core

Feature A ↛ Feature B
```

---

## 30. Bạn phát hiện một feature A phụ thuộc B, B phụ thuộc C và C lại phụ thuộc A. Bạn sẽ xử lý thế nào?

**Ý chính:** `Circular dependency` → extract abstraction / shared module / invert dependency.

**Ý diễn giải:**
Cycle khiến module coupling mạnh và khó build/migrate. Trước tiên xác định vì sao A cần B, B cần C và C cần A. Sau đó thường extract abstraction hoặc đưa phần dùng chung xuống module thấp hơn.

**Ví dụ:**

```text
❌ Trước:

A → B
B → C
C → A
```

Có thể chuyển thành:

```text
✅ Sau:

A ──→ Core ←── C
      ↑
      B
```

Hoặc:

```text
A → Protocol
B → Protocol
C → Implementation
```

# 31. Một Senior được yêu cầu “hãy dùng Clean Architecture cho toàn bộ app”. Bạn sẽ phản hồi thế nào?

**Ý chính:** Không áp dụng máy móc; `architecture follows complexity`.

**Ý diễn giải:**
Clean Architecture có lợi khi dependency boundaries, business rules và testability cần được kiểm soát. Nhưng với feature CRUD đơn giản, tạo View → VM → UseCase → Repository → DataSource có thể chỉ tạo boilerplate.

Senior nên hỏi:

```text
Feature này có business rule phức tạp không?
        ↓
Có nhiều data source không?
        ↓
Có cần thay implementation không?
        ↓
Có team ownership riêng không?
        ↓
Có cần test domain độc lập không?
        ↓
Có khả năng feature thay đổi mạnh không?
```

Nếu phần lớn câu trả lời là “không”, architecture đơn giản hơn có thể tốt hơn.

# VIII. SENIOR ARCHITECTURE SCENARIOS

## 32. Một feature hiện tại chỉ có API, nhưng sau này có yêu cầu offline. Bạn sẽ thiết kế từ đầu thế nào?

**Ý chính:** `Repository boundary` để che giấu data source.

**Ý diễn giải:**
Không cần xây toàn bộ offline architecture ngay hôm nay, nhưng nên có boundary đủ tốt để sau này thêm local source mà không sửa presentation/business logic.

**Ví dụ:**

```swift
protocol ProductRepository {

    func products() async throws -> [Product]
}
```

Ban đầu:

```text
Repository
   ↓
Network
```

Sau này:

```text
Repository
   ↓
Cache
   ↓
Database
   ↓
Network
```

ViewModel vẫn giữ nguyên.

---

## 33. Một màn hình cần dữ liệu từ ba repository khác nhau. ViewModel nên gọi cả ba trực tiếp hay tạo một abstraction khác?

**Ý chính:** Tùy `business workflow`; có thể dùng Use Case/feature service để orchestration.

**Ý diễn giải:**
Nếu việc kết hợp ba repository là business operation của feature, nên gom thành use case/service. ViewModel không nên biết chi tiết data orchestration.

**Ví dụ:**

```swift
struct DashboardUseCase {

    let users: UserRepository
    let posts: PostRepository
    let notifications: NotificationRepository

    func execute() async throws -> DashboardData {

        async let user = users.currentUser()
        async let posts = posts.latest()
        async let notifications = notifications.latest()

        return try await DashboardData(
            user: user,
            posts: posts,
            notifications: notifications
        )
    }
}
```

## 34. Domain model có nên là model dùng trực tiếp để decode JSON không?

**Ý chính:** Thường nên tách `DTO` và `Domain Model` khi boundary cần ổn định.

**Ý diễn giải:**
Nếu domain model conform Codable trực tiếp theo API structure, domain bị phụ thuộc contract của backend. DTO giúp map external representation sang stable domain representation.

**Ví dụ:**

```swift
struct UserDTO: Decodable {
    let user_id: Int
    let display_name: String
}

struct User {
    let id: Int
    let name: String
}

extension UserDTO {

    func toDomain() -> User {
        User(
            id: user_id,
            name: display_name
        )
    }
}
```

## 35. Một API thay đổi field `display_name` thành `name`, nhưng bạn muốn UI không thay đổi. Layer nào nên hấp thụ thay đổi?

**Ý chính:** Data mapping boundary.

**Ý diễn giải:**
API-specific change nên được hấp thụ ở DTO/mapper/repository. Domain model và presentation không nên biết backend field naming nếu không có lý do.

**Ví dụ:**

```swift
struct UserDTO: Decodable {

    let name: String

    enum CodingKeys: String, CodingKey {
        case name = "display_name"
    }
}

struct User {
    let name: String
}
```

## 36. Một team có 15 feature nhưng tất cả đều import một `Common` module khổng lồ. Vì sao đây có thể trở thành vấn đề?

**Ý chính:** `Dependency dumping ground` + high coupling.

**Ý diễn giải:**
Common ban đầu tiện lợi nhưng dễ chứa mọi thứ. Cuối cùng mọi feature phụ thuộc Common, thay đổi nhỏ cũng ảnh hưởng toàn app và dependency graph trở nên khó kiểm soát.

**Ví dụ:**

```text
❌

Profile ─┐
Search  ─┤
Checkout ├──→ Common
Cart    ─┤
Home    ─┘

Common chứa:
Network
Database
UI
Models
Analytics
Business Logic
...
```

Tốt hơn là chia các stable capability:

```text
Profile   → Networking
Search    → Networking
Checkout  → Payment
Profile   → DesignSystem
```

## 37. Khi nào abstraction trở thành over-engineering?

**Ý chính:** Abstraction cost > value.

**Ý diễn giải:**
Một abstraction trở thành over-engineering khi nó không giúp thay implementation, test, boundary hoặc giảm complexity mà chỉ tạo thêm protocol/class/file.

**Ví dụ:**

```swift
protocol UserNameProvider {
    func getUserName() -> String
}

final class UserNameProviderImpl: UserNameProvider {
    func getUserName() -> String {
        "John"
    }
}
```

Nếu chỉ có một implementation, không có boundary và chẳng có logic, abstraction này có thể không tạo giá trị.

---

## 38. Nếu một module có rất nhiều public class nhưng gần như mọi implementation detail đều bị expose, vấn đề architecture là gì?

**Ý chính:** `Leaky abstraction` + API surface quá lớn.

**Ý diễn giải:**
Module nên expose capability cần thiết thay vì toàn bộ implementation. Public API càng lớn, coupling với module khác càng cao.

**Ví dụ:**

```swift
// Tốt hơn
public protocol UserProviding {
    func user(id: Int) async throws -> User
}
```

Thay vì public toàn bộ:

```swift
public class SQLUserStorage { ... }
public class UserMapper { ... }
public class UserCache { ... }
public class UserAPI { ... }
```

## 39. Bạn cần thay `URLSession` bằng mock trong test nhưng phải sửa rất nhiều production code. Điều này thường nói lên điều gì?

**Ý chính:** Dependency boundary không tốt.

**Ý diễn giải:**
Nếu concrete network implementation đã lan ra khắp codebase, dependency inversion chưa được áp dụng đúng. Cần tạo abstraction tại boundary hợp lý và inject dependency thay vì truy cập global/static API khắp nơi.

**Ví dụ:**

```swift
protocol HTTPClient {
    func data(for request: URLRequest) async throws -> Data
}
```

Production:

```swift
struct URLSessionClient: HTTPClient {

    func data(
        for request: URLRequest
    ) async throws -> Data {
        try await URLSession.shared.data(
            for: request
        ).0
    }
}
```

Test:

```swift
struct MockHTTPClient: HTTPClient {

    var data: Data

    func data(
        for request: URLRequest
    ) async throws -> Data {
        data
    }
}
```

## 40. Một feature có thể hoạt động với Network hoặc Local Database tùy trạng thái hệ thống. ViewModel có nên biết nguồn dữ liệu hiện tại là nguồn nào không?

**Ý chính:** Không nên; `Repository` che giấu data source policy.

**Ý diễn giải:**
Presentation chỉ quan tâm dữ liệu. Quyết định local/network/cache/sync nên thuộc data layer/repository.

**Ví dụ:**

```swift
protocol ProductRepository {

    func products() async throws -> [Product]
}
```

ViewModel:

```swift
final class ProductViewModel {

    let repository: ProductRepository

    func load() async throws {
        let products = try await repository.products()

        // Không cần biết:
        // cache?
        // database?
        // network?
    }
}
```

# IX. 10 CÂU “BẪY SENIOR” VỀ ARCHITECTURE

### 41. “Mỗi class phải có protocol để dễ test.” Bạn đồng ý không?

**Ý chính:** Không. `Protocol` chỉ nên tạo khi có abstraction value.

**Ý diễn giải:**
Protocol không tự động làm code tốt hơn. Tạo protocol cho mọi class có thể làm dependency graph phức tạp và tăng boilerplate.

**Ví dụ:**

```swift
// Có giá trị nếu có nhiều implementation
protocol ImageLoader {
    func load(_ url: URL) async throws -> Data
}
```

Nhưng một helper nội bộ đơn giản có thể không cần protocol.

---

### 42. “ViewModel không được import UIKit.” Có phải luôn đúng?

**Ý chính:** Không tuyệt đối; phụ thuộc kiến trúc.

**Ý diễn giải:**
Nếu ViewModel thuộc presentation layer, một số UIKit type có thể hợp lý. Tuy nhiên càng giảm framework dependency ở business/domain logic càng dễ test và tái sử dụng.

**Ví dụ:**

```swift
// Domain
struct User {
    let name: String
}

// Presentation có thể format cho UI
let title = user.name
```

---

### 43. “Repository luôn phải là protocol.” Có đúng không?

**Ý chính:** Không. Protocol hữu ích khi cần abstraction/boundary/testability.

**Ý diễn giải:**
Nếu implementation đơn giản và không có reason để thay thế, concrete repository vẫn có thể hợp lý. Quan trọng là boundary và dependency direction.

**Ví dụ:**

```swift
struct UserRepository {
    let api: API

    func load() async throws -> User {
        try await api.fetchUser()
    }
}
```

---

### 44. “Clean Architecture càng nhiều layer càng tốt.” Đúng hay sai?

**Ý chính:** Sai. `Separation` không đồng nghĩa `maximum layers`.

**Ý diễn giải:**
Layer chỉ đáng tồn tại khi nó có responsibility hoặc boundary rõ. Quá nhiều layer khiến code bị ceremony, indirection và khó đọc.

**Ví dụ:**

```text
❌

View
 ↓
ViewAdapter
 ↓
ViewModelAdapter
 ↓
PresentationService
 ↓
UseCaseFactory
 ↓
UseCase
 ↓
RepositoryManager
 ↓
Repository
 ↓
DataProvider
 ↓
API
```

Có thể tốt hơn:

```text
View
 ↓
ViewModel
 ↓
Repository
 ↓
API
```

nếu feature đủ đơn giản.

---

### 45. “MVVM luôn tốt hơn MVC.” Bạn trả lời thế nào?

**Ý chính:** Không có architecture tốt tuyệt đối.

**Ý diễn giải:**
MVC phù hợp app/feature nhỏ. MVVM hữu ích khi presentation logic tăng. Chọn architecture dựa trên complexity và changeability chứ không theo trend.

**Ví dụ:**

```text
Simple feature:

ViewController
 ↓
Service
```

có thể hoàn toàn hợp lý.

---

### 46. “Coordinator giải quyết mọi vấn đề navigation.” Có đúng không?

**Ý chính:** Không. Coordinator chủ yếu giải quyết navigation flow và composition.

**Ý diễn giải:**
Coordinator không tự giải quyết state management, business logic, networking hay persistence. Nếu coordinator chứa tất cả những thứ đó thì nó sẽ thành “God Coordinator”.

**Ví dụ:**

```swift
final class AppCoordinator {

    func start() {
        showHome()
    }

    func showHome() {
        // Navigation only
    }
}
```

---

### 47. “Dependency Injection giúp code chạy nhanh hơn.” Có đúng không?

**Ý chính:** Không trực tiếp. DI chủ yếu cải thiện `coupling`, `testability`, `composition`.

**Ý diễn giải:**
DI là kỹ thuật quản lý dependency. Nó không phải performance optimization. Nếu dùng quá nhiều abstraction/runtime lookup, thậm chí còn có thêm complexity.

**Ví dụ:**

```swift
final class ViewModel {

    init(
        repository: UserRepository
    ) {
        self.repository = repository
    }

    private let repository: UserRepository
}
```

---

### 48. “Singleton là xấu.” Bạn phản biện thế nào?

**Ý chính:** Singleton không tự xấu; vấn đề là `global mutable state` và uncontrolled ownership.

**Ý diễn giải:**
Một số system-level service có singleton hợp lý. Nhưng business dependency truy cập singleton trực tiếp làm dependency ẩn, khó test và coupling cao.

**Ví dụ:**

```swift
// Có thể hợp lý
let notificationCenter = NotificationCenter.default
```

Nhưng:

```swift
// Dễ tạo hidden dependency
App.shared.database.save(user)
```

---

### 49. Khi thiết kế architecture cho một app mới, bạn nên bắt đầu bằng folder structure hay business flow?

**Ý chính:** Bắt đầu từ `requirement + data flow + responsibility`.

**Ý diễn giải:**
Folder chỉ là kết quả cuối. Trước tiên xác định user flow, state ownership, business rules, data source và dependency direction. Sau đó mới quyết định module/layer.

**Ví dụ:**

```text
User Action
    ↓
State Change
    ↓
Business Rule
    ↓
Data Source
    ↓
Result
    ↓
UI State
```

Từ flow này mới suy ra:

```text
View
 ↓
ViewModel
 ↓
UseCase
 ↓
Repository
```

---

### 50. Nếu được giao review một architecture của Senior khác, bạn sẽ nhìn vào đâu trước?

**Ý chính:** `Dependency direction + state ownership + lifecycle + coupling + testability`.

**Ý diễn giải:**
Đừng bắt đầu bằng câu hỏi “Có dùng MVVM không?”. Hãy xem:

```text
1. Ai sở hữu state?
2. Ai tạo dependency?
3. Dependency đi theo hướng nào?
4. Business logic nằm ở đâu?
5. Data source bị leak ra đâu?
6. Navigation thuộc responsibility nào?
7. Async lifecycle thuộc ai?
8. Có hidden dependency không?
9. Có circular dependency không?
10. Test boundary nằm ở đâu?
```

Sau đó mới đánh giá architecture có cần thay đổi hay không.

# SƠ ĐỒ ARCHITECTURE SENIOR CẦN HIỂU

```text
                    APP
                     │
             Composition Root
                     │
          ┌──────────┴──────────┐
          │                     │
       Feature A            Feature B
          │                     │
     Presentation         Presentation
          │                     │
      ViewModel             ViewModel
          │                     │
       UseCase               UseCase
          │                     │
      Repository            Repository
          │                     │
      ┌───┴────┐           ┌────┴───┐
      │        │           │        │
   Network   Database    Network   Database
```

Dependency nên đi theo hướng rõ ràng:

```text
Presentation
      ↓
Domain
      ↓
Data
      ↓
Infrastructure
```

Không nên để:

```text
Domain
   ↓
UIKit
```

hoặc:

```text
View
   ↓
CoreData
```

nếu mục tiêu là giữ domain/presentation tách biệt.

```text
Requirement

Business rules

    ↓
Data sources
    ↓
Dependency direction
    ↓
Testability
    ↓
Team ownership
    ↓
Change frequency
    ↓
Architecture
```

Và câu **Senior nhất** thường không phải:

> “Nên dùng Clean Architecture.”

Đó là điểm khác biệt giữa **biết pattern** và **biết thiết kế architecture**.
