# I. KEYCHAIN / SECURE STORAGE

## 1. Bạn cần lưu access token và refresh token để app có thể đăng nhập lại. Bạn sẽ lưu chúng thế nào?

**Ý chính:** `Keychain` + secure credential lifecycle.

**Ý diễn giải:**
Token là credential nên cần nơi lưu trữ được bảo vệ. Thường access/refresh token được lưu trong Keychain thay vì UserDefaults hoặc file plain text. Refresh token cần được bảo vệ nghiêm ngặt hơn vì lifetime thường dài hơn.

**Ví dụ:**

```swift
import Security

func saveToken(
    _ token: String,
    account: String
) throws {

    let data = Data(token.utf8)

    let query: [String: Any] = [

        kSecClass as String:
            kSecClassGenericPassword,

        kSecAttrAccount as String:
            account,

        kSecValueData as String:
            data
    ]

    let status = SecItemAdd(
        query as CFDictionary,
        nil
    )

    guard status == errSecSuccess else {
        throw KeychainError.saveFailed(status)
    }
}
```

---

## 2. Vì sao không nên lưu access token trong UserDefaults?

**Ý chính:** `UserDefaults` không phải secure credential storage.

**Ý diễn giải:**
UserDefaults phù hợp preferences/configuration. Credential cần security attributes, access control và lifecycle phù hợp hơn. Ngoài vấn đề storage, còn phải tránh logging hoặc đưa token vào analytics/crash metadata.

**Ví dụ:**

```swift
// ❌ Không nên
UserDefaults.standard.set(
    accessToken,
    forKey: "access_token"
)

// ✅
try keychain.save(
    accessToken,
    account: "access_token"
)
```

---

## 3. Nếu app đã lưu token trong Keychain nhưng logout vẫn cho phép app tự đăng nhập lại, bạn sẽ kiểm tra gì?

**Ý chính:** `Credential lifecycle` + Keychain cleanup + in-memory state.

**Ý diễn giải:**
Logout phải xác định rõ session kết thúc ở đâu. Có thể token vẫn còn trong Keychain, memory cache, cookie/session hoặc refresh mechanism. Không nên chỉ xóa một biến access token.

**Ví dụ:**

```swift
func logout() {

    memoryAccessToken = nil

    keychain.delete(
        account: "access_token"
    )

    keychain.delete(
        account: "refresh_token"
    )

    urlSession.resetCookies()

    userCache.clear()
}
```

# II. TLS / CERTIFICATE PINNING

## 4. HTTPS đã bảo vệ dữ liệu trên đường truyền. Vì sao một số ứng dụng vẫn triển khai thêm certificate pinning?

**Ý chính:** `TLS encryption` bảo vệ channel; `pinning` giới hạn certificate/public key được chấp nhận.

**Ý diễn giải:**
TLS thông thường dựa trên hệ thống trust chain của thiết bị. Certificate pinning bổ sung một constraint rằng app chỉ chấp nhận certificate/public key dự kiến cho server cụ thể. Điều này có thể giảm một số rủi ro liên quan compromised/mis-issued certificates.

**Ví dụ:**

```text
TLS:

App
 ↓
Certificate validation
 ↓
Trusted CA chain
 ↓
Server


Pinning:

App
 ↓
TLS validation
 ↓
Expected certificate/public key
 ↓
Server
```

---

## 5. Certificate pinning có nhược điểm gì khiến bạn không nên bật một cách máy móc?

**Ý chính:** `Operational risk + certificate/key rotation`.

**Ý diễn giải:**
Nếu certificate hoặc public key thay đổi mà app không có pin mới, toàn bộ network connection có thể bị từ chối. Vì vậy pinning cần chiến lược rotation, backup pins và release management phù hợp.

**Ví dụ:**

```text
App release
   ↓
Pinned Key A

Server rotates
   ↓
Key B

Nếu app chỉ chấp nhận A
   ↓
❌ Network failure
```

Thiết kế tốt hơn có thể chuẩn bị nhiều pin hợp lệ:

```text
Pin A
Pin B
   ↓
Trong thời gian rotation
```

---

## 6. Certificate pinning có thay thế việc kiểm tra TLS certificate chuẩn của hệ điều hành không?

**Ý chính:** Không. `Pinning bổ sung`, không phải thay toàn bộ TLS validation.

**Ý diễn giải:**
Không nên bỏ qua trust validation chuẩn rồi chỉ so sánh một giá trị pin một cách tùy tiện. HTTPS/TLS validation vẫn là nền tảng; pinning là additional restriction.

**Ví dụ:**

```text
Connection
    ↓
TLS validation
    ↓
Certificate / trust validation
    ↓
Pin validation
    ↓
Accept / Reject
```

# III. TOKEN SECURITY / OAUTH

## 7. Vì sao access token thường có lifetime ngắn hơn refresh token?

**Ý chính:** `Limit blast radius`.

**Ý diễn giải:**
Access token được gửi thường xuyên tới API nên có nhiều cơ hội bị lộ hơn. Lifetime ngắn làm giảm khoảng thời gian token bị lợi dụng. Refresh token có lifetime dài hơn nên cần protection chặt hơn và cơ chế revoke.

**Ví dụ:**

```text
Access Token
→ 5–30 minutes

Refresh Token
→ longer lifetime
→ stored more securely
```

Đây chỉ là ví dụ policy, lifetime thực tế phụ thuộc hệ thống authentication.

---

## 8. Nếu một attacker lấy được access token, app có thể ngăn attacker gọi API bằng token đó không?

**Ý chính:** Không thể dựa hoàn toàn vào client; `server-side authorization`.

**Ý diễn giải:**
Access token là bearer credential trong nhiều hệ thống. Nếu attacker có token hợp lệ, client-side checks không thể tin cậy để ngăn việc sử dụng token. Server phải xác thực token, kiểm tra scope/permission, expiration và các policy liên quan.

**Ví dụ:**

```text
Attacker
   ↓
Valid Access Token
   ↓
API Server
   ↓
Token validation
   ↓
Authorization
   ↓
Allow / Deny
```

Không nên dựa vào:

```swift
if !isJailbroken {
    allowRequest()
}
```

để thay server authorization.

---

## 9. OAuth giải quyết vấn đề gì trong hệ thống đăng nhập?

**Ý chính:** `Delegated authorization`.

**Ý diễn giải:**
OAuth cho phép một client truy cập resource thay mặt resource owner mà không cần client trực tiếp biết password của user. Trong mobile app, authorization code flow với PKCE là một pattern quan trọng.

**Ví dụ:**

```text
Mobile App
   ↓
Authorization Server
   ↓
User Login
   ↓
Authorization Code
   ↓
PKCE verification
   ↓
Access Token
   ↓
Resource Server
```

# IV. BIOMETRIC

## 10. Bạn có nên lưu password hoặc token “bằng Face ID” trực tiếp không?

**Ý chính:** `Biometric authenticates user; protected credential remains in secure storage`.

**Ý diễn giải:**
Biometric không phải nơi lưu password/token. Một pattern phổ biến là bảo vệ Keychain item bằng access control yêu cầu user presence/biometric authentication. App dùng LocalAuthentication và secure storage để kiểm soát việc truy cập credential.

**Ví dụ:**

```swift
import LocalAuthentication

let context = LAContext()

context.evaluatePolicy(
    .deviceOwnerAuthentication,
    localizedReason: "Xác thực để tiếp tục"
) { success, error in

    guard success else {
        return
    }

    // Tiếp tục truy cập protected resource
}
```

Flow:

```text
User
 ↓
Face ID / Touch ID
 ↓
LocalAuthentication
 ↓
Protected credential
 ↓
Use token/key
```

# V. APP TRANSPORT SECURITY

## 11. App Transport Security bảo vệ app khỏi vấn đề nào?

**Ý chính:** `Secure network transport policy`.

**Ý diễn giải:**
ATS đặt ra các yêu cầu bảo mật cho network connections, khuyến khích sử dụng HTTPS/TLS và hạn chế insecure HTTP. Exception nên được giới hạn và có lý do rõ ràng.

**Ví dụ:**

```xml
<key>NSAppTransportSecurity</key>
<dict>
    <key>NSAllowsArbitraryLoads</key>
    <false/>
</dict>
```

Không nên mở arbitrary loads chỉ để “cho API chạy được” nếu không cần.

---

## 12. Server nội bộ chỉ hỗ trợ HTTP. Bạn muốn tắt ATS toàn app để giải quyết nhanh. Bạn đánh giá cách này thế nào?

**Ý chính:** Không nên `disable globally`; cần exception nhỏ nhất có thể hoặc sửa server.

**Ý diễn giải:**
Tắt ATS toàn app mở rộng attack surface. Nếu bắt buộc dùng exception cho legacy endpoint, nên scope nó càng nhỏ càng tốt và có kế hoạch migrate sang HTTPS.

**Ví dụ:**

```text
❌

NSAllowsArbitraryLoads = YES
```

Tốt hơn là:

```text
App
 ↓
ATS enabled
 ↓
Specific exception
 ↓
Legacy internal endpoint
```

và loại bỏ exception khi server hỗ trợ HTTPS.

# VI. JAILBREAK / CLIENT COMPROMISE

## 13. Jailbreak detection có phải là một security boundary đáng tin cậy không?

**Ý chính:** Không. `Client-side detection can be bypassed`.

**Ý diễn giải:**
Jailbreak detection có thể làm tăng cost của attacker hoặc hỗ trợ risk signal, nhưng attacker kiểm soát thiết bị có thể patch/hook/check bypass. Không được dùng nó để thay thế server-side security.

**Ví dụ:**

```swift
if jailbreakDetected {
    showWarning()
}
```

Có thể hữu ích:

```text
Detection
   ↓
Risk signal
   ↓
Additional protection
```

Nhưng không nên:

```text
Jailbreak not detected
   ↓
"App hoàn toàn an toàn"
```

---

## 14. Nếu attacker đã reverse-engineer ứng dụng, bạn có thể giấu API secret bằng cách encode Base64 không?

**Ý chính:** Không. `Encoding ≠ encryption ≠ secret protection`.

**Ý diễn giải:**
Base64 chỉ là encoding. Secret hard-code trong client về bản chất có thể bị extract. Nếu secret là server-side credential, không nên đưa vào app như một shared secret đáng tin.

**Ví dụ:**

```swift
// ❌ Không phải security
let secret = "c2VjcmV0"
let decoded = Data(
    base64Encoded: secret
)
```

Attacker chỉ cần decode lại.

# VII. SENSITIVE DATA

## 15. Những dữ liệu nào Senior phải coi là nhạy cảm trong application?

**Ý chính:** `Credentials + PII + financial/health/business secrets + security metadata`.

**Ý diễn giải:**
Không chỉ password/token. Tùy app, email, phone, location, payment data, private documents, session identifiers và business secrets cũng có thể nhạy cảm. Cần xác định theo threat model và product requirements.

**Ví dụ:**

```text
Sensitive
├── Password
├── Access Token
├── Refresh Token
├── API Secret
├── Personal Data
├── Payment Data
├── Private Documents
└── Session Identifiers
```

Không nên dump tất cả vào log:

```swift
print(user)
print(tokens)
print(request)
```

---

## 16. Một app lưu sensitive data vào file local. Chỉ cần đặt tên file khó đoán là đủ không?

**Ý chính:** Không. `Obscurity ≠ security`.

**Ý diễn giải:**
Tên file random hoặc extension giả không bảo vệ dữ liệu thực sự. Cần chọn storage/security controls phù hợp và xem xét encryption, access protection, data lifetime.

**Ví dụ:**

```text
❌

/Documents/
    x8a91f.dat
```

Random filename không biến dữ liệu thành secure storage.

# VIII. SCREENSHOT / SCREEN RECORDING

## 17. Bạn có một màn hình hiển thị OTP hoặc thông tin rất nhạy cảm. Bạn có thể đảm bảo tuyệt đối user không chụp màn hình trên iOS không?

**Ý chính:** Không có `absolute guarantee`; có thể giảm exposure theo context.

**Ý diễn giải:**
iOS không cung cấp cơ chế đảm bảo tuyệt đối rằng người dùng không thể chụp bằng mọi phương thức. App có thể phát hiện một số trạng thái capture, che/mờ sensitive UI trong các lifecycle/capture scenarios phù hợp hoặc hạn chế nội dung khi cần.

**Ví dụ:**

```swift
NotificationCenter.default.addObserver(
    forName:
        UIScreen.capturedDidChangeNotification,
    object: nil,
    queue: .main
) { _ in

    let captured =
        UIScreen.main.isCaptured

    if captured {
        protectSensitiveUI()
    }
}
```

Đây là mitigation, không phải security guarantee tuyệt đối.

---

## 18. Vì sao che sensitive content khi app chuyển background có thể quan trọng?

**Ý chính:** `Snapshot protection`.

**Ý diễn giải:**
System có thể tạo snapshot của UI để dùng trong app switcher. Nếu màn hình đang chứa token, OTP, account information hoặc document nhạy cảm, app có thể che nội dung trước khi background để giảm exposure.

**Ví dụ:**

```swift
func applicationDidEnterBackground(
    _ application: UIApplication
) {
    privacyOverlay.isHidden = false
}
```

Khi foreground:

```swift
func applicationWillEnterForeground(
    _ application: UIApplication
) {
    privacyOverlay.isHidden = true
}
```

# IX. SECURE LOGGING

## 19. Vì sao logging có thể trở thành security vulnerability?

**Ý chính:** `Logs can leak sensitive data`.

**Ý diễn giải:**
Developer thường log request/response để debug. Nếu log Authorization header, token, cookies, personal data hoặc response nhạy cảm, credential có thể xuất hiện trong development tools, crash reports hoặc logging infrastructure.

**Ví dụ:**

```swift
// ❌

logger.debug(
    "Authorization: \(accessToken)"
)

logger.debug(
    "Response: \(responseBody)"
)
```

Tốt hơn:

```swift
logger.debug(
    "Request completed: status=\(statusCode)"
)
```

Hoặc redact:

```swift
func redact(
    token: String
) -> String {
    let prefix = token.prefix(4)

    return "\(prefix)****"
}
```

---

## 20. Bạn thiết kế secure logging cho production như thế nào?

**Ý chính:** `Redaction + log levels + least data + environment policy`.

**Ý diễn giải:**
Production log chỉ nên chứa thông tin cần cho operation/debugging. Sensitive values phải được redact hoặc loại bỏ. Debug log chi tiết nên được kiểm soát theo build configuration và không nên đẩy credential vào logging backend.

**Ví dụ:**

```swift
logger.info(
    "Login succeeded userID=\(user.id)"
)

logger.debug(
    "Request status=\(response.statusCode)"
)
```

Không:

```swift
logger.debug(
    """
    token=\(accessToken)
    refreshToken=\(refreshToken)
    password=\(password)
    """
)
```

# X. SENIOR SECURITY SCENARIOS

## 21. Một developer nói:

> “API key được hard-code trong binary nhưng đã obfuscate nên an toàn.”

Bạn đánh giá thế nào?

**Ý chính:** `Obfuscation only increases extraction cost`.

**Ý diễn giải:**
Nếu secret nằm trong client và client có thể bị reverse-engineer, attacker có thể tìm hoặc hook code để lấy giá trị. Obfuscation có thể làm khó hơn nhưng không biến secret thành trusted secret.

**Ví dụ:**

```text
❌

App Binary
    ↓
Obfuscated API Key
    ↓
Runtime decode
    ↓
API
```

Attacker có thể quan sát runtime value.

---

## 22. Nếu app bị compromise hoàn toàn, đâu là security boundary thực sự quan trọng?

**Ý chính:** `Server-side enforcement`.

**Ý diễn giải:**
Client không nên là nơi cuối cùng quyết định user có quyền làm gì. Server phải validate authentication, authorization, token, scope và business policy.

**Ví dụ:**

```text
Client
  ↓
Request + Token
  ↓
Server
  ├── Authentication
  ├── Authorization
  ├── Scope
  ├── Resource ownership
  └── Business rules
        ↓
     Allow / Deny
```

---

## 23. Access token bị lộ nhưng server chưa hết hạn token. App có thể thu hồi ngay không?

**Ý chính:** `Token revocation / session management`.

**Ý diễn giải:**
Tùy auth architecture, server có thể revoke token/session hoặc thay đổi token version/credential state. Client-side xóa token chỉ ngăn app đó dùng token, không thu hồi token đã bị attacker lấy.

**Ví dụ:**

```text
User
 ↓
Report compromise
 ↓
Server
 ↓
Revoke session/token
 ↓
Attacker token
 ↓
Rejected
```

---

## 24. Nếu refresh token được lưu an toàn nhưng app log nó ra console trong debug build, security model có còn tốt không?

**Ý chính:** `Secure storage can be defeated by insecure data handling`.

**Ý diễn giải:**
Bảo vệ storage không có ích nếu credential sau đó bị copy ra logs, analytics, crash report hoặc clipboard. Security phải bảo vệ toàn bộ data flow chứ không chỉ nơi lưu cuối cùng.

**Ví dụ:**

```text
Keychain
   ↓
Token
   ↓
❌ print(token)
   ↓
Log
   ↓
Credential leakage
```

---

## 25. Một API request chứa dữ liệu nhạy cảm. Ngoài HTTPS, bạn còn xem xét gì?

**Ý chính:** `Data minimization + authentication + authorization + logging + storage + lifecycle`.

**Ý diễn giải:**
TLS bảo vệ dữ liệu trên đường truyền nhưng không giải quyết mọi vấn đề. Cần xem dữ liệu được log ở đâu, lưu cache hay không, server kiểm tra quyền thế nào và response có được persist hay không.

**Ví dụ:**

```text
Sensitive Data
    ↓
Minimize
    ↓
HTTPS/TLS
    ↓
Server Auth
    ↓
Server Authorization
    ↓
No sensitive logging
    ↓
Secure persistence
    ↓
Proper deletion
```

```text
Credential
→ Keychain / secure access control

Transport
→ TLS
→ Pinning nếu threat model phù hợp

Authentication
→ Short-lived access token
→ Secure refresh token

Authorization
→ Server-side enforcement

Sensitive data
→ Minimize
→ Encrypt/protect
→ Không log

Client compromise
→ Không chứa server secrets đáng tin
→ Token revocation
→ Session control
→ Risk detection

Monitoring
→ Secure logging
→ Redaction
```

Điểm quan trọng nhất:

> **Mobile security không phải làm cho client “không thể bị hack”. Mục tiêu là giảm attack surface, bảo vệ credential/data và đảm bảo khi client bị compromise thì attacker vẫn không vượt qua được server-side trust boundary.**
