# CÂU HỎI ÔN TẬP GIT, CI/CD CHO ANDROID DEVELOPER

## CẤP ĐỘ 1: JUNIOR (CƠ BẢN)

### Chủ đề: Làm việc với mã nguồn hằng ngày

#### 1. Bạn vừa hoàn thành màn hình đăng nhập, làm thế nào để lưu phần thay đổi này để có thể quay lại khi cần?

**Ý chính:** **Git Commit** - Lưu một mốc thay đổi có mô tả rõ ràng trong lịch sử mã nguồn.

**Diễn giải:** Nên chia thay đổi thành các mốc nhỏ, mỗi mốc chỉ giải quyết một mục tiêu. Mô tả cần nói rõ thay đổi gì và lý do thực hiện để người khác dễ xem lại.

**Ví dụ:**

```bash
git add app/src/main/java/LoginViewModel.kt
git commit -m "feat: add login validation"
```

---

#### 2. Bạn đã sửa nhầm một file cấu hình và chưa lưu mốc thay đổi, làm thế nào để bỏ phần sửa đó?

**Ý chính:** **git restore** - Khôi phục file về trạng thái của mốc gần nhất.

**Diễn giải:** Chỉ dùng khi chắc chắn không cần giữ thay đổi hiện tại. Trước khi thực hiện, nên xem danh sách phần đã sửa để tránh mất công việc chưa lưu.

**Ví dụ:**

```bash
# Xem các file đang thay đổi
git status

# Bỏ thay đổi chưa lưu của một file
git restore app/build.gradle.kts
```

---

#### 3. Bạn muốn kiểm tra chính xác mình đã thay đổi những dòng nào trước khi gửi lên máy chủ chung?

**Ý chính:** **git diff** - Hiển thị sự khác nhau giữa nội dung hiện tại và mốc đã lưu gần nhất.

**Diễn giải:** Kiểm tra trước khi lưu giúp phát hiện file thừa, log debug hoặc thông tin nhạy cảm bị thêm nhầm. Đây là thói quen nhỏ nhưng giảm khá nhiều lỗi review.

**Ví dụ:**

```bash
# Xem thay đổi chưa đưa vào vùng chuẩn bị
git diff

# Xem thay đổi đã chuẩn bị để lưu
git diff --staged
```

---

#### 4. Một file chứa dữ liệu cá nhân và khóa ký ứng dụng chỉ dùng trên máy bạn, làm thế nào để tránh đưa nó lên kho chung?

**Ý chính:** **.gitignore** - Khai báo các file hoặc thư mục không được theo dõi.

**Diễn giải:** Các file như `local.properties`, file khóa ký, token và thư mục build không nên xuất hiện trong kho mã nguồn. Nếu file đã từng được theo dõi, chỉ thêm vào danh sách bỏ qua là chưa đủ.

**Ví dụ:**

```gitignore
# File cấu hình theo máy cá nhân
local.properties

# Khóa ký ứng dụng
*.jks
*.keystore

# Kết quả build
/build
```

---

#### 5. Bạn cần xem ai đã sửa một dòng cấu hình khiến bản cài đặt bị lỗi, nên tra cứu như thế nào?

**Ý chính:** **git blame** - Hiển thị người và mốc thay đổi gần nhất của từng dòng.

**Diễn giải:** Lệnh này hỗ trợ tìm bối cảnh của thay đổi, không nên dùng để quy trách nhiệm. Sau khi tìm được mốc, hãy đọc toàn bộ nội dung thay đổi để hiểu lý do ban đầu.

**Ví dụ:**

```bash
git blame app/build.gradle.kts
git show <commit-id>
```

#### 6. Bạn muốn xem lại các mốc thay đổi gần đây trước khi bắt đầu xử lý lỗi, cần dùng cách nào?

**Ý chính:** **git log** - Hiển thị lịch sử các mốc thay đổi của dự án.

**Diễn giải:** Lịch sử giúp xác định thay đổi nào có thể gây ra lỗi. Dạng rút gọn phù hợp để nhìn nhanh nhánh phát triển đang đi qua những mốc nào.

**Ví dụ:**

```bash
git log --oneline --decorate -10
```

### Chủ đề: Làm việc cùng nhóm

#### 7. Bạn sắp làm một chức năng mới nhưng không muốn ảnh hưởng phần ổn định mà mọi người đang dùng, nên bắt đầu ra sao?

**Ý chính:** **Git Branch** - Tạo vùng phát triển riêng cho một công việc cụ thể.

**Diễn giải:** Mỗi chức năng hoặc lỗi nên được xử lý ở một nhánh riêng. Cách này giúp thay đổi dễ review, dễ kiểm thử và dễ loại bỏ khi không còn cần thiết.

**Ví dụ:**

```bash
git switch main
git pull origin main
git switch -c feature/login-validation
```

---

#### 8. Trước khi gửi phần việc của mình để đồng đội xem, bạn cần lấy các thay đổi mới nhất từ kho chung. Làm thế nào?

**Ý chính:** **git pull** - Tải và tích hợp thay đổi mới từ máy chủ về nhánh hiện tại.

**Diễn giải:** Nên thực hiện thường xuyên để phát hiện xung đột sớm. Trước khi lấy về, cần lưu hoặc cất tạm phần đang làm để không bị gián đoạn.

**Ví dụ:**

```bash
git switch feature/login-validation
git pull origin feature/login-validation
```

---

#### 9. Bạn muốn gửi mốc thay đổi ở máy cá nhân lên kho chung để tạo yêu cầu xem xét, làm thế nào?

**Ý chính:** **git push** - Đẩy các mốc thay đổi ở máy cục bộ lên máy chủ chung.

**Diễn giải:** Chỉ nên gửi các mốc có nội dung hoàn chỉnh, mô tả rõ ràng và không chứa file nhạy cảm. Sau khi gửi lần đầu, nhánh cần được liên kết với nhánh trên máy chủ.

**Ví dụ:**

```bash
git push -u origin feature/login-validation
```

---

#### 10. Hai người cùng sửa một đoạn xử lý và hệ thống không thể tự ghép lại, bạn xử lý tình huống này như thế nào?

**Ý chính:** **Merge Conflict** - Xung đột xảy ra khi hai thay đổi cùng tác động lên một vùng nội dung.

**Diễn giải:** Cần hiểu mục đích của cả hai phần trước khi chọn nội dung cuối cùng. Sau khi sửa, phải chạy build hoặc kiểm thử để bảo đảm phần ghép không làm mất hành vi cần thiết.

**Ví dụ:**

```text
<<<<<<< HEAD
return validateEmail(email)
=======
return email.isNotBlank()
>>>>>>> feature/login
```

```kotlin
// ĐÚNG: giữ hành vi đầy đủ sau khi hiểu hai phía
return email.isNotBlank() && validateEmail(email)
```

#### 11. Bạn phát hiện phần thay đổi đang làm dở phải tạm dừng để xử lý lỗi khẩn cấp. Làm sao cất phần việc đó mà chưa cần tạo mốc?

**Ý chính:** **git stash** - Cất tạm thay đổi chưa lưu để làm việc khác trên cùng thư mục.

**Diễn giải:** Phù hợp cho thay đổi ngắn hạn đang dang dở. Nên đặt mô tả để sau này biết nội dung nào đang được cất, và tránh dùng nó như nơi lưu trữ lâu dài.

**Ví dụ:**

```bash
git stash push -m "WIP: login validation"
git switch hotfix/crash-on-start
# Sau khi xử lý xong
git stash pop
```

---

#### 12. Bạn vừa tạo mốc thay đổi với mô tả sai và chưa gửi lên kho chung. Cách sửa an toàn là gì?

**Ý chính:** **git commit --amend** - Cập nhật mốc thay đổi gần nhất khi nó chưa được chia sẻ.

**Diễn giải:** Có thể dùng để đổi mô tả hoặc bổ sung file bị quên. Không nên sửa lại lịch sử đã được nhiều người cùng dùng vì sẽ làm lệch lịch sử ở máy của họ.

**Ví dụ:**

```bash
git commit --amend -m "fix: validate empty email before submit"
```

### Chủ đề: Kiểm tra tự động cơ bản

#### 13. Làm thế nào để đảm bảo mỗi thay đổi được kiểm tra trước khi được đưa vào nhánh ổn định?

**Ý chính:** **CI (Continuous Integration)** - Tự động build và chạy kiểm tra mỗi khi có thay đổi.

**Diễn giải:** CI phát hiện lỗi sớm thay vì chờ đến lúc ghép nhiều phần lại. Với Android, kiểm tra cơ bản thường gồm build, kiểm tra định dạng và unit test.

**Ví dụ:**

```yaml
name: Android CI

on:
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./gradlew testDebugUnitTest
```

---

#### 14. Một thay đổi có thể chạy tốt trên máy bạn nhưng lại lỗi trên máy đồng đội. Làm thế nào để giảm tình trạng này?

**Ý chính:** **Build Automation** - Dùng cùng một quy trình build tự động trong môi trường thống nhất.

**Diễn giải:** Máy cá nhân có thể khác nhau về JDK, Android SDK hoặc biến môi trường. Pipeline giúp nhóm biết thay đổi có build được trong môi trường chuẩn hay không.

**Ví dụ:**

```yaml
- name: Build debug APK
  run: ./gradlew assembleDebug --stacktrace
```

---

#### 15. Bạn muốn hệ thống tự chạy kiểm tra mỗi khi có người gửi thay đổi để review, cần cấu hình điều kiện nào?

**Ý chính:** **Pull Request Trigger** - Sự kiện kích hoạt quy trình khi có yêu cầu ghép mã nguồn.

**Diễn giải:** Kiểm tra trên yêu cầu review giúp chặn lỗi trước khi vào nhánh chính. Có thể cấu hình chạy khi tạo mới, cập nhật hoặc mở lại yêu cầu.

**Ví dụ:**

```yaml
on:
  pull_request:
    branches:
      - main
```

---

#### 16. Vì sao không nên chỉ tin rằng ứng dụng đã chạy được trên máy lập trình viên trước khi gửi thay đổi?

**Ý chính:** **Reproducible Build** - Kết quả build cần lặp lại được trong môi trường chuẩn.

**Diễn giải:** Máy cá nhân có thể đang dùng dependency cache, file local hoặc cấu hình mà kho chung không có. Pipeline độc lập giúp phát hiện sự phụ thuộc ẩn này.

**Ví dụ:**

```bash
# Dùng Gradle Wrapper của dự án thay vì Gradle cài riêng
./gradlew clean assembleDebug
```

---

#### 17. Một thay đổi không qua được kiểm tra tự động. Bạn cần làm gì trước khi yêu cầu người khác xem lại?

**Ý chính:** **Failed Pipeline** - Pipeline thất bại cho biết thay đổi chưa đạt điều kiện tích hợp.

**Diễn giải:** Đọc log từ lỗi đầu tiên, sửa tại nguyên nhân và chạy lại phần kiểm tra liên quan. Không nên bỏ qua lỗi chỉ vì một lần build cục bộ từng thành công.

**Ví dụ:**

```bash
# Chạy lại đúng tác vụ lỗi trên máy cá nhân
./gradlew lintDebug testDebugUnitTest
```

---

#### 18. Bạn cần biết file cài đặt thử nghiệm được tạo từ lần kiểm tra nào, nên lưu thông tin đó ở đâu?

**Ý chính:** **Build Artifact** - File đầu ra được pipeline lưu lại sau khi build.

**Diễn giải:** Artifact giúp QA tải đúng bản cần kiểm thử và truy vết nó về thay đổi cụ thể. Cần đặt tên có phiên bản, số lần build hoặc mã thay đổi.

**Ví dụ:**

```yaml
- name: Upload APK
  uses: actions/upload-artifact@v4
  with:
    name: app-debug-${{ github.run_number }}
    path: app/build/outputs/apk/debug/app-debug.apk
```

## CẤP ĐỘ 2: MID-LEVEL (TRUNG CẤP)

### Chủ đề: Lịch sử thay đổi và review

#### 19. Bạn muốn đưa thay đổi mới nhất từ nhánh chung vào phần việc của mình nhưng vẫn giữ lịch sử thẳng, dễ đọc. Nên làm thế nào?

**Ý chính:** **git rebase** - Đặt lại các mốc thay đổi của nhánh hiện tại lên nền mới hơn.

**Diễn giải:** Cách này làm lịch sử gọn khi nhánh chưa được nhiều người cùng phát triển. Không nên dùng để viết lại lịch sử đã chia sẻ rộng rãi nếu nhóm không có quy ước rõ ràng.

**Ví dụ:**

```bash
git fetch origin
git rebase origin/main
```

---

#### 20. Bạn cần đưa một bản sửa lỗi nhỏ đã được kiểm chứng từ nhánh khác vào bản phát hành mà không lấy toàn bộ thay đổi của nhánh đó. Làm thế nào?

**Ý chính:** **git cherry-pick** - Sao chép một mốc thay đổi cụ thể sang nhánh hiện tại.

**Diễn giải:** Phù hợp cho hotfix hoặc backport. Sau khi áp dụng, vẫn phải kiểm thử vì ngữ cảnh ở nhánh đích có thể khác nhánh nguồn.

**Ví dụ:**

```bash
git switch release/2.4
git cherry-pick a1b2c3d
```

---

#### 21. Một bản sửa lỗi đã được gửi lên kho chung và sau đó gây lỗi mới. Làm sao hoàn tác mà không sửa lịch sử chung?

**Ý chính:** **git revert** - Tạo một mốc mới để đảo ngược thay đổi của mốc cũ.

**Diễn giải:** Đây là cách an toàn cho nhánh dùng chung vì mọi người vẫn giữ cùng lịch sử. Cần xác nhận mốc hoàn tác không xóa nhầm thay đổi phụ thuộc vào nó.

**Ví dụ:**

```bash
git revert a1b2c3d
git push origin main
```

#### 22. Khi xem thay đổi của đồng đội, bạn cần đánh giá những điểm nào ngoài việc mã có chạy được?

**Ý chính:** **Code Review** - Kiểm tra tính đúng đắn, khả năng bảo trì, bảo mật và mức độ phù hợp với dự án.

**Diễn giải:** Review tốt cần tập trung vào rủi ro thật: hành vi sai, thiếu kiểm thử, lỗi đa luồng hoặc lộ dữ liệu. Các góp ý về phong cách nên theo quy ước hoặc công cụ tự động.

**Ví dụ:**

```text
Góp ý tốt:
"Đoạn này có thể chạy sau khi màn hình đã bị hủy.
Bạn có thể dùng viewModelScope để tránh giữ tham chiếu sai vòng đời không?"
```

#### 23. Bạn muốn ngăn việc ai đó tự đưa thay đổi chưa được kiểm tra vào nhánh chính. Cần thiết lập quy tắc nào?

**Ý chính:** **Branch Protection Rule** - Quy tắc bảo vệ nhánh quan trọng khỏi thay đổi trực tiếp hoặc chưa được duyệt.

**Diễn giải:** Thường yêu cầu review, CI thành công và nhánh phải cập nhật theo nhánh chính. Quy tắc này giảm rủi ro nhưng không thay thế việc review có chất lượng.

**Ví dụ:**

```yaml
# Ví dụ quy ước mong muốn
main:
  require_pull_request: true
  required_approvals: 1
  required_checks:
    - unit-test
    - lint
```

#### 24. Một thay đổi quá lớn khiến review khó khăn và dễ bỏ sót lỗi. Bạn nên tổ chức lại như thế nào?

**Ý chính:** **Small Pull Request** - Chia thay đổi thành các yêu cầu nhỏ, độc lập và dễ kiểm chứng.

**Diễn giải:** Có thể tách phần chuẩn bị kiến trúc, giao diện, logic và tích hợp. Mỗi yêu cầu nên build được, không chứa thay đổi không liên quan và có mô tả rõ ràng.

**Ví dụ:**

```text
PR 1: Add domain model for login result
PR 2: Add login API implementation
PR 3: Connect login screen to ViewModel
```

### Chủ đề: Pipeline cho Android

#### 25. Làm thế nào để tự động phát hiện mã không tuân thủ quy tắc chất lượng trước khi tạo bản cài đặt?

**Ý chính:** **Android Lint** - Công cụ phân tích tĩnh để phát hiện lỗi và vấn đề Android phổ biến.

**Diễn giải:** Lint có thể cảnh báo resource không dùng, API không tương thích hoặc cách dùng Context rủi ro. Nên chạy trong pipeline và xử lý các cảnh báo quan trọng thay vì tắt hàng loạt.

**Ví dụ:**

```yaml
- name: Run Android lint
  run: ./gradlew lintDebug
```

---

#### 26. Làm thế nào để xác nhận các lớp xử lý nghiệp vụ vẫn đúng sau khi thay đổi mà không cần mở ứng dụng thủ công?

**Ý chính:** **Unit Test** - Kiểm tra tự động các đơn vị logic nhỏ, chạy nhanh và độc lập.

**Diễn giải:** Unit test phù hợp cho ViewModel, UseCase, mapper và validation. Test cần kiểm tra hành vi có ý nghĩa, không chỉ kiểm tra implementation hiện tại.

**Ví dụ:**

```yaml
- name: Run unit tests
  run: ./gradlew testDebugUnitTest
```

---

#### 27. Bạn cần kiểm tra luồng đăng nhập trên thiết bị mô phỏng trước khi phát hành. Pipeline nên làm gì?

**Ý chính:** **Instrumentation Test** - Kiểm tra chạy trên Android runtime hoặc thiết bị mô phỏng.

**Diễn giải:** Loại kiểm tra này phù hợp khi cần xác minh UI, database hoặc Android framework. Nó chậm hơn unit test nên nên được cấu hình thời gian chờ và log rõ ràng.

**Ví dụ:**

```yaml
- name: Run connected tests
  run: ./gradlew connectedDebugAndroidTest
```

#### 28. Bạn muốn tránh để khóa ký bản phát hành xuất hiện trong mã nguồn hoặc log build. Nên quản lý như thế nào?

**Ý chính:** **CI Secret** - Thông tin nhạy cảm được lưu mã hóa trong hệ thống pipeline.

**Diễn giải:** Khóa, mật khẩu và token phải lấy từ secret thay vì ghi trực tiếp trong file cấu hình. Pipeline cũng cần tránh in giá trị đó ra log.

**Ví dụ:**

```yaml
- name: Decode signing key
  env:
    KEYSTORE_BASE64: ${{ secrets.KEYSTORE_BASE64 }}
  run: echo "$KEYSTORE_BASE64" | base64 --decode > release.jks
```

#### 29. Pipeline cần dùng đúng phiên bản công cụ để build ổn định. Bạn nên cố định những gì?

**Ý chính:** **Build Environment Pinning** - Cố định phiên bản JDK, Android SDK, Gradle và dependency cần thiết.

**Diễn giải:** Việc dùng phiên bản mới nhất tự động có thể làm pipeline lỗi bất ngờ. Cố định phiên bản giúp kết quả nhất quán và nâng cấp có chủ đích.

**Ví dụ:**

```yaml
- name: Set up JDK 17
  uses: actions/setup-java@v4
  with:
    distribution: temurin
    java-version: "17"
```

#### 30. Pipeline Android chạy quá lâu vì lần nào cũng tải lại thư viện. Bạn tối ưu theo hướng nào?

**Ý chính:** **Dependency Cache** - Lưu lại dependency đã tải để tái sử dụng ở lần chạy sau.

**Diễn giải:** Cache giúp giảm thời gian build nhưng không được làm pipeline dùng kết quả cũ sai lệch. Cache key cần thay đổi khi file khai báo dependency thay đổi.

**Ví dụ:**

```yaml
- name: Cache Gradle
  uses: actions/cache@v4
  with:
    path: ~/.gradle/caches
    key: gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}
```

### Chủ đề: Phát hành và xử lý lỗi

#### 31. Bạn cần tạo bản cài đặt thử nghiệm cho QA mỗi khi nhánh kiểm thử được cập nhật. Nên thiết kế luồng nào?

**Ý chính:** **CD (Continuous Delivery)** - Tự động chuẩn bị bản phát hành sau khi các kiểm tra đạt yêu cầu.

**Diễn giải:** CD có thể build, ký, tải artifact lên hệ thống phân phối và thông báo cho QA. Bước phát hành ra người dùng thật vẫn có thể yêu cầu phê duyệt thủ công.

**Ví dụ:**

```yaml
on:
  push:
    branches:
      - develop

jobs:
  distribute:
    runs-on: ubuntu-latest
    steps:
      - run: ./gradlew assembleDebug
```

#### 32. Làm sao phân biệt rõ bản dành cho phát triển, kiểm thử nội bộ và người dùng thật?

**Ý chính:** **Product Flavors** - Tạo các biến thể ứng dụng cho từng môi trường sử dụng.

**Diễn giải:** Mỗi biến thể có thể dùng endpoint, tên ứng dụng và cấu hình riêng. Không nên để bản phát hành thật trỏ nhầm sang máy chủ kiểm thử.

**Ví dụ:**

```kotlin
android {
    flavorDimensions += "environment"
    productFlavors {
        create("staging") {
            applicationIdSuffix = ".staging"
        }
        create("production") {}
    }
}
```

#### 33. Một bản cài đặt thử nghiệm bị lỗi nhưng bạn không biết nó được tạo từ thay đổi nào. Nên bổ sung thông tin gì?

**Ý chính:** **Version Metadata** - Gắn số phiên bản, số build và mã thay đổi vào bản phát hành.

**Diễn giải:** Metadata giúp QA, developer và pipeline nói về cùng một bản. Có thể hiển thị trong màn hình thông tin ứng dụng hoặc log khi khởi động.

**Ví dụ:**

```kotlin
defaultConfig {
    versionCode = 120
    versionName = "2.4.0"
    buildConfigField("String", "GIT_SHA", "\"${System.getenv("GIT_SHA") ?: "local"}\"")
}
```

#### 34. Bản phát hành mới gây lỗi nghiêm trọng cho một nhóm người dùng. Bạn cần có khả năng nào để phản ứng nhanh?

**Ý chính:** **Rollback** - Quay về bản ổn định trước đó hoặc tắt tính năng gây lỗi.

**Diễn giải:** Với Android, người dùng không luôn nhận bản cài đặt mới ngay lập tức nên cần kết hợp theo dõi lỗi và cấu hình từ xa. Rollback phải được chuẩn bị trước, không nên đợi sự cố mới nghĩ tới.

**Ví dụ:**

```json
{
  "new_checkout_enabled": false
}
```

#### 35. Bạn muốn cho một nhóm nhỏ dùng thử tính năng mới trước khi mở rộng cho toàn bộ người dùng. Cách tiếp cận nào phù hợp?

**Ý chính:** **Feature Flag** - Cờ cấu hình cho phép bật hoặc tắt tính năng mà không cần phát hành lại ứng dụng.

**Diễn giải:** Có thể bật theo nhóm người dùng, phiên bản hoặc phần trăm lưu lượng. Cần có giá trị mặc định an toàn và kế hoạch xóa cờ sau khi tính năng ổn định.

**Ví dụ:**

```kotlin
if (remoteConfig.getBoolean("new_payment_enabled")) {
    showNewPayment()
} else {
    showCurrentPayment()
}
```

#### 36. Làm thế nào để thông báo nhanh cho nhóm khi quá trình tạo bản cài đặt thất bại?

**Ý chính:** **Pipeline Notification** - Gửi trạng thái pipeline đến kênh liên lạc của nhóm.

**Diễn giải:** Thông báo nên chứa liên kết tới log, nhánh, người gửi thay đổi và bước thất bại. Tránh gửi quá nhiều thông báo không cần thiết khiến mọi người bỏ qua cảnh báo thật.

**Ví dụ:**

```yaml
- name: Notify failure
  if: failure()
  run: |
    curl -X POST "$WEBHOOK_URL" \
      -d '{"text":"Android build failed. Check pipeline logs."}'
```

**Diễn giải:** Cách này giảm thời gian tồn tại của nhánh dài và giảm xung đột khi tích hợp. Nó đòi hỏi CI nhanh, review nghiêm túc và khả năng tắt tính năng chưa hoàn thiện.

#### 38. Sản phẩm cần duy trì nhiều bản đang phát hành cho các đối tác khác nhau. Bạn thiết kế cách quản lý bản sửa lỗi ra sao?

**Ý chính:** **Release Branch Strategy** - Dùng nhánh phát hành ổn định và đưa bản sửa cần thiết vào từng nhánh có kiểm soát.

**Diễn giải:** Cần xác định rõ thay đổi nào được phép đưa vào bản đang ổn định. Mỗi bản sửa nên được kiểm thử trên nhánh đích, không giả định rằng sửa ở nhánh mới nhất luôn hoạt động ở bản cũ.

#### 40. Pipeline hiện có thể phát hành nhầm bản kiểm thử sang môi trường thật. Bạn cần thiết kế chốt an toàn nào?

#### 41. Bạn muốn ngăn một thay đổi chưa hoàn thiện nhưng đã được ghép vào nhánh chính ảnh hưởng người dùng. Cần phối hợp những cơ chế nào?

### Chủ đề: Bảo mật chuỗi phát hành

#### 42. Làm thế nào để giảm rủi ro khóa ký ứng dụng bị lộ trong quá trình tạo bản phát hành?

**Ý chính:** **Signing Key Management** - Bảo vệ khóa ký bằng secret store, phân quyền tối thiểu và quy trình truy cập có kiểm toán.

**Diễn giải:** Khóa không nên nằm trong repository, máy developer hoặc artifact lâu dài. Chỉ job phát hành được cấp quyền truy cập và file tạm cần được xóa sau khi dùng.

**Ví dụ:**


#### 43. Một thư viện bên ngoài bị phát hiện có lỗ hổng. Pipeline nên giúp nhóm phát hiện sớm bằng cách nào?

**Ý chính:** **Dependency Scanning** - Quét dependency để phát hiện phiên bản có lỗ hổng đã biết.

**Diễn giải:** Kết quả quét cần được phân loại theo mức độ ảnh hưởng thực tế, không chỉ dựa vào điểm số. Nhóm cần có SLA xử lý rõ ràng cho các lỗ hổng nghiêm trọng.

**Ví dụ:**

```yaml
- name: Dependency vulnerability scan
  run: ./gradlew dependencyCheckAnalyze
```

#### 44. Làm thế nào để hạn chế việc một thay đổi độc hại được tự động phát hành chỉ vì đã vượt qua build?

**Ý chính:** **Separation of Duties** - Tách quyền viết mã, phê duyệt, sửa pipeline và phát hành.

**Diễn giải:** Một cá nhân không nên kiểm soát toàn bộ đường đi từ thay đổi đến production. Quy tắc review, protected environment và audit log tạo nhiều lớp kiểm soát.

**Ví dụ:**

```text
Developer: tạo thay đổi
Reviewer: duyệt thay đổi
Release manager: phê duyệt phát hành production
CI service account: thực hiện phát hành
```

#### 45. Bạn cần xác minh file cài đặt được phát hành đúng là file do pipeline tin cậy tạo ra. Nên dùng cơ chế nào?

**Ý chính:** **Artifact Attestation** - Chứng thực nguồn gốc artifact, bao gồm mã nguồn và pipeline đã tạo ra nó.

**Diễn giải:** Cơ chế này giúp giảm rủi ro artifact bị thay thế sau khi build. Nên lưu checksum và thông tin nguồn cùng artifact để phục vụ kiểm tra sau này.

**Ví dụ:**

```bash
sha256sum app-release.apk > app-release.apk.sha256
sha256sum --check app-release.apk.sha256
```

#### 46. Pipeline mất hơn một giờ khiến nhóm ngại gửi thay đổi nhỏ. Bạn phân tích và cải thiện theo thứ tự nào?

**Ý chính:** **Pipeline Optimization** - Đo thời gian từng bước, tối ưu nút thắt lớn nhất và chạy công việc song song khi độc lập.

**Diễn giải:** Bắt đầu từ dữ liệu: dependency download, build, test hay emulator. Không nên tối ưu bằng cách tắt các kiểm tra quan trọng chỉ để pipeline có màu xanh nhanh hơn.

**Ví dụ:**

```yaml
jobs:
```

#### 47. Làm thế nào để xác định thay đổi nào làm tỷ lệ lỗi tăng sau khi phát hành?

**Diễn giải:** Dashboard cần gắn phiên bản ứng dụng và thời điểm rollout để đối chiếu. Cảnh báo nên có ngưỡng phù hợp, tránh cả bỏ sót sự cố lẫn tạo cảnh báo nhiễu.

#### 48. Một số kiểm tra trên thiết bị mô phỏng đôi khi lỗi ngẫu nhiên dù mã không đổi. Bạn xử lý thế nào để không làm mất niềm tin vào pipeline?

**Ý chính:** **Flaky Test Management** - Xác định, cô lập, sửa nguyên nhân gốc và theo dõi tỷ lệ lỗi không ổn định.

**Diễn giải:** Không nên retry vô hạn vì nó che giấu lỗi thật. Test lỗi ngẫu nhiên cần được gắn nhãn, có owner và ưu tiên sửa tương xứng với mức độ ảnh hưởng.

```yaml
# Chỉ retry có giới hạn để thu thập thông tin, không thay thế việc sửa test
```

#### 49. Làm thế nào để tránh việc hai lần chạy cùng phát hành một bản hoặc ghi đè kết quả của nhau?

**Ý chính:** **Concurrency Control** - Kiểm soát để các quy trình cùng tài nguyên không chạy chồng chéo.

**Diễn giải:** Điều này đặc biệt quan trọng khi dùng cùng version code, cùng kênh phát hành hoặc cùng môi trường kiểm thử. Pipeline nên hủy bản cũ hoặc xếp hàng tùy tính chất công việc.

**Ví dụ:**

```yaml
concurrency:
  group: android-release-production
  cancel-in-progress: false
```

#### 50. Bạn thiết kế các điều kiện nào để một thay đổi có thể đi từ lúc gửi lên đến khi được phát hành an toàn?

**Ví dụ:**

```yaml
release_requirements:
```
