
# CÂU HỎI ÔN TẬP DEPENDENCY INJECTION (DI)

## CẤP ĐỘ 1: JUNIOR (CƠ BẢN)

### Chủ đề: Core DI & Hilt Basics

#### 1. Làm thế nào để giảm sự phụ thuộc chặt chẽ giữa các class?

**Ý chính:** Dependency Injection (DI) - Truyền các thành phần phụ thuộc từ ngoài vào class, thay vì để class tự khởi tạo.

**Diễn giải:** Giúp code giảm bớt sự gắn kết chặt chẽ (Loose coupling), dễ dàng thay thế linh kiện, bảo trì và viết Unit Test.

**Ví dụ:**

```kotlin
// SAI: Class tự khởi tạo phụ thuộc
class Car {
    val engine = Engine() // Gắn chặt với Engine cụ thể
}

// ĐÚNG: Dependency Injection qua Constructor
class Car(val engine: Engine) // Linh hoạt, dễ test
```

#### 2. Thư viện DI chính thức của Android là gì?

**Ý chính:** Hilt - Thư viện DI chính thức cho Android, được xây dựng trên nền tảng (Wrapper) của Dagger.

**Diễn giải:** Dagger rất mạnh nhưng cấu hình cực kỳ phức tạp. Hilt sinh ra để đơn giản hóa Dagger bằng cách định nghĩa sẵn các Component gắn liền với vòng đời Android (Activity, Fragment, ViewModel).

**Ví dụ:**

```kotlin
// Không cần viết mã cấu hình boilerplate khởi tạo Dagger Component nữa
@HiltAndroidApp
class MyApp : Application()
```

#### 3. Làm thế nào để kích hoạt Hilt trong toàn bộ ứng dụng?

**Ý chính:** `@HiltAndroidApp` - Kích hoạt Hilt trong toàn bộ ứng dụng của bạn.

**Diễn giải:** Bắt buộc phải gắn nhãn này ở class Application. Nó sẽ kích hoạt quá trình tự động sinh code (Code generation) của Hilt ở lớp nền tảng.

**Ví dụ:**

```kotlin
@HiltAndroidApp
class MyApp : Application()
```

#### 4. Làm thế nào để đánh dấu nơi Hilt sẽ inject dependencies?

**Ý chính:** `@AndroidEntryPoint` - Đánh dấu nơi Hilt sẽ bơm (Inject) các phụ thuộc vào class của Android.

**Diễn giải:** Dùng cho Activity, Fragment, View, Service, và Broadcast Receiver để báo rằng: "Class này cần nhận các instance từ Hilt".

**Ví dụ:**

```kotlin
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var repository: MyRepository
}
```

#### 5. Hai cách inject phụ thuộc khác nhau như thế nào?

**Ý chính:** Constructor Injection vs Field Injection - Constructor Injection truyền qua hàm tạo (Khuyên dùng); Field Injection bơm thẳng vào biến bằng `@Inject lateinit var`.

**Diễn giải:** Constructor Injection an toàn hơn vì class không thể tạo ra nếu thiếu phụ thuộc. Field Injection chỉ dùng khi class đó do hệ điều hành Android tự quản lý khởi tạo (như Activity/Fragment).

**Ví dụ:**

```kotlin
// Constructor Injection (Khuyên dùng):
class MyRepo @Inject constructor(val api: Api)

// Field Injection (Chỉ dùng cho Android components):
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var api: Api
}
```

#### 6. Khi nào cần sử dụng Module trong Hilt?

**Ý chính:** `@Module` - Khi ta cần chỉ cho Hilt cách khởi tạo các class mà ta không thể thêm `@Inject` vào constructor của chúng.

**Diễn giải:** Thường dùng cho các class thuộc thư viện bên thứ ba (Retrofit, Room RoomDatabase, OkHttpClient) hoặc các Interface.

**Ví dụ:**

```kotlin
// Class Retrofit.Builder() là của Square, 
// ta không thể nhảy vào sửa source code của họ để thêm @Inject
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.com")
        .build()
}
```

#### 7. Làm thế nào để viết logic khởi tạo một đối tượng trong Module?

**Ý chính:** `@Provides` - Đứng trong `@Module`, dùng để viết logic khởi tạo ra một đối tượng cụ thể.

**Diễn giải:** Hàm đi kèm `@Provides` sẽ trả về instance của class mà bạn muốn đăng ký vào hệ thống Hilt.

**Ví dụ:**

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.com")
        .build()
}
```

#### 8. Làm thế nào để xác định phạm vi sống của một Module?

**Ý chính:** `@InstallIn` - Xác định phạm vi sống (Scope) và nơi quản lý của một `@Module`.

**Diễn giải:** Bạn phải khai báo rõ Module này thuộc về Component nào, từ đó quyết định xem các đối tượng trong module sẽ tồn tại bao lâu.

**Ví dụ:**

```kotlin
// @InstallIn(SingletonComponent::class) nghĩa là 
// các đối tượng sống thọ bằng toàn bộ App
@Module
@InstallIn(SingletonComponent::class)
object AppModule {
    @Provides
    fun provideDatabase(): AppDatabase = ...
}
```

#### 9. Làm thế nào để inject một ViewModel bằng Hilt?

**Ý chính:** `@HiltViewModel` - Dùng annotation này trên class và `@Inject constructor`.

**Diễn giải:** Ở phía UI (Activity/Fragment), ta gọi lấy ViewModel thông qua hàm delegate `by viewModels()`.

**Ví dụ:**

```kotlin
@HiltViewModel
class MainViewModel @Inject constructor(
    val repo: MyRepo
) : ViewModel()

// Trong Activity/Fragment
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    private val viewModel: MainViewModel by viewModels()
}
```

#### 10. Tại sao biến inject không được phép là private?

**Ý chính:** Visibility của `@Inject lateinit var` - Vì Hilt cần truy cập trực tiếp từ bên ngoài class sinh ra (Generated code) để gán giá trị cho biến đó.

**Diễn giải:** Nếu để private, mã nguồn do Hilt tự sinh ở package khác không thể ghi dữ liệu vào biến, dẫn đến lỗi biên dịch.

**Ví dụ:**

```kotlin
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    // ĐÚNG
    @Inject lateinit var repository: MyRepository
    
    // SAI - Lỗi biên dịch
    // @Inject private lateinit var repository: MyRepository
}
```

### Chủ đề: Scopes & Components (Cơ bản)

#### 11. Các Component phổ biến trong Hilt và vòng đời của chúng?

**Ý chính:** Hilt Components - `SingletonComponent` (Toàn app), `ActivityComponent` (Theo Activity), `ViewModelComponent` (Theo ViewModel).

**Diễn giải:** Mỗi component tương ứng với một mốc vòng đời Android. Khi đối tượng Android bị hủy, Component tương ứng cũng bị hủy để giải phóng bộ nhớ.

**Ví dụ:**

```kotlin
// SingletonComponent - Sống suốt đời app
@Module
@InstallIn(SingletonComponent::class)
object AppModule { }

// ActivityComponent - Sống theo Activity
@Module
@InstallIn(ActivityComponent::class)
object ActivityModule { }

// ViewModelComponent - Sống theo ViewModel
@Module
@InstallIn(ViewModelComponent::class)
object ViewModelModule { }
```

#### 12. Làm thế nào để đảm bảo chỉ có một instance duy nhất trong toàn app?

**Ý chính:** `@Singleton` - Đảm bảo Hilt chỉ tạo ra đúng duy nhất 1 instance của class đó trong suốt vòng đời ứng dụng.

**Diễn giải:** Mọi nơi yêu cầu inject class này đều nhận chung một vùng nhớ. Đi kèm với SingletonComponent.

**Ví dụ:**

```kotlin
@Singleton
class AuthManager @Inject constructor(
    private val prefs: SharedPreferences
) {
    // Chỉ có 1 instance duy nhất trong toàn app
}

@Module
@InstallIn(SingletonComponent::class)
object AppModule {
    @Provides
    @Singleton
    fun provideDatabase(): AppDatabase = ...
}
```

#### 13. Phân biệt hai loại scope khác nhau?

**Ý chính:** `@Singleton` vs `@ActivityScoped` - `@Singleton` tạo 1 instance cho cả app; `@ActivityScoped` tạo 1 instance riêng cho mỗi Activity mới được mở.

**Diễn giải:** Nếu bạn mở 2 Activity khác nhau, đối tượng `@ActivityScoped` sẽ được tạo mới 2 lần độc lập.

**Ví dụ:**

```kotlin
// Singleton - Chung cho toàn app
@Singleton
class AppDatabase @Inject constructor() { }

// ActivityScoped - Mỗi Activity có instance riêng
@ActivityScoped
class ActivityAdapter @Inject constructor() { }
```

#### 14. Điều gì xảy ra khi không gắn Scope Annotation?

**Ý chính:** Unscoped - Hilt sẽ tạo ra một instance mới hoàn toàn mỗi khi có nơi yêu cầu inject class đó.

**Diễn giải:** Việc này giúp tiết kiệm bộ nhớ lâu dài vì xài xong app tự dọn rác, nhưng tốn chi phí khởi tạo nếu class đó nặng.

**Ví dụ:**

```kotlin
// Không có scope annotation - Tạo mới mỗi lần inject
class TempCalculator @Inject constructor() {
    // Instance mới mỗi lần được inject
}
```

#### 15. Làm thế nào để inject Context trong Hilt?

**Ý chính:** `@ApplicationContext` và `@ActivityContext` - Dùng annotation này để inject Context của ứng dụng hoặc Activity.

**Diễn giải:** Hilt cung cấp sẵn các qualifier này để tránh việc truyền nhầm loại Context gây rò rỉ bộ nhớ.

**Ví dụ:**

```kotlin
class SharedPrefManager @Inject constructor(
    @ApplicationContext val context: Context
) {
    private val prefs = context.getSharedPreferences("app_prefs", Context.MODE_PRIVATE)
}

@ActivityScoped
class ActivityHelper @Inject constructor(
    @ActivityContext val context: Context
) {
    // Sử dụng Activity context
}
```

## CẤP ĐỘ 2: MID-LEVEL (TRUNG CẤP)

### Chủ đề: Binds, Qualifiers & Multi-binding

#### 16. Phân biệt hai cách cung cấp dependencies trong Module?

**Ý chính:** `@Provides` vs `@Binds` - `@Provides` dùng cho code có logic khởi tạo; `@Binds` dùng để map một Interface vào một Class triển khai (Implementation) cụ thể.

**Diễn giải:** `@Binds` là hàm abstract, không chứa thân hàm, giúp Hilt tối ưu hiệu năng biên dịch và sinh ra ít code trung gian hơn.

**Ví dụ:**

```kotlin
@Module
@InstallIn(SingletonComponent::class)
abstract class AnalyticsModule {
    // @Binds - Cho interface
    @Binds
    abstract fun bindAnalyticsService(
        impl: AnalyticsServiceImpl
    ): AnalyticsService
}

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    // @Provides - Cho logic khởi tạo phức tạp
    @Provides
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.com")
        .build()
}
```

#### 17. Làm thế nào để phân biệt khi có nhiều cách khởi tạo cho cùng một kiểu dữ liệu?

**Ý chính:** `@Qualifier` - Giúp Hilt phân biệt khi có nhiều cách khởi tạo khác nhau cho cùng một kiểu dữ liệu.

**Diễn giải:** Nếu bạn có 2 bản OkHttpClient (một bản có Token bảo mật, một bản không), Hilt sẽ bị bối rối không biết đưa bản nào nếu chỉ dựa vào kiểu dữ liệu. Qualifier tạo ra nhãn riêng để chỉ định rõ.

**Ví dụ:**

```kotlin
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthenticatedOkHttpClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PublicOkHttpClient

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    @AuthenticatedOkHttpClient
    fun provideAuthClient(): OkHttpClient = OkHttpClient.Builder()
        .addInterceptor(AuthInterceptor())
        .build()
    
    @Provides
    @PublicOkHttpClient
    fun providePublicClient(): OkHttpClient = OkHttpClient.Builder()
        .build()
}
```

#### 18. Cách tạo và sử dụng Qualifier?

**Ý chính:** Custom Qualifier - Định nghĩa một `@Qualifier` annotation và gắn nó vào cả nơi `@Provides` lẫn nơi `@Inject`.

**Diễn giải:** Qualifier giúp phân biệt các instance cùng kiểu dữ liệu.

**Ví dụ:**

```kotlin
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthApi

// Trong Module
@Module
@InstallIn(SingletonComponent::class)
object ApiModule {
    @Provides
    @AuthApi
    fun provideAuthApi(): Api = Retrofit.Builder()
        .baseUrl("https://auth.api.com")
        .build()
        .create(Api::class.java)
}

// Nơi sử dụng
class Repo @Inject constructor(
    @AuthApi val api: Api
)
```

#### 19. Làm thế nào để gom nhiều đối tượng vào một tập hợp?

**Ý chính:** Multi-binding - Gom nhiều đối tượng từ nhiều module khác nhau vào chung một tập hợp Set hoặc Map.

**Diễn giải:** Giúp bạn thiết kế kiến trúc mở (Plugin-play). Các module con tự đăng ký tính năng của mình vào một Map tổng mà Module tổng không cần biết trước.

**Ví dụ:**

```kotlin
// Gom các interceptor từ nhiều feature module
@Module
@InstallIn(SingletonComponent::class)
object HomeModule {
    @Provides
    @IntoSet
    fun provideHomeInterceptor(): Interceptor = HomeInterceptor()
}

@Module
@InstallIn(SingletonComponent::class)
object ProfileModule {
    @Provides
    @IntoSet
    fun provideProfileInterceptor(): Interceptor = ProfileInterceptor()
}

// Sử dụng
class NetworkClient @Inject constructor(
    val interceptors: Set<@JvmSuppressWildcards Interceptor>
) {
    // Nhận tất cả interceptors từ các module
}
```

#### 20. Khi nào sử dụng IntoSet và IntoMap?

**Ý chính:** `@IntoSet` và `@IntoMap` - Dùng khi thực hiện Multi-binding để đưa một phần tử đơn lẻ vào Set hoặc Map chung của Hilt.

**Ví dụ:**

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object InterceptorModule {
    @Provides
    @IntoSet
    fun provideLoggingInterceptor(): Interceptor = LoggingInterceptor()
    
    @Provides
    @IntoSet
    fun provideAuthInterceptor(): Interceptor = AuthInterceptor()
}

// Sử dụng Set
class OkHttpProvider @Inject constructor(
    val interceptors: Set<@JvmSuppressWildcards Interceptor>
)
```

### Chủ đề: Hilt với các thành phần Jetpack khác

#### 21. Làm thế nào để inject dependencies vào Worker?

**Ý chính:** `@HiltWorker` và `@AssistedInject` - Dùng annotation này trên class và `@AssistedInject` cho constructor.

**Diễn giải:** Do WorkManager tự tạo Worker tại runtime, ta phải dùng cơ chế Assisted Injection để Hilt bơm các phụ thuộc, còn hệ thống truyền các tham số runtime (Context, WorkerParameters).

**Ví dụ:**

```kotlin
@HiltWorker
class MyWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    val api: MyApi
) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        // Sử dụng api được inject
        return Result.success()
    }
}
```

#### 22. Assisted Injection là gì và khi nào cần dùng?

**Ý chính:** Assisted Injection - Kỹ thuật inject đối tượng mà một số tham số do Hilt cấp, một số tham số do lập trình viên tự truyền vào lúc runtime.

**Diễn giải:** Cực kỳ hữu ích khi một class cần cả các dịch vụ hệ thống (như Repository) lẫn một ID cụ thể do người dùng click chọn từ màn hình trước.

**Ví dụ:**

```kotlin
class DetailViewModel @AssistedInject constructor(
    @Assisted val itemId: String,
    val repository: ItemRepository
) : ViewModel() {
    
    @AssistedFactory
    interface Factory {
        fun create(itemId: String): DetailViewModel
    }
}

// Sử dụng
@AndroidEntryPoint
class DetailActivity : AppCompatActivity() {
    @Inject lateinit var viewModelFactory: DetailViewModel.Factory
    
    private val viewModel by lazy {
        viewModelFactory.create(intent.getStringExtra("ITEM_ID")!!)
    }
}
```

#### 23. Tại sao Hilt không cần viết Component thủ công?

**Ý chính:** Predefined Components - Vì Hilt đã định nghĩa sẵn hệ thống Component phân cấp theo kiến trúc chuẩn của Android rồi.

**Diễn giải:** Giúp loại bỏ hoàn toàn mã nguồn boilerplate khổng lồ. Lập trình viên chỉ cần chọn Component có sẵn thông qua `@InstallIn`.

**Ví dụ:**

```kotlin
// Không cần viết:
// @Component(modules = [AppModule::class])
// interface AppComponent { ... }

// Chỉ cần:
@Module
@InstallIn(SingletonComponent::class)
object AppModule { }
```

#### 24. Component Hierarchy trong Hilt hoạt động như thế nào?

**Ý chính:** Component Hierarchy - Component con có thể nhìn thấy và sử dụng đối tượng của Component cha, nhưng cha không thể nhìn thấy của con.

**Diễn giải:** ActivityComponent là con của SingletonComponent. Vì vậy, một đối tượng Scope Activity có thể inject một đối tượng Scope Singleton, nhưng ngược lại thì không.

**Ví dụ:**

```kotlin
// ĐÚNG: Activity có thể dùng Singleton
@ActivityScoped
class ActivityHelper @Inject constructor(
    val appDatabase: AppDatabase // @Singleton
)

// SAI: Singleton KHÔNG thể dùng Activity-scoped
// @Singleton
// class AppService @Inject constructor(
//     val activityHelper: ActivityHelper // @ActivityScoped - LỖI!
// )
```

#### 25. Làm thế nào để lấy dependency từ Hilt trong class không được hỗ trợ sẵn?

**Ý chính:** EntryPointAccessors - Sử dụng để truy cập thủ công vào đồ thị đồ vật (Dependency Graph) của Hilt.

**Diễn giải:** Khai báo một interface đại diện có nhãn `@EntryPoint`, sau đó dùng Accessors để truy cập thủ công vào đồ thị đồ vật (Dependency Graph) của Hilt.

**Ví dụ:**

```kotlin
@EntryPoint
@InstallIn(SingletonComponent::class)
interface CryptoEntryPoint {
    fun getCrypto(): CryptoUtils
}

// Trong class không hỗ trợ @AndroidEntryPoint
class CustomView(context: Context) : View(context) {
    private val crypto: CryptoUtils by lazy {
        val hiltEntryPoint = EntryPointAccessors.fromApplication(
            context.applicationContext,
            CryptoEntryPoint::class.java
        )
        hiltEntryPoint.getCrypto()
    }
}
```

## CẤP ĐỘ 3: SENIOR (NÂNG CAO)

### Chủ đề: Dagger Deep Dive & Custom Components

#### 26. Dagger hoạt động theo cơ chế nào và tại sao hiệu năng cao?

**Ý chính:** Annotation Processing - Hoàn toàn dựa trên Annotation Processing (Sinh code ở thời điểm biên dịch - Compile time), không dùng Reflection ở runtime.

**Diễn giải:** Dagger duyệt qua các annotation và tự viết ra các class Java thuần thực hiện việc nối dây (Factories, MembersInjectors). Khi app chạy, nó chỉ là các lời gọi hàm Java thông thường, tốc độ tối đa, không tốn CPU quét bộ nhớ.

**Ví dụ:**

```kotlin
// Code bạn viết
class MyRepo @Inject constructor(val api: Api)

// Dagger tự sinh ra (đơn giản hóa):
// class MyRepo_Factory implements Factory<MyRepo> {
//     public MyRepo get() {
//         return new MyRepo(apiProvider.get());
//     }
// }
```

#### 27. Phân biệt Lazy và Provider trong Dagger/Hilt?

**Ý chính:** `Lazy<T>` vs `Provider<T>` - `Lazy<T>` trì hoãn việc tạo đối tượng và luôn trả về cùng một instance sau đó; `Provider<T>` tạo ra một instance mới hoàn toàn mỗi lần bạn gọi hàm `.get()`.

**Diễn giải:**
- `Lazy<T>`: Tối ưu khi đối tượng đó nặng và chưa chắc màn hình hiện tại đã cần dùng tới ngay.
- `Provider<T>`: Cần thiết khi bạn muốn lấy các instance ngắn hạn, độc lập liên tục.

**Ví dụ:**

```kotlin
class MyViewModel @Inject constructor(
    val heavyMatrix: Lazy<HeavyMatrix>, // Chỉ tạo khi gọi .get() lần đầu
    val tempCalculator: Provider<TempCalculator> // Tạo mới mỗi lần .get()
) : ViewModel() {
    fun calculate() {
        val matrix = heavyMatrix.get() // Lần đầu: tạo mới, lần sau: dùng lại
        val calc1 = tempCalculator.get() // Instance 1
        val calc2 = tempCalculator.get() // Instance 2 (khác calc1)
    }
}
```

#### 28. Subcomponent trong Dagger là gì?

**Ý chính:** Subcomponent - Là component kế thừa và mở rộng đồ thị phụ thuộc của một Component cha.

**Diễn giải:** Trong Dagger thuần, bạn phải tự viết quan hệ cha-con. Trong Hilt, mối quan hệ này được cấu trúc mặc định ngầm bên dưới (ví dụ: FragmentComponent thực chất là một Subcomponent của ActivityComponent).

**Ví dụ:**

```kotlin
// Trong Hilt, hierarchy tự động:
// SingletonComponent
//   └── ActivityComponent
//         └── FragmentComponent
//               └── ViewComponent

// FragmentComponent có thể truy cập dependencies từ ActivityComponent và SingletonComponent
```

#### 29. Làm thế nào để tạo Custom Component trong Hilt?

**Ý chính:** `@DefineComponent` - Hilt không khuyến khích tạo Custom Component tùy tiện, nhưng bạn có thể làm được bằng `@DefineComponent`.

**Diễn giải:** Bạn định nghĩa interface cho Component mới, chỉ định cha của nó, và tạo một Builder tương ứng để tự quản lý vòng đời của nó.

**Ví dụ:**

```kotlin
@Scope
@Retention(AnnotationRetention.RUNTIME)
annotation class UserSessionScope

@DefineComponent(parent = SingletonComponent::class)
@UserSessionScope
interface UserSessionComponent {
    @DefineComponent.Builder
    interface Builder {
        fun build(): UserSessionComponent
    }
}

// Tạo một UserSessionComponent riêng để lưu trữ dữ liệu 
// chỉ khi người dùng đã đăng nhập, và hủy sạch khi họ log out
```

#### 30. Nguy hiểm của việc lạm dụng Singleton?

**Ý chính:** Memory Bloat - Gây rò rỉ bộ nhớ (Memory Bloat) và phá vỡ tính đóng gói của tính năng.

**Diễn giải:** Các đối tượng Singleton không bao giờ bị xóa khỏi RAM cho đến khi app chết. Việc để quá nhiều class dạng này khiến app ngày càng nặng theo thời gian. Nên ưu tiên Unscoped hoặc gắn scope ngắn hạn.

**Ví dụ:**

```kotlin
// SAI: Lạm dụng Singleton
@Singleton
class TemporaryCache @Inject constructor() {
    // Cache này chỉ cần trong 1 màn hình nhưng lại sống suốt đời app
}

// ĐÚNG: Dùng scope phù hợp
@ActivityScoped
class TemporaryCache @Inject constructor() {
    // Tự động giải phóng khi Activity destroy
}
```

#### 31. Làm thế nào để Hilt phát hiện lỗi thiếu phụ thuộc trước khi App chạy?

**Ý chính:** Compile-time validation - Cơ chế kiểm tra lỗi ngay lúc biên dịch.

**Diễn giải:** Đây là ưu điểm tuyệt đối của Dagger/Hilt so với Koin. Nếu bạn quên chưa chỉ cách tạo Repo, Dagger sẽ lập tức báo lỗi đỏ rực khi nhấn nút Build, không bao giờ để lỗi lọt ra ngoài Store làm crash máy khách hàng.

**Ví dụ:**

```kotlin
// Nếu quên provide Repository
class MyViewModel @Inject constructor(
    val repository: MyRepository // Lỗi compile: Cannot find binding for MyRepository
)

// Phải thêm:
@Module
@InstallIn(SingletonComponent::class)
object DataModule {
    @Provides
    fun provideRepository(): MyRepository = MyRepositoryImpl()
}
```

#### 32. Cyclic Dependency là gì và cách giải quyết?

**Ý chính:** Cyclic Dependency - Class A cần Class B để khởi tạo, nhưng Class B lại đang đòi Class A.

**Diễn giải:** Tạo thành một vòng lặp vô tận khiến compiler bó tay. Cách giải quyết triệt để là tách phần chung ra một Class C thứ ba, hoặc sử dụng `Lazy<T>` ở một trong hai đầu để hoãn việc đòi instance.

**Ví dụ:**

```kotlin
// SAI: Cyclic dependency
class A @Inject constructor(val b: B)
class B @Inject constructor(val a: A) // Lỗi!

// ĐÚNG: Dùng Lazy
class A @Inject constructor(val b: Lazy<B>)
class B @Inject constructor(val a: A)
```

### Chủ đề: So sánh kiến trúc & Bản chất hệ thống

#### 36. So sánh chi tiết Hilt/Dagger và Koin?

**Ý chính:** Compile-time DI vs Runtime Service Locator - Dagger/Hilt là Compile-time DI (Kiểm tra lúc dịch code); Koin là Runtime Service Locator (Quét và cung cấp lúc app đang chạy).

**Diễn giải:**
- Hilt: An toàn tuyệt đối, phát hiện lỗi sớm, không tốn CPU lúc chạy, nhưng build app lâu hơn.
- Koin: Build app rất nhanh, code viết ngắn gọn dễ hiểu, nhưng nếu thiếu phụ thuộc thì app sẽ bị crash ngay lúc người dùng mở màn hình đó lên (Runtime crash).

**Ví dụ:**

```kotlin
// Hilt - Lỗi phát hiện lúc compile
class MyViewModel @Inject constructor(
    val repo: MyRepository // Lỗi compile nếu thiếu
)

// Koin - Lỗi phát hiện lúc runtime
class MyViewModel(
    val repo: MyRepository = get() // Crash runtime nếu thiếu
)
```

#### 37. Tại sao Koin được gọi là Service Locator chứ không phải DI?

**Ý chính:** Service Locator Pattern - Vì trong Koin, các class chủ động đi "đòi" đối tượng bằng cách gọi hàm `get()`, chứ không được đồ thị tự động "bơm" (Inject) vào từ bên ngoài một cách thụ động.

**Ví dụ:**

```kotlin
// Koin - Service Locator (chủ động lấy)
class MyViewModel : ViewModel() {
    val repo: MyRepository = get() // Chủ động đòi
}

// Hilt - Dependency Injection (thụ động nhận)
@HiltViewModel
class MyViewModel @Inject constructor(
    val repo: MyRepository // Thụ động nhận
) : ViewModel()
```

#### 38. Cơ chế Scope hoạt động bên trong Dagger như thế nào?

**Ý chính:** DoubleCheck - Dagger bọc Factory khởi tạo đối tượng bằng một class trung gian có tên là DoubleCheck.

**Diễn giải:** Class DoubleCheck này lưu lại instance đầu tiên được tạo ra. Ở những lần gọi sau, nó kiểm tra nếu biến đã có dữ liệu thì trả về luôn, tránh việc gọi lại hàm tạo mới. Nó áp dụng cơ chế khóa hai lớp (Double-checked locking) để an toàn đa luồng.

**Ví dụ:**

```kotlin

// public final class DoubleCheck<T> implements Provider<T> {
//     private volatile Object instance = UNINITIALIZED;
//     
//     public T get() {
//         if (instance == UNINITIALIZED) {
//             synchronized (this) {
//                 if (instance == UNINITIALIZED) {
//                     instance = provider.get();
//                 }
//             }
//         }
//         return (T) instance;
//     }

```

#### 39. Phân biệt Component và Module về mặt ngữ nghĩa?

**Ý chính:** Module vs Component - Module là nơi cung cấp vật liệu (Nơi sản xuất); Component là đại lý phân phối (Nơi kết nối vật liệu tới người dùng).

**Diễn giải:** Module chứa các công thức khởi tạo (`@Provides`). Component gom các Module lại và mở ra các cánh cổng (Hàm inject) để UI gắn vào lấy đồ.

**Ví dụ:**

```kotlin
// Module - Nơi sản xuất
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideApi(): Api = ...
}

// Component (Hilt tự tạo) - Nơi phân phối
// SingletonComponent {
//     fun inject(activity: MainActivity)
// }
```

#### 40. Field Injection có ảnh hưởng gì tới hiệu năng?

**Ý chính:** MembersInjector overhead - Có một chút siêu nhỏ tại thời điểm hàm `inject()` được gọi ở `onCreate()`.

**Diễn giải:** Lúc đó, Hilt phải gọi tới class MembersInjector tự sinh để gán thủ công từng biến một. Tuy nhiên, mức độ ảnh hưởng là không đáng kể so với việc dùng Reflection.

**Ví dụ:**

```kotlin
// Field Injection
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var repo: MyRepository
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // Hilt gọi MembersInjector ở đây
    }
}
```

#### 41. Làm thế nào để xử lý DI cho ứng dụng đa mô-đun với Dynamic Feature?

**Ý chính:** Dynamic Feature Modules - Các module dynamic không thể thấy code của Hilt chính, nên phải dùng Dagger Subcomponents hoặc Custom Entry Points.

**Diễn giải:** Vì Dynamic Feature Module được tải về sau cùng và nằm ở ngọn của sơ đồ phụ thuộc, Hilt mặc định không thể tự sinh code kết nối xuyên suốt được. Ta phải tự tạo các cầu nối Entry Point ở Module Base.

```kotlin
// Trong base module

class DynamicFeatureActivity : AppCompatActivity() {

            DynamicFeatureEntryPoint::class.java

        entryPoint.getRepository()
    }
}
```

#### 45. Điều gì xảy ra khi inject hai lần cùng một kiểu dữ liệu?

#### 46. Phân biệt Component.Builder và Component.Factory?

**Ý chính:** Component.Factory vs Component.Builder - Factory ép buộc bạn phải truyền tất cả các tham số cần thiết trong đúng một hàm duy nhất, an toàn hơn Builder (truyền từng hàm lẻ dễ quên).

**Diễn giải:** Từ phiên bản Dagger mới, Component.Factory luôn được ưu tiên lựa chọn để tăng tính an toàn lúc biên dịch.

**Ví dụ:**

```kotlin
// Factory - An toàn hơn
@Component.Factory
interface Factory {
    fun create(
        @BindsInstance context: Context,
        module: AppModule
    ): AppComponent
}

// Builder - Dễ quên tham số
@Component.Builder
interface Builder {
    @BindsInstance
    fun context(context: Context): Builder
    fun appModule(module: AppModule): Builder
    fun build(): AppComponent
}
```

#### 49. Giải thích cơ chế Module dạng object vs abstract class?

**Ý chính:** `object` vs `abstract class` - `object` chứa các hàm `@Provides` chạy nhanh hơn vì không cần tạo instance của Module; `abstract class` bắt buộc dùng cho các hàm `@Binds`.

**Diễn giải:** Nếu một Module vừa có `@Provides` vừa có `@Binds`, hãy biến Module thành interface hoặc abstract class và đặt các hàm `@Provides` bên trong một companion object.

**Ví dụ:**

```kotlin
// Chỉ có @Provides - Dùng object
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides
    fun provideRetrofit(): Retrofit = ...
}

// Chỉ có @Binds - Dùng abstract class/interface
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    abstract fun bindRepo(impl: RepoImpl): Repository
}

// Vừa có @Provides vừa @Binds
@Module
@InstallIn(SingletonComponent::class)
abstract class MixedModule {
    @Binds
    abstract fun bindRepo(impl: RepoImpl): Repository
    
    companion object {
        @Provides
        fun provideApi(): Api = ...
    }
}
```

#### 50. Triết lý lớn nhất khi thiết kế hệ thống DI?

**Ý chính:** Clean Architecture Alignment - Đồ thị DI phải phản ánh đúng Kiến trúc sạch (Clean Architecture) của ứng dụng.

**Diễn giải:** Tách biệt rõ ràng tầng Dữ liệu (Data), tầng Nghiệp vụ (Domain) và tầng Hiển thị (UI). Không cho phép các đối tượng ở tầng UI lọt vào sống ở tầng Singleton Component và ngược lại, giữ cho các module luôn độc lập và dễ dàng thay thế khi cần thiết.

**Ví dụ:**

```kotlin
// ĐÚNG: Phân tầng rõ ràng
// Data Layer - Singleton
@Singleton
class ApiService @Inject constructor()

// Domain Layer - Singleton
@Singleton
class UseCase @Inject constructor(val api: ApiService)

// UI Layer - Activity/ViewModel Scoped
@HiltViewModel
class MyViewModel @Inject constructor(
    val useCase: UseCase
) : ViewModel()

// SAI: UI object ở Singleton
// @Singleton // KHÔNG nên!
// class MyAdapter @Inject constructor()
```
