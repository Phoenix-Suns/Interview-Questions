# CÂU HỎI ÔN TẬP SECURITY & PERFORMANCE OPTIMIZATION

## PHẦN 1: PERFORMANCE OPTIMIZATION (TỐI ƯU HIỆU NĂNG & BỘ NHỚ)

### Chủ đề: Memory Management & Memory Leaks

#### 1. Hiện tượng đối tượng không thể bị dọn rác là gì?

**Ý chính:** Memory Leak (Rò rỉ bộ nhớ) - Đối tượng không còn dùng nhưng không thể bị dọn rác (GC) vì bị một thằng khác giữ chặt.

**Diễn giải:** Xảy ra khi một đối tượng có vòng đời ngắn (như Activity) bị một đối tượng có vòng đời dài (như Static variable hoặc Singleton) giữ lại reference, làm phình RAM và gây crash OutOfMemoryError (OOM).

**Ví dụ:**

```kotlin
// SAI: Gây Memory Leak
class MyActivity : AppCompatActivity() {
    companion object {
        var staticContext: Context? = null // Giữ Activity mãi mãi
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        staticContext = this // LEAK!
    }
}

// ĐÚNG: Dùng Application Context
class MyActivity : AppCompatActivity() {
    companion object {
        var appContext: Context? = null
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        appContext = applicationContext // An toàn
    }
}
```

#### 2. Làm thế nào để phát hiện và định vị Memory Leak?

**Ý chính:** LeakCanary và Memory Profiler - Dùng thư viện LeakCanary lúc code và Memory Profiler trong Android Studio để phân tích Heap Dump.

**Diễn giải:** LeakCanary tự động theo dõi các đối tượng đã bị hủy (như sau onDestroy), nếu chúng không bị GC dọn sau 5 giây, nó sẽ dump bộ nhớ và vẽ ra "đường đi của leak" (Leak trace).

**Ví dụ:**

```kotlin
// Thêm vào build.gradle
dependencies {
    debugImplementation("com.squareup.leakcanary:leakcanary-android:2.12")
}

// LeakCanary tự động chạy, xem kết quả trong notification
// Ví dụ leak trace:
// MainActivity -> handler -> Message -> MainActivity (LEAK!)
```

#### 3. Tại sao Handler và Inner Class dễ gây Memory Leak?

**Ý chính:** Implicit Reference - Các Inner Class thông thường luôn tự động giữ một reference ngầm (Implicit reference) đến Outer Class.

**Diễn giải:** Nếu bạn tạo một Handler ẩn danh trong Activity và gửi một Message delay 10 giây, tin nhắn đó sẽ giữ Handler, Handler giữ Activity. Nếu người dùng tắt Activity trước 10 giây đó, Activity sẽ bị leak.

**Ví dụ:**

```kotlin
// SAI: Inner Class gây leak
class MyActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper()) {
        // Handler giữ reference đến Activity
        true
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler.postDelayed({ /* ... */ }, 10000) // LEAK nếu Activity bị destroy trước 10s
    }
}

// ĐÚNG: Static Inner Class + WeakReference
class MyActivity : AppCompatActivity() {
    private val handler = MyHandler(this)
    
    class MyHandler(activity: MyActivity) : Handler(Looper.getMainLooper()) {
        private val weakActivity = WeakReference(activity)
        
        override fun handleMessage(msg: Message) {
            weakActivity.get()?.let { activity ->
                // Xử lý an toàn
            }
        }
    }
    
    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacksAndMessages(null)
    }
}
```

#### 4. Phân biệt hai loại reference trong quản lý bộ nhớ?

**Ý chính:** WeakReference vs StrongReference - WeakReference không giữ chân đối tượng, Bộ dọn rác (GC) có thể hốt nó đi bất cứ lúc nào nếu RAM cần.

**Diễn giải:** Khuyên dùng khi bạn cần truy cập Activity/Context từ một tác vụ bất đồng bộ ngắn hạn mà không lo làm nghẽn quá trình dọn rác.

**Ví dụ:**

```kotlin
class MyAsyncTask(activity: MyActivity) {
    private val weakActivity = WeakReference(activity)
    
    fun doWork() {
        // Làm việc bất đồng bộ
        GlobalScope.launch {
            delay(5000)
            
            // Kiểm tra Activity còn sống không
            weakActivity.get()?.let { activity ->
                // Cập nhật UI an toàn
                activity.updateUI()
            } ?: run {
                // Activity đã bị destroy, bỏ qua
            }
        }
    }
}
```

#### 5. Cơ chế dọn rác trong Android hoạt động như thế nào?

**Ý chính:** Mark-and-Sweep - Cơ chế dựa trên đồ thị tính tiếp cận từ các nút gốc (GC Roots).

**Diễn giải:** GC bắt đầu từ các nút gốc (như Thread đang chạy, biến static). Nó đi dọc theo các mối quan hệ để "đánh dấu" (Mark) các đối tượng còn sống. Những đối tượng nào nằm cô độc, không thể mò tới được từ GC Roots sẽ bị "quét sạch" (Sweep).

**Ví dụ:**

```kotlin
// GC Roots bao gồm:
// 1. Local variables trong stack của thread đang chạy
// 2. Static variables
// 3. Active threads
// 4. JNI references

class Example {
    companion object {
        var staticObject = MyObject() // GC Root - không bao giờ bị dọn
    }
    
    fun method() {
        val localObject = MyObject() // Sẽ bị dọn khi method kết thúc
    }
}
```

### Chủ đề: App Size, Start-up & Rendering Optimization

#### 6. Phân biệt hai định dạng đóng gói ứng dụng Android?

**Ý chính:** APK vs AAB (Android App Bundle) - APK chứa tài nguyên của mọi máy; AAB được Google Play dùng để cắt gọt tài nguyên, chỉ tải về những gì máy khách hàng cần.

**Diễn giải:** Khi xuất file .aab, Google Play sẽ tự động tạo ra các file APK tùy biến cho từng thiết bị (chỉ giữ lại cấu hình chip armeabi-v7a hoặc arm64-v8a, độ phân giải màn hình cụ thể, ngôn ngữ phù hợp), giúp giảm dung lượng tải xuống lên tới 50%.

**Ví dụ:**

```kotlin
// build.gradle.kts
android {
    bundle {
        language {
            enableSplit = true // Tách theo ngôn ngữ
        }
        density {
            enableSplit = true // Tách theo mật độ màn hình
        }
        abi {
            enableSplit = true // Tách theo kiến trúc CPU
        }
    }
}

// APK: 50MB (chứa tất cả)
// AAB → APK cho thiết bị cụ thể: 25MB (chỉ chứa cần thiết)
```

#### 7. Công cụ tối ưu hóa code thay thế ProGuard là gì?

**Ý chính:** R8 - Công cụ giúp tối ưu hóa, co ngắn tên biến/hàm (Obfuscation), và xóa code thừa (Shrinking).

**Diễn giải:** Chạy mặc định khi bạn build bản release. Nó quét toàn bộ đồ thị code, tìm ra các hàm không bao giờ được gọi (Dead code) để xóa bỏ, đồng thời mã hóa các tên class/method dài dòng thành a, b, c để giảm size app và cản trở dịch ngược.

**Ví dụ:**

```kotlin
// build.gradle.kts
android {
    buildTypes {
        release {
            isMinifyEnabled = true // Bật R8
            isShrinkResources = true // Xóa resource không dùng
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }
}

// Trước R8:
// class UserRepository { fun getUserById(id: String) { ... } }

// Sau R8:
// class a { fun b(c: String) { ... } }
```

#### 8. Các loại khởi động ứng dụng và cách tối ưu?

**Ý chính:** Cold/Warm/Hot Start - Cold start (Khởi động lạnh), Warm start, Hot start. Tối ưu bằng thư viện App Startup và Baseline Profiles.

**Diễn giải:** Cold start là khi app mở từ đầu (chưa có trong RAM). Ta tối ưu bằng cách dời các logic khởi tạo nặng trong Application.onCreate() sang chạy bất đồng bộ (Background thread) hoặc hoãn lại khi cần mới chạy (Lazy init).

**Ví dụ:**

```kotlin
// SAI: Khởi tạo đồng bộ trong onCreate
class MyApp : Application() {
    override fun onCreate() {
        super.onCreate()
        initHeavyLibrary1() // Chặn Main Thread
        initHeavyLibrary2() // Chặn Main Thread
        initHeavyLibrary3() // Chặn Main Thread
    }
}

// ĐÚNG: Dùng App Startup
class MyApp : Application(), Configuration.Provider {
    override fun getWorkManagerConfiguration() =
        Configuration.Builder()
            .setMinimumLoggingLevel(Log.INFO)
            .build()
}

// Initializer
class HeavyLibraryInitializer : Initializer<Unit> {
    override fun create(context: Context) {
        // Chạy bất đồng bộ
        initHeavyLibrary()
    }
    
    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}
```

#### 9. Baseline Profiles giải quyết vấn đề gì?

**Ý chính:** Baseline Profiles - Biên dịch trước (Pre-compile) các đoạn code quan trọng thành mã máy ngay lúc cài đặt để app mượt ngay từ lần đầu mở.

**Diễn giải:** Android sử dụng cơ chế JIT (Just-In-Time) để biên dịch code khi dùng, gây hiện tượng giật lag (Jank) ở lần đầu. Baseline Profiles gom sẵn các đường đi tối ưu (như mở app, cuộn danh sách đầu tiên) gửi lên Google Play để máy khách hàng biên dịch trước bằng AOT (Ahead-Of-Time).

**Ví dụ:**

```kotlin
// baseline-prof.txt
HSPLcom/example/MainActivity;-><init>()V
HSPLcom/example/MainActivity;->onCreate(Landroid/os/Bundle;)V
HSPLcom/example/MainViewModel;->loadData()V

// Thêm vào build.gradle.kts
plugins {
    id("androidx.baselineprofile") version "1.2.0"
}

dependencies {
    baselineProfile(project(":baselineprofile"))
}
```

#### 10. Hiện tượng giật màn hình xảy ra khi nào?

**Ý chính:** UI Jank - Khi App tốn quá 16.6ms (đối với màn hình 60Hz) để vẽ xong một khung hình (Frame).

**Diễn giải:** Hệ thống Android phát tín hiệu VSYNC sau mỗi 16.6ms để làm mới màn hình. Nếu Main Thread của bạn bận làm việc khác (như gõ file, đọc DB) và bỏ lỡ nhịp này, khung hình cũ sẽ bị giữ lại, gây ra hiện tượng giật lag mà người dùng cảm nhận được (Dropped frames).

**Ví dụ:**

```kotlin
// SAI: Làm việc nặng trên Main Thread
class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // Đọc file lớn trên Main Thread - Gây Jank
        val data = File("large_file.txt").readText()
    }
}

// ĐÚNG: Chuyển sang Background Thread
class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        lifecycleScope.launch(Dispatchers.IO) {
            val data = File("large_file.txt").readText()
            withContext(Dispatchers.Main) {
                // Cập nhật UI
            }
        }
    }
}
```

## PHẦN 2: SECURITY (BẢO MẬT ỨNG DỤNG)

### Chủ đề: Data Storage & Cryptography

#### 11. Làm thế nào để lưu trữ dữ liệu nhạy cảm an toàn?

**Ý chính:** EncryptedSharedPreferences và Android Keystore - Sử dụng để mã hóa dữ liệu người dùng (như Token, Password) an toàn tuyệt đối trên thiết bị.

**Diễn giải:** Đừng bao giờ lưu token dạng chữ thô (Plain text) vào SharedPreferences thông thường. EncryptedSharedPreferences tự động mã hóa cả Key và Value bằng thuật toán AES, đảm bảo máy có bị Root cũng không đọc được file XML thô.

**Ví dụ:**

```kotlin
// SAI: Lưu plain text
val prefs = getSharedPreferences("app_prefs", MODE_PRIVATE)
prefs.edit().putString("auth_token", "abc123xyz").apply() // Không an toàn!

// ĐÚNG: Dùng EncryptedSharedPreferences
val masterKey = MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
    .build()

val encryptedPrefs = EncryptedSharedPreferences.create(
    context,
    "secure_prefs",
    masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)

encryptedPrefs.edit().putString("auth_token", "abc123xyz").apply() // An toàn
```

#### 12. Hệ thống lưu trữ khóa mật mã an toàn là gì?

**Ý chính:** Android Keystore System - Lưu giữ các chìa khóa mật mã (Cryptographic keys) trong một vùng phần cứng biệt lập (TEE / StrongBox).

**Diễn giải:** Chìa khóa mật mã được tạo ra bên trong phần cứng an toàn của chip điện thoại và không bao giờ lộ diện ra ngoài vùng nhớ của hệ điều hành. App chỉ có thể gửi dữ liệu vào nhờ phần cứng mã hóa/giải mã hộ, giúp chống hack chìa khóa triệt để.

**Ví dụ:**

```kotlin
val keyGenerator = KeyGenerator.getInstance(
    KeyProperties.KEY_ALGORITHM_AES,
    "AndroidKeyStore"
)

val keyGenParameterSpec = KeyGenParameterSpec.Builder(
    "my_key_alias",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true) // Yêu cầu xác thực sinh trắc học
    .build()

keyGenerator.init(keyGenParameterSpec)
val secretKey = keyGenerator.generateKey()

// Key được lưu trong hardware, không thể trích xuất
```

#### 13. Làm thế nào để bảo mật database Room/SQLite?

**Ý chính:** SQLCipher - Thư viện mã hóa toàn bộ file cơ sở dữ liệu.

**Diễn giải:** Nó thay thế driver SQLite mặc định và thực hiện mã hóa 256-bit AES toàn bộ file cơ sở dữ liệu trên bộ nhớ. Khi mở DB, app bắt buộc phải truyền vào một passphrase (mật khẩu) được lấy an toàn từ Keystore.

**Ví dụ:**

```kotlin
// Thêm dependency
dependencies {
    implementation("net.zetetic:android-database-sqlcipher:4.5.4")
}

// Sử dụng với Room
val passphrase = getPassphraseFromKeystore()
val factory = SupportFactory(passphrase)

val db = Room.databaseBuilder(context, AppDatabase::class.java, "encrypted.db")
    .openHelperFactory(factory)
    .build()
```

#### 14. Phân biệt hai loại mã hóa?

**Ý chính:** Symmetric vs Asymmetric Encryption - Đối xứng dùng 1 chìa chung để mã hóa và giải mã (như AES); Bất đối xứng dùng một cặp khóa Công khai (Public Key) và Bí mật (Private Key) (như RSA).

**Diễn giải:**
- AES: Tốc độ rất nhanh, dùng để mã hóa file dữ liệu lớn tại chỗ.
- RSA: Tốn CPU hơn, dùng để trao đổi chìa khóa an toàn hoặc ký số (Digital signature).

**Ví dụ:**

```kotlin
// AES - Symmetric (nhanh)
val cipher = Cipher.getInstance("AES/GCM/NoPadding")
cipher.init(Cipher.ENCRYPT_MODE, secretKey)
val encrypted = cipher.doFinal(plaintext.toByteArray())

// RSA - Asymmetric (chậm hơn nhưng an toàn hơn cho key exchange)
val keyPairGenerator = KeyPairGenerator.getInstance("RSA")
keyPairGenerator.initialize(2048)
val keyPair = keyPairGenerator.generateKeyPair()

val cipher = Cipher.getInstance("RSA/ECB/PKCS1Padding")
cipher.init(Cipher.ENCRYPT_MODE, keyPair.public)
val encrypted = cipher.doFinal(plaintext.toByteArray())
```

### Chủ đề: Network Security & Reverse Engineering Defenses

#### 15. Kỹ thuật chống tấn công Man-In-The-Middle là gì?

**Ý chính:** SSL Pinning - Kỹ thuật găm chặt (Pin) chứng chỉ SSL của Server vào bên trong App để chống tấn công MITM.

**Diễn giải:** Giúp ngăn chặn hacker sử dụng các công cụ như Charles Proxy hoặc Fiddler cài chứng chỉ giả vào máy điện thoại để nghe lén, đọc trộm và sửa đổi các dữ liệu API gửi đi từ App.

**Ví dụ:**

```kotlin
val certificatePinner = CertificatePinner.Builder()
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()

// Nếu certificate không khớp, app sẽ từ chối kết nối
```

#### 16. File cấu hình bảo mật mạng là gì?

**Ý chính:** Network Security Configuration - File cấu hình XML cho phép tùy biến bảo mật mạng mà không cần sửa code Kotlin.

**Diễn giải:** Bắt đầu từ Android 9, hệ thống mặc định cấm tất cả các kết nối HTTP không mã hóa (Cleartext traffic). File này giúp bạn mở ngoại lệ cho một số tên miền test, hoặc cấu hình SSL Pinning một cách khai báo rõ ràng.

**Ví dụ:**

```xml
<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config cleartextTrafficPermitted="false">
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set expiration="2025-01-01">
            <pin digest="SHA-256">AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=</pin>
        </pin-set>
    </domain-config>
    
    <!-- Cho phép HTTP cho domain test -->
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="true">test.example.com</domain>
    </domain-config>
</network-security-config>
```

```xml
<!-- AndroidManifest.xml -->
<application
    android:networkSecurityConfig="@xml/network_security_config">
</application>
```

#### 17. Làm thế nào để phát hiện thiết bị bị Root?

**Ý chính:** Google Play Integrity API - Sử dụng để kiểm tra xem thiết bị có phải là máy chuẩn, phần mềm sạch hay là máy đã bị can thiệp hệ thống.

**Diễn giải:** API này gửi một yêu cầu lên server Google để kiểm tra xem thiết bị hiện tại có phải là máy chuẩn, phần mềm sạch hay là máy đã bị can thiệp hệ thống (Root, Unlock Bootloader, chạy Rom cook), từ đó giúp bảo vệ các app tài chính, ngân hàng.

**Ví dụ:**

```kotlin
// Thêm dependency
implementation("com.google.android.play:integrity:1.2.0")

// Sử dụng
val integrityManager = IntegrityManagerFactory.create(context)

val integrityTokenRequest = IntegrityTokenRequest.builder()
    .setCloudProjectNumber(CLOUD_PROJECT_NUMBER)
    .build()

integrityManager.requestIntegrityToken(integrityTokenRequest)
    .addOnSuccessListener { response ->
        val token = response.token()
        // Gửi token lên server để verify
    }
    .addOnFailureListener { exception ->
        // Thiết bị không đáng tin cậy
    }
```

#### 18. Cách chống dịch ngược mã nguồn ngoài R8/ProGuard?

**Ý chính:** JNI/NDK và Anti-debugging - Đưa các logic bảo mật cốt lõi xuống tầng C/C++ bằng JNI/NDK và áp dụng kỹ thuật chống Debug.

**Diễn giải:** Code Java/Kotlin dịch ngược ra rất dễ đọc (mã Smali/Decompiled Java). Code C/C++ được biên dịch thành mã máy (file .so), khiến việc dịch ngược và bẻ khóa (Crack) trở nên khó khăn hơn gấp nhiều lần.

**Ví dụ:**

```kotlin
// Kotlin
class SecurityManager {
    external fun validateLicense(key: String): Boolean
    
    companion object {
        init {
            System.loadLibrary("security")
        }
    }
}
```

```cpp
// C++ (security.cpp)
#include <jni.h>
#include <string>

extern "C" JNIEXPORT jboolean JNICALL
Java_com_example_SecurityManager_validateLicense(
    JNIEnv* env,
    jobject /* this */,
    jstring key) {
    
    // Logic phức tạp ở đây, khó dịch ngược
    const char* keyStr = env->GetStringUTFChars(key, nullptr);
    
    // Kiểm tra license
    bool isValid = checkLicense(keyStr);
    
    env->ReleaseStringUTFChars(key, keyStr);
    return isValid;
}
```

#### 19. Lưu trữ API Key trong build.gradle có an toàn không?

**Ý chính:** Không an toàn - Hacker chỉ cần dùng các công cụ giải nén APK cơ bản (như apktool) là có thể lôi toàn bộ các chuỗi string thô này ra trong vòng vài giây.

**Diễn giải:** Giải pháp là dùng secrets-gradle-plugin kết hợp mã hóa biến môi trường hoặc tải key từ server về lúc runtime.

**Ví dụ:**

```kotlin
// SAI: Lưu trong build.gradle
android {
```

#### 21. Vấn đề tạo đối tượng tạm thời trong vòng lặp là gì?

**Ý chính:** GC Churn - Tránh tạo ra các đối tượng tạm thời bên trong các hàm chạy liên tục (như onDraw của Custom View hoặc luồng Flow).

**Diễn giải:** Việc khởi tạo đối tượng mới liên tục trong vòng lặp ép Garbage Collector phải thức dậy làm việc liên tục (gọi là hiện tượng GC Churn), làm treo Main Thread tạm thời.

**Ví dụ:**

```kotlin
// SAI: Tạo object mới mỗi frame
class MyView : View {
    override fun onDraw(canvas: Canvas) {
        val paint = Paint() // Tạo mới mỗi lần vẽ - GC Churn!
        canvas.drawCircle(100f, 100f, 50f, paint)
    }
}

// ĐÚNG: Tái sử dụng object
class MyView : View {
    private val paint = Paint() // Tạo 1 lần duy nhất
    
    override fun onDraw(canvas: Canvas) {
        canvas.drawCircle(100f, 100f, 50f, paint)
    }
}
```

#### 22. Làm thế nào để tối ưu Recomposition trong Jetpack Compose?

**Ý chính:** Immutable Data và Remember - Tránh Recomposition không đáng có bằng cách sử dụng toán tử nhận Lambda hoặc ép kiểu dữ liệu `@Immutable`.

**Diễn giải:** Compose so sánh tham chiếu để quyết định có cần recompose không. Dùng `@Immutable` hoặc `@Stable` để báo cho Compose biết object không thay đổi.

**Ví dụ:**

```kotlin
// SAI: Recompose không cần thiết
@Composable
fun UserList(users: List<User>) {
    LazyColumn {
        items(users) { user ->
            UserItem(user) // Recompose mỗi khi users thay đổi
        }
    }
}

// ĐÚNG: Dùng key và Immutable
@Immutable
data class User(val id: String, val name: String)

@Composable
fun UserList(users: List<User>) {
    LazyColumn {
        items(
            items = users,
            key = { it.id } // Chỉ recompose item thay đổi
        ) { user ->
            UserItem(user)
        }
    }
}
```

#### 26. Quy tắc -keep trong ProGuard/R8 dùng khi nào?

**Ý chính:** `-keep` rules - Dùng để ra lệnh cho R8 không được đổi tên hoặc xóa bỏ các class cụ thể (thường là các data class dùng để parse JSON từ API).

**Diễn giải:** Nếu không `-keep`, R8 đổi tên biến `userId` thành `a`, khi nhận JSON từ server về sẽ không thể map dữ liệu vào được (Gây lỗi Gson/Moshi reflection). Nếu lạm dụng `-keep` bừa bãi, app sẽ bị phình to vì R8 không thể tối ưu được.

**Ví dụ:**

```proguard
# proguard-rules.pro

# Keep data classes cho JSON parsing
-keep class com.example.data.model.** { *; }

# Keep Retrofit interfaces
-keep interface com.example.data.api.** { *; }

# Keep Parcelable
-keep class * implements android.os.Parcelable {
    public static final android.os.Parcelable$Creator *;
}
```

#### 28. Phân biệt ArrayMap và HashMap?

**Ý chính:** ArrayMap vs HashMap - ArrayMap tối ưu cho bộ nhớ (RAM), chuyên dùng cho các tập hợp dữ liệu nhỏ (dưới vài trăm phần tử) trên thiết bị di động.

**Diễn giải:** HashMap tạo ra rất nhiều đối tượng Entry phụ cấu trúc dữ liệu bên trong gây tốn RAM. ArrayMap dùng hai mảng số nguyên nhỏ song song để lưu trữ khóa và giá trị, giúp tiết kiệm bộ nhớ tối đa dù tốc độ tìm kiếm có chậm hơn một chút ở quy mô lớn.

**Ví dụ:**

```kotlin
// HashMap - Tốn RAM hơn nhưng nhanh hơn với dataset lớn
val hashMap = HashMap<String, User>()

// ArrayMap - Tiết kiệm RAM cho dataset nhỏ
val arrayMap = ArrayMap<String, User>()

// Benchmark:
// 100 items: ArrayMap nhanh hơn và ít RAM hơn
// 10,000 items: HashMap nhanh hơn đáng kể
```

#### 29. Choreographer API dùng để làm gì?

**Ý chính:** Choreographer - Cho phép bạn nhận được thông báo (Callback) chính xác tại thời điểm hệ thống bắt đầu vẽ một khung hình mới.

**Diễn giải:** Giúp bạn đo chính xác thời gian render thực tế và tính toán được tỉ lệ FPS của ứng dụng một cách chuyên nghiệp mà không phụ thuộc vào log đoán mò.

**Ví dụ:**

```kotlin
class FpsMonitor {
    private var frameCount = 0
    private var startTime = 0L
    
    fun start() {
        startTime = System.nanoTime()
        Choreographer.getInstance().postFrameCallback(object : Choreographer.FrameCallback {
            override fun doFrame(frameTimeNanos: Long) {
                frameCount++
                
                val elapsed = (System.nanoTime() - startTime) / 1_000_000_000.0
                if (elapsed >= 1.0) {
                    val fps = frameCount / elapsed
                    Log.d("FPS", "Current FPS: $fps")
                    
                    frameCount = 0
                    startTime = System.nanoTime()
                }
                
                Choreographer.getInstance().postFrameCallback(this)
            }
        })
    }
}
```

#### 33. Tại sao không nên dùng MD5 hoặc SHA-1 để lưu mật khẩu?

**Ý chính:** Rainbow Table Attack - Vì chúng là các hàm băm (Hash functions) đã lỗi thời, dễ bị bẻ khóa bằng kỹ thuật Rainbow Table (Bảng tra cứu ngược băm sẵn).

**Diễn giải:** Hiện nay bắt buộc phải dùng các thuật toán băm mạnh hơn như SHA-256 kết hợp với cơ chế Salt (Thêm muối - chuỗi ký tự ngẫu nhiên) hoặc các thuật toán chuyên dụng như bcrypt/scrypt.

**Ví dụ:**

```kotlin
// SAI: MD5 không an toàn
fun hashPasswordMD5(password: String): String {
    val md = MessageDigest.getInstance("MD5")
    return md.digest(password.toByteArray()).joinToString("") { "%02x".format(it) }
}

// ĐÚNG: Dùng bcrypt với salt
// Thêm dependency: implementation("at.favre.lib:bcrypt:0.10.2")
fun hashPasswordBcrypt(password: String): String {
    return BCrypt.withDefaults().hashToString(12, password.toCharArray())
}

fun verifyPassword(password: String, hash: String): Boolean {
    return BCrypt.verifyer().verify(password.toCharArray(), hash).verified
}
```

#### 34. Làm thế nào để kiểm tra tính toàn vẹn của APK?

**Ý chính:** Signature Verification - Tự kiểm tra chữ ký (Signature Hash) của chính file APK đang chạy xem có đúng là do lập trình viên gốc ký ra không.

**Diễn giải:** Tránh việc hacker tải file APK của bạn về, unpack ra, chèn mã độc (Spyware), đóng gói lại rồi phân phối lên các chợ app lậu. Nếu mã băm chữ ký không khớp, App tự động đóng ngay lập tức.

**Ví dụ:**

```kotlin
fun verifyAppSignature(context: Context): Boolean {
    try {
        val packageInfo = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
            context.packageManager.getPackageInfo(
                context.packageName,
                PackageManager.GET_SIGNING_CERTIFICATES
            )
        } else {
            @Suppress("DEPRECATION")
            context.packageManager.getPackageInfo(
                context.packageName,
                PackageManager.GET_SIGNATURES
            )
        }
        
        val signatures = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.P) {
            packageInfo.signingInfo.apkContentsSigners
        } else {
            @Suppress("DEPRECATION")
            packageInfo.signatures
        }
        
        val md = MessageDigest.getInstance("SHA-256")
        val currentSignature = md.digest(signatures[0].toByteArray())
        val expectedSignature = "YOUR_EXPECTED_SIGNATURE_HASH"
        
        return currentSignature.contentEquals(expectedSignature.toByteArray())
    } catch (e: Exception) {
        return false
    }
}

// Trong Application.onCreate()
if (!verifyAppSignature(this)) {
    // App bị giả mạo, thoát ngay
    exitProcess(0)
}
```

#### 35. Phân biệt các phiên bản Signing Schemes?

**Ý chính:** V1/V2/V3/V4 Signing - Các phiên bản ký số càng mới thì càng tăng tốc độ cài đặt app và tăng độ an toàn chống giả mạo file.

**Diễn giải:** V1 chỉ ký các file đơn lẻ (dễ bị chèn file rác). V2 ký trên toàn bộ khối nhị phân của APK (giúp check toàn vẹn siêu nhanh). V3 cho phép cập nhật khóa ký (Key rotation). V4 ký bằng file chỉ mục độc lập bên ngoài để hỗ trợ tính năng cài đặt nhanh trực tuyến của Android 11.

**Ví dụ:**

```kotlin
// build.gradle.kts
android {
    signingConfigs {
        create("release") {
            storeFile = file("keystore.jks")
            storePassword = "password"
            keyAlias = "key"
            keyPassword = "password"
            
            // Bật tất cả signing schemes
            enableV1Signing = true // JAR signing (backward compatibility)
            enableV2Signing = true // APK Signature Scheme v2
            enableV3Signing = true // APK Signature Scheme v3
            enableV4Signing = true // APK Signature Scheme v4
        }
    }
}
```

#### 37. Implicit Intent Vulnerability là gì và cách phòng chống?

**Ý chính:** Implicit Intent Vulnerability - Rò rỉ dữ liệu khi gửi Intent không chỉ định rõ tên Class đích, khiến App độc hại có thể nhảy vào "hứng" mất dữ liệu.

**Diễn giải:** Khi truyền thông tin nhạy cảm giữa các thành phần nội bộ trong App, luôn luôn phải dùng Explicit Intent (Chỉ rõ tên Class xử lý) hoặc sử dụng Custom Permission có thuộc tính `protectionLevel="signature"`.

**Ví dụ:**

```kotlin
// SAI: Implicit Intent
val intent = Intent("com.example.ACTION_SENSITIVE_DATA")
intent.putExtra("secret", "sensitive_data")
startActivity(intent) // App độc hại có thể nhận được!

// ĐÚNG: Explicit Intent
val intent = Intent(this, SecureActivity::class.java)
intent.putExtra("secret", "sensitive_data")
startActivity(intent)
```

```xml
<!-- Hoặc dùng Custom Permission -->
<permission
    android:name="com.example.permission.SENSITIVE_DATA"
    android:protectionLevel="signature" />

<activity
    android:name=".SecureActivity"
    android:permission="com.example.permission.SENSITIVE_DATA" />
```

#### 38. Content Provider có thể gây rò rỉ dữ liệu như thế nào?

#### 42. Enum vs @IntDef/@StringDef ngày nay?

**Ý chính:** Enum Performance - Ngày xưa (thời Dalvik), Enum rất ngốn RAM và được khuyên thay bằng `@IntDef`. Nay với sự tối ưu vượt bậc của ART (Android Runtime) và R8, việc dùng Enum hoàn toàn không còn là vấn đề lo ngại về hiệu năng nữa.

**Ví dụ:**

```kotlin
// Ngày xưa: Dùng @IntDef
@IntDef(STATUS_LOADING, STATUS_SUCCESS, STATUS_ERROR)
@Retention(AnnotationRetention.SOURCE)
annotation class Status

const val STATUS_LOADING = 0
const val STATUS_SUCCESS = 1
const val STATUS_ERROR = 2

// Ngày nay: Dùng Enum thoải mái
enum class Status {
    LOADING,
    SUCCESS,
    ERROR
}

// Hoặc dùng sealed class (tốt hơn)
sealed class UiState {
    object Loading : UiState()
    data class Success(val data: String) : UiState()
    data class Error(val message: String) : UiState()
}
```

#### 44. Làm thế nào để tối ưu Pagination?

**Ý chính:** Paging 3 Library - Sử dụng kiến trúc thư viện Paging 3 của Jetpack.

**Diễn giải:** Tự động hóa khâu quản lý bộ đệm (Buffer), tự động kích hoạt gọi API khi người dùng cuộn gần tới cuối trang, và giải phóng các trang quá xa khỏi bộ nhớ để giữ RAM luôn sạch.

**Ví dụ:**

```kotlin
// PagingSource
class UserPagingSource(
    private val api: ApiService
) : PagingSource<Int, User>() {
    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, User> {
        return try {
            val page = params.key ?: 1
            val response = api.getUsers(page, params.loadSize)
            
            LoadResult.Page(
                data = response.users,
                prevKey = if (page == 1) null else page - 1,
                nextKey = if (response.users.isEmpty()) null else page + 1
            )
        } catch (e: Exception) {
            LoadResult.Error(e)
        }
    }
    
    override fun getRefreshKey(state: PagingState<Int, User>): Int? {
        return state.anchorPosition?.let { anchorPosition ->
            state.closestPageToPosition(anchorPosition)?.prevKey?.plus(1)
                ?: state.closestPageToPosition(anchorPosition)?.nextKey?.minus(1)
        }
    }
}

// ViewModel
class UserViewModel(private val api: ApiService) : ViewModel() {
    val users = Pager(
        config = PagingConfig(pageSize = 20, enablePlaceholders = false),
        pagingSourceFactory = { UserPagingSource(api) }
    ).flow.cachedIn(viewModelScope)
}

// UI
LazyColumn {
    items(users) { user ->
        UserItem(user)
    }
}
```

#### 45. Tại sao SSL Pinning có thể bị bypass bằng Frida?

**Ý chính:** Frida Bypass - Vì Frida có khả năng hook (bơm mã độc trực tiếp vào tiến trình bộ nhớ lúc đang chạy) để ép các hàm check chứng chỉ luôn trả về kết quả true.

**Diễn giải:** Để chống lại Senior Hacker dùng Frida, App của bạn cần triển khai thêm các đoạn code check phát hiện Frida ngầm (như quét các cổng kết nối mặc định của Frida Server hoặc check danh sách file hệ thống `/proc/net/tcp`).

**Ví dụ:**

```kotlin
// Phát hiện Frida
fun detectFrida(): Boolean {
    // Check Frida server port
    try {
        val process = Runtime.getRuntime().exec("netstat -an")
        val reader = BufferedReader(InputStreamReader(process.inputStream))
        var line: String?
        while (reader.readLine().also { line = it } != null) {
            if (line?.contains("27042") == true) { // Frida default port
                return true
            }
        }
    } catch (e: Exception) {
        // Ignore
    }
    
    // Check Frida libraries
    val maps = File("/proc/self/maps")
    if (maps.exists()) {
        maps.readLines().forEach { line ->
            if (line.contains("frida") || line.contains("gum-js-loop")) {
                return true
            }
        }
    }
    
    return false
}

// Trong Application.onCreate()
if (detectFrida()) {
    // Phát hiện Frida, thoát app
    exitProcess(0)
}
```

#### 46. Ý nghĩa của VSS, RSS, PSS, USS?

**Ý chính:** Memory Metrics - Các thước đo lượng RAM thực tế mà App đang chiếm dụng.

**Diễn giải:**
- **VSS (Virtual Set Size)**: Tổng bộ nhớ ảo (bao gồm cả shared libraries)
- **RSS (Resident Set Size)**: Bộ nhớ vật lý đang dùng (bao gồm shared)
- **PSS (Proportional Set Size)**: Chỉ số quan trọng nhất, tính lượng RAM riêng của app cộng với lượng RAM chia sẻ chung với app khác chia đều ra
- **USS (Unique Set Size)**: Lượng RAM độc nhất, nếu kill app này thì hệ thống sẽ thu hồi được ngay lập tức lượng RAM bằng đúng chỉ số này

**Ví dụ:**

```kotlin
// Xem memory info
val activityManager = getSystemService(Context.ACTIVITY_SERVICE) as ActivityManager
val memoryInfo = activityManager.getProcessMemoryInfo(intArrayOf(android.os.Process.myPid()))

memoryInfo[0].let {
    Log.d("Memory", "PSS: ${it.totalPss} KB") // Quan trọng nhất
    Log.d("Memory", "USS: ${it.totalPrivateDirty} KB")
    Log.d("Memory", "RSS: ${it.totalSharedDirty + it.totalPrivateDirty} KB")
}
```

#### 47. Làm thế nào để tối ưu Room database queries?

**Ý chính:** Database Indexing - Sử dụng chỉ mục (`@Index`) trên các cột thường xuyên tìm kiếm (WHERE) hoặc sắp xếp (ORDER BY).

**Diễn giải:** Giúp SQLite tìm kiếm dữ liệu theo cây thư mục rút gọn, tránh việc phải quét toàn bộ bảng (Table scan) cực kỳ tốn CPU và I/O của ổ cứng.

**Ví dụ:**

```kotlin
// Không có index - Chậm
@Entity(tableName = "users")
data class User(
    @PrimaryKey val id: String,
    val name: String,
    val email: String,
    val age: Int
)

// Có index - Nhanh hơn nhiều
@Entity(
    tableName = "users",
    indices = [
        Index(value = ["email"], unique = true),
        Index(value = ["age"])
    ]
)
data class User(
    @PrimaryKey val id: String,
    val name: String,
    val email: String,
    val age: Int
)

@Dao
interface UserDao {
    // Query này sẽ nhanh hơn nhờ index trên email
    @Query("SELECT * FROM users WHERE email = :email")
    suspend fun getUserByEmail(email: String): User?
    
    // Query này sẽ nhanh hơn nhờ index trên age
    @Query("SELECT * FROM users WHERE age > :minAge ORDER BY age")
    suspend fun getUsersOlderThan(minAge: Int): List<User>
}
```

#### 48. Chính sách mã hóa Data-in-Transit cho app tài chính?

**Ý chính:** TLS 1.3 + Payload Encryption - Ép buộc sử dụng TLS 1.3, cấm các cipher suite yếu, kết hợp mã hóa thêm một lớp thứ hai (Payload Encryption) bằng cặp khóa AES trước khi đẩy vào body của API.

**Ví dụ:**

```kotlin
// Cấu hình OkHttp với TLS 1.3
val connectionSpec = ConnectionSpec.Builder(ConnectionSpec.MODERN_TLS)
    .tlsVersions(TlsVersion.TLS_1_3, TlsVersion.TLS_1_2)
    .cipherSuites(
        CipherSuite.TLS_AES_128_GCM_SHA256,
        CipherSuite.TLS_AES_256_GCM_SHA384
    )
    .build()

val client = OkHttpClient.Builder()
    .connectionSpecs(listOf(connectionSpec))
    .certificatePinner(certificatePinner)
    .build()

// Mã hóa payload
fun encryptPayload(data: String, secretKey: SecretKey): String {
    val cipher = Cipher.getInstance("AES/GCM/NoPadding")
    cipher.init(Cipher.ENCRYPT_MODE, secretKey)
    val encrypted = cipher.doFinal(data.toByteArray())
    val iv = cipher.iv
    
    // Combine IV + encrypted data
    return Base64.encodeToString(iv + encrypted, Base64.NO_WRAP)
}
```
