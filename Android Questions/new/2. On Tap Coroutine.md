# CÂU HỎI ÔN TẬP COROUTINE

## CẤP ĐỘ 1: JUNIOR (CƠ BẢN)

### Chủ đề: Core Concepts (Khái niệm cốt lõi)

#### 1. Làm thế nào để xử lý nhiều tác vụ bất đồng bộ mà không làm treo ứng dụng?

**Ý chính:** Coroutine - Luồng gọn nhẹ (Lightweight thread) chạy bất đồng bộ.

**Diễn giải:** Coroutine không phải là Thread (luồng hệ điều hành). Nhiều Coroutine có thể chạy chung trên một Thread mà không làm treo Thread đó nhờ cơ chế tạm dừng (Suspending).

**Ví dụ:**

```kotlin
// Tạo 100,000 Coroutines - app vẫn mượt
repeat(100_000) {
    GlobalScope.launch {
        delay(1000L)
        println(".")
    }
}

// Tạo 100,000 Threads - app sẽ crash vì hết bộ nhớ
```

#### 2. Tại sao một hàm có thể tạm dừng mà không chặn luồng?

**Ý chính:** `suspend` - Từ khóa đánh dấu hàm có thể tạm dừng và tiếp tục lại sau mà không chặn luồng (Non-blocking).

**Diễn giải:** Khi gặp hàm suspend, Coroutine sẽ giải phóng Thread hiện tại cho việc khác. Khi xử lý xong việc ngầm, Coroutine sẽ quay lại Thread cũ (hoặc Thread khác) để chạy tiếp.

**Ví dụ:**

```kotlin
suspend fun fetchData(): String {
    delay(1000) // Tạm dừng 1s, thread vẫn rảnh để vẽ UI
    return "Data"
}
```

#### 3. Một hàm đặc biệt chỉ có thể được gọi ở những nơi nào?

**Ý chính:** Hàm `suspend` - Chỉ gọi được bên trong một hàm `suspend` khác hoặc bên trong một Coroutine Builder.

**Diễn giải:** Trình biên dịch (Compiler) cần ngữ cảnh Coroutine để quản lý trạng thái tạm dừng, nên bạn không thể gọi nó trong một hàm thông thường.

**Ví dụ:**

```kotlin
// Cách 1: Gọi trong Coroutine Builder
GlobalScope.launch {
    val data = fetchData()
}

// Cách 2: Gọi trong hàm suspend khác
suspend fun processData() {
    val data = fetchData()
}
```

#### 4. So sánh hai cách xử lý đồng thời trong lập trình?

**Ý chính:** Thread vs Coroutine - Thread do Hệ điều hành quản lý (tốn tài nguyên); Coroutine do Kotlin Runtime quản lý (rất nhẹ).

**Diễn giải:** Chuyển đổi giữa các Thread (Context switch) rất nặng. Chuyển đổi giữa các Coroutine chỉ là việc chuyển đổi hàm, tốn cực ít tài nguyên.

**Ví dụ:**

```kotlin
// Thread: Tốn ~1MB bộ nhớ cho mỗi thread
Thread {
    // Code
}.start()

// Coroutine: Chỉ tốn vài bytes
GlobalScope.launch {
    // Code
}
```

#### 5. Làm thế nào để quản lý vòng đời của các tác vụ bất đồng bộ?

**Ý chính:** CoroutineScope - Vùng quản lý vòng đời (Lifecycle) của Coroutine.

**Diễn giải:** Mọi Coroutine đều phải chạy trong một Scope. Khi Scope bị hủy, tất cả Coroutine bên trong nó tự động bị hủy theo để tránh rò rỉ bộ nhớ (Memory leak).

**Ví dụ:**

```kotlin
class MyViewModel : ViewModel() {
    init {
        viewModelScope.launch {
            // Tự động hủy khi ViewModel bị clear
        }
    }
}
```

### Chủ đề: Builders & Dispatchers (Bộ tạo & Bộ điều phối)

#### 6. Có những cách nào để khởi tạo một tác vụ bất đồng bộ?

**Ý chính:** Coroutine Builders - `launch`, `async`, `runBlocking`.

**Diễn giải:** Dùng để kích hoạt một Coroutine mới từ một hàm thông thường.

**Ví dụ:**

```kotlin
// launch: Trả về Job
val job = GlobalScope.launch {
    println("Launch")
}

// async: Trả về Deferred
val deferred = GlobalScope.async {
    "Async result"
}

// runBlocking: Chặn thread
runBlocking {
    println("Blocking")
}
```

#### 7. Khi nào cần kết quả trả về và khi nào không?

**Ý chính:** `launch` vs `async` - `launch` là "chạy và quên" (Fire and forget), `async` là chạy và chờ kết quả.

**Diễn giải:** `launch` không trả về kết quả cho bạn. `async` trả về một đối tượng `Deferred`, bạn phải gọi `.await()` để nhận kết quả trả về từ nó.

**Ví dụ:**

```kotlin
// launch: Không cần kết quả
launch {
    saveToDatabase()
}

// async: Cần lấy data
val data = async {
    apiCall()
}.await()
```

#### 8. Có một cách khởi tạo tác vụ bất đồng bộ nhưng lại chặn luồng, nó là gì và khi nào dùng?

**Ý chính:** `runBlocking` - Chặn Thread hiện tại cho đến khi Coroutine bên trong chạy xong.

**Diễn giải:** Thường dùng để viết Unit Test hoặc viết code block chính trong hàm `main` của ứng dụng Console. Không được dùng trên Main Thread của Android vì sẽ gây đơ màn hình (ANR).

**Ví dụ:**

```kotlin
// Dùng trong main function
fun main() = runBlocking {
    launch {
        delay(1000L)
        println("World!")
    }
    println("Hello,")
}

// KHÔNG dùng trong Android UI
// onCreate() {
//     runBlocking { // SAI - Gây ANR
//         delay(5000)
//     }
// }
```

#### 9. Làm thế nào để quyết định tác vụ bất đồng bộ chạy trên luồng nào?

**Ý chính:** CoroutineDispatcher - Bộ điều phối, quyết định Coroutine sẽ chạy trên Thread nào.

**Diễn giải:** Nó chỉ định công việc này thuộc nhóm xử lý giao diện, tính toán nặng, hay đọc ghi file.

**Ví dụ:**

```kotlin
launch(Dispatchers.Main) {
    // Chạy trên Main Thread
}

launch(Dispatchers.IO) {
    // Chạy trên IO Thread
}

launch(Dispatchers.Default) {
    // Chạy trên Default Thread
}
```

#### 10. Các loại bộ điều phối khác nhau như thế nào và khi nào dùng?

**Ý chính:** `Dispatchers.Main`, `Dispatchers.IO`, `Dispatchers.Default` - Main vẽ UI; IO làm việc mạng/file; Default tính toán nặng.

**Diễn giải:**
- `Main`: Luồng chính hiển thị Android UI.
- `IO`: Tối ưu cho việc đợi phản hồi (Network, Room DB, File).
- `Default`: Tối ưu cho thuật toán tốn CPU (Parse JSON lớn, Sort mảng, Edit ảnh).

**Ví dụ:**

```kotlin
// Main: Cập nhật UI
launch(Dispatchers.Main) {
    textView.text = "Loading..."
}

// IO: Gọi API
launch(Dispatchers.IO) {
    val users = api.getUsers()
}

// Default: Xử lý dữ liệu nặng
launch(Dispatchers.Default) {
    val sorted = largeList.sortedBy { it.value }
}
```

### Chủ đề: Flow (Cơ bản)

#### 11. Làm thế nào để phát ra nhiều giá trị theo thời gian một cách bất đồng bộ?

**Ý chính:** Kotlin Flow - Dòng dữ liệu bất đồng bộ phát ra nhiều giá trị theo thời gian.

**Diễn giải:** Tương tự như Sequence trong Kotlin nhưng hỗ trợ các hàm suspend. Nó có thể phát ra (emit) dữ liệu bất đồng bộ liên tục cho người nghe (collect).

**Ví dụ:**

```kotlin
fun downloadProgress(): Flow<Int> = flow {
    for (i in 1..100) {
        delay(100)
        emit(i) // Phát ra phần trăm tải file
    }
}

// Sử dụng
downloadProgress().collect { percent ->
    println("Downloaded: $percent%")
}
```

#### 12. Một dòng dữ liệu chỉ hoạt động khi có người lắng nghe được gọi là gì?

**Ý chính:** Cold Flow - Chỉ chạy và phát dữ liệu khi có người bắt đầu lắng nghe (collect).

**Diễn giải:** Bản thân luồng dữ liệu không tự chạy. Mỗi người nghe (Collector) mới sẽ kích hoạt một chuỗi thực thi độc lập mới từ đầu.

**Ví dụ:**

```kotlin
val coldFlow = flow {
    println("Flow started")
    emit(1)
    emit(2)
}

// Chưa in gì cả vì chưa có ai collect

coldFlow.collect { value ->
    println(value) // Bây giờ mới in "Flow started", 1, 2
}
```

#### 13. Làm thế nào để nhận dữ liệu từ một dòng dữ liệu?

**Ý chính:** `collect` - Toán tử kết thúc để kích hoạt Flow và nhận dữ liệu.

**Diễn giải:** Vì Flow là hàm suspend, việc gọi `collect` phải nằm trong một Coroutine.

**Ví dụ:**

```kotlin
val myFlow = flow {
    emit("Hello")
    emit("World")
}

// Phải gọi trong Coroutine
lifecycleScope.launch {
    myFlow.collect { value ->
        println(value)
    }
}
```

## CẤP ĐỘ 2: MID-LEVEL (TRUNG CẤP)

### Chủ đề: Cancellation & Exception Handling (Hủy bỏ & Xử lý lỗi)

#### 14. Cơ chế quản lý các tác vụ bất đồng bộ theo phân cấp là gì?

**Ý chính:** Structured Concurrency - Cơ chế quản lý Coroutine theo phân cấp Cha - Con rõ ràng.

**Diễn giải:** Coroutine con chỉ có thể chạy trong Scope của cha. Nếu cha bị hủy, con bị hủy. Cha luôn đợi tất cả con chạy xong mới hoàn thành. Giúp quản lý rác và lỗi cực tốt.

**Ví dụ:**

```kotlin
lifecycleScope.launch { // Cha
    launch { // Con 1
        delay(1000)
    }
    launch { // Con 2
        delay(2000)
    }
    // Cha đợi cả 2 con xong mới hoàn thành
}
// Khi Activity bị destroy -> lifecycleScope hủy -> Tất cả con tự động dừng
```

#### 15. Làm thế nào để dừng một tác vụ bất đồng bộ đang chạy?

**Ý chính:** `.cancel()` - Gọi hàm trên đối tượng Job để hủy Coroutine.

**Diễn giải:** Việc hủy bỏ chỉ có tác dụng nếu code bên trong Coroutine có tính hợp tác (Cooperative with cancellation).

**Ví dụ:**

```kotlin
val job = launch {
    repeat(1000) { i ->
        println("Job: I'm sleeping $i ...")
        delay(500L)
    }
}

delay(1300L)
println("Cancelling job...")
job.cancel() // Hủy job
job.join() // Đợi job kết thúc
println("Job cancelled")
```

#### 16. Một tác vụ bất đồng bộ cần điều kiện gì để có thể bị hủy?

**Ý chính:** Cooperative with cancellation - Code bên trong phải định kỳ kiểm tra xem mình đã bị hủy chưa.

**Diễn giải:** Nếu bạn chạy một vòng lặp `while(true)` tính toán nặng liên tục không có hàm suspend nào, dù gọi `.cancel()` bên ngoài, Coroutine vẫn chạy tiếp. Nó chỉ chịu dừng khi dùng các hàm suspend chuẩn (như `delay`, `yield`) hoặc check biến `isActive`.

**Ví dụ:**

```kotlin
// SAI: Không chịu hủy
launch {
    while (true) {
        // Tính toán nặng
    }
}

// ĐÚNG: Chịu hủy
launch {
    while (isActive) {
        // Tính toán nặng
        yield() // Cho phép kiểm tra cancellation
    }
}
```

#### 17. Làm thế nào để đảm bảo code dọn dẹp luôn chạy kể cả khi tác vụ bị hủy?

**Ý chính:** `withContext(NonCancellable)` - Đặt code trong khối `finally` và bọc bằng NonCancellable.

**Diễn giải:** Khi bị hủy, Coroutine ném ra một `CancellationException`. Khối `finally` sẽ chạy, nhưng nếu trong `finally` lại gọi một hàm suspend thông thường, nó sẽ bị bỏ qua. Phải dùng `NonCancellable` để ép nó chạy.

**Ví dụ:**

```kotlin
val job = launch {
    try {
        repeat(1000) { i ->
            println("Job: I'm sleeping $i ...")
            delay(500L)
        }
    } finally {
        withContext(NonCancellable) {
            println("Cleaning up...")
            delay(1000L) // Chạy an toàn
            println("Cleanup done")
        }
    }
}
```

#### 18. Làm thế nào để bắt lỗi tập trung cho tất cả tác vụ bất đồng bộ?

**Ý chính:** CoroutineExceptionHandler - Bắt các Exception chưa được xử lý trong Coroutine ở tầng gốc (Root).

**Diễn giải:** Nó hoạt động như một lưới bảo hiểm cuối cùng, tránh app bị crash khi có lỗi bất ngờ từ `launch`. Không có tác dụng với `async`.

**Ví dụ:**

```kotlin
val handler = CoroutineExceptionHandler { _, exception ->
    println("Caught exception: $exception")
}

val scope = CoroutineScope(Job() + handler)
scope.launch {
    throw Exception("Test exception")
}
```

#### 19. Xử lý lỗi trong hai cách khởi tạo tác vụ khác nhau như thế nào?

**Ý chính:** Exception trong `launch` vs `async` - `launch` ném lỗi ngay lập tức ra ngoài; `async` giấu lỗi vào `Deferred` và chỉ ném ra khi gọi `.await()`.

**Diễn giải:** Lỗi của `launch` nếu không bắt sẽ làm crash app hoặc kích hoạt handler. Lỗi của `async` có thể bắt gọn bằng `try-catch` bọc quanh hàm `.await()`.

**Ví dụ:**

```kotlin
// launch: Lỗi ném ngay
launch {
    throw Exception("Error in launch")
}

// async: Lỗi giấu trong Deferred
val deferred = async {
    throw Exception("Error in async")
}

try {
    deferred.await() // Lỗi ném ra ở đây
} catch (e: Exception) {
    println("Caught: $e")
}
```

#### 20. Làm thế nào để chuyển đổi luồng tạm thời trong một tác vụ bất đồng bộ?

**Ý chính:** `withContext` - Chuyển đổi Thread tạm thời và đợi kết quả (Đồng bộ trong Coroutine).

**Diễn giải:** Không tạo ra Coroutine mới, nó chỉ đổi Dispatcher cho đoạn code bên trong và chặn Coroutine hiện tại cho đến khi khối code đó chạy xong.

**Ví dụ:**

```kotlin
// Đang ở Main Thread
lifecycleScope.launch(Dispatchers.Main) {
    val data = withContext(Dispatchers.IO) {
        api.getData() // Đổi sang IO lấy data
    }
    textView.text = data // Tự động quay lại Main Thread để set UI
}
```

### Chủ đề: Hot Flows & State Management

#### 21. Một dòng dữ liệu tự động phát kể cả khi không có người nghe là gì?

**Ý chính:** Hot Flow - Tự động phát dữ liệu kể cả khi không có ai lắng nghe (Active phát sóng).

**Diễn giải:** Giống như một đài phát thanh. Dữ liệu phát ra liên tục, ai bật radio lên (collect) ở thời điểm nào thì nghe từ thời điểm đó, người vào sau sẽ lỡ mất dữ liệu quá khứ.

**Ví dụ:**

```kotlin
val hotFlow = MutableStateFlow(0)

// Phát dữ liệu liên tục
launch {
    repeat(10) {
        delay(1000)
        hotFlow.value = it
    }
}

// Người nghe vào sau sẽ nhận từ giá trị hiện tại
delay(3000)
hotFlow.collect { value ->
    println(value) // Bắt đầu từ 3, không nhận được 0, 1, 2
}
```

#### 22. Loại dòng dữ liệu nào phù hợp để quản lý trạng thái UI?

**Ý chính:** StateFlow - Một Hot Flow chuyên lưu trữ trạng thái hiện tại (State), luôn giữ duy nhất 1 giá trị cuối cùng.

**Diễn giải:** Là bản thay thế hoàn hảo cho LiveData trong Android. Khi có người nghe mới, nó ngay lập tức phát lại giá trị mới nhất hiện tại cho người đó. Yêu cầu phải có một giá trị khởi tạo.

**Ví dụ:**

```kotlin
class MyViewModel : ViewModel() {
    private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()
    
    fun loadData() {
        viewModelScope.launch {
            _uiState.value = UiState.Loading
            try {
                val data = repository.getData()
                _uiState.value = UiState.Success(data)
            } catch (e: Exception) {
                _uiState.value = UiState.Error(e.message)
            }
        }
    }
}
```

#### 23. Loại dòng dữ liệu nào phù hợp để gửi sự kiện một lần?

**Ý chính:** SharedFlow - Hot Flow chuyên dùng để gửi các sự kiện (Events) xảy ra một lần, không giữ trạng thái lâu dài.

**Diễn giải:** Không cần giá trị khởi tạo. Có cấu hình replay để quyết định phát lại bao nhiêu item cho người vào sau. Thích hợp cho việc điều hướng hoặc hiển thị thông báo.

**Ví dụ:**

```kotlin
class MyViewModel : ViewModel() {
    private val _events = MutableSharedFlow<NavigationEvent>()
    val events = _events.asSharedFlow()
    
    fun navigateToDetail() {
        viewModelScope.launch {
            _events.emit(NavigationEvent.GoToDetail)
        }
    }
}

// Trong Activity/Fragment
lifecycleScope.launch {
    viewModel.events.collect { event ->
        when (event) {
            is NavigationEvent.GoToDetail -> navigateToDetailScreen()
        }
    }
}
```

#### 24. Làm thế nào để chuyển đổi một dòng dữ liệu thụ động thành chủ động?

**Ý chính:** `.shareIn()` và `.stateIn()` - Toán tử biến Cold Flow thành Hot Flow.

**Diễn giải:** Truyền vào một CoroutineScope, chiến lược kích hoạt (SharingStarted), và giá trị mặc định nếu là `stateIn`.

**Ví dụ:**

```kotlin
val coldFlow = flow {
    emit(fetchDataFromApi())
}

// Biến thành StateFlow
val hotStateFlow = coldFlow.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5000),
    initialValue = InitialState
)

// Biến thành SharedFlow
val hotSharedFlow = coldFlow.shareIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5000),
    replay = 1
)
```

#### 25. Ý nghĩa của việc giữ dòng dữ liệu sống thêm 5 giây sau khi không có người nghe?

**Ý chính:** `SharingStarted.WhileSubscribed(5000)` - Giữ cho Hot Flow sống thêm 5 giây sau khi tất cả người nghe (UI) đã ngắt kết nối.

**Diễn giải:** Tránh việc hủy bỏ và khởi động lại luồng dữ liệu ngầm khi người dùng xoay màn hình điện thoại (lúc xoay, UI cũ hủy 1 tích tắc rồi UI mới đăng ký lại).

**Ví dụ:**

```kotlin
val uiState = repository.dataFlow.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5000),
    initialValue = emptyList()
)
// Khi xoay màn hình, Flow không bị hủy ngay mà đợi 5s
// Nếu UI mới đăng ký trong 5s, Flow tiếp tục phát
```

## CẤP ĐỘ 3: SENIOR (NÂNG CAO)

### Chủ đề: Advanced Exception & Concurrency

#### 26. Làm thế nào để lỗi của một tác vụ con không ảnh hưởng đến các tác vụ con khác?

**Ý chính:** SupervisorJob - Lỗi của một Coroutine con không làm ảnh hưởng đến các Coroutine con khác cùng cấp.

**Diễn giải:** Với Job thường, nếu một con bị lỗi, nó sẽ hủy luôn cha, và cha hủy hết tất cả các con còn lại. Với SupervisorJob, con lỗi tự chịu, cha vẫn sống và các anh em khác vẫn chạy bình thường.

**Ví dụ:**

```kotlin
val scope = CoroutineScope(SupervisorJob())

scope.launch {
    throw Exception("Error in child 1") // Chỉ child 1 bị hủy
}

scope.launch {
    delay(1000)
    println("Child 2 still running") // Vẫn chạy bình thường
}
```

#### 27. Cách đúng để bắt lỗi khi sử dụng cơ chế giám sát là gì?

**Ý chính:** `try-catch` bên trong Coroutine con - Phải đặt bên trong, chứ không phải bọc bên ngoài hàm Builder.

**Diễn giải:** SupervisorJob ngăn lỗi lan lên trên, nhưng nó vẫn cho phép lỗi ném ra. Nếu bạn bọc bên ngoài `launch`, nó không bắt được lỗi chạy ngầm bên trong.

**Ví dụ:**

```kotlin
// SAI: Vẫn crash app
try {
    scope.launch {
        throw Exception("Error")
    }
} catch (e: Exception) {
    // Không bắt được
}

// ĐÚNG:
scope.launch {
    try {
        throw Exception("Error")
    } catch (e: Exception) {
        println("Caught: $e")
    }
}
```

#### 28. Làm thế nào để tránh xung đột dữ liệu khi nhiều tác vụ truy cập cùng một biến?

**Ý chính:** Mutex (Mutual Exclusion) - Dùng để đồng bộ hóa truy cập dữ liệu mà không chặn thread.

**Diễn giải:** Không dùng `synchronized` block vì nó chặn (block) thread. Mutex cung cấp hàm suspend `withLock` giúp tạm dừng Coroutine một cách an toàn cho đến khi khóa được mở.

**Ví dụ:**

```kotlin
val mutex = Mutex()
var counter = 0

repeat(1000) {
    launch {
        mutex.withLock {
            counter++ // Thao tác an toàn
        }
    }
}
```

#### 29. Làm thế nào để giới hạn thời gian thực thi của một tác vụ?

**Ý chính:** `withTimeout` - Ném ra `TimeoutCancellationException` nếu khối code bên trong không chạy xong trong thời gian quy định.

**Diễn giải:** Bản chất là nó lên lịch một tác vụ hủy chính Coroutine đó sau X mili-giây.

**Ví dụ:**

```kotlin
try {
    withTimeout(5000) {
        downloadFile() // Phải xong trong 5s
    }
} catch (e: TimeoutCancellationException) {
    println("Download timeout!")
}
```

#### 30. Hai cách tạm dừng tác vụ khác nhau như thế nào?

**Ý chính:** `delay()` vs `yield()` - `delay` dừng hẳn trong một khoảng thời gian; `yield` chỉ nhường Thread cho Coroutine khác chạy trước rồi quay lại ngay nếu Thread rảnh.

**Diễn giải:** `yield()` dùng để giải tỏa các công việc tính toán nặng, liên tục bằng cách chủ động kiểm tra xem có ai đang đợi dùng Thread không để nhường chỗ.

**Ví dụ:**

```kotlin
launch {
    repeat(1000) {
        // Tính toán nặng
        yield() // Nhường Thread cho coroutine khác
    }
}
```

### Chủ đề: Deep Dive Flow Operators (Toán tử nâng cao)

#### 31. Ba cách xử lý khi dòng dữ liệu phát ra giá trị mới trong khi giá trị cũ chưa xử lý xong?

**Ý chính:** `flatMapConcat`, `flatMapMerge`, `flatMapLatest` - Cách xử lý khi một Flow phát ra một giá trị mới mà Flow con trước đó chưa chạy xong.

**Diễn giải:**
- `flatMapConcat`: Chạy tuần tự. Đợi Flow con 1 xong mới chạy Flow con 2.
- `flatMapMerge`: Chạy song song tất cả các Flow con cùng lúc.
- `flatMapLatest`: Hủy ngay Flow con cũ để chạy Flow con mới vừa phát ra.

**Ví dụ:**

```kotlin
// flatMapConcat: Tuần tự
flow { emit(1); emit(2) }
    .flatMapConcat { value ->
        flow {
            delay(100)
            emit("Result $value")
        }
    }

// flatMapMerge: Song song
flow { emit(1); emit(2) }
    .flatMapMerge { value ->
        flow {
            delay(100)
            emit("Result $value")
        }
    }

// flatMapLatest: Hủy cũ, chạy mới (dùng cho search)
searchQueryFlow
    .flatMapLatest { query ->
        searchApi(query) // Hủy API call cũ khi có query mới
    }
```

#### 32. Cơ chế xử lý khi bên phát dữ liệu nhanh hơn bên nhận là gì?

**Ý chính:** Backpressure - Tự động xử lý nhờ cơ chế tạm dừng (suspend) của hàm `emit`.

**Diễn giải:** Nếu bên phát (Producer) phát dữ liệu quá nhanh mà bên nhận (Consumer) xử lý chậm, hàm `emit` sẽ tự động tạm dừng lại (suspend) tại dòng đó cho đến khi bên nhận sẵn sàng nhận phần tử tiếp theo. Không sợ tràn bộ nhớ.

**Ví dụ:**

```kotlin
flow {
    repeat(100) {
        emit(it) // Tự động đợi nếu collector chậm
    }
}.collect { value ->
    delay(1000) // Xử lý chậm
    println(value)
}
```

#### 33. Có những cách nào để thay đổi cơ chế xử lý khi bên phát nhanh hơn bên nhận?

**Ý chính:** `buffer()`, `conflate()`, `collectLatest()` - Các toán tử can thiệp Backpressure.

**Diễn giải:**
- `buffer()`: Tạo hàng chờ chứa trước dữ liệu, bên phát cứ phát, bên nhận lấy dần.
- `conflate()`: Bỏ qua các giá trị cũ ở giữa, bên nhận chỉ lấy giá trị mới nhất khi rảnh.
- `collectLatest()`: Hủy xử lý của item cũ nếu có item mới tới.

**Ví dụ:**

```kotlin
// buffer: Tạo hàng đợi
flow { repeat(10) { emit(it); delay(100) } }
    .buffer()
    .collect { delay(300); println(it) }

// conflate: Bỏ qua giá trị cũ
flow { repeat(10) { emit(it); delay(100) } }
    .conflate()
    .collect { delay(300); println(it) }

// collectLatest: Hủy xử lý cũ
flow { repeat(10) { emit(it); delay(100) } }
    .collectLatest { value ->
        delay(300)
        println(value) // Chỉ in giá trị cuối
    }
```

#### 34. Làm thế nào để thay đổi luồng thực thi của các phép biến đổi dữ liệu?

**Ý chính:** `flowOn` - Thay đổi Dispatcher của các công việc phía trước (ngược dòng - upstream) nó.

**Diễn giải:** Khác với các toán tử Collections, `flowOn` có tác dụng ngược lên trên cho tới khi gặp một `flowOn` khác hoặc tầng gốc của Flow.

**Ví dụ:**

```kotlin
flow {
    emit(apiCall()) // Chạy trên IO
}
    .flowOn(Dispatchers.IO)
    .map { transform(it) } // Chạy trên Default
    .flowOn(Dispatchers.Default)
    .collect { render(it) } // Chạy trên Main (scope gọi collect)
```

#### 35. Hai cách bắt lỗi trong dòng dữ liệu khác nhau như thế nào?

**Ý chính:** Toán tử `catch` vs `try-catch` quanh `collect` - `catch` chỉ bắt được lỗi xảy ra phía trên (upstream) nó; `try-catch` bọc quanh `collect` bắt được lỗi ở mọi nơi bao gồm cả trong khối `collect`.

**Diễn giải:** Lỗi xảy ra lúc vẽ UI trong `collect { ... }` sẽ không thể bắt được bằng toán tử `.catch { ... }` đặt ở trên.

**Ví dụ:**

```kotlin
flow {
    throw Exception("Error in flow")
}
    .catch { e ->
        println("Caught in catch: $e") // Bắt được
    }
    .collect { value ->
        throw Exception("Error in collect") // catch KHÔNG bắt được
    }

// Để bắt lỗi trong collect:
try {
    flow { emit(1) }
        .collect { value ->
            throw Exception("Error")
        }
} catch (e: Exception) {
    println("Caught: $e") // Bắt được
}
```

### Chủ đề: Channels & Internal Mechanics

#### 36. Cơ chế giao tiếp trực tiếp giữa các tác vụ bất đồng bộ là gì?

**Ý chính:** Channel - Đường ống giao tiếp giữa các Coroutine; Flow là stream truyền dữ liệu thụ động, Channel là cơ chế truyền dữ liệu chủ động.

**Diễn giải:** Flow truyền data dạng 1-đến-nhiều (Unicast/Multicast tùy loại). Channel truyền dữ liệu dạng 1-đến-1: Một phần tử được đưa vào Channel thì chỉ có duy nhất 1 bên nhận lấy được nó (như hàng đợi tin nhắn).

**Ví dụ:**

```kotlin
val channel = Channel<Int>()

// Producer
launch {
    repeat(5) {
        channel.send(it)
    }
    channel.close()
}

// Consumer
launch {
    for (value in channel) {
        println("Received: $value")
    }
}
```

#### 37. Các loại bộ đệm của đường ống giao tiếp là gì?

**Ý chính:** Buffer Capacity - Rendezvous (0 đệm), Buffered (Đệm cố định), Unlimited (Vô hạn), Conflated (Chỉ giữ cái mới nhất).

**Diễn giải:** Rendezvous là mặc định: Bên gửi sẽ treo máy cho đến khi có bên nhận vào lấy dữ liệu.

**Ví dụ:**

```kotlin
// Rendezvous (mặc định)
val channel1 = Channel<Int>()

// Buffered
val channel2 = Channel<Int>(capacity = 10)

// Unlimited
val channel3 = Channel<Int>(Channel.UNLIMITED)

// Conflated
val channel4 = Channel<Int>(Channel.CONFLATED)
```

#### 38. Làm thế nào để chờ nhiều tác vụ và lấy kết quả của tác vụ hoàn thành đầu tiên?

**Ý chính:** `select` - Chờ đợi nhiều tác vụ bất đồng bộ cùng lúc và lấy kết quả của tác vụ nào hoàn thành đầu tiên.

**Diễn giải:** Lắng nghe cùng lúc nhiều Channels hoặc Deferreds, cái nào phản hồi trước sẽ được kích hoạt xử lý, các cái còn lại bị bỏ qua.

**Ví dụ:**

```kotlin
val server1 = async { fetchFromServer1() }
val server2 = async { fetchFromServer2() }

val result = select<String> {
    server1.onAwait { "Server 1: $it" }
    server2.onAwait { "Server 2: $it" }
}
println(result) // Lấy kết quả từ server phản hồi nhanh hơn
```

#### 39. Trình biên dịch chuyển đổi một hàm đặc biệt thành gì ở mức bytecode?

**Ý chính:** Continuation Passing Style (CPS) - Thêm một tham số có tên `Continuation` vào cuối hàm.

**Diễn giải:** Kiểu trả về thực sự của hàm biến thành `Any?`. Trình biên dịch tạo ra một State Machine bên trong hàm để theo dõi xem hàm đang tạm dừng ở dòng nào, lưu lại toàn bộ biến cục bộ tại thời điểm đó để khôi phục lại khi chạy tiếp.

**Ví dụ:**

```kotlin
// Code Kotlin
suspend fun fetchData(): String {
    delay(1000)
    return "Data"
}

// Bytecode tương đương (đơn giản hóa)
fun fetchData(continuation: Continuation<String>): Any? {
    // State machine logic
    when (continuation.label) {
        0 -> {
            continuation.label = 1
            return delay(1000, continuation)
        }
        1 -> {
            return "Data"
        }
    }
}
```

#### 40. Giao diện callback nâng cao của hệ thống chứa những gì?

**Ý chính:** Continuation - Chứa `CoroutineContext` và hàm `resumeWith(result: Result<T>)`.

**Diễn giải:** Nó đóng vai trò như một callback nâng cao của hệ thống để báo hiệu: "Tôi đã làm xong việc ngầm rồi, đây là kết quả, hãy chạy tiếp Coroutine đi".

**Ví dụ:**

```kotlin
interface Continuation<in T> {
    val context: CoroutineContext
    fun resumeWith(result: Result<T>)
}

// Sử dụng
suspend fun example() = suspendCoroutine<String> { continuation ->
    // Làm việc bất đồng bộ
    thread {
        Thread.sleep(1000)
        continuation.resume("Done")
    }
}
```

### Chủ đề: Context & Lifecycle

#### 41. Tập hợp các thông tin cấu hình của một tác vụ bất đồng bộ là gì?

**Ý chính:** CoroutineContext - Tập hợp các phần tử định nghĩa hành vi và cấu hình của một Coroutine.

**Diễn giải:** Hoạt động như một cấu trúc Map/Set đặc biệt. 4 thành phần chính gồm:
1. Job: Quản lý vòng đời.
2. CoroutineDispatcher: Quản lý Thread.
3. CoroutineName: Tên định danh (để debug).
4. CoroutineExceptionHandler: Bắt lỗi tập trung.

**Ví dụ:**

```kotlin
val context = Dispatchers.IO + 
              Job() + 
              CoroutineName("MyAPI") +
              CoroutineExceptionHandler { _, e -> println(e) }

launch(context) {
    // Coroutine với context đầy đủ
}
```

#### 42. Làm thế nào để kết hợp hoặc thay đổi các thông tin cấu hình?

**Ý chính:** Toán tử `+` - Dùng để gộp hoặc ghi đè các phần tử trong CoroutineContext.

**Diễn giải:** Phép cộng sẽ ghi đè phần tử nếu trùng kiểu (Key) hoặc bổ sung nếu khác kiểu.

**Ví dụ:**

```kotlin
val context1 = Dispatchers.IO + CoroutineName("Task1")
val context2 = context1 + Dispatchers.Main // Ghi đè Dispatcher
val context3 = context1 + Job() // Thêm Job mới

scope.launch(Dispatchers.Main + CoroutineName("UI-Job")) {
    // Chạy trên Main với tên "UI-Job"
}
```

#### 43. Vùng quản lý tác vụ sống suốt đời ứng dụng có vấn đề gì?

**Ý chính:** GlobalScope - Scope sống thọ bằng toàn bộ vòng đời của Ứng dụng (Bad Practice).

**Diễn giải:** Không tuân thủ Structured Concurrency. Coroutine chạy trong này không bao giờ tự hủy trừ khi App bị kill. Gây rò rỉ bộ nhớ, tốn pin, khó viết Unit Test.

**Ví dụ:**

```kotlin
// BAD: Không nên dùng
GlobalScope.launch {
    // Coroutine này sống mãi, không tự hủy
}

// GOOD: Dùng scope có lifecycle
lifecycleScope.launch {
    // Tự hủy khi Activity destroy
}
```

#### 44. Hai vùng quản lý tác vụ trên luồng chính khác nhau như thế nào?

**Ý chính:** MainScope vs lifecycleScope - `MainScope` chạy mặc định trên Thread Main và cần hủy thủ công; `lifecycleScope` gắn chặt vào Lifecycle của Activity/Fragment và tự hủy.

**Diễn giải:** Luôn ưu tiên dùng `lifecycleScope` hoặc `viewLifecycleOwner.lifecycleScope` trong UI để không cần viết code hủy trong `onDestroy`.

**Ví dụ:**

```kotlin
// MainScope: Cần hủy thủ công
class MyActivity : AppCompatActivity() {
    private val scope = MainScope()
    
    override fun onDestroy() {
        super.onDestroy()
        scope.cancel() // Phải nhớ hủy
    }
}

// lifecycleScope: Tự động hủy
class MyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launch {
            // Tự hủy khi Activity destroy
        }
    }
}
```

#### 45. Làm thế nào để tự động dừng lắng nghe dữ liệu khi màn hình vào background?

**Ý chính:** `repeatOnLifecycle` - Ngừng hẳn việc lắng nghe Flow khi UI vào trạng thái STOPPED và tự động lắng nghe lại khi quay lại STARTED.

**Diễn giải:** Tiết kiệm tài nguyên tuyệt đối. Nếu dùng `launch` thường, kể cả khi màn hình bị ẩn đi (Background), Flow ngầm vẫn có thể tiếp tục chạy và tốn CPU vô ích.

**Ví dụ:**

```kotlin
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state ->
            // Chỉ collect khi UI ở trạng thái STARTED
            // Tự động dừng khi vào STOPPED (background)
        }
    }
}
```

### Chủ đề: Testing & Optimization

#### 46. Làm thế nào để kiểm thử một hàm bất đồng bộ?

**Ý chính:** `runTest` - Bọc mã nguồn kiểm thử bằng hàm này để test suspend function.

**Diễn giải:** Hàm này thuộc thư viện `kotlinx-coroutines-test`. Nó có cơ chế bỏ qua thời gian thực (StandardTestDispatcher) giúp các hàm `delay()` chạy ngay lập tức, tiết kiệm thời gian chạy test.

**Ví dụ:**

```kotlin
@Test
fun testMySuspendFunction() = runTest {
    val result = myRepository.fetchData()
    assertEquals("Expected", result)
}
```

#### 47. Các loại bộ điều phối dành cho kiểm thử khác nhau như thế nào?

**Ý chính:** TestDispatcher - `StandardTestDispatcher` (hoãn thực thi, phải gọi `advanceUntilIdle`) và `UnconfinedTestDispatcher` (chạy ngay lập tức một cách đồng bộ).

**Diễn giải:** `UnconfinedTestDispatcher` giúp viết các ca kiểm thử đơn giản thuận tiện hơn vì không cần gọi các hàm điều khiển thời gian ảo.

**Ví dụ:**

```kotlin
// StandardTestDispatcher
@Test
fun testWithStandard() = runTest {
    val job = launch {
        delay(1000)
        println("Done")
    }
    advanceUntilIdle() // Phải gọi để chạy hết
    assertTrue(job.isCompleted)
}

// UnconfinedTestDispatcher
@Test
fun testWithUnconfined() = runTest(UnconfinedTestDispatcher()) {
    launch {
        delay(1000)
        println("Done") // Chạy ngay
    }
}
```

#### 48. Làm thế nào để xem tác vụ bất đồng bộ nào đang chạy trên luồng nào?

**Ý chính:** `-Dkotlinx.coroutines.debug` - Bật cờ JVM này khi chạy ứng dụng để debug Coroutine.

**Diễn giải:** Khi bật cờ này, tên của Coroutine hiện tại sẽ tự động được nối vào đuôi của tên Thread, hiển thị rõ ràng khi gọi `Thread.currentThread().name`.

**Ví dụ:**

```kotlin
// Thêm vào VM options: -Dkotlinx.coroutines.debug

launch(CoroutineName("MyCoroutine")) {
    println(Thread.currentThread().name)
    // Output: DefaultDispatcher-worker-1 @MyCoroutine#1
}
```

#### 49. Tại sao không thể tái sử dụng vùng quản lý sau khi hủy?

**Ý chính:** `CoroutineScope.cancel()` - Hàm này chuyển trạng thái của Job trong Scope thành hủy bỏ vĩnh viễn.

**Diễn giải:** Nếu muốn hủy các công việc đang chạy mà vẫn giữ lại Scope để bấm nút chạy lại sau, hãy dùng `scope.coroutineContext.cancelChildren()`.

**Ví dụ:**

```kotlin
val scope = CoroutineScope(Job())

// Hủy tất cả nhưng giữ scope
scope.coroutineContext.cancelChildren()

// Có thể launch lại
scope.launch {
    println("New coroutine")
}

// Nếu dùng cancel() thì không launch được nữa
// scope.cancel()
// scope.launch { } // Lỗi!
```

#### 50. Ưu điểm về hiệu năng của dòng dữ liệu so với thư viện phản ứng là gì?

**Ý chính:** Flow vs RxJava - Flow tận dụng compiler của Kotlin nên tạo ra cực ít đối tượng trung gian (Allocation) so với RxJava.

**Diễn giải:** RxJava tạo ra một chuỗi các đối tượng Observable phức tạp cho mỗi toán tử, gây áp lực lớn cho Garbage Collector (Bộ dọn rác). Flow sử dụng các hàm suspend lồng nhau gọn nhẹ và trực quan hơn rất nhiều.

**Ví dụ:**

```kotlin
// Flow: Ít object allocation
flow {
    emit(1)
    emit(2)
}
    .map { it * 2 }
    .filter { it > 2 }
    .collect { println(it) }

// RxJava: Nhiều object allocation
Observable.just(1, 2)
    .map { it * 2 }
    .filter { it > 2 }
    .subscribe { println(it) }
```
